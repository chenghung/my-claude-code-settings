# 計畫完整性

在計畫驅動開發下——先寫實作計畫，再把計畫拆成逐項任務簡報，每項派一個實作 subagent——實作者手上只有自己那份簡報，看不到計畫全文與設計文件，也沒有需求對話的脈絡。凡是沒有進到簡報的事實，對實作者而言等同不存在；計畫裡過時的敘述則會被當成當下唯一的事實來源照抄。因此計畫與簡報的錯誤不會在實作階段被攔下，只會被忠實地實作出來。本規則規範計畫本身與其拆解產物的兩項正確性要求。

## 事實推翻假設時，先修計畫再派下游任務

任務的實測、查證或審查結果推翻了計畫所依賴的假設時，在派出任何下游任務之前，必須先更新計畫本身，並重新產生受影響的下游簡報。只在當下那個任務裡繞過、把過時的敘述留在計畫中，不算處理完畢。

三個判定點都取可觀察形式，不留裁量空間：

- **何謂推翻**：照計畫原本的敘述做，會失敗或產生與計畫所述不同的結果。「有更好的做法」不算推翻，那是優化提案，走一般的計畫變更討論。
- **何謂受影響**：以該假設的關鍵詞搜過計畫全文，命中的每一處都算，連同由這些處產生的簡報。範圍靠搜尋界定，不靠回想改過哪幾項任務。
- **何謂處理完畢**：重跑同一組搜尋，剩下的命中全部落在已更新的敘述上；並且列得出被重新產生的簡報清單，或說明命中處為何不對應任何簡報——命中落在背景、理由這類本來就不產生簡報的段落時，空清單就是正確狀態。搜尋仍命中舊敘述即為未完成。

簡報產出端另有一項義務：每份任務簡報都要指示實作者，實測結果與簡報或計畫所述不符時回報這個落差，而不是就地改用可行的做法繼續。理由是這條規則只載入編排端的 context，實作者讀不到它；能修計畫的是編排端，先撞到事實的卻是實作者，訊號不主動要就不會浮上來。

失敗形狀：某份實作計畫裡有一段程式碼片段，假設某個 CLI 接受不帶值的某個旗標。動工後一個較早的任務對真實二進位做了實測，發現該寫法會被直接拒絕、行程立刻結束，於是那個任務改用別的方式——但計畫裡較晚那個任務的片段沒有跟著更新，落差也沒有被回報上來。輪到它時，實作者照著計畫把已被推翻的假設寫進程式碼，測試也抓不到，因為測試樁忽略命令列參數，錯的旗標與對的旗標在樁面前沒有差別。最後是審查者比對同一個檔案裡另一處留下的實測註解才發現。實作者沒有立場懷疑計畫，計畫是他當下唯一的事實來源。

例外：推翻假設後若計畫出現無法自行修補的缺口——原方案整條路走不通、或需要使用者在方案之間取捨——此時屬於人類介入邊界所定義的 blocker，停下詢問，而不是自行改寫計畫要達成的目標。

## 拆成簡報後，逐條核對使用者的明確需求

把計畫拆成逐項任務簡報後、派出任何任務之前，必須拿使用者明確表達過的需求逐條核對。兩個條件都要成立才算通過：

- 每一條需求都出現在至少一份簡報裡。
- 需求中的具體值、清單、命名與格式，以原文出現在簡報裡，而不是以指涉方式提及。「依使用者給的那四組預設組合處理」不算數——那四組的內容必須在簡報中看得到，實作者才可能照做。

核對的來源釘死在使用者訊息原文與 issue 內文，不含 AI 在設計或討論過程中推導出的需求。後者可以進計畫，但不能當核對基準，否則基準會隨推導漂移，核對就變成拿自己的產出對自己的產出。設計文件有寫也不等於簡報有寫：兩者是不同產物，只有簡報會送到實作者眼前。

失敗形狀：使用者在需求中給出了四組預設組合的具體內容，內容確實進了設計文件，但拆簡報時漏掉——負責寫文件的那個任務，拿到的簡報裡沒有這四組的定義。撰寫者是察覺簡報要求的「標註可用性」只在某個讀法下才說得通，才反推出定義缺失並停下來問。少了那一步僥倖，交付出來的會是一份看起來合理、卻完全不是使用者要的東西；而且因為它自洽，審查也不會擋下——審查者手上同樣沒有那四組定義可以比對。

自我檢測：逐條列出使用者原文中的需求，每一條都指得出它落在哪一份簡報的哪一段，且該段的內容夠實作者直接照做、不必回頭找原文嗎？任一條答否，那一條就是實作者收不到的需求。
