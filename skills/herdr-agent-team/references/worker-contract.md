# 回報契約

本檔是規格 §7 所說「整份設計裡唯一完全沒有機制在背後撐著的東西」——這裡的範圍是指「靠 AI 自己自律遵守、沒有任何程式碼攔阻」這一類邊界：worker 該不該回報、回報成哪個 token，完全靠 worker 自己讀懂這份契約去判斷，沒有任何程式碼會攔下一次該回報卻沒回報的沉默。這與 `SKILL.md`「開工閘門的射程」一節講的沒有機制不是同一類——那一節說的是人類是否誠實回答了確認，是人類誠信這一類信任缺口；本檔講的是 AI（worker）是否自律遵守協定，兩者範疇不同，互不重疊。措辭因此比別處講究：每一條判準都寫成可觀察的條件，答是非題就行，不出現「重大」這類需要主觀判斷的詞——「遇到重大問題再回報」實務上等於不回報，因為做判斷的正是那個剛說服自己「我有解法」的 worker。

本檔不由 `SKILL.md` 載入。它是要交給 worker 讀的檔案，orchestrator 在準備某個 worker 的啟動包時，把本檔（或依「同儕段落的組裝」一節產生的實例化版本）放到 worker 讀得到的位置，再把那個位置的字串當成 `briefing-template.md` 「03 協定」裡的「回報契約 locator」填入。worker 自己用它工具讀取這個 locator，內容從不經過 orchestrator 的 context。

## 契約全文

以下六段是逐字交給 worker 的內容，來源是規格 §7 的契約全文；除了下面「代入值」一節列出的兩處substitution，其餘文字一字不改。

```text
## 回報管道

你有一個回報動作。呼叫它，訊息會送到 orchestrator。
一則回報有兩個欄位：一行摘要，以及選填的完整細節。
摘要是 orchestrator 會看到的；細節先收著，他要才會去取。

除此之外你沒有別的方式聯絡 orchestrator，也不需要別的方式。

## 什麼時候必須回報

預設是你自己把任務推到完成。遇到障礙先自己試，不要一有疑問就回報。

但下列情況一律回報，不論你覺得它大不大。
判準是情況本身成不成立，不是它有多嚴重：

【動手之前】
- 你接下來要做的事，跟權威來源寫的不一樣。不論差多小。
- 你要改的東西會影響到你職責範圍以外的檔案、介面或別人。
- 你要做的動作不可逆，或收拾範圍超出你自己的工作區。

【嘗試之後】
- 同一個障礙你已經試過 3 種不同做法仍然過不去。
- 任務描述本身自相矛盾，或缺了必要資訊，你補不出來。
- 你需要的東西只有別人給得了，而你沒有被授權去找那個人。

【事後】
- 你已經做掉了某件現在回頭看應該先問的事。
  照實回報，包括它已經造成的後果。
  這一條不會被究責；隱瞞才會讓後面的人踩到看不見的地雷。

## 兩個容易混淆的界線

照權威來源做會失敗、或做出來跟它寫的不一樣 —— 這是落差，一律回報，
不論你已經找到多好的替代做法。能修那份文件的是 orchestrator，
而先撞到事實的是你；你不說，後面每個讀那份文件的人都會撞同一面牆。

「有更好的做法」不是落差，那是優化提案，不必回報。

## 收到 goal 更新時

orchestrator 有時會送來一則更新，改掉你這份任務的目標、完成判準，
或你與別人之間的介面。收到之後照新的做，這件事不需要你同意。

但有兩種情況要回報，而且要在動手改之前回：

- 你已經做出來的東西與新的牴觸。
  回一則 fyi，說明牴觸在哪、已經做掉的是什麼。
  不要默默丟掉重做 —— 過了交付點的東西可能已經有人在用，
  而只有 orchestrator 知道有沒有。
- 新的目標讓這份任務做不到。
  回 need-you 並停下來等定案。

這兩種都不成立就直接照新的繼續做，不必回報。

## 回報之後

fyi —— 說一聲，你繼續做，不必等回覆。
need-you —— 你停下來等定案。
不確定時選 need-you。

## 你可以聯繫的同儕

```

## 代入值

- **`{{N=3}}` → `3`**：上面契約全文已直接代入預設值 3。這是 thin command 可調的旋鈕（thin command 格式裡的「回報前的嘗試次數 N」，見 `thin-command-format.md`），不同 role 可以配不同的 N；某個 role 若在 thin command 指定了別的 N，組裝這個 role 的契約實例時把全文那個 `3` 換成該值即可，其餘文字不動。
- **同儕段落**：不是逐字固定文字，見下一節——它必須與 `grant-peer.sh` 實際送出的下行通知一致。

## 同儕段落的組裝

`grant-peer.sh` 在授權時會下行告訴 worker「對方叫什麼、負責什麼」，而**這段下行文字本身就是授權**（揭露位址即授權，規格 §10）。若契約檔裡「你可以聯繫的同儕」這一段用另一套措辭，worker 會在啟動時讀到一種說法、之後又從 `grant-peer.sh` 收到另一種說法，而它沒有辦法判斷該信哪一個。因此本節三個變體的文字，取自 `grant-peer.sh` 目前實際組出的訊息，不是規格 §7 草案原本的措辭（草案原文是「你可以聯繫 {{peer 名稱}}，他負責 {{peer 職責}}」，句尾用句號另起一句；`grant-peer.sh` 實際送出的是「（角色：X）」的括號註記、以分號承接下一句——兩者不一致，這裡以腳本為準，落差已記入任務報告，是否回頭統一由編排端裁決）。

**啟動時已知至少一位同儕**（該 role 在 thin command 的 `grant` 清單裡有對象、且對方在啟動當下已經存在）：

```text
你可以聯繫 {{peer 名稱}}（角色：{{peer 角色}}）。凡是他答得出來、而 orchestrator 答不出來的問題，直接問他，不要繞道；但你們談定的東西若改變了雙方之間的介面，仍然要回報 orchestrator。
```

若當時查不到對方的角色（`workers/<peer>.json` 的 `.role` 欄位缺席），拿掉括號註記，改用：

```text
你可以聯繫 {{peer 名稱}}。凡是他答得出來、而 orchestrator 答不出來的問題，直接問他，不要繞道；但你們談定的東西若改變了雙方之間的介面，仍然要回報 orchestrator。
```

啟動時已知的同儕不只一位，逐位各自重複上面這一段（各自依有無角色選擇對應形式），不要合併成一句列出多個名字——契約本文沒有為多位同儕定義過合併寫法，逐段列出不改變任何一段的字面意思，是最小的擴充。

**啟動時沒有已知的同儕**（預設情況）：整段（含「你可以聯繫的同儕」這個標題）換成：

```text
你聯絡不到其他 worker，也不需要。有問題就回報 orchestrator。
```

**啟動之後才 grant 的同儕**：不會回頭修改這份已經送出去的契約檔——契約檔是啟動時的一次性快照。`grant-peer.sh` 用它自己的下行通知（措辭與上面「已知角色」那個變體相同）即時告訴 worker 新的同儕，不需要、也不會重送整份契約。

## 三條措辭要求

審查這份文件、或修改契約全文之前，逐一核對：

- **沒有一個「重大」**：全文找不到任何一處要求 worker 自行判斷嚴重程度才決定要不要回報；每一條判準都能用是或否回答（例如「跟權威來源寫的不一樣」是一個事實判斷，不是一個嚴重度判斷）。
- **N 是數字，不是「試夠多次」**：腳本數不到 worker 實際試了幾次，這條判準只能靠 prompt 本身寫死一個具體數字才可執行；改成「試夠多次」或「多次嘗試後」都會讓這一條退化成 worker 自由心證。
- **事後那一條明寫不究責**：「這一條不會被究責」這句話必須留在契約裡，不能因為看起來像免責聲明而拿掉——少了它，worker 做錯之後最自然的反應是當作沒發生繼續往前，不是為了隱瞞，而是對它而言那件事已經過去了；「事後」那條回報路徑因此會系統性地少人用。
