# 漂移處置

本檔由 orchestrator 在一則 `fyi` 可能是漂移（判準一見 `SKILL.md` Token 表 `fyi` 列）、使用者要求變更 goal，或要叫停、改派、結束某個 worker（`done` 除外）時載入。

goal 不變的叫停、改派或結束（例如使用者直接要求、看門狗升級指到本檔）只取用第 3 步（叫停）與第 5 步（改派、結束）的做法本身，不走第 1、2、4、6 步。goal 要改變時（不論來自一則漂移 `fyi` 或使用者主動要求），依序走完六步，使用者主動要求者略過第 1 步判準一。`done` 的關閉依 `SKILL.md` Token 表 `done` 列，不走本檔。

`fyi` 的摘要可能是漂移時，依序走六步：

1. **判斷是不是漂移**（判準一）：照 goal 原本的敘述做會失敗，或做出與所述不同的結果。「有更好的做
   法」不算漂移，那是優化提案，走一般的變更討論，不進本流程。
2. **找出受影響的人**（判準二）：拿改動後的內容對每一個還活著的 role 比對三樣：完成判準、職責範圍
   （負責與不負責兩邊都算）、與其他 role 的介面（含 grant 對象），任一樣因此不再成立就是命中。**判
   不出來算命中**：多送一則是一次可控的打擾，漏送一則是一個靜默地建錯東西的 worker。
3. **先叫停他們**：對每個命中的 worker 逐一（不是群發）呼叫 `instruct.sh --to <worker> --kind halt
   --text <這次改動對你這一份的影響>`，內容是停手、先別交付任何東西、回報做到哪裡。**一定要帶
   `--kind halt`**：一般下行會把 `delivered` 撥回 `running` 重新納入看門狗照看，帶 `halt` 的不撥回；
   不帶的話，原本停在 `delivered` 的 worker 會被撥回 `running`，停手轉成閒置後被看門狗推「繼續」。之後派新任務或新目標的那一則不是
   `halt`，關卡自然撥回。`--kind halt` 的第二個作用：成功送達時不寫 `.last_delivered_at`，看門狗因此不會把自動推進計數歸零、替推進預算續杯，所以叫停一個 `running` 的停滯 worker 同樣要帶。這只指 `instruct.sh` 當下送達（結束碼 `0`）的那一則；結束碼 `7` 進了待補送、之後由看門狗補投送達的，補投成功時看門狗不分 kind 仍會把自動推進計數歸零。結束碼 `7`（收件方卡在 `blocked`、這則進了待補送）時不能放著：去處理那個
   核准框（見 `SKILL.md`「派調查者的時機」），補投才等得到解除；叫停正是最不該靜默送不到的一則，收不到的人會照
   舊繼續建東西。halt 仍擋不住看門狗對 `running` worker 的自動推進：被叫停的人閒下來仍
   會一直被推，直到上限才升級，所以第 3 步到第 5 步之間不要拖。
4. **定下新目標**：呼叫 `set-goal.sh` 寫入新的四項內容（不帶 `--confirmed`，第一版之後的變更由
   orchestrator 自決）。若印出 `GOAL-SUCCESS-CHANGED version=<N>`，代表動到「怎樣算成功」，要往事件
   流轉述給使用者。
5. **逐一處置成對齊、改派或結束三者之一**：對齊是任務還成立，用 `instruct.sh` 送出新目標的內容；改
   派是任務作廢但人還有用，用 `instruct.sh` 換一個新任務；結束是這個角色不再需要，呼叫
   `shutdown-worker.sh --reason abandon` 或 `superseded` 並附交接檔。凡是停在 `delivered` 的
   worker（第 3 步叫停後仍是 `delivered` 的也算在內），走「結束」之前都要先撥回 `running`（同 `SKILL.md`
   Token 表 `done` 那一列）。與其他 role 的介面（含 grant 對象）因此改變時，用 `grant-peer.sh` 新增對應授權，或帶
   `--revoke` 撤銷；要結束的 worker 若仍被其他 worker 的 `.grants` 指向，`shutdown-worker.sh` 會以
   結束碼 `4` 拒絕，先撤銷再關。**已交付的產物要逐一過目**：要問的是它跟新目標的落差要不要變成新的工作，出口是往前迭代，
   不是回頭改既成事實。
6. **收斂測試**：重跑第 2 步同一組比對，剩下的命中全部落在已處置的 role 上才算完成；還有人沒處置就
   是沒處理完。
