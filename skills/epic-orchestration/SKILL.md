# Epic Orchestration

觸發本 skill 後，當前對話的 AI agent 在這個 epic 的整個生命週期內扮演 orchestrator：把每個
phase 交給一個獨立的 Claude Code session（下稱 phase agent）去完成，自己不參與任何一個 phase
的開發。此 skill 與既有 `epic-design` skill 成對：`epic-design` 產出設計文件，本 skill 負責
把設計拆成的 phase 推到全部合併。

## Reference 載入時機

| Reference | 載入時機 |
| --- | --- |
| `references/phase-agent-contract.md` | 本 skill 自己不載入。它由開場指令以絕對路徑傳給 phase agent，由 phase agent 自行讀取；orchestrator 只有在要修改 phase agent 的行為約束本身時才打開它 |
| `references/rationale.md` | 本 skill 自己不載入。撞到反常症狀時才打開對照，例如 phase agent 啟動時卡住不動、跨 session 訊息送不到或沒有回應、phase agent 讀不到 epic 設計文件、由 issue 查不到對應的 PR、監控迴圈永久阻塞、phase agent 啟動時因權限模式旗標而卡在確認框 |

## 環境前提

orchestrator 必須跑在 herdr 環境下：進入本流程任何動作之前，先確認環境變數 `HERDR_ENV` 恰為
`1`。不是就停下，向使用者說明本流程要透過 herdr 開 tab、啟動與監控 phase agent，必須在 herdr
環境內執行，不要往下建依賴圖或詢問要推進哪個 phase。

自我檢測：`HERDR_ENV` 讀到的值是不是字面上的 `1`？不是的話就停在這一步，不要假設環境等同可用。

## Orchestrator 的職責

orchestrator 的職責只有三件：把每個 phase agent 成功啟動、監控整個 epic 各 phase 的進度、
phase 結束後把它關掉。決策處理（判定一個卡點該由自己回覆、該先派調查者，還是該停下問使用者，
再把定案轉達回去）屬於監控的一部分，不是獨立的第四件事——它是「監控進度」在遇到卡點時的具體
展開。

卡點的預設處置是 orchestrator 自決，只有命中「升級清單」任一項才停下問使用者。這條開放的是
「誰做決定」，不是「orchestrator 要不要介入開發判斷」：它依據的仍然是 epic 設計文件、依賴圖、
`phase-decision-investigator` 帶回來的結論，以及「失敗行為」一節列出的那四種證據（其中第四種
是觸發條件成立時讀到的那格 pane 所給出的判定結論），不自己去讀 phase 的開發內容（見「主
Context 的三條硬禁令」）。

## 進度表

orchestrator 對整個 epic 的認知，全部收斂在一張進度表裡，每個 phase（即每個 sub-issue）在表
上只有六個欄位：

| 欄位 | 說明 |
| --- | --- |
| sub-issue 編號與標題 | 這個 phase 對應的 GitHub sub-issue |
| 被哪些 phase 擋著 | 依 blocked by 關係列出的依賴 |
| 目前處在哪個關卡 | 例如：等待啟動、進行中、等待決策、PR ready、已合併、已收尾 |
| herdr 座標 | tab 識別碼、agent 名稱、session 位址 |
| worktree 路徑 | 該 phase 的 git worktree 絕對路徑 |
| PR 編號 | 該 phase 開出的 PR，尚未開時留空 |

表上容不下開發細節：只要不是這六個欄位能表達的東西（例如某個函式重構完了、某段測試現在過
了），就不屬於 orchestrator 需要記住或轉述的內容。

## 主 Context 的三條硬禁令

orchestrator 的主 context 受三條硬禁令約束：

1. 預設不使用任何會回傳模型產出文字的 herdr 指令，已知例示為 `herdr agent read` 與
   `herdr pane read`。`herdr agent list` 不在此列，它改用與第二條同形的用法約束：呼叫本身允
   許（流程有兩處非呼叫它不可——取自己的 session 名稱、核對 tab 存活），但回應中的
   `terminal_title` 與 `terminal_title_stripped` 兩個欄位不得納入判斷、不得轉述、不得寫進進
   度表。回應是整包回來的，那兩個欄位一樣會進 context，沒有機制濾掉它們；這一句約束的是拿到
   之後怎麼用，和第二條一樣只靠文字生效。唯一的例外動作是用 `herdr pane read` 讀該 phase 的
   pane，且僅在下列四個具名觸發條件之一成立時才允許，任一成立即可，不必同時成立：
   - **觸發條件一**：該 phase 的狀態處於 `idle` 或 `blocked`，而 orchestrator 沒有收到伴隨
     的上行訊息。「沒有收到」的時間範圍以這一次 `herdr agent wait` 的區間為準，與「監控節
     奏」的判定規則同一界定：這次呼叫期間沒收到就成立，更早之前收過的不影響這次判定。不論
     是剛從別的狀態轉過來，還是本來就一直停在這裡，都算。
   - **觸發條件二**：「啟動成功判準」的三項不齊備。
   - **觸發條件三**：「下行送出後的握手」逾時。
   - **觸發條件四**：同一個 phase 連續十輪整輪觀測都是 `working`，且期間沒有收到任何上行
     訊息（輪數怎麼累加、什麼時候歸零，見「監控節奏」）。
2. 不主動去取 phase 的程式碼、diff、測試輸出或 PR review 內容。依上一條例外讀 pane 時，讀的
   目的只有一個：判定它停在什麼上面。畫面上其餘內容不納入判斷、不轉述、不寫進進度表。
3. 不修改任何 phase worktree 裡的檔案。

判準是該指令或欄位回不回傳模型產出的文字，或該操作是否觸及 phase 的開發內容，而不是有沒有被
列在上面的清單裡——清單只是已知例示，不是窮舉；日後新增的任何承載模型輸出的欄位或指令，一樣
落在第一條禁令底下。

第三條只擋 phase worktree，所以可寫範圍要正面界定一次：orchestrator 會寫入的檔案只有兩個對
象——狀態檔（在工作區的 `.tmp` 底下，見「狀態檔與中斷恢復」），以及開場指令那份 epic 設計文件
的**主倉庫**絕對路徑。倉庫內的檔案只有後者這一個，其餘一概不寫。這句界定的對象是「寫哪個檔
案」：「升級清單」第四項排除的那些例行編排動作——建立 worktree、開關 tab 這一類——不算本句所
說的檔案寫入，兩處用同一組字，不各自認定。

設計文件這一個是刻意開的例外，而且同時偏離兩條 rule，理由各自不同：`git-worktree-workflow` 要
求對 repo 內檔案的寫入都在隔離的 worktree 中進行，但這份文件位於被 `.gitignore` 忽略的 `docs`
目錄、不會隨 worktree 出現（同一個事實也是「開場指令」一節要求給主倉庫路徑的理由），照那條
rule 執行反而寫不到它；`markdown-editing` 要求 markdown 檔案的編輯委派給專門的 subagent，但這
裡是編排端依 `plan-integrity` rule 對自己流程文件所做的即時修正，不是一件可以外包出去的文件撰
寫任務。

第一條的例外分兩種情形，各有各的理由，不共用同一條。

觸發條件一與四（phase agent 已經接手、正在跑）的理由在契約那一端：`phase-agent-contract.md`
要求 phase agent 正常停下的每一種情況——要決策、PR 開好了、收尾做完了——都先送一則上行訊息。
所以「停了卻沒訊息」不會是正常流程的一部分，它只可能是 phase agent 停在某個非自願的東西上（例
如核准框），或是契約沒被遵守；兩種都是異常，兩種都只有畫面上看得出來。

觸發條件二與三（phase agent 還沒接手）用不了上面那條理由：這兩個時點對方根本還沒有送訊息的義
務——判準不齊備時開場指令還沒送出，握手逾時代表這則下行送出後對方連 `working` 都沒轉進去。它
們自己的理由是另一件事：這兩個時點各有一個明確的、預期中的狀態轉換沒有發生（該轉為三項齊備的
`idle`、該轉為 `working`），而 herdr 回傳的狀態欄位只說得出它現在是什麼狀態，說不出它為什麼沒
有往前走；沒有往前走的原因（信任對話框、責任確認對話框、agent 根本沒起來）一樣只有畫面上看得
出來。

這是讀 pane 這個動作唯一無可替代的位置，例外只開到這四個觸發條件為止。

讀取本身失敗，或讀回來是一片空白的，這條例外給不出判定結論，而觸發條件成立時它是這一格唯一
的證據來源，沒有別的可換——命中「升級清單」第九項（自決手段已用盡），走升級路徑。

這三條沒有 permission 設定或 hook 在背後強制執行——orchestrator 本身具備呼叫這些 herdr 指令
的能力，技術上執行得到任何一條被禁止的操作；邊界完全靠這份定義檔的文字對模型的約束力生效，
不是被系統擋下的。第二條的「不納入判斷」要照同一個標準說明白：讀 pane 讀進來的畫面，讀進
context 就是讀進去了，沒有任何機制把「它停在什麼上面」以外的內容從 context 裡濾掉，也沒有任
何機制阻止那些內容影響後續判斷；這一句約束的是 orchestrator 讀完之後怎麼用，只靠文字生效。正
因為沒有機制兜底，第一條的例外只開上面那四個列名的觸發條件，其餘措辭不放寬。

這三條只綁 orchestrator 自己的主 context，不綁 `phase-decision-investigator`：調查者存在的
目的正是把 orchestrator 不能看的東西全部看完，只把結論帶回來，它的職責範圍見它自己的定義檔。

自我檢測：我準備使用的這個 herdr 指令或欄位，回不回傳模型產出的文字？回傳的話，我指不指得出
自己現在正落在第一條那四個觸發條件的哪一個？我準備讀的這份內容，是不是 phase 的程式碼、
diff、測試輸出或 PR review？我準備寫入的這個檔案，是不是落在狀態檔與那份 epic 設計文件這兩個
對象以外？觸發條件指不出是哪一個，或任一題答「是」或「不確定」，就不要做。

## 升級清單

自決是預設，升級是例外。以下九項是唯一該停下問使用者的情況：命中任一項就停，清單以外的卡點
一律由 orchestrator 自己決定。這份清單是窮舉的，不是舉例——「這件事好像有點大」不構成升級理
由，指不出命中哪一項就是不命中。

1. **需要在方案之間做價值取捨。** 判準是兩個方案的後果都成立，選哪一個取決於使用者要什麼，
   而不是哪一個會失敗。有一邊會失敗的不是取捨，是判斷，自己判。
2. **會改變 epic 設計文件所定的 phase 之間介面，或改變某個 sub-issue 的範圍。**
3. **設計文件的假設被推翻，而影響不只落在提出請求的那一個 phase。** 判準不靠裁量，直接沿用
   `plan-integrity` rule 本來就要求做的那次搜尋——假設被推翻時，orchestrator 一定要拿該假設
   的關鍵詞搜過設計文件全文（完整程序見「決策迴圈」底下「設計文件的假設被推翻時」）：
   - 搜尋只命中提出請求的那個 phase：自行改設計文件並回覆，不升級。
   - 搜尋命中其他 phase，或修補需要增刪 sub-issue，或要改動 blocked by 依賴圖：升級。
   - 命中落在不對應任何 phase 的段落（背景、架構總覽這一類）：歸第一種那一邊，自行改、不升
     級。`plan-integrity` 本來就把這種命中算成不對應任何下游產物，空的下游清單即為正確狀
     態；一次搜尋若同時命中這種段落與其他 phase，仍以命中其他 phase 那一條為準。這一條只決
     定本項的分支，第二項（改到 phase 之間的介面）仍各自獨立判定。

   本 skill 在這裡刻意收窄了 `plan-integrity`：那條 rule 把「修計畫、再往受影響的下游傳播」
   整件事都指派給編排端自理，不分影響落在幾個 phase；本 skill 把命中其他 phase 的那一種改成
   升級，理由是跨 phase 的影響值得使用者知情——他當初核准的是那張依賴圖與那組 phase 之間的
   介面，改動一旦跨出單一 phase，他就有可能想換一個修法。
4. **會產生不可逆或波及該 phase 以外的後果。** 這一項規範的是 orchestrator 自己要做、或要親
   手批准的動作，「親手批准」有兩條出口：代按核准框，以及走 A 或 B 路徑的回覆內容本身授權對
   方去做某個具體動作——後者一樣算親手批准，不因為動手的是對方就不算。相對的「自行完成」專
   指 phase agent 未經請示、自己就做掉的動作，本項不涵蓋那一種，那一種由
   `phase-agent-contract.md` 的動手前守衛約束；這條排除依賴一個未查證的假設（見「決策迴圈」
   入口二對 `--permission-mode auto` 射程的說明）：落在信任邊界上的動作會以核准框的形式回到
   orchestrator 手上，才輪得到本項攔它。假設不成立時，一整批不可逆動作會完全不經過本項。本項
   也不涵蓋 orchestrator 例行的編排動作：建立 worktree、開關 tab、寫狀態檔、fetch、送下行訊
   息（本項首句那兩條出口——代按核准框，以及授權對方做某個具體動作的回覆內容——除外），以及
   委派 `github-manager` 執行的唯讀查詢，以及 Epic 收尾階段關閉 parent issue 的操作。
   下面那份名單是地板，不是提示：列名的一律命中，不必再套判準，也不得因為「套判準好像過
   得了」就判定不命中——名單上的「引入新的外部依賴」與「改動專案級設定」正是這一種：
   檔案落在該 phase 自己的 worktree 內、回復也不需要別人配合，前兩支判準都不成立，它們靠
   的是第三支才命中。判準負責往外擴，把名單以外的同類納進來，三支任一成立就命中：回復這
   件事需不需要動到該 phase worktree 以外的東西，或需不需要別人配合；影響會不會落到其他
   phase、共用資源或外部服務上，而且不是該 phase 自己收得回來的；這個改動當下落在該
   phase 自己的 worktree 內，但合併之後會落到其他 phase 或整個 repo 身上（例如改
   `.gitignore`、改 lockfile、改測試基礎設定）。名單：合併；對共用分支 force push 或改寫
   歷史；刪除遠端分支；發布或 release；憑證輪替或寫入；對外部服務寫入；刪除或覆寫該
   phase worktree 以外的資料；引入新的外部依賴；改動專案級設定（例如 CI、lint、依賴清
   單）。force push 值得單獨點名：它不是「對外部服務寫入」的自然讀法，卻是這個多
   worktree、多 phase 並行的流程裡最容易發生、也最不可逆的一種。本項判準命中之後，唯一
   的排除是 orchestrator 依上一項的自決分支更新 epic 設計文件——那份文件在任何 phase
   worktree 之外，字面上落在本項的「覆寫該 phase worktree 以外的資料」裡，但上一項已經
   對它給出處置，那一種以上一項為準，不因本項而改判升級。
5. **workspace 信任對話框。** 它問的正是使用者信不信任這個目錄，這個問題只有使用者答得了，
   orchestrator 不自行決定按哪一個選項；使用者答覆之後，仍由 orchestrator 依「決策迴圈」的出
   口代按轉達。
6. **同一個 phase 就同一議題再次回來且無法決定，或同一議題進入第三輪。** 「同一議題」的界
   定：對方這次要的裁決，與上一次要的裁決指向同一個待決事項——換個問法、換個切入角度、把問
   題拆小、補上新的嘗試紀錄，都還是同一議題；只有待決事項本身換了，才是新議題。不是第二次回
   來就升級：第二次先再試一次回覆，只有確認無法決定才升級。「確認無法決定」的可觀察判準是這
   一輪指不指得出一個與上一輪不同、而且直接回答對方原文那個問題的依據——設計文件的另一段，
   且該段寫出了這次要選的那一項的判準；或調查者這次讀到的新事實。「設計文件另有一段提到相關
   主題」不算，那只換了引用、沒換答案。天花板是硬的，而且不帶前提：同一議題進到第三輪一律升
   級，不再問自己指不指得出新依據，也不問先前有沒有派過調查者——派過與否不是升級的觸發條
   件；升級時要呈上什麼材料，一律依「決策迴圈」升級路徑第一層依來源取基底。每多一輪就依「自
   決事項的即時回報」報一行給使用者，讓輪數在使用者眼前是可見的。
7. **依賴圖成環，或依賴指向不存在的 issue。** 停下回報，不猜測順序。
8. **合併確認。** `human-in-the-loop-boundaries` rule 明定 AI 不自動 merge，本 skill 不放寬
   這一條。
9. **orchestrator 受禁令或能力所限做不到，或自決手段已用盡仍判不出來。** 兩種情形都算：一是
   該做的動作被「主 Context 的三條硬禁令」擋住，或超出 orchestrator 的能力範圍（例如殘留
   worktree 的移除，第三條禁令連改一個檔案都不允許，何況整個目錄）；二是自決手段已經用盡
   ——該重試的重試過、「失敗行為」列出的四種證據中取得條件成立的都取過、取不到的指得出被哪一
   條擋住（第四種讀 pane 以四個觸發條件之一成立為前提，一個都不成立時它本來就取不到，把這一
   點指出來就算這一格答完）、該派的調查者也派過——仍然判不出該怎麼處置，或沒有下一個做得到的
   動作。這一項是清單的收尾項：前八項攔的是特定情境，這一項攔的是「情境本身沒問題、但這一端
   做不到或看不出來」，有它，「指不出命中哪一項就自己決定」才不會把 orchestrator 推去硬做一
   件它做不掉的事。

第四項（不可逆或波及該 phase 以外）與第八項（合併確認）合起來已經涵蓋「tab 已不在而 PR 未合
併」這種情形：合併本身歸第八項，而自行重派會在同一個 sub-issue 上開出第二條分支，屬於第四項
所說的波及該 phase 以外的後果。這種情形不必另外找一項來對應。

自我檢測：這個卡點命中的是上面第幾項，我指得出編號嗎？指不出來就不是升級案件，自己決定——但
「自己決定」的前提是這一端做得到也判得出來，做不到或判不出來的那一種，指出來的編號就是第九
項。

## 啟動階段

使用者提供 parent issue 後，orchestrator 委派 `github-manager` 依序取得 parent issue 內
文、其下的 sub-issue 清單，以及每個 sub-issue 的 blocked by 關係，據此建出依賴有向圖與初始
進度表。

所有經由 `gh` 對 GitHub 的操作，含唯讀查詢，一律委派 `github-manager`；orchestrator 不自行
呼叫 `gh`。

建表之後，sub-issue 的 `state` 與 PR 的合併狀態就是進度的權威來源——後續任何關於某個 phase
完成到什麼程度的判斷，都以這兩者為準，不是以狀態檔或記憶中的印象為準。

## 派工階段

對每個沒有未完成依賴的 phase，orchestrator 依序做以下動作：

1. 先 fetch `origin/main`，再於倉庫內的 `.worktrees` 目錄底下建立該 phase 的 worktree。先
   fetch 這一步不可省略：省略的話，worktree 會是從尚未更新的本地 main 拉出來的，一開始就
   落後。
2. 在 orchestrator 自己所在的 workspace 開一個 tab：cwd 指向該 worktree、帶 `no-focus`、
   label 帶 sub-issue 編號。開 tab 時必須顯式指定 workspace 識別碼。省略時的落點未查證，據信
   會取當下使用者介面焦點所在的 workspace，不一定是 orchestrator 自己所在的那個；推翻時顯式
   指定只是白做一步，但這個說法若是對的而識別碼被省略，tab 會開在別的 workspace，
   orchestrator 之後按進度表上的座標找不到它。
3. 在該 pane 啟動 kind 為 `claude` 的 agent。啟動時帶 `--permission-mode auto` 這個旗標，字
   串照此原文，不要改寫成別的權限模式；同時要帶 `add-dir` 旗標指向 epic 設計文件所在目錄，
   理由見下方「開場指令」一節。herdr 傳遞原生參數給 agent 的方式，是在 `herdr agent start`
   指令的 `--` 之後接續原生參數，這兩個旗標都走這條路徑傳遞。
4. 啟動時要給這個 agent 一個名稱，格式為 `phase-` 接 sub-issue 編號（例如 `phase-123`）；
   這個格式在同一個 repo 的 sub-issue 編號空間內唯一，射程只到這裡：跨 repo 的兩個 epic 平行
   推進時，同號的 sub-issue 會取出同一個名稱，而 herdr 的名稱空間是不是跨 workspace 全域，未
   查證——若是全域，後起的那個 epic 會撞名，啟動被拒或訊息送到另一個 epic 的 agent 上。
   （herdr 對名稱另有字元集與長度限制，不合時啟動會被直接拒絕並指出原因、不是靜默失敗，這兩
   點都未查證；推翻時的後果是取名不合規而啟動靜默失敗，要到「啟動成功判準」那一關才發現。照
   上面的格式取名不會撞到這些限制，不必另外記。）
5. 確認啟動成功（見下方「啟動成功判準」）之後才送出開場指令。

`--permission-mode auto` 的字串照原文帶，不可換成其他權限模式：換掉的後果是打壞下方「啟動成
功判準」（agent 停在確認對話框上而不是 `idle`），或造成靜默拒絕（phase agent 在第一個需要權限
的動作上被擋下，而沒有任何訊息說明這件事）。後一種未查證：推翻時它其實會以核准框或錯誤訊息
現身，那就退化成前一種，照原文帶這條要求不受影響。這也是下一段那句「以 `--help` 為準」不適用
於這個值的原因：`--help` 列得出有哪些候選值，列不出哪一個不會打壞啟動成功判準。

上面涉及的 herdr 旗標（workspace 識別碼、`no-focus`、`add-dir`、agent 名稱與 kind、`--` 之
後接續原生參數）是已知存在的能力，但確切的旗標名稱與語法以呼叫當下該子命令自己的 `--help`
或不帶參數的輸出為準，不要照記憶湊。

自我檢測：這五個動作的順序有沒有被打亂，尤其是 fetch 是不是排在建立 worktree 之前、啟動成功
判準是不是排在送出開場指令之前？順序錯了就先停下重來，不要將錯就錯往下做。

### 啟動成功判準

`herdr agent get` 回應的三項要齊備才送出開場指令：

- `agent_status` 為 `idle`
- `launch_pending` 不為真——這個欄位不保證出現：對一個剛啟動完成、已就緒的 agent 下
  `herdr agent get`，回應裡根本查不到 `launch_pending`，不是查到它的值為 `false`；已實測到
  的另一種情形是，卡在信任對話框時這個欄位存在且為 `true`。因此欄位缺席一樣算
  「不為真」，不要因為查不到這個欄位就以為要停下查明
- `interactive_ready` 為真

三項不齊備時停下查明：查明的具體動作是 orchestrator 自己用 `herdr pane read` 讀那一格 pane，
判定它停在什麼上面。這正是「主 Context 的三條硬禁令」第一條例外的觸發條件二所指的情形。此處
不委派調查者——這個時點 phase agent 還沒報到，要知道的也只有「它停在什麼上面」這一句。不得對
著一個卡住的畫面送出開場指令，但理由不是怕靜默失敗：已實測到對一個處於 `blocked` 的 agent 送
`herdr agent prompt`，指令回傳 `agent_blocked` 錯誤並拒絕執行，事後讀那格 pane 也找不到送出
的字串，所以送了只會白費一次往返、拿到一則錯誤。這個關卡真正的價值在順序——先查明它為什麼卡
住再決定處置，而不是先送再看。要注意這道保護只涵蓋 `herdr agent prompt`：
`herdr agent send-keys` 是直接送按鍵，沒有這道檢查（此點未查證，推翻時的後果是代按可能把按
鍵留在一張無效的畫面上，而且不會有錯誤訊息）。判定結果只分兩條路，沒有第三條：卡在信任對話
框（workspace 信任提示）的，命中「升級清單」第五項，停下問使用者要不要信任這個目錄，不自行
決定按哪一個選項；其餘一切情形（例如 agent 沒起來、啟動指令失敗、停在別的確認框）走「失敗行
為」第一列——自行關掉這個 pane 重啟一次，第二次仍失敗才升級（第九項）。

自我檢測：這三項是不是同時為真？只要有一項答否或答不出來，就不送開場指令。

### 開場指令

開場指令只帶四項：

1. sub-issue 編號
2. epic 設計文件的**主倉庫**絕對路徑
3. orchestrator 自己的 session 名稱
4. `phase-agent-contract.md` 的絕對路徑

設計文件必須給主倉庫絕對路徑，不能給 worktree 內的路徑：本倉庫的 `.gitignore` 忽略整個
`docs` 目錄，被忽略的檔案不會隨 git worktree 出現，phase agent 若拿到 worktree 內的路徑會
讀不到這份文件；這也是上一節要求啟動時帶 `add-dir` 旗標指向設計文件所在目錄的理由。

orchestrator 取得自己 session 名稱的方式是呼叫 `ListAgents` 工具，其回應第一行會指出當前
session 的名稱；這個名稱就是其他 session 用來定址它的位址，直接使用，不必另外查找或猜測。
「回應第一行指出的就是當前 session」這一點未查證：推翻時的後果是 orchestrator 把某個別的
session 名稱當成自己的、交給每一個 phase agent，所有上行訊息全數送不回來，而在第一則報到訊
息該出現卻沒出現之前，這件事不會有任何徵兆。

契約全文由 phase agent 自己讀取 `phase-agent-contract.md`，不經開場指令的指令列傳遞。

### phase agent 報到

phase agent 收到開場指令後的第一個動作是送出報到訊息。orchestrator 從報到訊息的
`from-name` 取得它的 session 位址，寫進進度表的 herdr 座標欄位。

## 通訊協定

下行與上行走不對稱的機制，各取該方向最可靠的。

下行，從 orchestrator 到 phase agent，走 `herdr agent prompt`：它帶有 `agent_blocked` 檢
查，對方處於 `blocked` 時會明確拒絕（實測依據見「啟動成功判準」，那次實測的對象正是一個處於
`blocked` 的 agent）；狀態不是 `blocked` 的畫面不在這道保護的射程內。唯一例外是回答核准框本
身，那要用 `herdr agent send-keys` 代按選定的那個選項——這個選項由誰選定（orchestrator 自己
或使用者），見下方「決策迴圈」。

上行，從 phase agent 到 orchestrator，走跨 session 訊息（`cross-session-message`）：它是主
動推送，orchestrator 不必輪詢就能收到。

phase agent 唯一能主動送出的訊息只有以下四種，表中用字是 orchestrator 視角，對應的規範在
`phase-agent-contract.md`（例如契約檔對 phase agent 寫「你的推薦」，此處寫「phase agent 的推
薦」）：

| 訊息 | 帶的欄位 |
| --- | --- |
| 報到訊息 | phase 編號、自己的 session 位址 |
| 決策請求 | 問題、已經試過什麼、選項與各自後果、phase agent 的推薦、設計文件依據 |
| PR ready | PR 編號、一句話結論 |
| 收尾完成 | 一句話 |

「設計文件依據」這個欄位要指出這個問題對應 epic 設計文件的哪一段，或明白說明設計文件沒有交代
這件事。它是提示，不是閘門：它存在的目的只是給下方「決策迴圈」的分流一個起點，A 路徑成不成立
一律要 orchestrator 自己打開那一段做完內容測試。欄位指得出對得上的段落時，起點就是那一段；欄
位缺席、看不出指向哪裡，或寫的是「設計文件沒有交代」時，orchestrator 自己拿問題的關鍵詞搜一
次設計文件，就這一次：搜得到段落且通過 A 路徑的內容測試，走 A 路徑；搜不到，或搜到的段落過不
了內容測試，才走 B 路徑派調查者。不自己搜就直接判 B 路徑，等於把該不該走 A 路徑交給資訊比自
己少的那一端單方認定，代價是每一次都吃掉一輪 subagent 往返。禁的是另一件事：不得在沒有打開段
落的情況下宣稱有依據，也不得推測一個段落補進欄位裡。

收到不屬於這四種的訊息內容時，不要當成又一種新格式接受，先懷疑契約有沒有被遵守（見
`references/rationale.md`「待驗證的假設」一節）。這則訊息本身仍要處置，不是丟掉：從中取出它
到底要 orchestrator 做什麼決定，依「決策迴圈」照決策請求處理，其餘內容不納入判斷。取不出待決
事項的走 B 路徑，派調查者去查明這個 phase 究竟停在什麼待決事項上，事由就寫「收到一則不屬於四
種格式的上行訊息，取不出待決事項」；調查者也給不出待決事項時，才依「升級清單」第九項升級，連
同「收到的是契約外格式」這件事一起呈給使用者。

上行是對方主動推送，所以第二條禁令那句「不主動去取」擋不到它——決策請求的「已經試過什麼」與
「選項與各自後果」兩個欄位，天然容得下程式碼片段與 diff。推送進來的內容比照讀 pane 那一段的
用法約束：收到就是收到了，但只取決策所需的那幾項（問題、選項與後果、推薦、設計文件依據），其
餘內容不納入判斷、不轉述給別的 phase、不寫進進度表。

自我檢測：這則決策請求的「設計文件依據」欄位，指出的是設計文件的某一段嗎？不是（欄位缺席、看
不出指向哪裡，或明說設計文件沒有交代）的話，我是不是自己搜過一次設計文件，才決定走 A 還是
B？我這次據以判斷的，是不是只有決策所需的那幾項，沒有把附帶送來的程式碼或 diff 算進去？

## 監控節奏

上一節的上行機制是主動推送，但 phase agent 停在核准框或其他非自願的東西上時不會送任何訊息
（不在四種之內），這種情況只能靠 orchestrator 主動觀測狀態變化才能發現。orchestrator 用以下
節奏維持觀測：對進度表上每一個目前在跑（非等待決策、非等待啟動、非 PR ready）的 phase，逐一
呼叫 `herdr agent wait <agent 名稱> --until idle --until blocked --timeout <單次逾時毫秒>`；
這個呼叫會阻塞到逾時或狀態變成 `idle` 或 `blocked` 為止。

`idle` 與 `blocked` 兩個值都要顯式帶上（同時指定兩個值的確切寫法以該子命令自己的 `--help` 為
準），不要改用不帶 `--until` 的預設值：預設集合還包含 `done`，而 `done` 對一個 Claude Code
session 的確切語意尚未實測，帶進來等於在判定裡混進一個沒人知道意思的狀態。

呼叫因狀態變成 `idle` 或 `blocked` 而回傳時，判定規則只有一條——這段期間有沒有收到該 phase
的上行訊息：

- 有：依訊息類型正常處理（決策請求走下方「決策迴圈」入口一，其餘三種是報到、PR ready、收尾
  完成）。
- 沒有：進入下方「決策迴圈」。回傳時狀態為 `blocked` 的是入口二、為 `idle` 的是入口三，兩者
  的處置相同。

呼叫是逾時回傳、狀態仍為 `working` 的，兩邊都不算，換下一個 phase 繼續；這種輪次要計數，供下
面的十輪條款使用。

每呼叫完一個 phase，先處理這段期間累積的任何上行訊息，再輪到下一個 phase；如此循環，讓「等
待上行訊息」與「輪流觀測狀態變化」共用同一個迴圈，不各自獨立跑。PR ready 的 phase 是依設計
閒置等 review，不落在這個觀測集合裡，否則每一輪都會白白吃掉一次逾時。orchestrator 阻塞在某
一個 phase 的這次等待時，其他 phase 推來的訊息要等這次呼叫結束才處理得到，這是這個機制本身
的代價。

整輪觀測（依序對目前在觀測的每個 phase 各呼叫一次 `herdr agent wait`）訂一個牆鐘上限：
60000 毫秒（60 秒）。單次逾時毫秒 = 這個上限除以目前在觀測的 phase 數，讓整輪的總阻塞時間
不隨 phase 數增加而拉長。`herdr agent wait` 其餘的旗標語法與 `--until` 還接受哪些值，以呼叫
當下該子命令自己的 `--help` 為準，不要照記憶湊；要帶哪兩個值則已由上面釘死，不隨 `--help`
列出的清單改變。

同一個 phase 連續十輪整輪觀測都是 `working`、且期間沒有收到任何上行訊息時，命中「主 Context
的三條硬禁令」第一條例外的觸發條件四：用 `herdr pane read` 讀一次那格 pane，判定它是在做事還
是空轉。這十輪合計至多約十分鐘，通常更短——每輪 60 秒是牆鐘上限而不是下限，只要有 phase 提早
回傳，整輪就短於 60 秒。

輪數只在連續的逾時輪次上累加。這個 phase 一旦回傳非 `working` 的狀態、收到任何一則上行訊息、
或離開觀測集合（例如轉為等待決策或 PR ready），計數就歸零；之後回到觀測集合時從零開始重算，
不接續離開前的舊值。

讀完 pane 一定要有出口，不能讀完就回到迴圈——`working` 但空轉不落在「決策迴圈」三個入口的任
何一個，沒有出口就等於讀完之後無程序可循：

- 判定它在做事：重置這個 phase 的輪數計數，繼續觀測。
- 判定它空轉：併入「決策迴圈」的 B 路徑，委派 `phase-decision-investigator`，帶的事由就是這
  一句判定結論。

兩種判定都要依「自決事項的即時回報」報一行（讀 pane 落在該節第四項）。

自我檢測：進度表上正在跑的每一個 phase，是不是都在最近一輪迴圈裡被 `herdr agent wait` 觀測
過？漏掉任何一個，入口二與入口三對那個 phase 就形同不存在。

### 下行送出後的握手

orchestrator 每次下行送出後（`herdr agent prompt` 或 `herdr agent send-keys`），先呼叫
`herdr agent wait <agent 名稱> --until working --timeout 10000` 確認對方確實接手了，再把這
個 phase 放回上面的一般觀測迴圈。

這個握手呼叫必須帶明確的 `--timeout`，初始值取 10000 毫秒（10 秒）。不能省略的理由是
`herdr agent wait` 不帶 `--timeout` 時會無限等待——這一點已查證，依據是該子命令自己的
`--help` 輸出末段逐字這樣寫。握手一旦沒設逾時，只要這則下行訊息沒被接手，orchestrator 就永久
阻塞在這一次呼叫上，整個 epic 跟著停擺——它是唯一在盯所有 phase 的那一端，它停下就沒有別的
機制會發現。逾時後不當成失敗處置：它命中「主 Context 的三條硬禁令」第一條例外的觸發條件三，
由 orchestrator 用 `herdr pane read` 讀該 phase 的 pane 判因，再依「決策迴圈」入口二與入口三
的同一條處置往下走（判定結果併入 A 路徑或 B 路徑）。

不做這個握手會產生一種誤判：剛送出 prompt 的那一瞬間，phase agent 還停在 `idle`，一般觀測迴
圈於是立刻判成入口三，orchestrator 跑去讀一張根本沒事的 pane。

自我檢測：這次下行送出後，我是不是拿到了 `--until working` 的回傳（接手了，或逾時了），才把
這個 phase 放回一般觀測迴圈？沒有的話就還不能放回去。

## 決策迴圈

決策迴圈有三個入口，另有兩條讀完 pane 之後併入的路徑。處置只有 A、B、升級三條，出口只有一
個。預設由 orchestrator 自己決定，只有命中「升級清單」才轉給使用者。

三個入口：

- 入口一：phase agent 主動送出決策請求，走上一節「通訊協定」的上行機制。
- 入口二：它撞到權限提示或核准框而進入 `blocked`，orchestrator 從「監控節奏」的迴圈觀測中看
  得到狀態變化，但狀態本身不帶提示內容。`--permission-mode auto`（見「派工階段」第 3 步）不
  會讓這個入口消失。這個旗標實測到的射程只有一件事：以 auto 啟動的 agent，被要求用 Bash 工具
  對工作目錄以外的路徑建立檔案時，檔案確實被建立，過程中沒有出現任何核准框。射程之外它是不
  是無條件放行，要把兩件事分開講。可查證的一件：作用中的使用者層設定檔帶有一個 `autoMode` 環
  境區塊，裡面記著若干信任邊界，例如名稱帶 `prod` 或 `production` 的遠端目標、IAM 與 RBAC 與
  networking 這類受保護的 IaC 範圍。要注意這個區塊自述的信任倉庫是另一個倉庫（一個 Obsidian
  vault），區塊裡以那個倉庫為前提列舉的路徑與慣用指令，對本 epic 所在的倉庫沒有射程；它對預
  設分支那一欄也只寫了 main 是預設分支、沒有列出任何 branch protection 規則，並自陳這一點未
  經確認。未查證的一件：這些邊界在 auto 之下是不是真的會跳出核准框，沒有任何量測背書——推翻
  時壞掉的是「升級清單」第四項那條排除（phase agent 自行完成的動作不歸該項），落在邊界上的不
  可逆動作會既不跳框、也不經過第四項，兩道都攔不到。所以入口二要當成常態管道看待，不是罕見
  情形；workspace 信任對話框只是其中一種殘留來源，不是主要的那一種。
- 入口三：它處在 `idle`，而 orchestrator 沒有收到伴隨的上行訊息。這一個與入口二並列，不是取
  代關係——正常停下的每一種情況都會先送訊息，停了卻沒訊息就是異常（機制見「主 Context 的三
  條硬禁令」第一條）。

另有兩條不是入口、但讀完 pane 之後併進本節處置的路徑：下行送出後的握手逾時（見上一節），以
及同一個 phase 連續十輪整輪觀測都是 `working` 而判定為空轉（見「監控節奏」）。這兩條與入口
二、入口三一樣，都是先讀 pane 拿到一句判定結論，再併入 A 路徑或 B 路徑；升級路徑呈交內容也
與那兩個入口同一組。

分流規則。入口一先看決策請求的原文分類：

- **A 路徑（orchestrator 直接回覆）**：問題屬於設計文件該回答的，也就是 phase 邊界、與其他
  phase 的介面、判準已寫在設計文件裡的方案選擇這幾類。orchestrator 依 epic 設計文件與依賴圖
  直接回覆。A 路徑的守衛是內容測試，不是引用測試：決策請求的「設計文件依據」欄位只是起點
  （欄位缺席或自陳沒有交代時，起點改為 orchestrator 自己搜一次設計文件，程序見「通訊協
  定」），orchestrator 要自己打開那一段讀過，確認它寫出了這次要選的那一項的判準——只是提到相
  關主題、或只是背景描述，都不算；回覆時把該段的標題或原文一句一併帶上，讓「確實讀過那一段」
  留得下痕跡。這個測試不成立就改走 B 路徑，不要用「照常理應該是」補上去——orchestrator 看不
  到這個 phase 的開發內容，它的常理沒有材料支撐。
- **B 路徑（先調查再回覆）**：其餘一律走這條。委派 `phase-decision-investigator` 做完整調
  查，再依它的推薦回覆。

入口二與入口三一律先由 orchestrator 自己用 `herdr pane read` 讀該 phase 的 pane，判定它停在什
麼上面（這正是第一條禁令的觸發條件一所開的例外），再依判定結果併入 A 路徑或 B 路徑。這一步不
改派調查者，理由是規模不對稱：調查者做的是完整調查，對「只需要知道它停在什麼上面」這一句話過
重，而每一次觀測都吃掉一輪 subagent 往返，會拖慢整個 epic 的推進。真正需要完整調查的情形不會
因此漏掉——讀完之後由 B 路徑承接，該派的仍然會派。

任一路徑中一旦命中「升級清單」任一項，就轉第三條路徑：

- **升級路徑**：呈給使用者的內容分兩層取，兩層可疊加，不是從一份清單裡挑一組的單選。第一層
  依這次升級從哪裡來，三組必取其一，取到的那一組就是基底；第二層依命中「升級清單」第幾項，
  命中下列項次的把該組疊上去做增補，沒有對應項次的，基底就是全部。

  第一層，依來源取基底：
  - 入口一引發的：先確保完整調查已經做過（走 A 路徑還沒派調查者的，此時補派），再把 phase
    agent 的原文請求與調查者的分析兩份並列呈上，不得只給分析結果——調查者可能誤判，並列才讓
    使用者有機會發現分析讀歪了。
  - 凡是讀過 pane 才轉進來的（「啟動成功判準」三項不齊備而讀 pane、入口二、入口三、握手逾
    時、連續十輪空轉）：這幾條都以「沒有收到伴隨的上行訊息」為前提，沒有原文請求可以並列，
    改為呈上讀 pane 得到的那一句判定結論；先前已經派過調查者的把它的分析一併並列，沒派過的
    不為了升級補派，只並列判定結論。不補派的理由是判定結論已經辨識到動作的層級時，第四項的
    判準就是由它滿足的，補派一次完整調查不會多給使用者任何判斷材料。
  - 既沒有原文請求、也沒有 pane 可讀的（例如「tab 已不在而 PR 未合併」——tab 沒了就讀不到
    pane，這件事也不是 phase agent 提出來的；依賴圖成環、合併確認、殘留的收尾也都落在這一
    組）：呈上三件事——這件事的事實、為什麼 orchestrator 自己決定不了、有哪些可選處置與各自
    的後果（典型如「要重派還是接手」）。

  第二層，依項次增補：
  - 判定為 workspace 信任對話框（第五項）：不派調查者（見「啟動成功判準」），加上是哪一個目
    錄、等在那裡的是哪一個 phase。
  - 依賴圖成環或指向不存在的 issue（第七項）、合併確認（第八項）：不派調查者。這兩種的事實
    全在依賴圖與使用者自己的宣告上，沒有可調查的對象；第七項還發生在啟動階段，那時 worktree
    與 herdr 座標都還不存在，調查者的必填輸入根本湊不齊。
  - 做不到或判不出來（第九項）：加上已經取過哪幾種證據、試過哪些自決手段、卡在哪一條禁令或
    哪一項能力上；先前已經派過調查者的把它的分析一併並列，沒派過的不為了升級補派。

委派 `phase-decision-investigator` 時，依它自身定義檔 `Input from Main Agent` 一節提供：
sub-issue 編號、該 phase worktree 的絕對路徑、herdr 座標中的 tab 識別碼與 agent 名稱、觸發本
次調查的具體事由（入口一給 phase agent 送出的原文——問題、已經試過什麼、選項與各自後果、推
薦、設計文件依據；凡是讀過 pane 才轉進來的——入口二、入口三、握手逾時、連續十輪空轉——一律
給那一句判定結論，即它停在什麼上面，不含畫面其餘內容；收到契約外格式訊息而取不出待決事項的
那一種，另給一句由 orchestrator 自己寫的、對那則訊息內容的概括——原文依「通訊協定」那一節的
用法約束不逐字轉述，但這條線索只有 orchestrator 拿得到，調查者未必復原得了）、該 phase 已開
PR 時的 PR 編號。可選提供已知的相關背景，以及 epic 設計文件的主倉庫絕對路徑。不需要（且依「主 Context 的三條硬禁令」也不
能）額外提供 codebase 內容、git log、diff、pane 畫面內容或 PR review 留言本身——那些原本就是
調查者自己會去讀的部分。

出口只有一個：orchestrator 把定案轉達回該 phase agent。自己的決定和使用者的決定走同一個出
口，沒有第二條路。轉達形式依對方停在什麼上面而定：一般情形走 `herdr agent prompt`；對方正卡
在核准框時，`herdr agent prompt` 會被 `agent_blocked` 檢查擋下，改用 `herdr agent send-keys`
代按選定的那個選項——但代按只在這個核准框問的正是這次定案要回答的那件事時，才算把定案轉達出
去。核准框問的是別件事（例如定案是介面選型，對方卻卡在「要不要跑某條指令」）時，按下去只解
得開阻塞、送不到定案：先過下面的代按守衛把它按掉解除阻塞，等狀態離開 `blocked` 之後，再以
`herdr agent prompt` 送出定案。送出後依「監控節奏」的握手確認對方接手，再放回一般觀測迴圈；
先解阻塞再送定案的那一種，兩次下行各自跑一次握手。

代按是 orchestrator 親手放行破壞性動作的地方之一（另一處是「失敗行為」第一列的關掉 pane 重
啟，那一處的守衛見該節），而且是唯一一個放行什麼由畫面上那個核准框決定、orchestrator 只負責
按下去的，所以它自帶一道前置守衛。守衛的最前面是一道分支：這一次的判定結論就是 workspace 信
任對話框的，直接走「升級清單」第五項的升級路徑，由使用者定案之後再由 orchestrator 代按，不進
入下面那道測試——那個框放行的是整個目錄的信任，本來就指不出單一具體動作，拿它去問「是哪一個
動作」只會得到指不出來。其餘情形才進測試：按下去之前，先看手上這一次讀 pane 得到的那句判定結
論，或調查者回傳中指名的那個動作，指不指得出核准框要放行的是哪一個具體動作——要寫哪個檔案、
要跑哪一條指令、要對哪個遠端做什麼。三種答案三條路：

- 指不出來：一律改走 B 路徑派調查者，不得先按了再說。調查者回來之後再走一次這道守衛，這次
  的證據換成它回傳中指名的那個動作（它不會逐字帶回核准框原文，那是它的定義檔明文禁止的）。
  派過調查者仍然指不出是哪一個動作的，就是「升級清單」第九項（自決手段已用盡），走升級路
  徑，不得回頭代按——這是這條分支的終止條件，不會停在原地反覆改派。
- 指得出來，而該動作命中「升級清單」第四項的判準：走升級路徑，由使用者決定。
- 指得出來且不命中第四項：才代按。

走到代按這一步（含前置分支那條由使用者定案後回來按的）還有最後一道前置條件：按下去之前重新
確認這個 agent 的 `agent_status` 仍為 `blocked`，不是就中止這次代按、重讀一次 pane 再走一遍本
節。理由是這道守衛的證據是這一次讀 pane 得到的判定結論，它與按鍵送出之間隔著一段時間，而
`herdr agent send-keys` 沒有 `agent_blocked` 檢查（見「啟動成功判準」），按在一張已經換掉的畫
面上不會有任何錯誤訊息。這道檢查只取狀態欄位、不回傳模型產出文字，不受第一條禁令限制。

第二條禁令只准 orchestrator 從畫面上取「它停在什麼上面」這一句，這道守衛要的正是這一句必須辨
識到動作的層級；取不到就是取不到，用推測把它補齊，等於在不知道自己放行了什麼的情況下按下去。

自我檢測：我這次走的是 A 路徑、B 路徑還是升級路徑？走 A 路徑的話，我打開的那一段設計文件，寫
出了這次要選的那一項的判準嗎？走升級路徑的話，這次升級的來源落在第一層哪一組基底、命中的又是
「升級清單」第幾項，兩個我都指得出來嗎，且呈上的內容就是那一組基底加上該項次若有的增補嗎？這
次轉達出去的內容——不論是代按核准框，還是用 `herdr agent prompt` 送出的回覆——授權了對方去做
哪一個具體動作？沒有授權任何具體動作（典型是 A 路徑一次答完的介面裁決）就算通過這一題；指得
出具體動作的，才續問那個動作命不命中第四項。任一題答不出來，就是路徑選錯或內容不完整，不要
送出。

### 設計文件的假設被推翻時

定案（不論出自 orchestrator 還是使用者）若代表 epic 設計文件的某個假設被推翻，只轉達給發起請
求的這個 phase agent 還不夠。「推翻」的判準是：照設計文件原本的敘述做會失敗、或產生與所述不
同的結果；「有更好的做法」不算推翻，那是優化提案，不觸發以下處置。

假設確實被推翻時，第一個動作固定是搜尋：以該假設的關鍵詞搜過 epic 設計文件全文。這一次搜尋同
時決定兩件事——這件事要不要升級，以及有哪些 phase 受影響——所以只做一次，不是兩套判準：

- 只命中提出請求的那個 phase：orchestrator 自行更新設計文件並回覆，不升級。
- 命中其他 phase，或修補需要增刪 sub-issue、要改動 blocked by 依賴圖：走升級路徑（「升級清
  單」第三項，設計文件假設被推翻）；使用者定案後，仍由 orchestrator 更新設計文件並完成下面的
  傳播。
- 命中落在不對應任何 phase 的段落（背景、架構總覽這一類）：歸第一種那一邊，自行更新、不升
  級。這種命中在 `plan-integrity` 底下本來就不對應任何下游產物，下面的傳播對它而言空清單即
  為正確狀態；一次搜尋若同時命中這種段落與其他 phase，仍以命中其他 phase 那一條為準。這一條
  只決定本節的分支，「升級清單」第二項（改到 phase 之間的介面）仍各自獨立判定。

第二種要升級，是本 skill 對 `plan-integrity` 的刻意收窄：那條 rule 本來把「修計畫再往下游傳
播」整件事都交給編排端自理，不分影響落在幾個 phase（收窄的理由見「升級清單」第三項）。

不論哪一種，判斷設計文件哪些內容因此過時，只能依據該 phase 的決策請求原文（凡是讀過 pane 才
轉進來的都沒有原文，改依讀 pane 得到的那一句判定結論）與調查者分析，不得讀 phase 的程式碼、
diff 或 pane 畫面上判定結論以外的內容。設計文件更新後，依搜尋命中處逐一處理其他 phase——已經
在跑的通知它假設已更新，尚未派工的確保派出時讀到的是更新後的內容。`plan-integrity` rule 把這
個義務放在編排端：唯有 orchestrator 同時知道這個 epic 有哪些 phase、各自處在哪個關卡，能修設
計文件的是它，先撞到被推翻假設的卻是提出請求的那個 phase agent，訊號不主動處理就傳不到其他
phase。判斷是否處理完畢的方式是重跑同一組搜尋，剩下的命中全部落在已更新的敘述上；仍命中舊敘
述就是未完成。

orchestrator 動了設計文件，依「自決事項的即時回報」報一行給使用者。

自我檢測：這次牽涉的假設，是不是已經搜過設計文件全文，且我指得出搜尋結果落在哪一種——只命中
發起請求的那個 phase、或只命中不對應任何 phase 的段落（兩種都自己修），還是命中其他 phase
（升級）？修完之後重跑同一組搜尋，還有沒有命中落在舊敘述上？在跑與尚未派工的 phase 是不是都
各自處理過？任一項答否就還沒完成。

## 自決事項的即時回報

自決不等於靜默：使用者沒有被停下來問，就只能靠回報知道 orchestrator 剛才替他決定了什麼。回報
的粒度由觸發條件界定，不靠「覺得重要就報」這種自由心證——下面五項任一成立就即時報一行，五項
都不成立的自決不另外報。本節只管自決事項這一條回報線；「PR Ready 的處置」與「失敗行為」各自
要求的回報不受本節限制，照那兩節做。

1. 本次曾在「升級清單」的兩項之間比對，或一度判為命中後又改判不命中。
2. 調查者回傳了落差（見 `phase-decision-investigator` 的落差回報義務）。
3. 同一議題（界定見「升級清單」第六項）進入第二輪以上的回覆。
4. orchestrator 讀了 pane。
5. orchestrator 修改了 epic 設計文件。

五項都不成立的那一種不報，典型是：A 路徑一次答完、依據明確落在設計文件某一段、「升級清單」
的九項編號一個都指不出來，過程中也沒有在任何兩項之間比對過。

報的那一行帶哪些欄位，依事件種類分三組，不多寫——後兩種不是「回覆了一個決策」，套第一組的欄
位會有欄位填不出來：

| 事件 | 那一行帶的欄位 |
| --- | --- |
| 回覆了一個決策（第一、二、三項） | phase 編號、問題一句話、依據、回覆一句話 |
| 讀了 pane（第四項） | phase 編號、命中的是第一條禁令例外的哪一個觸發條件、判定結論一句話 |
| 改了 epic 設計文件（第五項） | phase 編號、被推翻的假設、改動的段落、搜尋命中的其他 phase |

自我檢測：這次自決命中上面五項的哪一項，我指得出編號嗎？指得出就報，且報的是那一項對應的那一
組欄位；五項都指不出來的自決就不報——加報會把這條回報線稀釋成雜訊，使用者也就不會再逐則讀
它。

## PR Ready 的處置

phase agent 送回 PR 編號與一句話結論後，orchestrator 只記下 PR 編號、不讀 PR 內容，回報給
使用者。該 phase 的 tab 保持開啟——review 可能要求改動，phase agent 還要回去做。

使用者若要求某個 phase 修改，orchestrator 透過下行機制（`herdr agent prompt`）把修改要求轉
達給該 phase agent；phase agent 改完後會重新送來一則「PR ready」訊息——這是既有第三種訊息
的重複使用，不是新的訊息類型（見 `phase-agent-contract.md`「PR ready 之後的 review 往返」
節）。orchestrator 收到這次重新送來的「PR ready」，回到本節開頭的處置：記下 PR 編號、回報
使用者、tab 繼續保持開啟，直到使用者說可以合併為止。

## 合併與收尾的連鎖

使用者在 orchestrator 這裡說可以合併後，依序做四件事：

1. 委派 `github-manager` 執行合併。
2. 通知該 phase agent PR 已合併、請它收尾；同時通知其餘還在跑的 phase agent，main 已經動
   了，請自行同步並處理衝突。
3. 等該 phase agent 回報收尾完成後，orchestrator 才關閉它的 tab；關閉前兩項守衛都要成
   立：要關的 tab 識別碼與進度表上該 phase 那一列記的 herdr 座標中的 tab 識別碼一致，且不等於
   orchestrator 自己所在的 tab——自己所在的 tab 識別碼取自環境變數 `HERDR_TAB_ID`。「herdr
   會把呼叫端的座標注入每個受管 pane」這一點未查證：推翻時（變數不存在、或注入的不是自己那
   一格）第二道守衛會拿著空值或錯的值比對而形同虛設，orchestrator 有可能把自己所在的 tab 當
   成 phase 的 tab 關掉，而它是唯一在盯所有 phase 的那一端。因此 `HERDR_TAB_ID` 讀到空值時，
   直接當成這道守衛不成立，不要關。整套中斷恢復機制是為「orchestrator 中斷後接回」設計的，不
   是為「orchestrator 執行中把自己關掉」設計的，識別碼核對錯誤就是後者。
4. 重查依賴圖，把因此解鎖的 phase 派出去。

orchestrator 不自行清理 phase 的 worktree——那是 phase agent 收尾程序的一部分，見
`phase-agent-contract.md`。

自我檢測：關閉這個 tab 之前，是不是已經收到這個 phase 的收尾完成訊息，且要關的識別碼同時滿
足「與進度表座標中的 tab 識別碼一致」與「不等於 `HERDR_TAB_ID`」兩項？任一答否就不要關。

## Epic 收尾

所有 sub-issue 都關閉後，由 orchestrator 判斷關閉 parent issue 的時機並委派
`github-manager` 執行。這是 orchestrator 專屬的職責，phase agent 不做這件事——每個 phase
agent 收尾時只關自己的 sub-issue，parent 什麼時候該關，只有看得到全局的 orchestrator 判斷
得出來，任何一個 phase agent 都只看得到自己那個 phase。

## 狀態檔與中斷恢復

狀態檔是本地快照，不是權威。它記的是 GitHub 上查不到的東西：

- herdr 座標（tab 識別碼、agent 名稱、session 位址）
- worktree 路徑
- 每個 phase 目前處在哪個關卡

進度本身仍以 sub-issue 的 `state` 與 PR 的合併狀態為準。狀態檔依 `tmp-file-usage` rule 放
在工作區的 `.tmp` 底下。

中斷後接回的恢復順序固定三步：

1. 讀狀態檔取得座標。
2. 向 GitHub 重查進度。
3. 用 `herdr agent list` 核對哪些 tab 還活著。

三步之間對不上時，一律以 GitHub 與 herdr 的現況為準並改寫狀態檔——狀態檔唯一會過時的情境正
是 orchestrator 中斷的那一刻。

自我檢測：這三步的順序有沒有被打亂，尤其是讀狀態檔是不是排在向 GitHub 重查之前、向 GitHub
重查是不是排在核對 tab 存活之前？順序錯了就先停下重來，不要將錯就錯往下做。

tab 已不在但 PR 尚未合併的 phase，據實回報給使用者，由使用者決定要重派還是接手；orchestrator
不自行重派。

## 失敗行為

共同原則：orchestrator 在看不見 phase 開發內容的前提下判斷，它手上能用的證據有四種——
`agent_status`、tab 還在不在、GitHub 上的 issue 與 PR 狀態，以及觸發條件成立時讀到的那格
pane（第四種的取得條件見「主 Context 的三條硬禁令」第一條例外）。這四種裡取得條件成立的都取
過、取不到的指得出被哪一條擋住，仍判不出來時，是不是命中「升級清單」第九項，一律依該項自己的
門檻判定，本節不另立一套較寬的版本；命中就交給使用者，不自行終止任何 phase。

| 情境 | 處置 |
| --- | --- |
| 「啟動成功判準」的三項不齊備，開場指令因此還沒送出 | 依判定分流，命中第一條禁令例外的觸發條件二。orchestrator 讀該 pane 判因：判定是信任對話框就升級（清單第五項）；其他情形（例如 agent 沒起來、啟動指令失敗、停在別的確認框）自行關掉這個 pane 重啟一次，第二次仍失敗才升級（清單第九項，自決手段已用盡） |
| 開場指令已送出、握手也成功，但遲遲沒有收到報到訊息 | 自決，但不走重啟，改由下一列的處置涵蓋：狀態始終 `working` 的歸第一條禁令例外的觸發條件四（讀 pane，判定在做事就繼續觀測），轉為 `idle` 而沒有伴隨訊息的歸「決策迴圈」入口三。這一列與上一列的分界是開場指令送出與否，不由「等多久」裁量；不重啟的理由是關掉 pane 會丟掉這個 agent 已經累積的整段 context，而它已經接手在跑，換不回來 |
| 長時間沒有任何訊息 | 自決，分兩種：處在 `idle` 而沒有伴隨訊息的，由「決策迴圈」入口三涵蓋；狀態始終 `working` 卻一直沒有任何訊息的，由第一條禁令的觸發條件四涵蓋——同一個 phase 連續十輪整輪觀測（每輪 60 秒是牆鐘上限而非下限，十輪至多約十分鐘，phase 早退時更短）都是 `working` 且沒有收到任何上行訊息時，讀一次 pane，判定它是在做事還是空轉，兩種判定各自的出口與輪數歸零規則見「監控節奏」 |
| 合併失敗（例如衝突或 CI 未過） | 自決。不由 orchestrator 解決，把失敗訊息原文轉給該 phase agent——那是唯一有開發脈絡的一端 |
| tab 已經不在而 PR 未合併 | 升級（清單第四項，不可逆或波及該 phase 以外的後果）。說明後果並詢問使用者要重派還是接手，不自己重派——自行重派會在同一個 sub-issue 上開出第二條分支 |
| 依賴圖成環，或依賴指向不存在的 issue | 升級（清單第七項）。停下回報，不猜測順序 |
| PR 已合併但對應的 sub-issue 仍然開啟 | 整條升級（清單第九項，殘留的 worktree 移除觸犯第三條禁令，orchestrator 做不掉），不拆。回報使用者，由使用者決定如何完成殘留的收尾；orchestrator 不自行接手清理 |

第一列關掉那個 pane 時，「合併與收尾的連鎖」第 3 步的兩項守衛照樣適用：要關的 tab 識別碼須與
進度表上該 phase 那一列記的 herdr 座標中的 tab 識別碼一致，且不等於 orchestrator 自己所在的
tab（識別碼取自環境變數 `HERDR_TAB_ID`）。重啟走的是自決，關錯 tab 的後果卻不可逆，兩項核對
不因為這次是自決而省略。

最後一列為什麼整條升級、不拆成兩半：表面上它拆得開——關閉 sub-issue 不觸犯任何一條禁令，委派
`github-manager` 就做得掉。但同一件收尾裡殘留的 worktree 移除觸犯第三條禁令，連改一個檔案都
不行，何況整個目錄移除，orchestrator 做不掉。拆的結果是留下「issue 關了、worktree 還在」這種
半殘狀態，比整條升級更糟：issue 一關，就沒有任何後續流程會再回頭看這個 phase 一眼，殘留因此
更難被發現。

自我檢測：這一列的每一種情境各判成什麼——自決還是升級，我指得出理由嗎（升級的話是「升級清
單」第幾項）？指不出來就不要動手。
