# Epic Orchestration

觸發本 skill 後，當前對話的 AI agent 在這個 epic 的整個生命週期內擔任 orchestrator：把每個
phase（一個 sub-issue）交給一個獨立的 Claude Code session（下稱 phase agent），自己不寫任何
一行程式碼，並把全部 phase 推到合併與收尾。orchestrator 不輪詢、不阻塞、不讀開發內容——它被
事件喚醒，派調查者去看，只收回一句結論。本 skill 與 `epic-design` 成對：後者產出 epic 設計
文件，本 skill 把該文件拆成的 phase 推到全部合併。

epic 設計文件是所有 phase 在內容上的權威來源。預設情境下它位於主倉庫被 `.gitignore` 忽略的
`docs` 目錄下，因此不會隨任何 git worktree 出現——使用者當初若在 `epic-design` 那一端指定了別
的路徑，這個推論就不適用，要自己確認那個路徑是否被忽略。凡是要傳遞它的路徑一律給**主倉庫**絕
對路徑。

## 環境前提

orchestrator 必須跑在 herdr 環境內：進入本流程任何動作之前，先確認環境變數 `HERDR_ENV` 的值
恰為 `1`。不是就停下，向使用者說明本流程要透過 herdr 開 tab、啟動 phase agent 並接收事件，
必須在 herdr 環境內執行，不要往下建依賴圖或詢問要推進哪個 phase。腳本自己也擋這一關（結束碼
3），但那時 tab 與依賴圖的動作已經開始了。

自我檢測：`HERDR_ENV` 讀到的值是不是字面上的 `1`？不是的話就停在這一步，不要假設環境等同可用。

## 三個角色

三者的資訊視野刻意互不重疊，這是整個設計的基礎：orchestrator 手上沒有讀畫面的動作可用。畫面
文字只有狀態標記行這一條窄通道會抵達它，而這條通道由白名單約束成四個固定值——`working-ok`、
`need-decision`、`pr-ready`（後面可再帶一個純數字的 PR 編號）、`wrapped-up`；超出白名單的內容
不會被轉發，會被當成標記缺席走 `marker=none`。

| 構面 | Orchestrator | Phase Agent | Investigator |
| --- | --- | --- | --- |
| 知道什麼 | 依賴圖、進度表、epic 設計文件全文 | 自己那個 sub-issue、設計文件、自己的契約 | 單次調查所需的一切：畫面、worktree、git、PR 留言 |
| 看不到什麼 | 任何 phase 的程式碼、diff、測試輸出、PR 內容、終端畫面 | 其他 phase 的存在與進度 | 沒有這一格，它的職責就是去看 |
| 做什麼 | 啟動與關閉 phase agent、處理事件、自決或升級、委派合併、關 parent issue | 開 worktree、開發、self review、開 PR、依 review 修改、合併後收尾 | 讀取、判斷、回傳結論與推薦 |
| 不做什麼 | 讀畫面、碰任何 worktree、跨 workspace 操作、自行 merge、自行呼叫 `gh` | 主動送訊息、改設計文件、關 parent issue、刪任何分支 | 任何檔案寫入、對 phase agent 送出任何輸入 |
| 生命期 | 整個 epic | 從派工到收尾完成 | 單次調查 |

所有經由 `gh` 對 GitHub 的操作，含唯讀查詢，一律委派 `github-manager`；orchestrator 不自行呼
叫 `gh`。這是 `subagent-routing` rule 的要求，本 skill 不放寬。

委派 `phase-decision-investigator` 時給四樣：phase 編號、觸發本次調查的事件類型與那一句事由、
該 phase 的 PR 已經開出時的 PR 編號、以及 epic 設計文件的主倉庫絕對路徑。後兩樣各有各的非給不
可，理由同形：編排端獨有、調查者自己推不出來，而且都是識別碼或路徑、不是開發內容，給它們不影
響調查者那一側的 context 純度。

PR 編號：調查者的職責之一是讀 PR 上已有的 review 留言，而由 issue 反查 PR 已知不可靠。少了它的
失敗場景：review 往返期間來的一則決策請求，調查者讀不到 PR 上的留言，回傳的選項裡不含 reviewer
已經表過態的那一項，編排端據此回覆，phase agent 改完再撞同一個 review。

設計文件路徑：編排端本來就持有它，每次開場指令都要傳一次給 phase agent（見「生命週期」第 3
步）；而調查者無從推導——決策請求檔的「設計文件依據」欄位只帶段落標題或原文一句、不帶路徑，那
份文件又預設落在被 `.gitignore` 忽略的目錄下，且使用者可以在 `epic-design` 那一端指定別的路
徑。少了它的失敗場景：每一次派工都落進調查者那一側的退路，於是它「拿調查所得與設計文件所述互
相比對」那一步永遠不執行、設計文件那一半的落差回報義務永遠不可能觸發，而它每次回傳最前面都固
定掛一則「調查前提缺損」——一份看起來完整的調查，少的正是它被設計來加上的那道交叉比對。

不給 worktree 路徑、不給 herdr 座標——前者不在進度表上（見「進度表與狀態檔」），編排端自己也沒
有；後者由腳本自行從狀態檔查出並驗證 workspace，orchestrator 轉述反而會給出過期的值。分界是同
一條，不是逐項清單：編排端手上有、而對方推不出來的才給；對方自己查得到、或查得比編排端準的，
一律不給——設計文件路徑落在前者，worktree 路徑與 pane 識別碼落在後者。

## 兩層約束

約束分兩類，判準是「擋不擋得住」；分開寫是為了讓讀者知道哪一條可以信任、哪一條只能靠自律。

- **權限半徑：orchestrator 的每一次 herdr 互動一律經六支腳本，沒有例外。** 以某個 phase 為目
  標的入口守衛有四道，逐支不齊，沒有哪一道是六支都有的，所以要逐支點名而不是寫成統一處理（另
  計兩類：環境前提那一道八支腳本都有，不通過以 3 拒絕；`close-phase.sh` 自身還有兩道，見腳本表
  那一列）：workspace 守衛在
  `read-phase-pane.sh`、`close-phase.sh`、`phase-status.sh`、`send-to-phase.sh`、
  `press-approval.sh` 五支（不通過以 4 拒絕。射程是擋在任何以該 phase 為目標的 herdr 呼叫與任
  何資料取用之前，不是「守衛之前不會有任何 herdr 動作」——守衛自己就是一次 `herdr tab list`，
  而 `phase-status.sh` 查全部時那一次整包 snapshot 也早於守衛，它擋的是用 pane 識別碼挑出該
  phase 那一列，跨 workspace 的資料因此到不了輸出）；`start-phase.sh` 沒
  有這一道，因為它是以本 workspace 開出新 tab，當下還沒有既存 tab 可驗。模型產出文字的欄位在
  `phase-status.sh` 走白名單——只組 `agent_status`、狀態序號與規則名三欄，不是把原始回應剝掉幾
  個具名欄位；別用「剝除」的說法描述它，那會引導後續維護者往黑名單方向擴充。限制讀取行數只在
  `read-phase-pane.sh`；代按前的必填參數只在 `press-approval.sh`。角色表「不做什麼」那格的「跨 workspace 操作」落在這一層：對活著
  的 agent 送出輸入的是 `send-to-phase.sh` 與 `press-approval.sh` 這兩支，它們現在都擋得下
  ——這道守衛不是理論顧慮，狀態檔路徑與 agent 名稱都只綁主倉庫、不含 workspace，同一個倉庫在
  兩個 workspace 各跑一次 epic，兩邊的狀態檔與 agent 名稱會重合。逐支不齊不動搖「腳本層是這些
  守衛唯一的實作位置」這一點：每一道都只實作在對應腳本的入口，呼叫端不重複做，本檔裡也沒有等
  價的約束可以替代。但「一律經腳本」這件事本身沒有 hook 或 permission 在背後執行，這道門靠的
  是結構：把呼叫寫在腳本裡。直接呼叫 herdr 會把其他 workspace 的資料與模型產出文字整包帶進
  context，而且不會有任何錯誤訊息告訴你這件事發生了。事件產生器直接呼叫 herdr 是它自己那一層
  的事，它是這道門的呼叫端而非包裝層，不構成 orchestrator 這一側的例外。
- **context 純度，靠角色分工的結構保證，沒有程式攔阻。** 落在這一層的有四條：不讀畫面、不碰
  任何 worktree（含不移除殘留的 worktree）、不主動去取 phase 的程式碼與 diff 與測試輸出與 PR
  review 內容、不自行呼叫 `gh` 也不自行 merge。這四條違反時不會有任何錯誤訊息，也沒有結束碼會
  擋下它們，邊界完全靠本檔的文字對模型的約束力生效——別把它們誤讀成「試了會被擋住」。它撐得住
  的原因是出口只有一個：`read-phase-pane.sh` 的兩種模式 orchestrator 都不呼叫（讀畫面全文歸調
  查者，抓標記行歸事件產生器），要知道畫面上有什麼就派調查者，讀進來的只有它重新組織過的一句
  結論。編排端呼叫得到的那幾支腳本也不轉發 herdr 的回應原文或錯誤原文（`read-phase-pane.sh`
  的預設模式是例外，它的職責就是回傳畫面文字——也正因如此編排端不呼叫它）：herdr 失敗時抵達編
  排端的只有重組過的錯誤碼與錯誤訊息兩個純字串欄位——那是 herdr 自己的錯誤文字，不是模型產出內
  容；連這兩欄都解析不出來時（herdr panic、印出用法說明這類非 JSON 輸出）只會得到一則帶原始結
  束碼的固定訊息。

orchestrator 會寫入的倉庫內檔案只有一個對象：epic 設計文件，且只在「升級清單」第三項的自決分
支下寫（見該項）。這句的射程是「不碰 phase 的內容」這條邊界，「生命週期」第 6 步的兩個 git 動
作不在射程內、是本檔明文允許的：刪掉該 phase 已合併的 local branch 不是檔案寫入；把 local
main 快轉同步到 `origin/main` 會改寫工作樹裡的檔案，但它動的是本地歷史與工作樹，不是任何 phase
的開發內容。這一個偏離 `git-worktree-workflow` 是刻意的：那條 rule 要求 repo 內檔案的寫
入都在隔離 worktree 中進行，但這份文件位於被 `.gitignore` 忽略的 `docs` 目錄、不會隨 worktree
出現，照那條 rule 執行反而寫不到它。`markdown-editing` 沒有偏離，照辦：實際的編輯委派
`markdown-editor`，給它三樣——檔案絕對路徑、修改意圖、內容重點摘要，且 prompt 是純文字、不夾
任何 markdown 語法。

狀態檔的寫入，orchestrator 這一側一律經 `set-phase-field.sh`，不得自己 `jq` 或以編輯工具手改那
個 JSON 檔（腳本自己的寫入不在這句的射程內，見「進度表與狀態檔」）。這句話由
兩道機制撐著，各擋一半，只講一半會誤導：檔案鎖把單次呼叫內的「讀-改-寫」序列化，手改繞過它就
會與事件產生器的併發寫入互相覆蓋，而且不會有任何錯誤訊息；但鎖擋不住另一種——兩個都以為自己是
某欄位唯一寫入者的行程，各自覆蓋對方剛寫的另一個欄位。擋住後者的是「雙方只碰自己那組欄位」這
個約定，而腳本的欄位白名單把那個約定變成程式碼保證。所以不要從「寫入都有鎖」推論出「放行更多
欄位也安全」：欄位集合不重疊正是「不必為每個欄位單獨加鎖」這個決定的依據，放寬白名單等於同時
拆掉那個依據。讀取不受此限，直接讀檔即可——腳本的寫入是暫存檔加 `mv` 原子置換，讀到的一律是完
整的某一版。

自我檢測：我準備做的這次 herdr 互動，是不是六支腳本之一？我準備讀進 context 的這份內容，是不
是 phase 的程式碼、diff、測試輸出、PR 內容或終端畫面？兩題各自獨立：第一題答否就不要做；第二
題答是也不要做。

## 腳本與結束碼

腳本把「怎麼呼叫」收進程式，本檔只留「什麼時候呼叫、拿到結果之後怎麼判斷」。

| 腳本 | 什麼時候呼叫 | 拿到結果之後怎麼判斷 |
| --- | --- | --- |
| `start-phase.sh` 帶 sub-issue 編號 | 派工：確保狀態檔存在、開 tab 並啟動 phase agent | 它在開 tab 之前先初始化狀態檔（冪等、可並行，已存在就不動內容），所以全新 epic 的第一次派工不必先做任何準備。成功時印一行帶 tab 識別碼、pane 識別碼與 agent 名稱，成功本身就是就緒憑據，直接接著送開場指令，不再另外查任何欄位；結束碼 8 是啟動未就緒，此時開場指令一定還沒送出，走「失敗行為」第一列 |
| `send-to-phase.sh` 帶 sub-issue 編號與一段文字 | 送開場指令、轉達定案、通知收尾、廣播 main 動了 | 印出憑據已取得即為對方已接手；結束碼 7 印未取得憑據，這不是一般失敗，派調查者判定對方是已接手在做事還是卡住了。廣播那一則、以及 `SPINNING` 判定空轉後那一則都帶不握手選項（對象都在做事中），印出略過握手並以 0 結束即算送出，不等任何狀態；但送出當下被 herdr 拒絕（典型是收件方剛好卡在核准框）仍以 6 結束，那一則沒有送到 |
| `phase-status.sh` 帶 sub-issue 編號，省略時查全部 | 中斷恢復核對哪些 tab 還活著；判 `UNCLASSIFIED` 的成因（診斷模式） | 每行一個 phase 的狀態與狀態序號。查全部模式逐 phase 隔離失敗：某一行印出錯誤標記只代表那一個 phase 查不到，其餘各行仍然有效；結束碼 1 的語意就是「掃完了但至少一個 phase 失敗」，不要當成整輪查詢失效 |
| `press-approval.sh` 帶 sub-issue 編號、按鍵與放行動作說明 | 代按核准框，前置守衛見「代按守衛」 | 放行動作說明是必填參數，缺了以 2 結束——那正是這支腳本存在的理由。腳本代按前會重查狀態仍為 `blocked`；兩種模式代按後等的都是「狀態已離開 `blocked`」，差別只在落點收得多寬——非啟動階段 `idle`、`done`、`working` 三種都算，啟動階段只收 `idle` 與 `done`。非啟動階段之所以不是只放寬拒絕鍵，是因為這支腳本分辨不出手上那顆鍵是放行還是拒絕：按鍵是原樣轉送的不透明字串，腳本從不讀畫面，同一顆 `2` 在不同的框上可能是「是，而且以後不要再問」，也可能是「否」，硬寫一份拒絕鍵名單等於猜那個框長什麼樣。換掉的東西要知道：`handshake=ok` 不再蘊含「被放行的動作已經開始跑」，要判斷那件事改查 `phase-status.sh`。啟動階段不一起加 `working`，是因為那個時點沒有任何指令排著等做（開場指令稍後才由 `send-to-phase.sh` 送），落點本來就是停下態；加上 `working` 會讓兩條分支完全相同，那個旗標對它唯一控制的事情就失去意義。這一支的 6 有兩種來源：herdr 拒絕，或代按前重查發現狀態已離開 `blocked`——後者代表阻塞在委派調查與代按之間自行解除了，直接改用 `send-to-phase.sh` 送定案，不要重按。它也會回 7：代按之後那次等待逾時，而此時按鍵已經真的送出去了，不得重按——畫面上若跳出第二個框，重按等於放行一個編排端沒看過的動作。派調查者確認那個框是不是已經消失、現在的狀態是什麼，再依結論走決策三路徑 |
| `close-phase.sh` 帶 sub-issue 編號 | 收尾完成後關 tab；啟動未就緒、要重啟前先關 | 三道守衛全數通過才關，成功關閉後該筆記錄已從狀態檔移出。結束碼 4 要看 stderr 指出的是哪一道：守衛二（tab 識別碼在檢查期間被改寫）重試一次即可；守衛一或三不成立（不屬本 workspace、目標等於自己的 tab、或 `HERDR_TAB_ID` 未設）是環境問題，重試永遠不會通過，直接走升級清單第九項，tab 保留不關。兩種都不改用別的方式關 |
| `set-phase-field.sh` 帶 sub-issue 編號、欄位名與值 | 關卡變動、記下 PR 編號、設放與收回持有旗標 | 這是 orchestrator 寫狀態檔的唯一入口。只放行 `stage`、`pr`、`held_by_orchestrator` 三個欄位，事件產生器擁有的六個欄位在白名單外，連同不合法的值一律以 2 拒絕；對不在狀態檔的 phase 以 5 拒絕、不寫入——它只修改既有記錄，建立記錄是 `start-phase.sh` 的職責 |
| `read-phase-pane.sh` | orchestrator 兩種模式都不呼叫 | 不適用。讀畫面全文歸調查者，抓標記行歸事件產生器 |
| `event-generator.sh`，無參數常駐 | 建圖之後、第一次派工之前掛上 Monitor 工具，見「事件通道」 | 每一行 stdout 是一則事件通知，依「事件處置」分流 |

九個結束碼所有腳本共用同一組語意：

| 碼 | 意義 |
| --- | --- |
| 0 | 成功 |
| 1 | 查全部模式下掃描已完成但至少一個 phase 失敗（`phase-status.sh`）；`event-generator.sh` 的主迴圈在低頻掃描子行程死亡時也以 1 結束，並在 stderr 請編排端重掛 |
| 2 | 呼叫端用錯：缺必填參數、參數格式不對 |
| 3 | 環境前提不成立：`HERDR_ENV` 不等於 `1` |
| 4 | workspace 守衛不通過 |
| 5 | 狀態檔缺漏：檔案不存在，或該 phase 不在檔內 |
| 6 | herdr 拒絕：`agent_blocked`、`agent_not_found`、`pane_not_found`、`tab_not_found` 等 |
| 7 | 握手未取得憑據（逾時或 `agent_prompt_stalled`） |
| 8 | 啟動未就緒，也就是 agent start 未在逾時內回報就緒 |

結束碼 2 預設當成 orchestrator 自己這次呼叫用錯：修正參數再試，不改判成那個 phase 出了問題。
例外是它的第二個來源——傳進去的本來就只有 phase 編號與文字、找不到可修之處時，那是 herdr 自身
的語法錯誤被原樣拋上來，代表腳本與 herdr 介面不符，編排端改不動，走升級清單第九項。

## 事件通道

掛起事件產生器時必須指定 `persistent`，不要用預設值。理由是預設 5 分鐘、上限 1 小時就會被收
掉，而一個 epic 要跑 8 到 12 小時：整條事件通道會在第一個小時內靜靜死掉，而 orchestrator 不輪
詢，之後不會再有任何東西喚醒它。

掛起當下，每個已經停下的 phase 會各補發一則事件，但只補最後一次——中斷期間停了幾次都只看得到
最後那一個標記；標記為 `working-ok` 的那一種由產生器自動消化，不會補發事件行，所以回來的則數
少於停著的 phase 數是正常的。反方向也要知道：中斷之前就已經被消化過的那個標記，會以
`marker=none` 回來——標記序號沒有變大，產生器把它當成標記缺席。所以重掛後的第一則 `marker=none`
先核對狀態檔的 `stage`，已經是 `pr-ready` 或 `awaiting-decision` 的就不必派調查者。掛起之後 orchestrator 進入靜止：只被事件行與使用者的訊息喚醒，其餘時間不做任
何事，不主動去查任何 phase 的狀態。

事件行有兩種形狀，都帶 phase 編號：一種是停下事件，帶停下狀態（`idle`、`done` 或 `blocked`）
與該回合的狀態標記（`working-ok`、`need-decision`、`pr-ready`、`wrapped-up`，或抓不到新標記
時的 `marker=none`；`pr-ready` 那一種的標記後面另外帶 PR 編號）；另一種只帶一個關鍵字，其中兩
種另帶一個數字（`SPINNING`、`UNCLASSIFIED`、`GONE`、`AUTO-PUSH-LIMIT` 帶連續自動推進的次數、
`AGENT-RESTARTED` 帶畫面上的標記序號）。最頻繁的 `working-ok` 由產生器自己推一把，通常根本不產
生事件行——一個 phase 跑 8 到 12 小時會停下幾百次，四個 phase 平行就是上千個回合，那一刀不切，
context 會隨 epic 長度線性膨脹，正好摧毀這個設計要保護的東西。這一刀有三個條件、不是無條件，三
種例外與各自的處置見「事件處置」開頭。

`idle` 與 `done` 是同一個底層休止態的兩個名字，差別只在那個 tab 有沒有在 herdr UI 裡被使用者
點進去看過。無人值守下回合結束一律落在 `done`。因此 `stopped=idle` 的處置必須與 `stopped=done`
完全相同，不要因為名字不同就分兩套判斷。

同一件事在 `press-approval.sh` 的啟動階段模式上也成立：它代按後等的是「離開 `blocked`」，而離
開之後可能是 `idle` 也可能是 `done`——取決於使用者有沒有點進過那個 tab，而工作區信任對話框由使
用者在對話裡定案、實際按下去的是編排端，所以那個 tab 未必被看過。因此那條路徑兩種狀態都收，不
是只等 `idle`。

## 進度表與狀態檔

orchestrator 對整個 epic 的認知全部收斂在一張進度表裡。表上容不下開發細節：只要不是這五個欄位
表達得了的東西（例如某個函式重構完了、某段測試現在過了），就不屬於編排端需要記住或轉述的內容。

| 欄位 | 內容 | 權威來源 |
| --- | --- | --- |
| sub-issue 編號與標題 | 這個 phase 對應的 GitHub sub-issue | GitHub |
| 被哪些 phase 擋著 | 依 blocked by 關係列出的依賴 | GitHub |
| 目前處在哪個關卡 | 等待啟動、進行中、等待決策、PR ready、已合併、已收尾 | 這一欄是衍生視圖，不是單一來源：「等待啟動」由狀態檔裡沒有這筆記錄表達，其餘五個讀狀態檔的 `stage` 欄位。記錄是 `start-phase.sh` 在派工那一刻建立的，所以尚未派工的 phase 只存在於依賴圖裡，而依賴圖的權威是 GitHub |
| herdr 座標 | tab 識別碼、pane 識別碼、agent 名稱 | 狀態檔，由 `start-phase.sh` 寫入 |
| PR 編號 | 該 phase 開出的 PR，尚未開時留空 | 狀態檔的 `pr` 欄位。正常運行中唯一的來源是 `pr-ready` 那一則事件帶回來的編號；只有在中斷恢復、而且表上這一格是空的時候，才得以分支命名慣例反查後回填（見「中斷恢復」第 3 步）。其餘任何時候看到這一格是空的都不去反查 |

進度本身一律以 sub-issue 的狀態與 PR 的合併狀態為準，不以記憶中的印象為準。

狀態檔是本地快照而非權威，它只記 GitHub 上查不到的東西，路徑是主倉庫底下的
`.tmp/epic-orchestration/state.json`（`.tmp` 依 `tmp-file-usage` rule 指向家目錄下的專案專用資
料夾）。路徑要寫明是因為找不到檔案的失敗方向危險：它會被誤判成「狀態檔遺失」，而那正是觸發
PR 編號反查退路的條件。檔案本身由 `start-phase.sh` 在建立第一個 phase 記錄之前初始化，冪等、可
並行，重複呼叫不覆蓋既有內容。初始化刻意沒有做成「寫入時發現檔案不存在就順手建」：那樣會把
「檔案不存在」這個有語意的訊號從所有路徑抹掉——常駐的事件產生器中途若狀態檔被移除，會靜靜拿到
一份空檔繼續跑，而不是失敗讓編排端察覺。

寫入端分兩邊，欄位集合刻意不重疊：座
標由 `start-phase.sh` 寫、整筆記錄由 `close-phase.sh` 在成功關閉後移除、六個非座標欄位（標記序
號、自動推進次數、連續 unknown 輪數與三個靜音旗標，即腳本表 `set-phase-field.sh` 那一列白名單
以外的那些）由事件產生器維護；orchestrator 這一側只寫三個欄位，一律經
`set-phase-field.sh`（見「兩層約
束」），只有一個例外——`held_by_orchestrator` 的初始值由 `start-phase.sh` 在建立記錄時與三個座
標同一批直接寫成 `false`，例外僅止於建立記錄那一刻，之後這個欄位的每一次寫入都經
`set-phase-field.sh`。這個例外不動搖不重疊那個前提：事件產生器從頭到尾都不寫這個欄位，它只
讀，讀不到就當 `false` 繼續。關卡每次變動就寫一次 `stage`，合法值就是五個、逐字為 `running`、`awaiting-decision`、
`pr-ready`、`merged`、`wrapped-up`；`pending` 已不在合法值之列，寫它會以 2 被拒絕，這五個以外
的任何值同樣以 2 拒絕。比進度表那一欄少一個是對的，不是漏列：進度表的「等待啟動」由狀態檔裡沒
有這筆記錄表達——它描述的是一個還在依賴圖裡、尚未派工的 phase，而那時狀態檔裡還沒有它的記錄；
把它寫進一筆已經存在的記錄，等於宣告一個已經派工過的 phase 還在等待啟動。PR 編號在收到
`pr-ready` 事件時寫進 `pr`；
`held_by_orchestrator` 依「事件處置」的互斥設放與收回。
這三個欄位寫進狀態檔而不是只留在對話裡，是為了讓 orchestrator 這一端中斷後接得回來（見「中斷
恢復」）。

worktree 路徑不在表上——phase agent 自己開、自己清，編排端不需要也不該碰；調查者需要時自己依
命名慣例查出來。

## 生命週期

順序是實質的：每一步的前置條件由上一步產生，錯序會靜默出錯。

1. **建圖。** 委派 `github-manager` 依序取得 parent issue 內文、其下的 sub-issue 清單、每個
   sub-issue 的 blocked by 關係，據此建出依賴有向圖與初始進度表。成環或依賴指向不存在的
   issue 時停下問使用者（升級清單第七項），不猜測順序。建圖之後、第一次派工之前，依「事件通
   道」掛起事件產生器。
2. **派工。** 對每個沒有未完成依賴的 phase 呼叫 `start-phase.sh`，把回傳的座標記進進度表；事
   件產生器下一輪重讀狀態檔就會自動把它納入監看，不必重啟產生器。啟動未就緒（結束碼 8）時走
   「失敗行為」第一列。
3. **開場。** 對啟動成功的 phase 呼叫 `send-to-phase.sh` 送出開場指令，只帶三項：sub-issue
   編號、epic 設計文件的主倉庫絕對路徑、`phase-agent-contract.md` 的絕對路徑。契約全文由
   phase agent 自己讀取，不經指令列傳遞；不要帶 orchestrator 自己的 session 名稱——沒有上行
   通道之後它沒有收件人，帶著只會誘使 phase agent 送出一則沒人接的訊息。取得握手憑據後把
   `stage` 寫成 `running`——記錄是 `start-phase.sh` 建的，那時還沒有這個欄位。
4. **運行。** orchestrator 進入靜止，每個事件依「事件處置」分流。
5. **合併。** 前置是使用者在 orchestrator 這裡說可以合併，AI 不自動 merge。委派
   `github-manager` 執行合併，接著通知該 phase 收尾，再廣播其餘還在跑的 phase「main 動了，請
   自行同步並處理衝突」。廣播前先把每個收件 phase 標成持有中、送完逐一放掉（理由見「事件處
   置」的互斥那段）。廣播那幾則一律帶不握手選項：收件的每個 phase 都還在做事，照握手做就
   是每一則各逾時一次、各誤判成握手失敗一次、各白派一個調查者。失敗形態是某個 phase 沒接到而
   沒同步，要到後續合併衝突才浮現——所以廣播的哪一則以 6 結束就標記為待補送，等那個 phase 下
   一則停下事件到達、確認它離開 `blocked` 之後補送一次，並記得放掉它的持有旗標。合併成功後把
   該 phase 的 `stage` 寫成 `merged`；合併失敗時走「失敗行為」，關卡不動。
6. **收尾。** 收到該 phase 的 `wrapped-up` 事件後，依序收回持有旗標、把 `stage` 寫成
   `wrapped-up`、再呼叫 `close-phase.sh`（它成功關閉後會把整筆記錄移出狀態檔，事件產生器下一輪
   就不再監看它）。兩個寫入都必須排在關閉之前，記錄一旦移除就寫不進去了（會以 5 被拒）；
   `stage` 這個值只在關閉失敗時派得上用場——關成功了記錄就不在了，而關不掉的那一種正是需要它的
   情形。分支清理歸這一端，四個動作依序做，順序是實質的：一，委派 `github-manager` 查得該 PR
   的 merge commit 已經在 `origin/main`——不要拿「PR 顯示已合併」直接當成這個條件成立。二，
   orchestrator 把自己的 local main 同步到 `origin/main`，只做取得遠端狀態後的快轉，不做會產生
   commit 的合併，也不做會丟東西的重設。這一步不能省：下一步那個不強制的刪除，它的「已完全合
   併」檢查看的是本地歷史，而第一步查到的是遠端事實，local main 沒同步過就看不到那個合併，刪除
   會在分支其實已經合併的正常情況下照樣拒絕，而拒絕理由會把人引向錯誤的診斷。三，orchestrator
   自己刪掉該 phase 的 local branch，用不強制的刪除——這時拒絕才真的代表有未合併的工作（phase
   agent 若有沒推上去的 commit，那段工作沒有第二份副本）。四，委派 `github-manager` 刪掉 remote
   branch。四個動作都屬例行收尾，不吃升級清單第四項。worktree 不在此列，它由 phase agent 自己在
   收尾程序裡移除。這個拆分偏離了 `git-worktree-workflow`，點名如下：那條 rule 把同步 local
   main、移除 worktree 及其 local branch、刪除 remote branch 寫成同一個 agent 在合併確認後一次
   做完；本檔把四件事逐一重新指派——同步 local main 與兩種分支的刪除留在編排端，worktree 移除留
   給 phase agent（`phase-agent-contract.md` 已在它那一側宣告過同一條收窄），因為 phase agent
   移除 worktree 之後 local branch 仍留在共用的 `.git` 裡，而只有編排端看得到全局、也只有它知道
   合併確認已經取得。接著重查依賴圖，派出因此解鎖的 phase。全部
   sub-issue 關閉之後，由 orchestrator 判斷時機並委派 `github-manager` 關閉 parent issue——這
   是編排端專屬職責，只有它看得到全局，每個 phase agent 只關自己那個 sub-issue。

## 事件處置

每一則事件行都要走到下表的某一列，唯一的例外是 `marker=working-ok`——它不在表上，處置在本節下
面那段。其餘事件指不出落在哪一列時，依 `marker=none` 那一列處置：多花一次調查是安全的方向，漏
掉一個停下的 phase 不是。

開始處理某個 phase 的事件之前，先以 `set-phase-field.sh` 把該 phase 的 `held_by_orchestrator`
設為 `true`；這則事件處理完（定案已轉達，或確認這則事件不需要任何動作）再設回 `false`。事件產
生器見到持有旗標為真就不對它自動推一把。這條互斥非做不可的理由是實測顯示兩則下行會被併進同一
個回合一起執行：一則「繼續」黏在一則定案後面送達時，phase agent 讀到的是一個混合意圖，而兩則
訊息都沒有掉、看起來一切正常。

同一條互斥有兩處射程要各自處理：

- **合併後的廣播也要標。** 它不由任何事件觸發，所以不在「處理事件之前」這句話的射程內，但風險
  一模一樣：收件的每個 phase 都還在跑，任一個在廣播前後停下並印出 `working-ok`，產生器就會自動
  推它一把，正好併成一個混合意圖。廣播前把每個收件 phase 標成持有中，送完再逐一放掉。
- **收尾那一種的收回要排在關 tab 之前。** `close-phase.sh` 成功關閉後會把整筆記錄移出狀態檔，
  之後再去設回 `false` 會落在一筆已不存在的記錄上、以 5 被拒絕；那是每個 phase 收尾都會發生一
  次、看起來像故障的失敗。順序固定為：收回旗標 → 寫 `stage` → `close-phase.sh`。

收到帶 `marker=working-ok` 的停下事件時，那本身就是訊號，而且它不走下表——下表各列的鍵是標記與
關鍵字，沒有一列以停下狀態為鍵，`blocked` 更是全表無列，硬套會被塞進 `marker=none` 那一列，對
一個其實正常在跑的 phase 寫下等待決策的關卡、再白派一個調查者。它自己的處置在這裡。

產生器自動消化這一種的條件有三個，三個同時成立才不印事件行：持有旗標不為真、停下狀態不是
`blocked`、標記確實是 `working-ok`。所以它抵達 orchestrator 只有三種原因，先分辨是哪一種：

- **停下狀態是 `blocked`：** 對方卡在核准框上，那行 `working-ok` 是上一回合印的、與現在無關。
  走「決策與升級」的「代按守衛」，不要對它送文字下行——`blocked` 的對象會被 herdr 以
  `agent_blocked` 拒絕。
- **持有旗標還開著：** 上一輪處理沒收回，或編排端中斷時留著。先收回旗標。
- **兩者都不是：** 那就是產生器自動推進送出失敗後回退印出來的，而它偏偏是唯一明確代表「這個
  phase 沒收到繼續指令、正停著」的一種。

後兩種的出口相同，而且非給不可：由 orchestrator 自己以 `send-to-phase.sh` 送出一則「繼續」。這
個 phase 已經停下，產生器印完就進內層等待、在有人送出下行之前不會再產生任何事件，低頻掃描也接
不住（休止態既不是做事中、不觸發 `SPINNING`，也不是 `unknown`、不觸發 `UNCLASSIFIED`），三條通
道同時盲掉。後兩種不要派調查者去查待決事項：`working-ok` 這個標記的語意就是這一回合沒有待決事
項。`blocked` 那一種仍要派一次調查者，但目的不同——是取得代按守衛要的那句按鍵指名。

| 事件 | 處置 |
| --- | --- |
| 停下且標記為 `pr-ready` | 以 `set-phase-field.sh` 把標記帶回來的 PR 編號寫進 `pr`——那一格的權威是狀態檔，不是 GitHub，因為由 issue 反查 PR 已知不可靠——並把 `stage` 寫成 `pr-ready`。接著回報使用者，tab 保持開啟（review 可能要求改動）。不讀 PR 內容 |
| 停下且標記為 `wrapped-up` | 走「生命週期」第 6 步 |
| 停下且標記為 `need-decision` | 詳情在請求檔裡、不在畫面上。把 `stage` 寫成 `awaiting-decision`，派調查者，依回傳走「決策與升級」的三條路徑；定案轉達出去之後把 `stage` 寫回 `running` |
| 停下且 `marker=none` | 標記缺席、抓不到，或標記序號沒有變大（上一回合的舊標記還留在畫面上）。派調查者，同上 |
| `AUTO-PUSH-LIMIT` | 同一個 phase 被產生器連續自動推進超過門檻時才印這一行（`working-ok` 通常不進 orchestrator，例外見本節開頭）。派調查者判定它是在推進還是原地打轉，再依判定結論走「決策與升級」的出口：把定案、或一則「繼續」以 `send-to-phase.sh` 送出去。這一行是在它已經停下時印的，出口不能省——產生器印完就進內層等待，在收到下行之前不會再產生任何事件，低頻掃描也接不住，少了這一次下行就沒有任何通道會再把它帶出來 |
| `SPINNING` | 持續做事但狀態序號久未變化。派調查者：判定在做事就放回監看、什麼都不做；判定空轉就依判定結論走「決策與升級」的出口，而這一次下行要帶不握手選項——`SPINNING` 印出來的當下那個 phase 一定是做事中（產生器只在做事中的分支判空轉），對做事中的對象沒有任何短握手可用，照握手做就是十秒逾時、拿到 7、再白派一次調查者去查一則其實已經送達的下行 |
| `UNCLASSIFIED` | 狀態長期停在 `unknown`：herdr 認得出有 agent，卻分類不出來。派調查者判定它實際停在什麼上面，必要時以 `phase-status.sh` 的診斷模式取 herdr 自己的判定規則名。`unknown` 不代表完成——沒有這一列，這個 phase 會從編排端的視野裡無聲消失 |
| `AGENT-RESTARTED` | 這個 phase agent 中途重啟過、標記計數歸零（畫面上的序號比狀態檔記的基準小），產生器已經以當下值重設了基準。派一次調查者查明它為什麼重啟。產生器在重設基準的那一輪不把觸發判定的那則標記往下分類，所以不要等一則對應的常規停下事件——它不會來。這是刻意的：一個剛重啟的 agent 已經失去它的 context，對它的標記自動推一把等於叫它繼續做它已經不記得的工作。資訊沒有遺失，調查者會讀畫面與請求檔。判定完同樣要走出口：依結論走「決策與升級」，把定案、或一則「繼續」以 `send-to-phase.sh` 送出去。它也是在已經停下時被發現的，事件通道、內層等待、低頻掃描三條都不會再自行把它帶出來 |
| `GONE` | tab 被關或 session 掛掉。orchestrator 自己剛關的則忽略；否則升級，不自行重派——自行重派會在同一個 sub-issue 上開出第二條分支 |
| 握手未取得憑據（`send-to-phase.sh` 結束碼 7） | 派調查者。已接手就放回監看；卡住就走「決策與升級」。只有對停下中的對象送出才走得到這一列：廣播、以及 `SPINNING` 判定空轉後那一次下行都帶不握手選項，兩者都不會產生這個事件。`press-approval.sh` 的 7 也不走這一列，它的處置在腳本表那一列 |
| 事件產生器的串流結束，含它自己異常結束 | 立刻重掛一次並向使用者報一行。重掛也失敗才升級——那之後不會再有任何東西喚醒 orchestrator |
| 使用者說可以合併 | 走「生命週期」第 5 步 |
| 使用者要求某個 phase 修改 | 轉達給該 phase agent，並把 `stage` 從 `pr-ready` 寫回 `running`。它改完會再送一則 `pr-ready`，回到本表第一列 |

事件產生器異常結束與串流結束是同一件事，不是兩件：產生器在子行程異常死亡時會主動結束整支腳
本，而那個結束對 orchestrator 而言就是 Monitor 的串流結束。因此兩者共用上表同一列的處置，不
要因為原因不同而以為另有一套。

## 決策與升級

自決是預設，升級是例外：指不出命中「升級清單」哪一項，就是不命中，自己決定。「這件事好像有點
大」不構成升級理由。處置只有三條路徑，出口只有一個。

| 路徑 | 什麼時候走 | 怎麼做 |
| --- | --- | --- |
| A · 直接回覆 | 問題屬於設計文件該回答的：phase 邊界、與其他 phase 的介面、判準已寫在設計文件裡的方案選擇 | 打開設計文件那一段，確認它確實寫出了這次要選的那一項的判準——只是提到相關主題、或只是背景描述都不算。回覆時帶上該段標題或原文一句。這個測試不成立就改走 B，不要用「照常理應該是」補上去：orchestrator 看不到開發內容，它的常理沒有材料支撐 |
| B · 調查後回覆 | 其餘一律走這條 | 委派 `phase-decision-investigator` 做完整調查，依它的推薦回覆 |
| 升級 · 交給使用者 | 命中「升級清單」任一項 | 呈上調查者的判定結論與分析；沒派過調查者的不為了升級補派——判定結論已經辨識到動作的層級時，補派一次完整調查不會多給使用者任何判斷材料 |

出口只有一個：orchestrator 把定案透過 `send-to-phase.sh` 轉達回該 phase agent。自己的決定與使
用者的決定走同一個出口，沒有第二條路。對方正卡在核准框時，文字下行會被 herdr 以
`agent_blocked` 拒絕（腳本以結束碼 6 回報），此時先依「代按守衛」把框按掉解除阻塞，等狀態離開
`blocked` 之後再送定案；代按只有在那個框問的正是這次定案要回答的那件事時，才算把定案轉達出
去，框問的是別件事就只解得開阻塞、送不到定案。

### 升級清單

以下九項是唯一該停下問使用者的情況。這份清單是窮舉的，不是舉例。

1. **需要在方案之間做價值取捨。** 判準是兩個方案的後果都成立，選哪一個取決於使用者要什麼。
   有一邊會失敗的不是取捨，是判斷，自己判。
2. **會改變設計文件所定的 phase 之間介面，或改變某個 sub-issue 的範圍。** 判準是拿請求要改動
   的那個標的當關鍵詞——函式或型別名稱、檔案路徑、資料欄位、端點、指令名——搜過設計文件全文與
   各 sub-issue 內文：只命中提出請求的那一個 phase 的段落，自行決定；命中其他 phase 的段落、或
   這個改動會把某件事從一個 sub-issue 挪到另一個、或讓某個 sub-issue 的驗收條件與它的內文對不
   上，升級。搜的是那個標的的名稱，不是「介面」這兩個字——設計文件用什麼詞描述它不影響判定。與
   第三項的分工：第三項的觸發源是事實推翻了假設，搜的是那個假設的關鍵詞；本項的觸發源是有人提
   議改動一個跨 phase 共用的東西，搜的是那個標的的名稱。兩項同時命中時都指向升級，不必分辨算
   哪一項。少了這條判準的失敗形狀：phase agent 問「這個介面改成回傳整個物件比較好」，而設計文
   件未必用「介面」這個詞寫過那一段，編排端指不出算不算命中，落回「指不出命中就自己決定」的預
   設，改掉的正好是使用者當初核准的那組介面。
3. **設計文件的假設被推翻，而影響不只落在提出請求的那一個 phase。**「推翻」的判準是照設計文
   件原本的敘述做會失敗、或產生與所述不同的結果；「有更好的做法」不算推翻，那是優化提案，不
   觸發本項。假設確實被推翻時，第一個動作固定是搜尋：拿該假設的關鍵詞搜過 epic 設計文件全
   文。這一次搜尋同時決定要不要升級與有哪些 phase 受影響，所以只做一次，不是兩套判準：
   - 只命中提出請求的那個 phase：自行更新設計文件並回覆，不升級。
   - 命中落在不對應任何 phase 的段落（背景、架構總覽這一類）：歸上一種，自行更新、不升級。
     `plan-integrity` 本來就把這種命中算成不對應任何下游產物，空的下游清單即為正確狀態。
   - 命中其他 phase，或修補需要增刪 sub-issue、要改動依賴圖：升級。一次搜尋同時命中不對應任
     何 phase 的段落與其他 phase 時，以命中其他 phase 這一條為準。
   本項對 `plan-integrity` 的收窄是刻意的：那條 rule 把「修計畫、再往受影響的下游傳播」整件事
   都指派給編排端自理，不分影響落在幾個 phase，本 skill 把命中其他 phase 的那一種改成升級，理
   由是使用者當初核准的正是那張依賴圖與那組 phase 之間的介面。本項各分支說的「自行更新」指的
   是由 orchestrator 決定改什麼，落筆一律委派 `markdown-editor`（見「兩層約束」）。不論升級與
   否，傳播都要做完：設計文件更新後依搜尋命中處逐一處理其他 phase——已經在跑的通知它假設已更新，尚未派工的確保派
   出時讀到的是更新後的內容——並重跑同一組搜尋，剩下的命中全部落在已更新的敘述上才算處理完
   畢；仍命中舊敘述就是未完成。
4. **會產生不可逆或波及該 phase 以外的後果。** 名單是地板，列名的一律命中，不必再套判準：合
   併；對共用分支 force push 或改寫歷史；刪除遠端分支（指該 phase 自己那條已合併分支以外的分
   支——它自己那條的合併後清理是「生命週期」第 6 步的例行動作，不吃本項）；發布或 release；憑
   證輪替或寫入；對外
   部服務寫入；刪除或覆寫該 phase worktree 以外的資料；引入新的外部依賴；改動專案級設定（例
   如 CI、lint、依賴清單）。判準負責往外擴，把名單以外的同類納進來，三個問句任一答「是」就命
   中：
   - 回復這件事需不需要動到該 phase worktree 以外的東西，或需不需要別人配合？
   - 影響會不會落到其他 phase、共用資源或外部服務上，而且不是該 phase 自己收得回來的？
   - 這個改動當下落在該 phase 自己的 worktree 內，但合併之後會不會落到其他 phase 或整個 repo
     身上（例如改 `.gitignore`、改 lockfile、改測試基礎設定）？

   本項規範的是 orchestrator 自己要做、或親手批准的動作，「親手批准」有兩條出口：代按核准框，
   以及回覆內容本身授權對方去做某個具體動作。phase agent 未經請示自己做掉的動作不歸本項——那
   一種只有契約裡的動手前守衛擋著，而且已實測 `--permission-mode auto` 之下寫工作目錄外的檔案
   直接放行、不跳核准框，所以那一類根本不會回到 orchestrator 手上，本項攔得到的只有經由核准框
   或回覆內容回來的那些。例行編排動作也不算：開關 tab、送下行、委派唯讀查詢、Epic 收尾關閉
   parent issue，以及依第三項自決分支更新 epic 設計文件。
5. **工作區信任對話框。** 它問的是使用者信不信任這個目錄，只有使用者答得了。使用者答覆之後仍
   由 orchestrator 依「代按守衛」代按。
6. **同一個 phase 就同一議題再次回來且無法決定，或同一議題進入第三輪。**「同一議題」指對方這
   次要的裁決與上一次指向同一個待決事項——換問法、換切入角度、把問題拆小、補上新的嘗試紀錄，
   都還是同一議題；只有待決事項本身換了才是新議題。不是第二次回來就升級：第二次先再試一次，
   「無法決定」的可觀察判準是這一輪指不指得出一個與上一輪不同、而且直接回答對方原本那個問題的
   依據——設計文件的另一段，且該段寫出了這次要選的那一項的判準；或調查者這次讀到的新事實。
   「另有一段提到相關主題」不算，那只換了引用、沒換答案。第三輪一律升級，不再問自己指不指得出
   新依據。
7. **依賴圖成環，或依賴指向不存在的 issue。**
8. **合併確認。** `human-in-the-loop-boundaries` rule 明定 AI 不自動 merge，本 skill 不放寬。
9. **受限做不到，或自決手段已用盡仍判不出來。** 該重試的重試過、「失敗行為」列出的四種證據中
   取得條件成立的都取過、該派的調查者也派過，仍然判不出處置，或沒有下一個做得到的動作。這一項
   是清單的收尾項：前八項攔的是特定情境，這一項攔的是「情境本身沒問題，但這一端做不到或看不出
   來」——有它，「指不出命中哪一項就自己決定」才不會把 orchestrator 推去硬做一件它做不掉的事。

自我檢測：這個卡點命中的是上面第幾項，我指得出編號嗎？指不出來就不是升級案件，自己決定；但
「自己決定」的前提是這一端做得到也判得出來，做不到或判不出來的那一種，指出來的編號就是第九項。

### 代按守衛

先說發生率，免得這一節的份量被誤讀成頻率：`--permission-mode auto` 之下執行中途的核准框已實測
不會為「寫工作目錄外的檔案」這一類跳出來，而 cwd 指向已被信任的主倉庫之後，啟動階段的工作區信
任對話框也幾乎不會出現，所以 `press-approval.sh` 在正常運行中幾乎不會被呼叫。它仍然這麼嚴，是
因為它擋的是唯一一個「放行什麼不由編排端決定、編排端只負責按下去」的動作，一次做錯的代價與它
的發生率不成比例。

按哪一顆同樣不是編排端算得出來的。編排端不讀畫面，而框上有哪些選項、哪一顆對應「只放行這一次
這個動作」，這個資訊只存在畫面上，所以按鍵值一律取自調查者的回傳：它的契約要求在回報時以自己
的話一併指名要按的那一顆及其語意（例如「按 1，那個選項是只允許這一次」）。那是重新組織過的指
名，不是把畫面原文帶回來。回傳裡沒有這句指名，就等同下面的「指不出來」：補派一次調查者，不得
由編排端自己挑一顆按下去。

- 判定結論是工作區信任對話框：直接走第五項升級，由使用者定案之後才由 orchestrator 以腳本的啟
  動階段模式代按，不進下面那些測試——那個框放行的是整個目錄的信任，本來就指不出單一具體動作。
  不論調查者指名哪一顆，這一種一律歸第五項，不吃下面拒絕鍵那條例外。
- 指名的那一顆是 esc、或「否」「拒絕」「取消」這一類不放行任何動作的按鍵：先走這一條，不落到
  下面幾條。它仍然算代按案件、仍然經 `press-approval.sh`，但那個必填參數改填明訂的保留值
  「不放行任何動作，僅解除阻塞」，並在同一個參數裡帶上調查者給的按鍵語意。
- 其餘情形先問：手上這一次調查者的結論，指不指得出這個框要放行的是哪一個具體動作——要寫哪個檔
  案、要跑哪一條指令、要對哪個遠端做什麼。四種答案四條路：
  - 指不出來：改走 B 路徑派調查者，不得先按了再說。派過調查者仍然指不出來的，走第九項升級，不
    得回頭代按——這是這條分支的終止條件，不會停在原地反覆改派。
  - 指得出來且命中第四項：升級，由使用者決定。
  - 指得出來，但那一顆的放行範圍大於這一次的具體動作：一律走第九項升級，不代按。若框上出現
    「總是允許」或「不要再問」這一類選項，它剛好通得過上面兩道問句——具體動作指得出來，單看那
    一個動作也不命中第四項——可是按下去放行的是往後所有同類動作，遠大於那句動作說明所描述的範
    圍，而之後每一次放行都不會再回到編排端手上。寫成「若出現」而不是斷言它一定在，是因為 auto
    之下的核准框長什麼樣、有沒有這一類選項屬未查證推斷：要看到真實的框只能讓一個活的 agent 撞
    上它，沒有無副作用的探測手段。
  - 指得出來、範圍恰好就是這一次那個動作、且不命中第四項：才代按，並把那個動作原文填進腳本的
    放行動作參數。

拒絕鍵走獨立處置而不是一律升級，理由是守衛擋的風險方向。守衛擋的是「放行了編排端看不見的東
西」，而拒絕鍵的方向相反：它不放行任何東西，最壞的後果是 phase agent 的某個動作被否決、它得改
走別條路，那是可逆的，而且它下一次停下就會再產生一則事件回到編排端手上。若改成一律升級，每一
次卡在框上都得停下問使用者才能解除阻塞，那與「自決是預設，升級是例外」牴觸，也讓「先把框按掉
解除阻塞」這條路永久走不通——卡在 `blocked` 的 phase 連文字下行都收不到，不按掉就沒有別的出路。

自我檢測：我這次要按下去的那一顆，是調查者指名的嗎？它會放行某個動作嗎——會的話，那個動作我填
得進必填參數，而且它的放行範圍就是這一次那個動作嗎？第一題答否就補派調查者；第二題在「會放行
某個動作」時答否，才是升級訊號，拒絕鍵那一種答否是正常的，照保留值填。

### 自決事項的即時回報

自決不等於靜默：使用者沒有被停下來問，就只能靠回報知道 orchestrator 剛才替他決定了什麼。下列
任一成立就即時報一行，都不成立的自決不另外報——加報會把這條回報線稀釋成雜訊，使用者也就不會再
逐則讀它。

- 本次曾在「升級清單」兩項之間比對，或一度判為命中後又改判不命中。
- 調查者回報了落差。
- 同一議題（界定見第六項）進入第二輪以上的回覆。
- 修改了 epic 設計文件：報被推翻的假設、改動的段落、搜尋命中的其他 phase。
- 代按了核准框：報按了哪一顆、放行的是哪一個具體動作；拒絕鍵那一種報的就是「僅解除阻塞」。

## 失敗行為

orchestrator 在看不見開發內容的前提下判斷，手上能用的證據只有四種：`phase-status.sh` 回的狀態
與狀態序號、事件行帶回的那一個狀態標記、GitHub 上的 issue 與 PR 狀態、以及調查者帶回來的結論。
四種裡取得條件成立的都取過、取不到的指得出被哪一條擋住，仍判不出來時命中升級清單第九項；命中
就交給使用者，不自行終止任何 phase。

| 情境 | 處置 |
| --- | --- |
| 啟動未就緒（`start-phase.sh` 結束碼 8） | 派調查者判因。判定是工作區信任對話框就走第五項升級；其餘（agent 沒起來、啟動指令失敗、停在別的確認框）自行以 `close-phase.sh` 關掉這個 tab 重啟一次，第二次仍失敗才走第九項升級。關 tab 時三道守衛照樣適用，不因為這次是自決就繞過 |
| 開場指令已送出、握手也取得憑據，但長時間沒有任何動靜 | 不重啟——關掉會丟掉這個 agent 已累積的整段 context，而它已經接手在跑。狀態始終在做事的由 `SPINNING` 涵蓋，轉為停下的由停下事件涵蓋，兩條都不必 orchestrator 主動去查 |
| 合併失敗（衝突或 CI 未過） | 自決。不由 orchestrator 解決，把合併指令自己的拒絕訊息原文轉給該 phase agent——那是唯一有開發脈絡的一端。範圍就是那一則拒絕：不可合併、有衝突、必要檢查未通過這一類結果行，不含 CI 日誌或測試輸出本體。日誌與測試輸出仍在「三個角色」那份看不到的清單裡，編排端不取也不轉；要看它們的是 phase agent，它本來就看得到。轉這一則只是讓它知道被擋在哪一關——那份清單的價值就在於沒有例外 |
| tab 已不在而 PR 未合併 | 升級（第四項）。說明後果並詢問使用者要重派還是接手，不自行重派 |
| PR 已合併但對應的 sub-issue 仍然開著 | 整條升級（第九項），不拆。關 issue 做得到，但同一件收尾裡殘留的 worktree 移除落在「不碰任何 worktree」那條邊界上——那一條屬於靠結構保證的那一層，沒有腳本、沒有結束碼會擋下它，所以這裡不能靠「試了會被擋」自我約束，是編排端自己不做。拆的結果是「issue 關了、worktree 還在」，之後沒有任何流程會再回頭看它一眼 |
| 調查者回報讀畫面得到 `pane_not_found` | 這個 pane 已經不在了，歸 `GONE` 處置，不是第九項。herdr 對已關閉的 pane 給的是明確錯誤碼，不是空白 |
| 調查者回報讀畫面失敗（其他錯誤）或讀回空白 | 這一格沒有別的證據可換，命中第九項，走升級 |

## 中斷恢復

orchestrator 這一端中斷後接回時，恢復順序固定五步，順序是實質的：

1. 讀狀態檔，取得 herdr 座標、每個 phase 的關卡（`stage`）與 PR 編號（`pr`），據此重建進度
   表。讀取直接讀檔即可，要改才必須經 `set-phase-field.sh`。中斷時留在 `true` 的
   `held_by_orchestrator` 順手收回——留著它，那個 phase 每次停下都會被交回 orchestrator，正是
   這個設計要省掉的成本。
2. 委派 `github-manager` 重查進度——sub-issue 狀態與 PR 的合併狀態才是權威。
3. 只有 PR 編號為空、或整份狀態檔遺失時才走退路：委派 `github-manager` 拿分支命名慣例反查（分
   支名帶該 sub-issue 編號），查到之後寫回 `pr`。狀態檔完整時直接用檔案裡的編號，不必反查。
4. 以 `phase-status.sh` 查全部模式核對哪些 tab 還活著。
5. 重新掛起事件產生器（依「事件通道」，一樣要 `persistent`）。它隨 session 結束而消失，但狀態
   檔還在，所以監看清單接得回來；掛起當下每個已經停下的 phase 各補發一則事件，但標記為
   `working-ok` 的那一種由產生器自動消化、不補發，別把少掉的那幾則判成異常；中斷前已被消化過
   的標記則會以 `marker=none` 回來，依「事件通道」那條先核對 `stage` 再決定要不要派調查者。

各步之間對不上時，一律以 GitHub 與 herdr 的現況為準並把關卡寫回 `stage`——狀態檔唯一會過時的情
境正是編排端中斷的那一刻。tab 已不在但 PR 尚未合併的 phase 據實回報，由使用者決定要重派還是接
手，orchestrator 不自行重派。

自我檢測：這五步的順序有沒有被打亂，尤其是事件產生器是不是排在最後、在進度表重建之後才掛起？
順序錯了就先停下重來，不要將錯就錯往下做。
