# Obsidian Learning Series Skill

## 定位

此 skill 是「在 Obsidian vault 中建立一整套連貫學習系列」的統一入口，協調從發想、事實查證、逐篇撰寫到整體驗證與合併的完整流程。分工如下：

- **撰寫**委派 `obsidian-md-editor`、**圖表選型與渲染**委派 `diagram-designer`、**外部事實查證**委派 `doc-research`。
- **審查**委派一個獨立的審查 subagent（一個乾淨 context 的 general-purpose agent，給它審查 brief），main agent 不自己讀全文做內容判斷。
- main agent 只做協調、派工與品質把關，不自行動筆、不自行審查，盡量不把各篇內容吸進自己的 context，最終只持有各篇檔案路徑、spec 與驗證結論。跨篇的協調脈絡（回指關係、伏筆、待裁決的 Minor）由 main agent 保管，這屬協調不屬內容。

本 skill 自包含，不依賴任何特定外部套件。若環境有 superpowers，可用其 `brainstorming`、`writing-plans`、`subagent-driven-development` 三個 skill 依序驅動下面的執行流程；沒有也能照這份流程手動推進。

**格式一律比照 vault 內既有的學習系列**（例如 `aws/vpc/`、`networking/wifi/`）：檔名編號、frontmatter 欄位、學習定位區塊、index 結構、根 index 的分類清單寫法，都以既有系列為範本，本 skill 不重複描述那些慣例，動工前先讀一個既有系列當樣板。

## 觸發時機

應觸發：

- 要在 vault 建立多篇連貫、一起交付的學習系列
- 既有系列要新增或重構多篇

不應觸發：

- 單篇筆記的建立或編輯，走 `obsidian-notes`
- 純結構操作（rename、move、backlink 查詢、frontmatter 讀寫），走 `obsidian-notes`

## 執行流程

把「一篇 = 一個可獨立審查、可獨立回退的單元」當成整套流程的軸。

1. **發想與定位**：先敲定系列骨架與邊界，別急著寫。要決定的：
   - 敘事骨架選型——**雙軌**（技術主線與實務答案並行，靠 index 的任務查找表分流；當讀者同時想「懂原理」又想「做決策」時最合適）／**純編年**（主題是單純的機制演進、讀者只想由淺入深時）／**問題導向**（主題本身就是一組待解的痛點時）。
   - 讀者輪廓、原理深度——若後續多篇都會用到同一組基本概念，先立一篇「共用直覺」地基篇，把詞彙與核心心智模型集中在那裡。
   - 範圍邊界：哪些子題涵蓋、哪些明確排除。
   - 篇數：以「可獨立吸收的子概念數」為準，一個核心概念一篇，別硬湊也別把兩個獨立概念塞進一篇。
   - 產出一份 **spec**：這是一份規劃文件、不是 vault 筆記，寫成一個 markdown 檔放在專案的 plan/spec 區或 `.tmp`（可由 main agent 直接寫，不走 `obsidian-md-editor`）。內容為每篇的 title、description、獨立吸收點、逐段的圖意圖。它是後續每篇撰寫與審查的唯一需求來源。
1. **事實查證優先（列為第一個任務）**：凡是會過期或可能與記憶不符的事實（法規、標準時程、型號規格、各平台操作步驟），先委派 `doc-research` 查第一手來源，結果寫進 `.tmp`（一份總表，逐項標來源與查證日期）。查不到就誠實標「查無明確來源」，不要用似是而非的說法補洞。工具失效時換手再查——某條取檔路徑不通就換另一條管道，別因為一個工具壞了就退回憑記憶。
1. **建立共用視覺語彙（在動筆任何一篇之前）**：委派 `diagram-designer` 先定案全系列共用的視覺約定——反覆出現的實體怎麼標色、核心比喻怎麼畫、對立狀態怎麼表示——並把地基篇那張核心心智模型圖先定死，寫進 `.tmp` 供各篇引用。整套圖才會是同一套語言而不是各自為政。
1. **逐篇撰寫**：沿用 vault 既有的分支慣例（從 `main` 切一條 feature branch，逐篇 commit，最後 no-ff 合併）。一篇一個任務，每篇的循環：讀該篇 spec → 委派 `diagram-designer` 產圖並渲染驗證 → 委派 `obsidian-md-editor` 把圖嵌進對應段落、文字只作圖的註解 → 驗證後 commit。每篇獨立 commit，任何一篇出問題可單獨回退。前一篇建立的詞彙、伏筆、關鍵圖，寫進下一篇的委派 prompt 供其正確回指。
1. **每篇獨立審查**：每篇寫完，委派審查 subagent 讀該篇 diff 加該篇 spec，回傳兩個獨立判定——規格符合度、內容品質。判定用機械檢查抓不到的角度（見「內容心法」與「常見坑」）。嚴重度分級：**Critical**＝事實錯誤或會誤導讀者、敘事斷裂；**Important**＝違反設計原則或跨篇不一致；**Minor**＝風格與可讀性。Critical 與 Important 退回對應篇章的撰寫委派修正、再複審；Minor 記進進度追蹤，累積到最後一起裁決。
1. **整體驗證加建 index**：全部寫完後——
   - 機械檢查：檔案數、圖總數、簡體字、wiki-link 死連結、每篇行數、每篇有無學習定位區塊；圖一律經 `diagram-designer` 用本機 `mmdc` 實際渲染過。
   - 語意檢查：跨篇回指是否都成立、埋的伏筆有無回收、範圍排除有無守住、關鍵事實跨篇是否一致。
   - **index 最後才建**（理由見「常見坑」）：系列 index（流程圖、篇目導覽、任務查找表、延伸閱讀）、必要時的分類 index、更新根 index，格式比照既有系列。
   - 委派審查 subagent 做一輪最終全分支審查，裁決累積的 Minor。
1. **合併**：全部驗證通過後，no-fast-forward 合併回 `main`。

## 內容心法

- **圖為主、文字為輔**：每個核心段落至少一張圖把概念講清楚；文字是圖的註解，不是主體。
- **統一骨架當教學工具**：平行的篇章（例如每一代技術）共用同一個段落結構，例如「前一代卡在哪 → 這代用什麼機制解決 → 你實際感受得到嗎」。重複本身讓讀者建立預期、降低認知負擔。
- **建立共用心智模型並反覆回指**：地基篇立一個貫穿全系列的核心比喻，後續每篇回指它而非重新解釋；在早篇埋伏筆、在後篇回收（例如「你手上的裝置其實只有 X」先埋、談到瓶頸時回收）。
- **每篇誠實回答「你實際感受得到嗎」**：正面講行銷宣稱與真實體驗之間的落差，不幫任何一代或任何選項說好話。這是這類系列最稀缺、也最有價值的部分。
- **雙軌敘事加任務查找表**：技術主線與實務答案並行，index 的查找表讓只想解決某個具體問題的讀者不必讀完全部。

## 常見坑（審查時逐項對照，這些機械檢查抓不到）

- **正文洩漏 mermaid 的 class 名稱或 CSS 識別字**：`squeezed`、`genOld` 這類是實作細節，讀者不該看到。描述圖要用讀者看得懂的話講圖的結論，不要提顏色代號或 class 名。
- **同一論點講四遍**：散文加情境故事加「換句話說」加條列，把一個點反覆說服。留最有畫面感的一種，其餘砍掉。圖為主的系列尤其容易在這裡灌水。
- **協定定義相對於實機的混淆**：規格上成立、但與讀者手上實機不符的陳述（例如「某代 router 沒有某頻段」在協定定義上對、但每台實機其實都有），會讓讀者認定整篇是錯的。主動點出兩者的差別。
- **行銷數字可能是被撤回的草案**：坊間廣傳的峰值或規格，可能來自已被標準組織刪掉的早期草案。查官方原文核對，並反過來拿這件事當「規格數字別盡信」的教材。
- **循環論證的類比**：類比對目標讀者必須自足，不能預設讀者已經知道結論才讀得通。找一個純生活經驗、不需任何預備知識就成立的類比。
- **先寫的篇章回指還沒建立的內容**：所以 index 最後才建；早篇不要用 wiki-link 指向還沒生出來的檔案（會是死連結），改純文字提及；收尾篇別寫「索引之後才會建立」這種寫完就過期的話。
- **mermaid 的渲染限制**：節點文字過長會被裁切；subgraph 標題換行的第二行會被邊框吃掉；同層若無連線串接，會忽略 `direction LR` 而垂直堆疊，破壞左右對照版面（用隱形連線 `~~~` 串起來繞過）。一律用本機 `mmdc` 驗證渲染，不要用 kroki——遠端渲染與本機字型量測落差會產生假性的裁切警報。

## 委派約定

main agent 給 subagent 的是任務目標、事實與約束，不指定其內部要用哪些指令或步驟。遵守既有 rules：

- `markdown-editing`：vault 筆記一律委派 `obsidian-md-editor`。本 skill 產出的 spec、查證摘要、視覺語彙等規劃與傳輸緩衝檔除外，可由 main agent 直接寫。
- `diagram-output`：需 renderer 的圖先經 `diagram-designer` 選型與渲染驗證。
- `tmp-file-usage`：查證結果、圖表原始碼、共用視覺語彙、spec 等暫存一律走 `.tmp`。
- `subagent-routing`：跨範圍任務拆解後分別委派對應 subagent。

## 產出物

- 系列各篇正文，放在 vault 對應主題目錄下，檔名採「兩位數編號加英文 slug」，例如 `<領域>/<系列>/01-slug.md`。領域目錄優先沿用 vault 既有的頂層分類；主題不屬於任何既有分類時才新開一個頂層領域。
- 系列 index：流程圖、逐篇一句話的篇目導覽、任務查找表、延伸閱讀。
- 若是新開的頂層領域，補一個分類 index，並在根 index 補上該分類條目。
