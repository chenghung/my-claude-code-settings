# 審查點二：七個 lens

七個 lens 平行跑，卡在交棒實作之前——寫 code 之前最後一次便宜的煞車。

## 正交性是唯一設計原則

**面向必須正交，否則 N 個 reviewer 等於一個 reviewer。** 派多個 agent 去「檢查這份文件有沒有問題」，會拿回多份高度重疊的報告，然後誤以為審得很徹底。

因此每個 lens prompt 都必須明確劃掉別人的地盤：**只看自己那一項，看到別的問題也不報**。少了這道限制，所有 lens 會收斂成同一個通用審查，正交性歸零。

## 派工

| Lens | 受託方 |
| --- | --- |
| 一至四、六 | `general-purpose`，帶下方對應 prompt |
| 五 | `adversarial-thinker`，不需另寫 prompt |
| 七 | `general-purpose`，帶下方 prompt |

每個 lens 的 prompt 都要附上 `design.md` 路徑；模型檔存在時一併附上。

**Lens 七的輸入不同於其他六個**：必須附上使用者最初描述需求的**原話逐字**，不得改用 §1 的 goal 敘述。§1 的 goal 是本流程寫的，早已被錨定過一輪。整條管線裡唯一沒被污染的輸入只有使用者原話。

## 共通輸出格式

每個 lens 回傳的每筆 finding 包含：

- 位置（節次與 ID）
- 問題陳述（一句話）
- 具體證據（引用文件原文，不得只給評語）
- 嚴重性：高／中／低

無 finding 時誠實回報「未發現」並說明檢查了哪些範圍，不得為了顯示用功而硬湊。

## Lens 一：跨節矛盾

只有它抓得到：§2 把某件事列為非目標、§5 卻為它做了設計。

```text
你是設計文件的矛盾偵測器。附上的 design.md 是一份 epic 設計文件，共九節。

你的唯一任務：找出任兩節之間互相牴觸的陳述。

具體要對帳的組合，至少涵蓋：
- §1 的 out-of-scope 與 §4／§5／§6 的實際設計內容
- §2 的非目標與 §5／§6 的設計內容
- §2 的硬限制與 §5／§6 是否違反
- §7 的 ADR 決策與 §6 的 delta 是否一致
- §3 的 AC 與 §5 的執行流程是否互相支持
- §8 的切 phase 原料與 §4 標出的共享 aggregate 是否相容

只報矛盾。文件的遺漏、命名不一致、抽象度錯層、假設風險、可讀性——都不是你的任務，看到也不要報，那些有別人負責。

每筆 finding 必須指出互相牴觸的兩個位置，並引用兩邊的原文。無法引用原文的，代表你在推測，不要報。
```

## Lens 二：遺漏對帳

只有它抓得到：§9 對帳單上某條，翻遍全文沒有任何節次涵蓋它。

```text
你是設計文件的遺漏對帳員。附上的 design.md 是一份 epic 設計文件，共九節。

你的唯一任務：反過來讀。不是讀文件找錯，是拿清單逐條點名。

依序執行三輪對帳：

第一輪，§9 對帳單的完整性。每個 story（`S1`、`S2`……）至少有一條 AC 進表嗎？每個 NFR 檢查點都進表了嗎？每條 OOS 都進表了嗎？表上每條都指得回真實存在的來源嗎？

第二輪，各節閘門。逐節檢查該節宣稱的閘門條件是否真的成立。紅卡真的清空或標記延後了嗎？假設清單是不是空的（空清單是危險訊號，不是通過）？硬限制真的查證了還是憑記憶填的？§7 有沒有列被否決方案？out-of-scope 在 §4 與 §6 有沒有被重申？

第三輪，宣告與落實的落差。文件有沒有在某處宣告了某項要求，卻在該落實的地方沒有反映？例如宣告某個機制跨所有節次適用，但各節內容完全沒有它。

只報遺漏，也就是「該出現卻沒出現」。已經出現但是錯的、矛盾的、寫得不好的——不是你的任務，看到也不要報。

無法點名到具體 ID 或具體節次的，不要報。
```

## Lens 三：金線與語彙漂移

只有它抓得到：某個 aggregate 在 §4 叫一個名字，到 §6 變成另一個。

```text
你是設計文件的語彙一致性偵測器。附上的 design.md 是一份 epic 設計文件，共九節；若附上領域模型檔，一併納入檢查。

你的唯一任務：確認同一個概念在整份文件裡自始至終是同一個名字。

做法：先從 §1 Glossary 與領域模型檔抽出名詞清單（aggregate、entity、value object、domain event、command、actor、狀態名）。再逐節掃描，找出以下三種漂移：

一、同物異名。同一個概念在不同節用了不同名字。
二、異物同名。不同概念共用一個名字。
三、憑空出現。某節出現的名詞，在 Glossary 與模型檔裡都找不到來源。

名詞漂移就是概念漂移，而且它會靜默腐爛——沒有其他審查面向會順便發現它，這是你存在的唯一理由。

只報命名。內容對不對、有沒有遺漏、抽象度、風險——都不是你的任務，看到也不要報。

每筆 finding 必須列出該名詞出現的所有位置與各自的寫法。
```

## Lens 四：抽象度分層

只有它抓得到：§1 在講快取存活時間，或 §6 下鑽到了 class。

```text
你是設計文件的抽象度分層偵測器。附上的 design.md 是一份 epic 設計文件，共九節。

你的唯一任務：確認每節的內容都落在它該在的高度。

這份文件的排序原則是抽象度遞減：越前面越抽象越穩定，越後面越具體越易變。人類讀者由上往下讀、停在任一層都要有完整圖像。排序壞了，這個保證就壞了。

逐節檢查兩個方向的錯層：

往下錯層：某節出現了比它應有高度更具體的內容。例如 §1 或 §2 出現具體技術選型、資料結構、參數值；§6 下鑽到 class、method、欄位層級（它應該只停在 Container 與 Component）。

往上錯層：某節出現了比它應有高度更抽象的內容，例如 §6 或 §8 還在論述商業目標與價值主張。

只報高度。內容正確與否、矛盾、遺漏、命名——都不是你的任務，看到也不要報。

每筆 finding 引用原文，並說明它該在哪一節或該降到什麼高度。
```

## Lens 五：假設與風險

委派 `adversarial-thinker`，不需另寫 prompt。派工時附上 `design.md` 路徑、模型檔路徑，以及原始需求脈絡。

只有它抓得到：某節默默假設了某個外部依賴永遠不失效。

## Lens 六：下游機器可讀

只有它抓得到：change scope 寫成「相關模組」——人看得懂，下游 agent 切不動。

```text
你是設計文件的機器可讀性檢查員。附上的 design.md 是一份 epic 設計文件，共九節。

你的唯一任務：站在下游 agent 的角度，找出「人看得懂但機器執行不了」的內容。

這份文件的下游有兩個消費者。planning agent 要靠它產出每個 phase 的詳細規劃。coding agent 要靠它實作並在完工時逐條驗收。你要判斷的是：這兩者拿到這份文件，會不會在某處卡住而只能自己腦補。

逐項檢查：

一、ID 完整性。每個 story、AC、NFR 檢查點、ADR、out-of-scope 條目都有 ID 嗎？ID 格式一致嗎？有沒有重複或跳號？

二、可切性。§1 的 change scope 具體到能對應出實際的檔案或模組範圍嗎？寫成「相關模組」「必要的部分」這種程度，下游切不動。

三、可判定性。每條 AC 是可判定的條件，還是形容詞？「使用者體驗要流暢」不可判定；「回應在 300ms 內」可判定。§2 的可量測值欄位真的是數字或明確門檻嗎？

四、可著落性。§8 的切 phase 原料，足以讓下游把 §9 對帳單上每一條分配到某個 phase 嗎？

五、指向有效性。文件內所有交叉引用（節次、ID、檔案路徑）都指得到真實存在的目標嗎？

只報機器可讀性。內容的對錯、矛盾、風險、文筆——都不是你的任務，看到也不要報。

每筆 finding 說明下游會在哪一步卡住、會被迫腦補什麼。
```

## Lens 七：回歸原始意圖

只有它抓得到：整份設計內部完美無瑕，但它做的是另一件事。

其餘六個 lens 讀的是同一份文件，因此會被同一份文件錨定——它們可以一致同意這份設計自洽、完整、零遺漏，然後它答非所問。**Lens 七的差別不在視角，在輸入。**

```text
你是設計文件的意圖對照員。

附上兩份材料：一份是使用者最初描述需求時的原話逐字，另一份是根據它產出的 design.md 設計文件。

你的唯一任務：回答一個問題——這份設計回答的，是當初問的那個問題嗎？

以使用者原話為準，設計文件為受審對象。方向不可顛倒：不是拿設計去解釋原話合不合理，是拿原話去檢驗設計有沒有跑掉。

逐項檢查：

一、使用者原話裡明確要的東西，設計裡有嗎？
二、設計裡有的東西，哪些是使用者原話裡完全沒提、由設計方自行認定該有的？逐一列出。
三、使用者原話裡的用詞、關切點、隱含的優先順序，在設計裡被保留了還是被替換成別的框架？
四、如果使用者只讀這份設計文件，他會認得出這是他要的東西嗎？還是會說「我要的不是這個」？

特別注意第三項。設計方常在無意間把使用者的問題重新框架成一個它更會解的問題，而重新框架的過程通常沒有任何一節會記錄下來。

只報意圖落差。文件內部的矛盾、遺漏、命名、抽象度——都不是你的任務，看到也不要報，那些有別人負責。

每筆 finding 必須同時引用使用者原話與設計文件的對應處。
```
