# Epic Design

## 定位

此 skill 是 epic 層級設計討論的統一入口，產物是一份九節設計文件。領域建模整節委派出去，本 skill 不自行建模、不自行審查。

三個立場決定了此 skill 與一般「產出設計文件」任務的差異，違反任一條就失去存在意義：

**產物與過程分離。** 產物永遠九節完整；過程只在硬觸發響鈴時停下來詢問使用者。這兩件事不衝突，不得因為「使用者只想被打斷幾次」就省略節次，也不得因為「要寫九節」就一次性 dump 完再請使用者 approve。

**缺席即腦補許可證。** 不適用的節次要寫出「不適用」與理由，不得省略。下游 agent 無法區分「考慮過但不相關」與「根本忘了」，面對空白它會自己填。

**產出者不能宣告自己通過。** 此 skill 的閘門只有兩種形式算數：真的停下來等使用者回應，或交給沒有寫這份產物的 agent 檢查。不得由產出內容的同一個 context 自行宣告「紅卡已清空」「假設已檢視」。

## 觸發時機

應觸發：

- epic 規模的需求要在實作前做設計討論
- 需要一份能餵給下游 planning 與 coding agent 的設計文件

不應觸發：

- 單一 story、純 CRUD、往現有 aggregate 加欄位這類小型改動
- 純唯讀解說既有設計，不產出新設計

## 執行流程

1. **Step 0 Framing**：閘門是使用者能否用一句話說出「哪個 actor、達成什麼結果」。說不出來就停下來問，不得代為腦補。此步驟不產出文件節次，產物是那句話，會成為 §1 目標敘述的基礎。使用者只有模糊目標、講不出有哪些 story 時，先擠出候選 story 並挑最薄、風險最高的一片，再往下。
1. **§1 至 §3**：依 `references/sections.md` 逐節產出。
1. **審查點一**：委派 `adversarial-thinker` 審查 §1 至 §3。
1. **§4**：委派 `ddd-modeling`。
1. **§5 至 §8**：依 `references/sections.md` 逐節產出，按需讀取模型檔。
1. **§9 對帳單**。
1. **審查點二**：七個 lens 平行 panel，見 `references/review-lenses.md`。
1. **收斂迴圈**：findings 退回對應節次修正後重審。回合數需有節制，多輪仍不收斂時停下，把剩餘衝突呈報使用者裁決。
1. **交付**：回報產物路徑與審查結論。

跑到各節時才載入 `references/sections.md`，不預先全部讀入。

## 六條硬觸發

這六條取代「由 AI 自評不確定性來決定跑多深」。**不評估自己確不確定，只查事實**；任一成立就無條件停下來詢問使用者，不論當時跑到哪一節。

1. **越界**：要動到 §1 change scope 以外的東西。
1. **升級**：要新增 bounded context，或發現既有邊界畫錯。此時停止本流程並呈報使用者，不得在本文件內逕自重畫邊界。
1. **踩線**：碰到任何 §2 標記為硬限制的項目。
1. **共享**：出現跨 story 共享的 aggregate 或規則。
1. **查不到**：硬限制查證失敗。不得改以記憶或推測填值。
1. **紅卡未清就要進昂貴階段**：紅卡還開著卻要進 §4 委派或交棒實作。

硬觸發決定的是「停不停下來問使用者」，不是「寫不寫這節」。九節永遠都寫。

## 兩個審查點

審查點卡在成本階梯的每一階前面，也就是使用者即將付出大筆成本的前一刻。不得移到最後統一跑（那時錨定已經發生），也不得每節都跑（節與節之間成本落差不大）。

| 審查點 | 位置 | 執行 |
| --- | --- | --- |
| 一 | §3 結束、§4 委派之前 | 單獨委派 `adversarial-thinker` |
| 二 | §9 結束、交棒實作之前 | 七個 lens 平行 panel |

## 產物

落點為 `docs/design/<epic-slug>/`，使用者可於觸發時指定其他路徑。

| 檔案 | 產出者 |
| --- | --- |
| `design.md` | 本 skill |
| `domain-strategic.md` | `ddd-modeling`，**可能不存在** |
| `domain-tactical.md` | `ddd-modeling` |

戰略模型檔可能不存在，因為受託方會自行判斷需求規模並可能略過戰略建模。讀取前先確認檔案是否存在，不得假設兩份都在。

過程中的中間 scratch 依 `tmp-file-usage` rule 使用暫存區。

## ID 規則

| 對象 | 形式 |
| --- | --- |
| Story | `S1` |
| AC（Example Mapping 的藍卡規則） | `AC-S1-1` |
| NFR 檢查點 | `NFR-1` |
| ADR | `ADR-1` |
| Out-of-scope 條目 | `OOS-1` |

**GWT 不給獨立 ID。** 它是 AC 的可執行附件，不是獨立條目；下游測試指回 AC。

**ID 一旦寫進文件即不可重新編號**，包括插入新條目時不得重排既有編號。向上追溯靠它指認來源、向下對帳靠它點名，重編號會讓兩個方向同時失效。

## 委派要求

各受託方無狀態，prompt 須自帶完整脈絡。只描述目標與所需事實，不指定對方內部該用哪個方法或工具。

| 受託方 | 用途 | 必須給 | 不得給 |
| --- | --- | --- | --- |
| `ddd-modeling` | §4 全節 | 需求脈絡、兩個目標寫檔路徑 | 建模深度、要跑哪些階段 |
| `doc-research` | §2 硬限制查證 | 要查什麼、用途 | — |
| `diagram-designer` | §5、§6 圖表 | 要溝通什麼 | 圖表語法 |
| `adversarial-thinker` | 審查點一、panel lens 五 | 待審內容路徑、原始需求 | — |
| `general-purpose` | panel 其餘六個 lens | 對應 lens prompt、待審內容路徑 | — |

`ddd-modeling` 會自行評估需求規模並據此決定建模深度，指定深度會覆蓋掉它的判斷。

## 圖表

只畫 §5 的 sequence 與 state machine、§6 的 C4 delta。§1 與 §8 用清單，不畫圖。§4 的圖由受託方產在模型檔內，本 skill 不重畫。

圖表一律經 `diagram-designer` 選型與預覽，依 `diagram-output` rule 處理，不自行決定語法、不將圖表 DSL 輸出到對話。

## 合理化對照表

下列每一條都是無此 skill 時的實測行為，不是假想。左欄是當時的理由，右欄是它實際造成的後果。

| 合理化 | 現實 |
| --- | --- |
| 「不能跟使用者來回對話，所以我先把東西產出來」 | 受測者事後自陳：「就算可以對話，我也不確定我會停。我的傾向是先把東西產出來。」無法對話時的正解是停下並回報阻塞，不是代為決定後補上標記 |
| 「架構還沒定，畫圖是假的」 | 受測者用這個理由單方面跳過全部圖表。理由本身成立，但跳過的決定沒有經過使用者 |
| 「我有標記這是我的建議，也請使用者表態了」 | 受測者把「第一版不要做這個功能」寫進正式文件結構，事後自陳「那個位置本身就帶有份量，等於我在替使用者做決定」 |
| 「這個假設太明顯，不用列」 | 受測者最貴的假設——把需求預設成自己開發、從未考慮採購現成方案——不在它列出的清單裡，事後自陳「這個遺漏可能讓你白花好幾個月」 |
| 「這個數字我大概記得」 | 受測者事後自陳同一份文件內標準不一致：法規誠實說「我不確定」，延遲與工作量卻直接斷言，其中一個數字是憑空編的 |
| 「使用者只講了三句話，我得幫他補完」 | 受測者自行估算產出中僅約 5% 來自使用者原話，其餘 95% 為自行添加，包含一條主動否決使用者需求的建議 |

## 紅旗

出現以下任一念頭，就是正在合理化，停下來：

- 「先產出來再說，之後再問」
- 「這個理由夠充分，可以自己決定」
- 「我有標記了，所以沒問題」
- 「使用者應該會同意」
- 「這個假設太明顯了」
- 「這個數字大概是這樣」

## 邊界與失敗行為

- Step 0 閘門過不了（使用者說不出一句話的目標）：停下並說明原因，不得代為腦補目標後往下跑
- 硬觸發任一成立：停下並詢問使用者，不得自行裁決後繼續
- 受託方回報 context 不足：補齊後重派；補不齊則呈報使用者
- 收斂迴圈多輪不收斂：停下，明確標示未解衝突，交由使用者裁決
- 使用者要求跳過某節：說明該節缺席對下游 agent 的後果，仍寫入該節並標記「使用者要求略過」與理由

## 輸出格式

最終回應包含：

- `design.md` 與各模型檔的路徑
- 審查點二的判定與經修正後收斂的簡短摘要
- 未解衝突（若有），明確標示待使用者裁決
- 對帳單條目數，以及其中有幾條尚無 GWT（下游需轉為可執行場景的數量）
