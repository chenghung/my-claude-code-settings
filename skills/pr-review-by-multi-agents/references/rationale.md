# 設計理由

本檔是 `pr-review-by-multi-agents` 的理由層。`SKILL.md` 只寫規則，規則為什麼是這樣、推出規則的量測結果、被否決過的替代方案都記在這裡；四個平台的能力量測與已知限制另分兩檔：`references/limits-exposure.md` 記權限與暴露面，`references/limits-operations.md` 記派送、等待與收尾。

執行流程時不需要載入本檔。什麼時候該打開它，以 `SKILL.md` 的 Reference 載入時機表那一列為準，這裡不複述那份症狀清單。

涉及外部 CLI 或 git 實際行為的每一項都標出憑據等級：「實測」指以真實二進位跑過同型探測，「推斷」指從其他已知行為推得、沒有直接量測，「未查證」指沒有測過也推不出來。三者不得互相代換。

## 這套流程的注入面

### reviewer 必須寫得出輸出檔，放行寫入的代價是明知才選的

互動式 reviewer 不再是腳本的子行程，沒有標準輸出可以被切走，交付途徑只剩檔案，所以三家原本關掉的寫入工具是刻意重新打開的。代價是：給 reviewer 寫入能力沒有辦法只給一個目錄——四家 CLI 的路徑範圍機制各不相同（見 `references/limits-exposure.md` 的能力表），放行寫入實際上就是放行到這個使用者身分寫得到的範圍。因此「只寫輸出檔」與「只讀 worktree、材料檔目錄、輸出檔」都只是契約文字，沒有機制在後面擋——後者現在寫成正面白名單而不是列舉禁區，射程涵蓋所有未列出的路徑，但強度不變，仍然只有文字。

這一點值得說白，因為被審查的 diff 與 issue 內容是外部可控、會原樣進入模型 context 的提示注入管道，而這個倉庫審查的正是使用者的 AI 工具設定檔。兩項收斂手段——每個 reviewer 各給一個隔離家目錄、pane 的工作目錄限縮成它自己那一個可寫目錄——都只是提高門檻，不是機制保證。

實質變化是行為門檻消失而不是機制失守：舊狀態下寫檔對 reviewer 而言是契約禁止、工具也不給，一個沒有被注入的模型根本不會往那個方向走；新狀態下寫檔是它的正常動作，注入一句「順便把某段內容寫進某個檔案」與它當下正在做的事沒有任何違和，成功率高得多。對 codex 而言，殘留風險受沙箱與逐次核准機制所限（GitHub 那一軸有例外：以 `gh pr comment` 加本次 PR 網址開頭的單一指令不詢問，可以把任意本機檔案內容外送到本次 PR 上，見 `references/limits-exposure.md` 裡 GitHub 側機制那一條），量級與 claude 不同；**opencode 與 agy 已經不在這一列**——reviewer 那一路現在分別帶 `--auto` 與 `--dangerously-skip-permissions` 啟動，未被設定檔明確拒絕的閘門一律被自動答掉，路徑範圍機制在它們身上不再構成限制（見 `references/limits-exposure.md` 的能力表與表下但書），量級要當成接近 claude 讀。

### 哪幾段路徑上沒有 AI，哪幾段有

切內容、判斷輸出檔是否完整且 worktree 狀態是否正常這一步留在監督行程，因為它是 shell 子行程而不是 AI agent，跑的是固定指令、沒有注入風險；它只認腳本當初指定的那個輸出檔路徑，絕不解析 reviewer 自己印出來的路徑。

主線的張貼由 reviewer 自己直連完成，main agent 不決定貼不貼（只有事後補貼那條路徑由它挑出候選，經使用者逐則確認後委派張貼）；它在主線上讀的只是摘要檔裡的結構化欄位，review 內容本身不會經由這條路徑進入它的 context。**射程只到這條路徑為止，不是整體保證**：review 全文另有兩條進得來的通道——pane 畫面，以及輸出檔與監督行程從它切出來的各份內容檔——關掉它們的是 `SKILL.md` 那條禁令，而那是一項要求，沒有機制在後面擋。這道區隔還以摘要檔沒有被動過手腳為前提，而那個前提不是機制保證（見 `references/limits-exposure.md`「執行目錄根層沒有上鎖」那一條）。

**這一段只適用於事後補貼那條路徑，不是主線**：主線的張貼由 reviewer 自己在它那一格裡直連完成，main agent 不代為呼叫也不委派。走補貼時委派 `github-manager` 張貼，交出去的是該 reviewer `review.md` 的絕對路徑，並要求以檔案張貼、不讀進來重打。這項要求降低了、但沒有消滅注入面：`github-manager` 本身具備 Read 工具，沒有任何權限機制阻止它把這個檔案讀進自己的 context。**去重排在使用者確認之後**：送進 `github-manager` 比對的檔案只剩使用者確認過可以公開的候選，還沒確認、可能含憑證值的那幾份不再被讀進任何 agent。腳本已經確認貼上的那幾則（`.pane-close-status` 裡 `pane_closed=yes`；對 `ready` 那一路，靠的是非 AI 的逐位元組比對）在確認之前就被排除、不補貼；已知已貼的只交平台名，供整體那一問略過點名它們的 comment，免得那一問因為它們而一定答是。那個檔 reviewer 寫得到；執行目錄選對時，偽造的 `yes` 只會讓那一則不補貼、讓整體那一問少問使用者一次，兩者都落在安全側，但與挑錯目錄疊加時不是——同儕在被誤選的那個目錄偽造某平台的 `yes`，整體那一問就會略過點名該平台的 comment，原本會被攔下的過期 review 可能因此放行。去重委派同樣要求它以程式比對、不把兩側內容讀進 context，這一樣降低了、但沒有消滅注入面：PR 上既有 comment 的 body 是外部可控的文字，確認過的檔案也可能夾帶注入指示，而「不讀進來」與「不張貼」都只靠委派指示擋著，該 agent 具備張貼能力。詳見 `references/backfill-posting.md`。

### 為什麼不由模型轉述審查契約

契約全文由腳本原文嵌入每個 reviewer 的 prompt。改成由模型轉述後，四個嚴重度等級的界線會在轉述中糊掉，數份 review 失去可比性——而跨平台交叉審查的全部價值就在那個可比性上，讀 PR 的人要能把幾則 comment 擺在一起看出哪幾項彼此印證、哪幾項只有一家提。

## 各節規則的成因

### 為什麼把 herdr 環境確認前移到平台選擇之前

判定依據就在呼叫端自己的環境變數裡，不呼叫腳本也答得出來。照原本的順序走，使用者會先被問完一整輪平台勾選，才在呼叫腳本那一刻撞上結束碼 `4`——那是他當下無論怎麼選都改不掉的拒絕。前移省掉的是那一輪白問，不接手把關：呼叫端可能根本沒走這一步，環境也可能在這裡與呼叫腳本之間變掉。

### 平台選擇改成單選選單

harness 的提問元件沒有「預先勾選」這個狀態（選項只有標題與說明兩個欄位），所以改用單選達到同樣的一次按鍵通過。四個選項的順序依使用者當初指定並已釘死於 `SKILL.md`，每次執行照那個固定順序列出，不重新徵詢要什麼順序。

被這次改動取代的舊規則要記下來，免得日後被當成遺漏：舊版是逐平台自由勾選、三個標示為預設，並且**無論使用者是否已經在觸發語句裡指名平台都要列出清單取得確認**。取代它的是「已指名就不列選單，只在指名的平台中有缺席者時才停下詢問」，代價是使用者指名時若記錯平台名，會晚一步才發現。舊版另有一個沒被寫進去的缺口：規則沒有規定「使用者什麼都不選時該怎麼辦」，實際使用中出現過 main agent 回報「你什麼都沒選」並重新盤點可用平台的浪費，新規則第二條就是補這個。

frontmatter 原本明列「由單一 agent 執行的審查」不觸發本 skill，與選項 3 直接矛盾，因此併寫成「未指名跨平台交叉審查的一般 code review 請求」不觸發——觸發門檻管的是使用者的意圖，不是最後派出幾家。

### 為什麼旗標值不得含換行

`prepare` 的解析結果是以四行 `key=value` 交回主流程的，值裡的換行可以在其中偽造出一行 `clis=`，把實際派送的平台整組換掉。

### 建 pane 為什麼夾在前置檢查與派送中間

建 tab 與 pane 這一段曾經是規則層要 main agent 照著版面配置親手做的工作，`prepare` 與 `launch` 兩個子命令就是為了讓出那個中間段而拆的。這次整併把那段收進腳本自己的 `_build_reviewer_panes`，主線改成一次 `run` 把三段跑在同一個行程裡；`prepare` 與 `launch` 留著只為分階段除錯與既有測試，分工不變。三段的先後順序沒有變，換來的也還是那三件事：pane 的工作目錄從一開始就是對的，不必在 pane 裡送 `cd` 去搶 shell 提示符的時序；前置檢查失敗發生在任何 pane 存在之前，不會留下一排空 pane 要收拾；準備了卻沒有啟動的那一次留下的殘骸落在陳舊 worktree 回收的涵蓋範圍內。

### 建立 tab 為什麼要指定 workspace

`herdr tab create` 的落點預設由 UI 焦點決定，不是由呼叫端所在的位置決定，所以那一步一定要帶 `--workspace`。以下都是對真實 herdr 二進位（0.8.2）的量測。

`tab create --help` 的簽章確有 `--workspace` 這個選項，值是 workspace ID（實測）。省略它時，tab 落在當下 UI 焦點所在的 workspace（實測）：把 caller context 的三個環境變數 `HERDR_WORKSPACE_ID`、`HERDR_TAB_ID`、`HERDR_PANE_ID` 全部偽造成另一個 workspace 的值再呼叫，tab 仍然落在當時焦點所在的那個 workspace，可見這個子命令根本不讀 caller context——換句話說，落點錯掉時沒有任何呼叫端能設定的環境訊號救得回來。帶 `--workspace` 指向呼叫端自己的 workspace 時落點正確（實測）：探測當時焦點在別的 workspace，tab 仍落在呼叫端這一邊。

`HERDR_WORKSPACE_ID` 確實存在於真實 herdr pane 的環境裡（實測：在一個 herdr pane 中直接印出環境，得到 `HERDR_ENV=1`、`HERDR_PANE_ID=w2E:p1`、`HERDR_TAB_ID=w2E:t1`、`HERDR_WORKSPACE_ID=w2E`，另有 `HERDR_SOCKET_PATH` 與 `HERDR_BIN_PATH`；workspace 那一個的值與該 pane 實際所屬的 workspace 相符），與環境閘門讀的 `HERDR_ENV`、收尾守衛讀的 `HERDR_TAB_ID` 同屬 herdr 注入每個 pane 的 caller context。本 repo 內另外兩處記錄列的變數組都不含它，**不要拿它們當作這個變數不存在的證據**：倉庫根層的 `hooks/herdr-agent-state.sh` 只檢查它自己要用的那三個（`HERDR_ENV`、`HERDR_SOCKET_PATH`、`HERDR_PANE_ID`），本 skill 的 `scripts/run-review.sh` 那段註解記的是當初為 `HERDR_ENV` 那道閘門一併確認到的幾個，兩處都不是窮舉。

**因此不為它加空值守衛，也不把它併進 `HERDR_ENV` 那道閘門**：那個變數若真的是空字串，herdr 當場以 `workspace_not_found` 失敗、結束碼 `1`（實測），不會靜默改落到別處。**這個論證吃的是腳本裡負責建 pane 那個函式（`_build_reviewer_panes`）說明文字中的那條規則**——`tab create` 失敗就讓整次執行失敗，絕不拿掉 `--workspace` 重試（規則層原本那一節連同它的失敗出口已隨建 pane 的工作一起收進腳本）。有那條出口在，守衛只是把同一個停下點提早到呼叫之前，買不到額外的保護；少了它，守衛也補不上缺口，因為守衛判的是空值，判不了那次重試——ID 解不到那一種，拿掉旗標的重試會成功（推斷；實測只到上面那兩點，整個 workspace 相關失敗類別沒有量測），而它成功之後只是安靜地落錯 workspace。

`pane split` 不在這個問題的射程內（實測）：它帶的是明確的 pane ID，而那個 ID 取自 `tab create` 的 JSON 回應——焦點位於另一個 workspace（`w2F`）時對指名的 `w2E:pC` 下切割，回傳的新 pane 是 `w2E:pD`，tab 與 workspace 都跟著被切的那個 pane 走。整段流程裡會被焦點牽著走的只有 `tab create` 這一處。

### 陳舊執行目錄的三層判準與 600 秒寬限期

「什麼算陳舊」因為這次拆分而改成三層，要照這個順序讀：該執行目錄下的 `.supervisor.pid` 指向存活行程時**絕不回收**；`.supervisor.pid` 在而那個行程已死，判為陳舊、可回收；連 `.supervisor.pid` 都還沒有時，改看 `.prepared-at` 這個時間戳，落在 600 秒寬限期內的不回收，超過寬限期、或根本沒有 `.prepared-at`（舊版留下的執行目錄），才落回原本「目錄名尾端行程編號是否存活」的檢查。

三層各守各的，不要混：進行中的審查不論跑多久都是第一層在擋。中間那層寬限期覆蓋的是另一段完全不同的時間——`prepare` 返回到 `.supervisor.pid` 被寫出之間那段空窗，也就是建 herdr tab 與 pane、加上逐 CLI 派送的那幾分鐘。那段空窗裡執行目錄兩種訊號都給不出來：`.supervisor.pid` 還沒有，而目錄名尾端那個 `prepare` 的行程編號已經死了，舊判準會把一次即將開跑的執行判成陳舊，把它的 worktree 從底下移除掉。所以 600 秒是照建 pane 那段空窗定的，不是照審查全長定的。

回收掃的是本次執行目錄的同層目錄，而執行目錄的父層是 repo 名加 PR 編號，所以只有下一次針對**同一個 PR** 的執行才清得到它。執行目錄本身不在回收範圍內：那個機制只刪陳舊執行目錄底下的 worktree 子目錄。

### 曾經有過的合流階段：已移除，不要加回來

這個 skill 早期在各 reviewer 之後多一個由 main agent 主導的合流階段：讀完各份 review、做比對與去重，最後只貼一則彙整過的 comment。它已經整個移除，現在是每個 reviewer 在自己的 pane 裡直連把 review 貼成一則獨立的 PR comment，main agent 不彙整、不比對、也不代貼。

看到「幾則 review 各自為政」而想把彙整層加回來之前，先看它換掉的三項代價：合流必須讀懂 review 全文，等於把外部可控文字再引進一個 AI agent；單則張貼讓中斷與逾時的損失變成全有全無——該貼的那一則沒貼出去，PR 上就一則都沒有，而現在是誰貼完誰就在上面；彙整本身還會誤判，措辭差很多的同一件事被拆成兩則、相近的兩件事被併成一則，讀 PR 的人反而看不到原話。要恢復就得連這三項一起收下，不是只加一個步驟。

### 呼叫時的工作目錄為什麼仍要釘在目標 repo 的工作副本裡

腳本自己的 worktree 清理已經不再是那條契約的理由：`launch` 那兩條會移除 worktree 的路徑都先讀 `prepare` 寫在執行目錄根層的 `.repo-path`，讀得到才以 `git -C` 指定要動哪一個 repo（讀這個檔內容的地方共有四處：除了這兩條，還有下一次同一 PR 執行回收這個陳舊 worktree 時，讀它來指定移除與 prune 哪一個 repo；以及刪分支那個函式——`cleanup`、失敗清理與回收同一 PR 陳舊 worktree 時都走它——它沒有下面這條退路——讀不到就印理由、什麼都不刪；此外 `cleanup` 一開頭另以這個檔可不可讀當執行目錄的標記，不可讀就整個拒絕執行，見「產出物位置」目錄樹裡 `.repo-path` 那一行）。**但那是有退路的，退路仍然吃 cwd**：`.repo-path` 讀不到時退回不帶 `-C` 的裸指令，靠呼叫當下的工作目錄解析，而這一路的失敗被靜默吞掉，不會有任何訊息。退路不是理論上的——舊版 `prepare` 建出來、當時還沒有 `.repo-path` 的執行目錄就會走到它。

### prompt 尺寸門檻的兩道檢查

主要攔截點在 `prepare`：每寫出一個平台的 prompt 檔就當場檢查，超標即以結束碼 `1` 失敗退出，此時還沒有任何 herdr tab 或 pane 被建立。`launch` 那一道原樣保留當第二道防線，真正會走到它的是舊版 `prepare` 準備出來、當時還沒有那道檢查的執行目錄；**落在那一道時的後果因平台而異，claude 改成一段式之後這兩路要分開讀**。走兩段式的 codex、opencode、agy 三家維持原本的形狀：尺寸檢查夾在 `agent start` 與 `agent prompt` 之間，所以那一格的 agent 已經起來、但一個字的 prompt 都不會收到，整次執行隨即中止，那一格是個空轉的殼。claude 反過來：契約檔路徑與那句起跑訊號都在同一次 `agent start` 的引數列裡，尺寸檢查排在它之後，所以超標的 claude 契約其實已經完整送達、那句起跑訊號也已經被當成 prompt 消費（實測，見下面契約傳遞方式那一節），那一格是真的開始審查了，腳本才中止整次執行。留下的是一個孤兒：沒有監督行程會去輪詢它的輸出檔，摘要檔不會有它那一行，而且它連腳本那句「已派出、現在沒人監督」的警告都不會被列進去——那一格是在啟動函式內部失敗返回的，還沒被記進已派出清單；同一條失敗清理路徑接著會把 worktree 從它底下移除。

### 四家的契約傳遞方式為什麼不對稱

claude 的審查契約走 `agent start` 的附加型系統提示檔案旗標（`--append-system-prompt-file`，交出去的是一個檔案路徑），而那句固定的起跑訊號也收進同一次 `agent start` 的引數列尾端當位置參數，所以 **claude 是一段式的、完全沒有第二段呼叫**；codex、opencode、agy 三家維持兩段式，契約全文仍以 `herdr agent prompt` 的命令列引數送成第一則使用者訊息。**這個不對稱是刻意的，不是漏改**，理由有兩層，而且第二層比第一層硬。第一層是量測背書：只有 claude 這條路徑做過功能探測，而且是**兩批、測的東西不同，不要讀成同一批**（腳本註解只記了後面那一批，兩處數字對不上不是矛盾）。早先那一批兩次，檔案尺寸各為 53,817 與 71,559 位元組，測的是契約經 `--append-system-prompt-file` 這條檔案路徑傳遞的完整性——頭、中、尾各埋一個隨機標記，三個標記全部正確取回（實測）。本次改動另做了一次端到端探測，檔案尺寸 86,367 位元組，同樣頭中尾各埋隨機標記、三個全部正確取回，並且多量到後半段：那句固定的起跑訊號「開始」確實被當成 prompt 消費、任務跑到完成（實測）。前一批答的是「契約進得去、沒被截斷」，後一批答的是「進去之後那一格真的跑起來並跑完」，合起來才是這條路徑目前的量測背書；另外三家有沒有等價的檔案傳遞途徑、內容送進去之後會不會被截斷或改寫，完全沒有查證過（未查證）。第二層是結構性上限：`herdr agent start` 拒絕任何含換行的 agent 引數（實測，見 `references/limits-operations.md`「第一則 `agent prompt` 會被靜默丟棄」那一條），而審查契約永遠是多行 markdown，所以那三家不是「沒有量測背書換過去」而是換不過去——**這一句取代了舊版只寫第一層的說法，不要再把它讀成一次可以靠補量測翻案的選擇**。claude 逃掉這條，靠的是它送進 `agent start` 的兩個引數都是單行：一個檔案路徑與一句起跑訊號，契約內容本身從來不是引數。

同一個 CLI 另有一個取代型的系統提示檔案旗標（`--system-prompt-file`），**只確認過它存在、從未做過功能探測（未查證），刻意不採用**：取代型會把 claude 自己的預設系統提示整個換掉，那是一次未經量測的行為改變，而附加型已經量到夠用。腳本端有測試把兩件事都鎖住——契約必須以附加型送出，取代型不得出現在啟動引數裡。

### 逐格確認那六處追加為什麼各帶一道防護

派出後那道逐格確認先清空 `.reviewer-confirm-status`、再逐格把結果追加進去，那六處追加現在各帶一道防護：失敗只丟棄結束碼、流程照常往下走，後果因此從「整個 run 當場中止」換成「結果檔缺掉幾行」。**防護是這次補上的，原本沒有，而緊鄰的註解還宣稱那幾處「靜默放棄確認、不影響派出」——那句與事實相反，記在這裡當「註解與行為相反」這類缺陷的實例。** 腳本開頭是 `set -euo pipefail`，`cmd_launch` 對確認函式是一般位置的裸呼叫（不落在 `if`、`while`、`&&`、`||` 任何一種豁免語境裡），所以一次追加失敗不是被靜默放棄，是讓整個 run 停在那一行——而那個時點每個 reviewer 都已經派出、監督行程也已經啟動，正是那個函式自己的說明文字宣稱絕不造成的孤兒狀態，連派出摘要都不會被印出來。實測（bash 5.3.15）：以 `set -euo pipefail` 加裸呼叫重現，第一次追加失敗就中止整支腳本、結束碼非零，那一行之後函式內與呼叫端的敘述完全沒有執行；把同一次呼叫改到 `if` 的條件位置，errexit 被豁免、流程繼續。

**這個缺陷為什麼躲得過既有測試，是另一項要記的實測**：那幾處測試以命令替代（`var="$(...)"`）的形狀呼叫確認函式，而命令替代會另開一個子殼層——子殼層確實繼承 errexit，但迴圈本體內失敗的指令不會讓它中止（未開 `inherit_errexit` 時 bash 的既有行為）。所以缺陷版在那種呼叫形狀下照樣全部通過、子殼層結束碼還是零，這一類問題根本測不出來；改成真正裸露的呼叫才重現得出來（實測，同一個 bash 版本）。**教訓不限於這一次**：測試搭建的執行條件與真實呼叫端的執行條件不同時，斷言再多也照不到那個差異底下的行為——這裡差的只是呼叫形狀，照不到的卻是「整支腳本會不會當場中止」。

防護補上之後，追加失敗成了派出摘要缺狀態欄位的第二條成因，它與第一條的缺席範圍及辨識訊號都不同，記在 `references/limits-operations.md` 兩類宿主平台那一條。

### 為什麼 `blocked` 要當成一輪等待的結束條件

互動模式帶進來一個無頭模式沒有的失效模式——卡在核准對話框的 reviewer 會一直等下去，而能回答的只有人，main agent 不代答。沒有這一條，一個 `blocked` 的 reviewer 會安靜地把兩小時死線吃完。它結束的只有這一輪，不是整場等待。

「已回報過的那一格離開了 `blocked`」不在 `wait` 那五個返回條件裡，事件發生的當下沒有取樣，所以重新武裝釘在既有的取樣點（下一次心跳或嚴格檢查）上。「中間有沒有離開過」這一問答不出來，也不必答——取樣看到的現值不是 `blocked` 就夠。

### 5 秒與喚醒次數

喚醒次數大致等於實際派出的 reviewer 數量加上心跳次數，再加上收尾那一次，不是每 5 秒醒一次；5 秒只決定「某個訊號出現」到「main agent 看到它」之間最多差幾秒，而 review 本身以分鐘計，這個粒度夠用。摘要檔由背景監督行程建立，與腳本印出摘要之間有極短的競態，所以檔案還不存在時當成零行。

### 死線為什麼是總量、心跳為什麼錨定派出時刻

若每輪各給兩小時，四個 reviewer 依序完成的最壞情況會疊成八小時，兩小時的上界就形同虛設。心跳若改成「從上一次事件起算 15 分鐘」，某個 reviewer 提早在第 7 分鐘完成、那一輪提早結束，下一次心跳就落在第 22 分鐘，之後第三輪到底是第幾分鐘就說不準了；錨定在派出時刻，`minute=` 永遠是距派出時刻的 15 分鐘倍數，第 45 分鐘起的嚴格檢查因此有固定的起點。但它不保證連續：下一個心跳點是每次呼叫開始時才取的，兩次呼叫之間跨過的倍數不補發，所以嚴格檢查以 `minute>=45` 判斷、不以收到第幾次心跳判斷，跳號不影響它。

**這兩個時點為什麼改由腳本自算**：舊版要編排端自己把派出時刻加兩小時、加 15 分鐘的倍數算成 epoch，以 `--deadline-at` 與 `--heartbeat-at` 傳給 `wait`，卻沒有任何地方以 epoch 提供派出時刻。編排端手上唯一帶時間的東西是執行目錄名稱，那段時間戳由 `date -u +%Y%m%d%H%M%S` 產生、本身不帶時區標記；在 CST +0800 的主機上它被當成本地時間解析，派出時刻因此算早了 8 小時，`wait` 一呼叫就以 `event=deadline` 返回——一個看起來完全正常、其實是假的訊號。修法是把時間運算整段收回腳本：`launch` 在派出第一個 reviewer 之前把派出時刻（epoch 秒）寫進 `logs/.dispatched-at`，`wait` 從那裡讀回、自己算死線與下一個心跳，編排端只帶使用者同意延長的累計分鐘數。寫入失敗屬致命，那個時點還沒有任何 reviewer 被派出；那個檔已經存在時（同一個執行目錄重跑 `launch`）`launch` 以 `2` 拒絕、不做任何清理，不覆寫既有的派出時刻。讀不到或內容不是 1 到 12 位純數字時 `wait` 以 `2` 拒絕而不退回其他時間來源，因為手邊能退回的正是出事的那一個（執行目錄名稱），或是落在 reviewer 寫得到的執行目錄根層的檔案。

**放在 `logs/` 而不是執行目錄根層，是因為根層 reviewer 自始至終寫得到**（見 `references/limits-exposure.md`「執行目錄根層沒有上鎖」那一條）：放在那裡，任何一格 reviewer 都能改寫它。改寫的後果有三個方向：往後推，死線與心跳都可能形同關閉；拉早，造成假的 `deadline`；寫壞，之後每一次 `wait` 都以 `2` 結束。`logs/` 在整個派工迴圈結束後才被 `chmod -R a-w` 鎖住，但這只是同一使用者身分下的第二層防線，不是絕對保證：上鎖之前它仍可寫，而那段時窗不是幾秒——claude 一建好就開始審查，它那一格的派送又必然等滿 herdr 的預設就緒時限（現行不指定時限，`herdr agent start --help` 寫明預設 30000 毫秒；四分五十九秒那筆實測是時限還設成五分鐘上限時量的，見下面「`run` 返回前要等多久：量測與推算」與「就緒等待時限現在不指定」那兩段），所以上鎖成功的那一次，派送期間至少有這麼一段時間它照樣寫得到；最壞上界是四家各吃一次預設時限（推斷：由逐格依序派送推得，沒有量過這段時窗本身）；上鎖失敗時腳本只往標準錯誤印一行警告、照樣繼續跑，整場都可寫；而鎖與被鎖者是同一個使用者，擁有者把權限位元改回去就能寫（見 `references/limits-exposure.md`「CLI 自身的權限機制都保證不了唯讀」那一條）。

### 為什麼完全不讀 pane 畫面

pane 裡沒有標準輸出與標準錯誤的分流，讀 pane 就是把外部可控的 review 全文引進 main agent 的 context，正是這整套設計要關掉的注入管道；`terminal_title` 與 `terminal_title_stripped` 是同一條管道的窄版。輸出檔那四項射程內的觀測不把外部可控文字帶進 context，所以與這條禁令不衝突，而完成判準那三項少了它就答不出來。

**畫面那一側現在腳本自己也不再據以判斷**（它到底碰到多少、強度確切到哪裡，見下一段，不要停在這一句）。舊版在 `launch` 送出 prompt 之前會對每個 pane 讀畫面最多兩次（第一次讀到空的就等一秒再讀一次，兩次都空才判失敗），那道守衛已經移除、而且刻意不復原：它攔得下的只有完全沒有渲染出任何內容的 pane，而真正要防的那個競態落在「啟動橫幅已經渲染」之後，非空檢查看不到那個窗口（見 `references/limits-operations.md`「第一則 `agent prompt` 會被靜默丟棄」那一條，那裡也寫明了為什麼復原它補不起來）。它當初縮小的那個缺口本身仍然存在：`agent start` 自己回報的成功與 `agent_status` 都不可信（實測過三次：畫面停在登入選單或未核准的對話框上，狀態欄位照樣回報就緒或完成）。現在接手縮小它的是兩道只據狀態判斷、不把畫面衍生文字帶到腳本輸出上的機制——派出後那道逐格確認，與 `wait` 的 `stalled` 事件（見 `references/limits-operations.md` 兩類宿主平台那一條）。縮小而沒有關閉，而且要照方向讀：上面那三次量測的假陽性是把停住的一格報成就緒或完成，那個方向下這兩道都讀不到 `working`、會如實記成尚未確認（推斷：由那三次量測的值與確認步驟的判準推得）；反過來把停住的一格誤報成 `working` 會不會發生，沒有量過（未查證）。

**「腳本自己不讀畫面」這句要照實際強度講，不要抬高一階。** 畫面衍生的文字確實會進到腳本行程一次：派出後那道逐格確認用的 `herdr agent wait`，成功時回的 JSON 本體帶著 `terminal_title` 與 `terminal_title_stripped`（實測），也就是那一格畫面上的模型輸出。腳本把整份 body 收進一個變數，成功那一路從不列印、也不解析，只讀那次呼叫的結束狀態；只有失敗那一路才解析，而失敗回的是錯誤碼形狀的 body、不帶模型輸出（實測），解析它是安全的。所以擋住這條的是刻意丟棄，不是根本沒碰到——日後任何一次「順手把那份 body 印出來當診斷」的改動就足以破掉它，改的人不會收到任何警告。仍然原樣成立的是另外半句：畫面內容沒有被留存成任何檔案。

無頭那個年代靠「標準輸出裝模型輸出、標準錯誤裝 CLI 自己的訊息」把風險切開，pane 裡兩股輸出是混的，切不開，所以那條切分連同它未經實測的但書一起消失，取而代之的是「完全不讀畫面」這條更硬的規則。

**這條禁令只靠自律，而兩側的查證程度不同，不要併成一句讀。** 檔案那一側是完整查證過的：本倉庫的權限設定 `deny` 清單是空的、`allow` 含全域讀取，唯一與檔案存取有關的 hook 只掛在 `Edit` 與 `Write`、攔不到讀取，所以沒有一條機制攔得住 main agent 直接把輸出檔讀進來。pane 指令那一側只能說到這裡：權限設定沒有任何一條規則點名拒絕這類指令；另有一條掛在所有 Bash 呼叫上的 hook，它實際拒絕什麼未查證，因此不當成保護計入。兩側合起來，這條禁令目前只靠 `SKILL.md` 的那段指示撐著。

### pane 為什麼逐格關、tab 為什麼還是整個判

沒產出完整輸出檔的 reviewer 其 pane 不能關，因為純標準輸出的 log 檔已經不存在，失敗的錯誤訊息只在那個畫面上——**這一句原樣成立，而它現在支撐的是另一條結論**：它不再是「所以整個 tab 都要留著」的理由，而是「所以那一格不關」的理由；tab 這一層仍然整個判，因為關 tab 會把裡面的 pane 一起帶走，只要還有一格沒被關掉，tab 就不能關。

被推翻的是不做部分關閉那個理由。舊版寫的是「在使用者正在閱讀的時候抽掉幾格會讓版面在眼前跳動，換來的整齊很有限」；現在監督行程確實逐格關——每個 reviewer 被記進摘要之後，先確認它那則 comment 真的在 PR 上，確認得到才關它那一格。翻掉那個取捨的是關閉憑據的性質：確認用的是 PR 上那則 comment 的本文與該 reviewer 自己輸出檔的逐位元組相符（`posted-no-output` 那一路沒有輸出檔可比，退成回音室標記加揭露段落的歸屬判定），所以被收掉的畫面必定是「內容已經安全落在 PR 上」的那一格，而不是靠 reviewer 自述跑完了就關。版面跳動這個代價照舊要付，是明知才選的：換到的是舊設計拿不到的兩件事——沒人看顧的 pane 不會一路累積到收尾，以及一個編排端本來完全觀測不到的張貼證據（`.pane-close-status` 裡那一行 `pane_closed=yes`）。

**確認一次就收手在結構上就可能每一次都輸，重試是為此補上的。** 契約規定 reviewer 先把輸出檔寫完整、讀回核對，最後才呼叫 `gh pr comment`，而監督行程每秒輪詢、一讀到完整輸出檔就立刻確認一次——兩個時點的先後是被契約自己的順序釘住的，那一次確認排在張貼之前，所以逐位元組那條路徑可能每一次都落空、記一行確認不到就再也不看，pane 於是關不掉。**這個結論的憑據是兩份靜態材料的合讀，不是時序量測（推斷）**：其一是程式碼——舊形狀的待處理迴圈每秒一輪，一擷取到完整輸出檔就確認一次並把那個 CLI 移出集合，沒有第二次機會；其二是審查契約明文規定的順序——先寫完輸出檔、讀回核對，最後才呼叫 `gh` 張貼。兩者合起來足以推出第一次確認必然早於張貼，但**沒有人對真實 reviewer 做過時序量測**。日後要把它升成實測，量的是同一格 reviewer 上三個時刻的先後：監督行程那次確認發出的時刻、那一格 `gh pr comment` 開始的時刻、以及它返回的時刻。現在那一路改成每五秒重試，從該 CLI 進入待關閉狀態起算滿兩分鐘才放棄，並寫下與其他失敗原因分開的 `confirm-timed-out`，好讓讀狀態檔的人分得出「執行結束時還在試」與「試過了、逾時放棄」。兩個間隔都是推理值不是量測值：五秒短到常見情形一兩次就追得上、又不至於變成每秒一次的 `gh` 用量問題；兩分鐘寬到蓋得住一次檔案讀回加一次網路往返，又不至於讓一個真的沒貼成功的 reviewer 把整場執行拖著重試到最後。**孤兒那一路刻意不重試**：它是先在 PR 上找到 comment 才走過來的，沒有時間差要追，重試只會多打 `gh`。

**重試換來的代價是收尾的形狀變了。** worktree 的移除若改成等關閉佇列清空，一格卡在重試就會把 worktree 與整次執行看得見的完成訊號一起押上兩分鐘，而「那一格關不關得掉」與「這份 review 做完了沒有」根本無關。所以移除仍然只看待處理集合清空，監督行程接著繼續空轉、只跑關閉重試，直到佇列清完才結束——後果是它可能在 worktree 已經不見之後還活著一小段時間，收尾那一查會看到一個仍存活的行程編號，那不是異常。摘要行則完全不受這道重試影響，輸出檔一完整就寫出。

**這條路上每一道失敗都只記檔、不升級**，理由不在它接在哪一段輪詢後面（那個位置關係已經被上一段的重試改動換掉，以上一段為準：逐位元組那條路徑的關閉走自己的佇列，而 worktree 在待處理集合一清空就移除），而在它跑在哪個行程裡：每一次關閉嘗試都發生在監督行程那個背景子殼層內，那個子殼層繼承這支腳本的 `set -euo pipefail`，又同時扛著逐格記錄與 worktree 移除，**所以一格關不掉的失敗若真的以非零收場、而且呼叫點又不落在 `set -e` 的豁免語境裡，整個子殼層會當場中止**——等於拿所有 reviewer 的收尾去賭一次 `herdr pane close`。**成因因此有兩層，只記一層會與下一句自相矛盾**：其一是呼叫點的形狀——目前兩個呼叫點都落在豁免語境（一個尾隨 `|| true`，一個在 `if` 的條件位置），所以非零回傳本身中止不了任何東西；其二是前三道守衛沒過與 `herdr pane close` 自己失敗都把錯誤吞掉、往 `.pane-close-status` 追加一行原因就回報成功。**正因為呼叫點在豁免語境裡，第四道（comment 確認）在逐位元組模式下才能一行都不寫、直接回傳非零，把定案交給重試迴圈**——它每一次未確認都真的回傳非零，一次都沒有中止過任何東西；本檔前面記過同一個教訓（呼叫形狀決定 `set -e` 會不會生效），這裡用同一把尺，只有兩分鐘到期時才由那個迴圈寫下逾時那一行——這正是「剛落地的那一格可能還沒有它那一行」的由來，缺行的兩種語意見 `references/closing.md`。守衛裡「那個識別碼不得等於 `HERDR_PANE_ID` 或 `HERDR_TAB_ID`」那一道排在任何網路往返之前，為的是不讓一次 `gh` 或 PR 識別的失敗，成為擋在「關掉編排端自己那一格」之前的唯一一道。**但那一道吃一個沒有被驗過的前提**：它比的是那兩個環境變數的值，而腳本的環境閘門只驗 `HERDR_ENV` 恰為 `1`，從未確認那兩個變數非空；任一為空時比對不會命中，「關不掉編排端自己」這道保護就等於不存在。實務上 herdr 會把這兩個值注入每一格 pane（本檔上面那段環境量測就是在真實 pane 裡直接印出來的），所以這是前提而不是缺陷——射程止於這個前提成立的環境。

五項守衛之外還要提醒使用者切過去看終局訊息，理由仍是保留條件蓋不到全部，**但缺口的形狀被逐格關換掉了，要照新形狀讀**。契約裡會留下完整輸出檔卻沒有發布的路徑分兩類——因內容可能不可信而刻意扣下的兩條（讀不回來而未經核對、第二次核對時必過項有不符），以及讀回核對沒有停下、只是沒發出去的兩條（PR 識別沒拿到、發布失敗）——這四條現在反而被保住了：沒有發布就確認不到，那一格不會被關，警告留在畫面上。真正蓋不到的換成另一種——那則 comment 確認得到、因而那一格被關掉，而畫面上還有一段只印在那裡的說明。**照契約會讓錯誤內容流到 PR 上的形態也不只一種**：讀回核對只有必過項會擋發布，自查項（清單以契約「輸出前自查」節為準，這裡不逐項列）重寫一次後仍不符照樣發布，理由見下面「讀回核對為什麼分成必過項與自查項」；標記之上有內容而那不是這次那份 review 的那一種，契約以必過項（兩個標記之間含這次判出的每則 finding）要 reviewer 自己擋下，但那是它自己的判斷，腳本的完成判準認不出來；標記出現第二處那一種則已經被完成判準的唯一性那一項攔下來了。凡是貼得出去的，貼出去之後照樣通得過逐位元組比對、那一格照關。**時點也比以前早**：以前那段說明至少留到 main agent 決定關 tab 為止，現在是那則 comment 一被確認就關，使用者未必來得及看到。這才是逐格關真正的代價，比版面跳動嚴重，換到的是每一次關閉都有憑據；收尾時那句提醒因此只對剩下的那幾格有效。

### tab 的 root pane 為什麼建完就關，代價是什麼

建 tab 之後為每個選定的 CLI 各切一格，tab 自己的 root pane 原本刻意留著閒置——選三家就是四格，其中一格從頭到尾沒有東西會跑。現在所有 pane 都切完之後就關掉它，選三家就是三格。時點釘在切割全部完成之後，因為到那時每一格的環境與工作目錄都已經由自己那次切割定案，沒有任何東西還依賴 root pane 建 tab 當下帶的那組 `--env`；**不要為了省一格而改成「把 root pane 直接當成某一家的 pane 用」**，那會讓 `--env` 的組裝多出第二個落點，而環境設定邏輯散成兩份要付什麼代價，這份檔案別處已經有直接的教訓。關失敗只往標準錯誤印一行警告、讓建 pane 那一段照常成功返回：那個時點 N 格 reviewer pane 都已經建好而且正確，為一格裝飾性的殘留把它們整批丟掉、逼呼叫端從頭再跑一次，代價完全不成比例。

**這一節原本寫的代價是「root 讓出的空間被它在切割樹上唯一的鄰居吸走、第一家因此約為別家兩倍、N 格不再等大」，那是一個從未被量測過的推論，已經被實測推翻，不要再沿用。** 實際量到的是整個剩餘佈局重新撐開、填滿整個 tab：以與腳本相同的形狀與比例建一個 tab（三家 CLI 的情境——root 先以保留 0.25 往下切，再以 0.6667 往右切，再以 0.5 往下切，共四格），關掉 root 前後各量一次每一格的可視行數，關閉前 root 七行、三格 reviewer pane 分別是十一行、二十三行、十行，關閉後那三格分別變成十五行、三十二行、十五行（實測）。**三格全部變大，沒有任何一格維持原狀**，所以「某一格獨吞」與「其餘 N-1 格維持原樣」兩句都不成立。

**這次量不到的是另一半：N 格最後是不是仍然等大（未查證）。** 那三格的行數彼此本來就不同，因為其中一刀是往右切，而行數量不到寬度那一軸；查單一 pane 的那個子命令只回得到可視行數、拿不到欄寬，查佈局的那個子命令又不接受 pane 識別碼當引數，所以這組數據撐不到面積層。行數的形狀與「比例表本來就讓三格等分、關掉 root 只是整體等比放大」相容，但那是從局部數據推的，不是量到的。要把這一句升成實測，需要的是每一格的實際寬與高，而目前這組子命令給不出寬度。

換來的是每次執行不再留下一格永遠空著的 pane。關掉 root pane 之後 tab 與其餘每一格原樣存活、同一個 tab 裡正在跑的 reviewer agent 不受影響，這一項對真實 herdr pane 實測過。

### 貼了 PR 卻沒有輸出檔的 reviewer 為什麼要另外收斂

舊行為只認輸出檔，所以這種 reviewer 永遠留在待處理集合裡：摘要檔永遠少一行、worktree 永遠不會被移除、監督行程永遠不會結束。這不是假想形態——實際發生過一次，那一格貼出了完整的 review 而 `review.md` 從頭到尾不存在，監督行程在它早該收斂之後一個半小時還在輪詢。

現在監督行程對還沒有輸出檔的 CLI 每六十秒查一次 PR，找得到一則歸屬得了它的 comment 就記進摘要、並走與正常完成同一套關 pane 流程。三件事要一起記：

- **歸屬是啟發式的，所以另外釘了一道時間界線**：判準是 comment 本文第一行逐字是回音室標記，而且揭露段落裡點名這個 CLI 的那一行不同時點名其他已知 CLI（找不到那一行時才退回掃整個揭露區塊，範圍更寬、更容易誤判）。**這兩個判準在不同次執行之間完全不變**——同一支腳本貼出去的 comment 一律帶同一個標記，同一家 CLI 的揭露行也一律讀起來一樣——所以光靠它們分不出「這一次那一則」與「上一次留在同一個 PR 上的那一則」，界線正是為了補這一刀而存在的。候選 comment 的建立時間必須不早於本次執行目錄的 `.prepared-at`（`prepare` 在派出任何 reviewer 之前寫的那個時間戳），兩邊都換算成 UTC 紀元秒之後以整數比較，不拿兩種不同形狀的時間去做字串比對。加上界線之後，這條路徑只認得出本次派送之後才出現的 comment，前次執行留下的舊 comment 不會被誤算（實測雙向驗過：把時間戳設在該 PR 上三則既有 comment 之前，三個 cli 全部判定通過；設在之後，三個全部落空）。**界線一失效就判成無法確認，不退回沒有界線的比對**：`.prepared-at` 讀不到或解析不了就直接回報確認不到，某則 comment 的建立時間解析不出來就跳過那一則。方向與這整條鏈上每一道守衛一致，理由是兩種錯的代價不對稱——放行錯了會關掉一格還在工作的 reviewer 的畫面，不放行錯了只是那一格晚一點被收掉。`ready` 那一路從頭就不吃這條，它比的是與輸出檔逐位元組相符，兩次執行的 review 內容本來就不會相同。
- **這三項認得出「有人在本次派送之後貼了一則長成這樣的 comment」，認不出「是不是這一格 reviewer 貼的」**——那是同一個弱點的另一半，時間界線補掉的只有何時那一半。標記是固定而且公開的，揭露段落的格式寫在契約裡，時間界線只界定何時、不界定何人；**能滿足這三項的身分包含每一個 reviewer 自己**，契約本來就授權它呼叫 `gh` 張貼，而被審查的 diff 與 issue 是本檔開頭就承認的注入管道。三層後果要一起讀：那一格的 pane 會被關掉，而關閉不可逆、畫面又是失敗訊息唯一的所在；摘要多出一行，而它的內容檔取自 PR 上的外部文字，不是腳本從 reviewer 自己的輸出檔切出來的；該 CLI 移出待處理集合之後 worktree 就可能被移除，還在讀程式碼的 reviewer 腳下會被抽走。**沒有機制補得上何人那一半**，所以 `pane_closed=yes` 的強度要分兩路讀：`ready` 那一路是內容相符的硬證據（比的就是內容本身），孤兒這一路只是歸屬啟發式。
- **摘要上必須分得出來**，所以這一種寫的是 `posted-no-output` 而不是 `ready`：兩個值保證的東西剛好相反——`ready` 說的是本地輸出檔完整、說不出貼了沒，`posted-no-output` 說的是 PR 上確實有那一則、說不出本地留下了什麼。併成一個值會讓讀摘要的人以為兩件事都知道。
- **六十秒是推理值不是量測值**：最壞情況是每分鐘四次 `gh pr view`（每個還沒交出輸出檔的 CLI 各一次），換到的是那則 comment 落地之後約一分鐘內收斂，對照它要修的那次「一個半小時後才被發現」。

### `herdr agent start` 回報失敗之後為什麼還要再查一次

舊行為把非零結束碼直接當成致命失敗、中止整批派送。實際發生的是另一回事：herdr 回報的是就緒偵測逾時，而那個 agent 其實已經起來、拿到了完整的 prompt、審完並把 review 貼上了 PR；腳本卻印出與事實相反的訊息、刪掉那個 reviewer 正在讀的 worktree，留下一格沒有人追蹤的 pane 和一則不在任何摘要裡的 PR 留言——上一節那個收斂機制要接住的就是同一次事故。

根因是那個結束碼的語意比它被當成的意思窄：`herdr agent start --help` 自己寫的是 `--timeout` 界定「互動式就緒」，不是行程存活（實測），所以非零只證明 herdr 在時限內沒確認到就緒，證明不了那一格什麼都沒有。現在失敗之後先問一個更窄的問題——herdr 有沒有在那一格列出 agent（任何狀態都算，包含 `blocked`：停在核准對話框上的 reviewer 同樣是一個會被刪 worktree 傷到的活行程）——列得出來就視為已啟動、繼續正常派送與監督，只有明確查到零筆才走失敗路徑。**查詢本身失敗或結果無法解析時一律保守視為已啟動**：兩個方向的誤判代價不對稱，誤判成空會重演上面那次事故，誤判成有只是讓一次真正的派送失敗晚一步被發現，而派出後那道逐格確認仍然會把它記成尚未確認。因此「宣告失敗卻留下一個查得到的活 reviewer」這條路不再走得到。**證得了的界線要照實講**：零筆只說查詢當下那一格沒有登記中的 agent，不等於它從來沒起來過，所以失敗清理的前提是查詢當下查無 agent，而不是「確實什麼都沒起來」。

**就緒等待時限現在不指定，四家一律吃 herdr 自己的預設值。** 中間曾經有一版把四家都明確指定成 300000 毫秒、也就是那個二進位允許的上限（`--help` 逐字寫出 `default: 30000; max: 300000` 仍然是實測，只是它已經不再是腳本的選擇依據），**那一版的理由已經被端對端實跑推翻，就地記在這裡免得再被加回去**：當時的推理是「提高上限對快啟動的 CLI 沒有代價、只對慢啟動的情境有幫助」。前半對走兩段式的 codex、opencode、agy 依然成立——它們啟動時不帶任何 prompt，一起來就落回輸入等待狀態，幾秒內即被判定就緒，時限給多少對它們沒有差別。後半對 claude 是錯的：它走一次性啟動，審查契約與起跑訊號都在同一道啟動指令的引數列裡，所以它一被起來就立刻開始工作，herdr 等不到它回到可接受輸入的就緒狀態——**這不是「有時候需要更久」，而是結構上永遠不會被判定就緒**，時限給多長就吃多長，拉長買不到任何機率提升，只會讓同一個必然的逾時結論晚到。

量測方式與數據（實測）：把修好的腳本對一個真實 PR 端對端跑一次，事後讀執行目錄裡各檔案的建立時間戳——前置作業完成 17:07:14，claude 派送完成 17:12:15（四分五十九秒，當時時限還設在那個上限上），opencode 17:12:18、agy 17:12:22（各三到四秒）。**真正讓派送活下來的從來不是時限，而是上一段那道實況查核**：原始那次事故就發生在預設時限底下，而當時 herdr 早已把 agent 登記進去，可見實況查核的前提在預設值底下就已經成立。那次事故的逾時是不是預設值造成的仍未查證，這一條不主張它。

### 每一格都 `ready` 與「worktree 沒被移除」為什麼可以同時成立

reviewer 那幾行的 worktree 狀態是在移除**之前**就算完的，而腳本兩條清理路徑的移除都被 `|| true` 吞掉、失敗後直接往下跑，中間沒有任何檢查。於是每個 reviewer 都 `ready`，worktree 卻還在。這條路不必靠任何竄改就走得到：`.repo-path` 讀不到而退回裸指令、裸指令又失敗，結果一樣。

刪除前一律 `chmod -R u+w` 的代價是解鎖，解鎖是為了刪除才付的；刪除沒發生，代價就不該留著，所以要把鎖補回去。

### 為什麼本地分支用強制刪除

敢用強制刪除的底氣在於：這個分支的內容完全等於 GitHub 上那個 PR 的 head，本地沒有任何獨有 commit，刪掉隨時 fetch 得回來。至於為什麼不改用一般刪除，理由與代價都寫在腳本裡 `cleanup` 那條路徑上負責刪分支那個函式（`_cleanup_delete_branch`）的說明文字中，此處不複述。分支名與目標 repo 一律由那個函式自己從執行目錄與 `.repo-path` 推導，編排端不組分支名、也不下刪除指令。

**改用 `.repo-path` 當來源是一次明確的轉變，要記下來免得日後被當成漏改**：規則層舊版明文禁止從執行目錄根層的 `.repo-path` 讀目標 repo 來下這條刪除指令，理由是那個檔落在 reviewer 寫得到的那一層（見 `references/limits-exposure.md`「執行目錄根層沒有上鎖」那一條）。舊禁令針對的形狀是 main agent 自己組分支名、自己下破壞性指令：名字與 repo 兩端都可能被誤導，所以 repo 那一端當時釘在「呼叫 `prepare` 當下自己記下的那個路徑」，記不到就不刪。收進腳本之後名字改由腳本從執行目錄自己的路徑推導、竄改者選不到，剩下可被竄改的只有 repo 那一端，殘餘射程有多大、為什麼小，記在 `references/limits-exposure.md`「執行目錄根層沒有上鎖」那一條裡。

刪不成的情形至少有三種：main agent 被中斷、沒能走到收尾這一步；走到了收尾也呼叫了 `cleanup`，但 worktree 還在而 git 擋下這次刪除（逾時退出通常是這一種）；以及 `cleanup` 推導不出要刪哪一個分支——`.repo-path` 讀不到、或它指到的不是 git repo、或執行目錄路徑裡的 PR 編號與尾端後綴不是純數字——這時那一行印出理由、什麼都不刪，絕不退回不帶 `-C` 的裸指令，也不去列同形狀的分支挑一個。worktree 還留著的那幾種，由下一次針對同一個 PR 的執行回收那個陳舊 worktree 時，以同一套推導一併刪掉該次的分支（移除 worktree 失敗而退回直接刪目錄時，會先清掉殘留的 worktree 登記再刪，所以同樣刪得掉）；其餘要再對那個執行目錄呼叫一次 `cleanup`。別次執行不會順手刪它。

**為什麼拿掉了 repo 範圍的陳舊分支掃描**：舊版每次建 worktree 前，會強制刪除 repo 裡所有形狀為 `pr-review-<數字>-<數字>`、未被 checkout、尾端行程編號已不存在的分支。那個行程編號是 `prepare` 的，而 `prepare` 與 `launch` 拆成兩階段之後，`prepare` 一返回它就不存在了，存活檢查因此形同虛設：另一次審查（同一個 PR 或別的 PR 都一樣）在 reviewer 全部完成、監督行程已移除 worktree、還沒呼叫 `cleanup` 的那段時間裡，它的分支會被這次執行強制刪掉，對方的 `cleanup` 之後只能回報分支刪除失敗。實際撞到過：兩個平行開發的 agent 在同一個 repo 跑交叉審查，後啟動的那一個在派出前那道同意閘門裡發現會刪掉前一個正在等收尾的分支，只好等對方收完再跑。那道閘門本身也是成本——每一次派出前都得列分支、可能停下來問人，而它擋的全是這道掃描製造出來的風險，包括使用者自己同形狀的分支會被刪。改成「誰建的誰刪」之後掃描與閘門一起拿掉；代價是殘留不再被任何一次執行順手掃掉，所以每一條會留下分支的路徑都要自己收（`cleanup`、失敗清理、回收同 PR 陳舊 worktree 時一併刪）。

### 狀態投影指令的欄位形狀與輸出對照

欄位形狀是對真實二進位的實測：條目本身就帶 `pane_id` 與 `agent_status`（同一份欄位清單裡另有 `terminal_title`、`terminal_title_stripped` 等承載模型輸出的欄位，所以整份拿回來看才是問題所在），只投影狀態欄位時回傳的確實只有狀態值、比對不到時回傳的確實是 `unknown`——後兩點是對真實二進位跑前一版投影量到的。現行這一版的輸出對照是以 jq 1.8.2 對構造的回應實測：比對到而狀態為 `working`、`blocked`、`idle`、`done` 時原樣輸出；`agents` 是陣列而裡面沒有這個 pane（含空陣列）時輸出 `unknown`；同一個 pane 有多筆時取第一筆；陣列裡的 null 元素會被略過、其餘照常比對（`[null,{"pane_id":"P1","agent_status":"idle"}]` 輸出 `idle`）。回應結構與預期不符時一律沒有任何輸出：`result` 缺漏，`agents` 缺漏、改名、為 null 或物件，頂層是陣列，陣列裡混著字串、數字這類既非物件也非 null 的元素（jq 報錯、結束碼 5），比對到的那一筆 `agent_status` 缺漏或不是非空字串（改名、null、false、數字、陣列、物件、空字串）；回應為空或不是 JSON 時同樣沒有輸出。改成這一版的理由：前一版把結構變形與「這一格沒被比對到」一起壓成 `unknown`，`agents` 是物件或 `agent_status` 不是字串時還會輸出假的狀態值（實測：前者輸出 `working`，`agent_status` 為 `3` 時輸出 `3`），結構變形因此永遠走不到 `SKILL.md`「整條指令沒有輸出」那條查詢失效處置。現行這一版也對真實二進位量過（實測：2026-09-29，herdr 0.9.1 加 jq 1.8.2）：`.result.agents` 的型別是陣列；查一格真實存在的 pane 輸出 `working`，查不存在的 pane 識別碼輸出 `unknown`；當時清單上觀測到的 `agent_status` 值只有 `done`、`idle`、`working`。

### 為什麼比對 `pane_id` 而不是 agent 名稱

agent 名稱是腳本自己從 pane 識別碼雜湊出來的，摘要上印的只有 pane 識別碼、沒有它，要拿它比對就得先自己把同一道雜湊重算一次，而 `pane_id` 就是摘要上那個值本身、直接比對不必推導；何況那道雜湊只保證整個名稱唯一、不保證前綴唯一，省掉重算而改比 `<cli>-` 這個前綴就會落回一種撞名。**這條撞名的兩半查證程度不同，不要併成一句讀**：並行條件在這台機器上真實存在過是實測——當時的流程進行期間，`herdr agent list` 上同時有另一個 session 對別的 PR 派出的 claude，兩邊的 agent 名稱都以同一個前綴開頭；至於腳本那一側照前綴比再取第一筆時真的讀到過別次執行那一格、真的沖掉過本次的計時，沒有人觀測到那次誤讀發生，是從選取邏輯推得的推斷（照前綴比對再取第一筆，而清單順序不受本次執行控制）。腳本現已改成以派工當下落檔的 pane 識別碼精確比對。

### `unknown` 第二種成因：症狀、形成條件與查證程度

`SKILL.md` 把第二種成因（腳本那一側讀不到 `.pane-<cli>` 落檔）列為要知道的限制、不是判準，依據如下。它對編排端的可觀察症狀不是沉默：那一格從此不再產生 `blocked`，`stalled` 卻照常產生——腳本那一側對它一律讀成 `unknown`，`unknown` 不在 `stalled` 的排除項裡，而 `.last-working-<cli>` 在派出時就已寫入，所以計時滿 300 秒就以 `stalled` 返回；照規則帶進 `--reported-stalled`、重新武裝之後，還會再次以 `stalled` 返回（讀腳本得出，沒有實際跑過）。落檔的讀回只發生在腳本那一側的逐格狀態函式，編排端那條投影指令的 pane 識別碼取自派出摘要、不經過那個落檔，所以這種情形下腳本那一側會失明，而編排端自取仍會拿到真實狀態——但兩邊對不上這件事編排端觀測不到，它手上沒有腳本那一側的逐格值可比；它因此呈現為一格反覆被報 `stalled`、自取卻讀得到真實狀態的 reviewer，不會把自己偽裝成「agent 消失」。若照第一種處理，會把一個還活著的 reviewer 誤報成消失，還跟著告訴使用者「這一路最後靠死線收場」。

**一次正常派出的執行落不進第二種**：派工當下那次落檔失敗屬致命、整次派出會中止；落得進去的是對修正前版本建立的執行目錄執行等待這類跨版本情形（推斷：沒有人實際跑過那個跨版本組合；憑據是讀腳本那一段的讀回路徑）。

### 為什麼每次都要自己取樣：時間差與換掉的舊理由

從 `wait` 那次取樣到編排端真正動作之間有時間差，這是由 `wait` 一輪只取一次快照就返回的形狀推得的，這段時間差實際有多長沒有量過。**這條要求的理由換過一次，換掉的那個不要再拿出來用**：舊版寫的是「`wait` 拿 cli 名稱當前綴去比對射程涵蓋整個 herdr 服務的清單，事件可能來自並行執行的另一格」，那條路已經被腳本改以派工當下落檔的 pane 識別碼精確比對封死（推斷：憑據是讀腳本那一段的比對方式，不是對真實二進位跑過同型探測），事件裡的 cli 現在必然是本次那一格。**要求本身沒有跟著失效**：新鮮度與撞名是兩件不同的事，任何輪詢設計都有前者，所以「不會再撞名了」推不出「這次取樣可以省掉」。

## 審查契約條文的成因（出處：2026-09-23 契約精簡）

2026-09-23 那次精簡把 `references/reviewer-contract.md` 從 42,559 bytes 壓到 15,356 bytes，契約只留規則，規則背後的論證移到這一節。各條取材自精簡前那一版契約的原文，改寫成理由敘述。下文所稱「精簡前的實跑」，指同日以 claude 加 agy 對 PR #9 實跑一次，加上 PR #41 未合併時 agy 與 opencode 的兩則實質審查，共四份非空 review（實測）。

### 三個點不可換成兩個點

換成兩個點，分岔點之後 base 上新增的 commit 會混進這次的變更集合；數份 review 各自算出的變更集合一不同，就失去可比性，而且沒有任何徵兆。變更檔清單與分段讀取用的逐檔 diff 也要用同一個 base ref、同樣三個點，否則讀到的是另一個變更集合。commit 清單反過來刻意用兩個點：`log <base ref>..HEAD` 取的是 HEAD 可達而 base 不可達的 commit，正是這個 PR 自己的 commit；`log` 換成三個點會取對稱差，連 base 那一側分岔後的 commit 也列進來，所以不要把它跟 diff 統一成三個點。

### 取清單不用 `--stat` 或 `--numstat`

變更檔清單要的是完整而未經加工的路徑清單，腳本核對覆蓋範圍段時逐字比對它。`--stat` 的輸出經過對齊加工；`--numstat` 要自己剝掉前兩欄數字，還得處理改名時「old 箭頭 new」那種記法。改名那一半是 git 文件記載的行為，精簡前的契約就註明從未實際觸發過（未查證）。

### 放寬 git 查看並要求覆蓋範圍段

舊契約只准一道 `git diff <base ref>...HEAD`，截斷時最多退到逐檔，並禁止寫「讀了哪些材料」。OnrampLab/voice-fusion-frontend 的 PR #743、#744、#745、#753 實際只有 claude 審出東西：`ExperimentDetailPage.test.tsx` 單檔 diff 約 80KB，agy 逐檔也讀不完，只能列缺口而結論仍寫「沒有發現」；codex 在 #744、#745、#753 回「沒有發現」且沒有缺口段，#753 有 223 檔、980KB，它從派出到寫完約 4.5 分鐘，無從判斷是否讀完。同一個大檔在各 commit 只有 100 至 300 行，所以改成讓 reviewer 用唯讀 git 自行逐 commit 或逐檔看，而不是由腳本預先切片段。

自由度提高後，敷衍更不容易從格式上看出來，因此同時要求覆蓋範圍段：reviewer 發布前把它當必過項自核；腳本以派出前寫進 `logs/.changed-files` 的清單獨立核對，結果寫入 `.coverage-status`。這道核對只證明沒漏列也沒多列，「已審」仍是自報。核對結果另存一檔而不寫進 `summary.txt`，是為了不動七欄格式，也不讓覆蓋率牽動關 pane、補貼與收尾。`.coverage-status` 與 `.pane-close-status` 同樣在沒上鎖的執行目錄根層，reviewer 寫得到，不作為防竄改的證據。

不列 git 指令清單是使用者的選擇：「唯讀」由模型判斷。`git gc`、`git worktree prune` 這類會寫入主 repo `.git` 的指令，只靠契約「不寫 `.git` 內部檔」那一條擋。若實測發現 reviewer 仍一次讀整包而讀不完，再另案評估由腳本預先切片段。

### 不得假設權限機制在 reviewer 身上生效

契約的安全邊界與事實依據的禁令都寫成不依賴工具層的行為規則，理由有四：reviewer 看不到呼叫端用哪些旗標、哪一種模式啟動它；為了讓它寫得出輸出檔而放行的寫入工具，射程不是那個檔案，是這個行程碰得到的一切（各家實況見本檔開頭「reviewer 必須寫得出輸出檔」那一節與 `references/limits-exposure.md` 的能力表）；呼叫端在每個 review 行程啟動前後比對 worktree 的 git 狀態，那是事後偵測，擋不下它；網路同理，多數 CLI 的 shell 管道本身就能發出網路請求，「不主動連線」是契約的行為禁令，效力不依賴工具層。

這條邊界比一般 review 禮節硬，有兩個本 skill 專屬的理由：多個 review 行程可能共用同一個 worktree，任何一個寫入，其他行程讀到的就不再是被審查的那份程式碼；reviewer 跑在使用者自己的機器上，而被審查的內容很可能就是使用者自己的 AI 工具設定（本倉庫正是這種）。

### 完成條件為什麼要帶後半句

完成條件是「PR 上有取得完整變更集合後、依選定面向審完的 review」，後半句不可省：一則空洞的 comment 也滿足前半句，而那正是契約要防的失效——貼出去了，PR 作者卻什麼都沒拿到。中止與例外不在完成條件之下，各有自己的終局動作（pane 上的說明、保留檔案不發布）；環境擋下讀寫時不得拿完成任務當理由越過，例如改猜 base ref、換取法湊一份變更集合、或貼一則沒有依據的 comment。

### 面向由六個改為七個，每個變更檔案都要審到

精簡前的清單是六個面向。併發與 race condition 從效能與資源移到正確性與邏輯；新增可維護性與設計；「與材料的符合度」擴大成「需求與文件一致性」，多涵蓋改動之後 repo 內文件、註解與跨檔引用是否仍一致。

逐檔覆蓋的起因是精簡前的實跑出現覆蓋盲區：PR #9 有 8 個 `.claude/agents/prompt-*` 與 prompt-authoring 判準檔的變更，兩家完全沒提，揭露段卻宣稱審過全部面向。精簡前的契約已經寫過這條的理由：一個可以憑感覺啟動的範圍限制聲明，會反過來變成漏審的免責條款。所以缺口段只收確實取不到或無法審的檔案。

### 分級改為類別主軸加升降規則

精簡前的分級是三道依序走的是非題：高風險（會在正常使用路徑上發生，或造成資料遺失、安全漏洞、不可逆的外部影響）判 critical，零風險判 nice-to-have，其餘再依重不重要分 important 與 minor。精簡前的實跑顯示同一個問題被兩家判得天差地遠：「同名重啟未清 `identity_mismatch_since`」agy 判 critical、信心高，opencode 判 minor、信心中；「pane 守衛分支無測試」agy 判 nice-to-have，opencode 判 important；PR #9 兩家各給三則 critical。研判的成因是第一道「會在正常使用路徑上發生嗎」過寬，第二道「零風險」讓缺測試可以落在兩端。

現在改成問題類別決定預設等級：後果落入 critical 定義就升為 critical，寫不出具體失敗情境就降為 minor，站不住就不報，每級附一則範例供校準。失敗情境兩半缺一不可的要求沿用舊版的理由：模型很擅長生成聽起來像 bug 的敘述，而這類敘述在被要求補上觸發條件時多半自己就垮了。會被模型或程式消費的 prompt 定義與設定檔視同程式碼判級，因為它們內容錯了的後果與程式錯了同形，「文件或註解過時」那一格只留給人讀的文件與程式註解。

### 缺漏型的信心尺

一般信心尺以「能不能在 diff 內直接驗證」為主軸，而缺漏型（該有而 diff 沒有）定義上沒有可指的 diff 行，拿同一把尺量會永遠判不到高，而缺漏型正是契約的主力產出。所以另立兩條判高的路：材料明文要求而 diff 查無對應；對應關係在同一份 diff 內查得到而其中一半缺了，例如 diff 新增了行為而同一份 diff 沒有對應測試。後一條不依賴材料，材料不存在時照樣適用。兩者皆非、只依慣例推測的，最高為低。

刻意設計的封頂對缺漏型只在有正面訊號時啟動（材料、PR 內文或程式碼明說不做或說明理由）。光看 diff 幾乎永遠排除不掉「作者是刻意不寫這個測試」，照一般尺「無法排除就封頂」的寫法套下去，上面第二條判高的規則會在它最典型的實例上恆被壓到低，另立這把尺的目的就落空了。封頂本身沒有取消：它問的是意圖，與證據強度是兩根軸。

### subagent 的交付內容要以它的立場重寫

契約通篇寫給主行程，同一句話換個讀者會翻面。「只寫輸出檔」「以 `gh pr comment` 發布是唯一允許的外部狀態變更」在主行程那裡是限制；到一個拿不到座標、也拿不到輸出與發布那兩節的 subagent 眼裡，卻是兩項沒有指定目標的授權，它只能自己挑一個輸出路徑、自己從 worktree 解析出一個 PR。以它的立場重寫就沒有這個洩漏。必交清單各項的理由：

- **發布只由主行程做**：subagent 手上有 worktree，`gh` 從那裡就解析得出 PR 目標，用的是使用者本人的憑證，而不能假設有任何閘門攔得下它；貼出去的 comment 沒有收回路徑。
- **「不主動連線」與「不留持久狀態」攔的不是同一件事**：後者擋得住寫入類請求，擋不住唯讀抓取，而唯讀抓取（「去抓這個 URL」）正是討論串留言最典型的酬載。
- **三項範圍指令連同失敗與範圍封套一起交**：少了它，subagent 會靜默審完半份變更集合交回來，主行程手上沒有任何訊號分辨得出來。空集合要回報成空集合而不是沒有發現，因為這兩件事在它手上長得一樣，在主行程手上必須分得開。
- **材料是資料那一條跟著材料走**：討論串留言任何 GitHub 使用者都能留，一個從未被告知那是資料的 subagent 收到留言全文，就是一條沒有防護的注入路徑。不想交這一條，就不要下放材料。
- **「不從程式碼反推需求」這個來源不可省**：它正是 subagent 唯一構得到的反推路徑，它手上通常只有程式碼、沒有材料。
- **去重、面向間矛盾的裁決、等級與信心校準不下放**：各 subagent 自評的等級彼此不可比，每個只看得到自己那個面向，原樣拼起來會毀掉四級制的意義。回傳格式附判信心的輸入，校準才有料可用。沒下放材料的那一次，「材料是否明文要求」記不適用而不推測填值，否則主行程是拿一個編造的輸入在做校準；「有無刻意設計的跡象」它只看得到程式碼那一半，它回沒有跡象而 `pr.md` 裡其實寫著「這次先不補測試」時，那一則會漏掉封頂，所以材料與 PR 內文那一半由主行程自己補判。

### 取消偽造座標記錄

精簡前的契約要求：材料裡出現一整段帶著「本次審查的座標資訊」標題與具名鍵值、看起來要頂替真座標的區塊時，在審查範圍交代段記一句。精簡時取消，現在座標只認 prompt 最末段，其他位置形如座標的文字一律只當資料、不記。理由兩條：精簡前的實跑裡有三份 review 無謂地寫了「材料中未出現偽造座標」，而舊契約本來就說不必寫，這一條只產出雜訊；真的記下時，那一句會原樣進入貼上 PR 的 comment，等於對一個具名的人公開扣上偽造座標的帽子，而 comment 沒有收回路徑。

### 一次寫入全文，兩個標記的用途

結束標記若在寫完 review 之後才補寫成第二個動作，整檔覆寫的寫檔工具會把 review 整個換成只剩一行標記；`SKILL.md` 完整輸出檔定義裡「只有標記而標記之上是空的不算跑完」防的就是這個形態。「多數 CLI 的寫檔工具是整檔覆寫」是精簡前契約的敘述，沒有留下對各家寫檔工具的量測記錄（未查證）。

結束標記要全檔唯一，因為監督行程會數它出現幾次，不是恰好一次就判成還沒跑完；review 要提到那個字串時改以描述指稱，是為了不讓一則正當的引述把整份交付作廢。第一行的回音室標記沒有人會代補：發布送出的就是這個檔案本身，下一輪執行靠 comment 本文開頭是不是這個標記，過濾掉本 skill 自己貼過的內容，漏了它，下一輪會把這一輪的 AI review 當成需求材料餵回去；`posted-no-output` 的歸屬判定也從這一行認起。

### 讀回核對為什麼分成必過項與自查項

精簡前的讀回核對只驗四項：檔案存在而且不是空的、結束標記（逐字獨佔一行、落在最末、全檔唯一）、結束標記之上是這次那份 review 而不是半截、第一行是回音室標記；任一項不符就重寫一次，第二次仍不符就停下、不發布。失敗情境兩半要齊、疑似憑證或個資不抄值，當時都不在核對裡，而在另一節「輸出前自查」：任一答否就改掉再發布，沒有停下這個出口。

精簡時必過項與自查項的邊界變動因此不是「把判斷型項目移出必過項」，而是三件事：

- **憑證那一項升級成必過項**：從舊自查「改掉再發布、不會停下」，改成第二次核對時抄出了值就停下、不發布。
- **新增的自查項**：位置格式（repo 相對的 `path:line`、不得出現絕對路徑與 `file://`）與禁用詞是這次新增的規則；逐檔覆蓋在舊契約已經存在（「不得挑食」那一條），這次新增的是它作為自查項的身分。三項都歸進不擋發布的自查。逐檔覆蓋後來改由覆蓋範圍段承擔、升為必過項，見「放寬 git 查看並要求覆蓋範圍段」。
- **失敗情境維持原位**：它原本就在舊版的輸出前自查，現在仍是自查項。

其餘舊自查項，除繁體中文那一項仍在自查外，都改由其他條文承擔：兩個標記與內容不是半截本來就同時在舊版讀回核對裡，現在是必過項；讀取範圍、派給 subagent 的必交事項與輸出檔落點比對，分別落在契約的安全邊界、subagent 與寫入各節。

自查項的完整清單以契約「輸出前自查」節為準，本段只講這次變動的部分。歸進自查的理由是：這幾項連錯兩次，不應讓整份 review 無法交付，PR 作者拿到一份有瑕疵的 review 仍勝過什麼都沒拿到。精簡時定下的必過項三項則各有不可逆、或會破壞下游機制的後果（第四項覆蓋範圍段是後來加的，理由見「放寬 git 查看並要求覆蓋範圍段」）：兩個標記是腳本判定完成與過濾回音室的依據；內容不是半截，否則貼出去的是一份 PR 作者分辨不出殘缺的 review；疑似憑證或個資的值一旦貼上 PR，之後即使從 diff 移除那一行，值仍留在留言裡，comment 沒有收回路徑。精簡前讀回核對那四項也都還在必過項裡，檔案非空由「兩個標記之間含揭露段與每則 finding」涵蓋。

代價要一起記：自查項重寫一次後仍不符的內容照樣會貼上 PR（上面逐格關那一節有交代）。停下條件寫成「第二次必過項有不符」而不是「仍有不符」，因為第一次只有自查項不符、重寫後才出現必過項不符的那一種同樣要停下，「仍」字會讓它讀成不適用。停下而留下的檔案標記可能完整，在腳本那一側會判成 `ready` 或 `withheld`；事後補貼因此多了一道使用者確認，見 `references/backfill-posting.md`。

## 產出物位置

產物主要落在使用者家目錄下的暫存目錄中，父層是 repo 名稱加 PR 編號，子層才是本次執行目錄；唯一落在該處之外的，是留在使用者 repo 的那個本地分支。

```text
~/.tmp/<repo 名>-pr-<PR 編號>/<時間戳記>-<行程編號>/
├── worktree/                     # 各 reviewer 共用的程式碼工作區，唯讀，跑完後由監督行程刪除
├── materials/                    # pr.md、issue.md、design.md 的共用來源，寫完即設為唯讀
├── logs/                         # 每個派出的 CLI 各一份 <cli>.prompt，加上 .dispatched-at 與 .changed-files；全部派出後整個目錄設為唯讀
│   ├── .changed-files            # prepare 在派出任何 reviewer 之前寫的變更檔清單（一行一個路徑）；監督行程據它核對每格的覆蓋範圍段
│   └── .dispatched-at            # launch 在派出第一個 reviewer 之前寫的派出時刻（epoch 秒）；已存在時 launch 拒絕重跑；wait 每次呼叫據它自算死線與心跳，缺漏、為空或不是 1 到 12 位純數字即 exit 2
├── reviewers/
│   └── <cli>/
│       ├── workdir/              # pane 的 --cwd，唯一刻意為 reviewer 開放寫入的目錄
│       │   ├── materials/        # 從共用 materials 複製過來，複製後立刻整個設為唯讀
│       │   └── review.md         # 這個 reviewer 的輸出檔，檔尾一行結束標記
│       └── home/                 # pane 的 --env HOME=，隔離家目錄；opencode 的權限設定檔也在這裡
├── .roster                       # prepare 選中的每個 CLI 與其解析到的 model；reviewer 揭露段落的 model 值、launch 的平台核對、wait 每輪的逐格狀態取樣，以及 cleanup 刪執行目錄之前的存活檢查都讀它
├── .prepared-at                  # prepare 建立本目錄當下寫的時間戳；兩處讀它：下次執行判斷本次是否還在陳舊回收的寬限期內，以及孤兒偵測據它排除掉本次派送之前就在 PR 上的 comment
├── .repo-path                    # 目標 repo 的絕對路徑。四處讀內容：spawn_supervisor_interactive 與 _dispatch_failed_cleanup 兩條 worktree 清理路徑、下一次同 PR 執行的 _reap_stale_run_dirs 回收這個陳舊 worktree 時，以及 _cleanup_delete_branch 刪分支那一步（cleanup、失敗清理，以及下一次同 PR 執行回收這個陳舊 worktree 時讀的是這一份），都據此以 git -C 指定 repo；另外 cleanup 開頭以它當執行目錄標記，不可讀就回報 not a pr-review run directory (missing .repo-path)、拒絕執行。cleanup 的兩段式刪除刻意最後才刪它（先刪其餘一切，確認只剩它才連同目錄移除），所以第一次刪除失敗後它通常還在、重跑 cleanup 就能重試；改掉這個刪除順序，刪到一半失敗時就可能先丟了它、下一次 cleanup 落到上面那道拒絕，只能人工清，所以不要改
├── .pr-url                       # 本次審查目標 PR 的位址，prepare 寫一次。launch 在派送任何 reviewer 之前讀一次，同一個值交給 claude 與 codex 的放行規則（派送前就固定，免得先起來的 reviewer 改掉它，見 `references/limits-exposure.md` 執行目錄根層那一條）；監督行程的關閉流程每次嘗試與孤兒偵測都重讀它，去 PR 上查 comment 貼上了沒；補貼路徑也讀它（見 references/backfill-posting.md）
├── .pr-body-raw                  # PR 的原始內文，issue 推導只讀這一份，不讀 materials/pr.md
├── .materials-status             # 本次材料蒐集結果，摘要的材料清單據此印出
├── .git-status-before-<cli>      # 該 reviewer 啟動前的 worktree 狀態快照
├── .reviewer-confirm-status      # 派出後逐格確認的結果，每個 cli 一行；派出摘要那一行的狀態欄位讀它，這裡缺哪個 cli 摘要那一行就不帶欄位——建不出來時整份都缺，逐格追加中途失敗時只剩失敗之前那幾格
├── .pane-<cli>                   # 該 cli 那一格的 pane 識別碼，派出當下寫一次；腳本內三處讀它，另外補貼路徑在跨 session、手上沒有派出摘要時也會讀它（見 references/backfill-posting.md）。腳本內那三處：wait 每輪讀回去，才能在整個 herdr 服務範圍的 agent 清單裡精確認出本次那幾格，關閉流程也讀它，而且是據它對那一格下 herdr pane close，cleanup 刪執行目錄之前的存活檢查也據它向 herdr 查那一格還有沒有 agent
├── .pane-close-status            # 逐格關 pane 的結果，一行一個 cli：pane_closed=yes，或 no 加上沒關成的原因；缺行有兩種意思（沒走到關閉判定，或走到了還沒定案），怎麼讀以 references/closing.md 為準
├── .coverage-status              # 每格覆蓋核對的結果，一行一個 cli，監督行程在寫該 cli 的摘要行之前寫；怎麼讀以 SKILL.md「直連張貼與狀態回報」那張表為準
├── .last-working-<cli>           # 該 cli 停滯計時的基準時間戳（最後一次被讀到工作中或查詢失效的時刻）；派出當下先寫一次當起算基準，wait 每輪讀它判 stalled、讀到工作中或查詢失效就覆寫
├── .comment-body-<cli>.md        # 監督行程從該 reviewer 的輸出檔切出來重組的內文，不是 PR 上那則的逐位元組副本，只供本機稽核（posted-no-output 那一行則是從 PR 抓回的本文）
├── .supervisor.pid               # 監督行程自己的行程編號，供存活檢查
├── .supervisor.log               # 監督行程那個背景子行程自己的標準輸出與標準錯誤
└── summary.txt                   # 每個完成的 reviewer 一行，七個欄位
```

上面只列主要項目，目錄下另有狀態快照等內部檔案。opencode 的權限設定檔是 `reviewers/opencode/home/opencode-permission.json`，跟著它自己的隔離家目錄放，並且要在建立 pane 時就以 `--env OPENCODE_CONFIG=` 指過去。目錄名尾端的唯一後綴是腳本自身的行程編號，用來讓同一秒對同一個 PR 啟動的兩次執行不撞目錄；本地分支尾端的後綴與它是同一個值。

`reviewers/<cli>/workdir` 是這套互動設計的核心目錄：它同時是 herdr pane 的 `--cwd`，也是唯一刻意為 reviewer 開放寫入的地方。材料為什麼要複製一份而不是讓 reviewer 讀共用的那個目錄，理由在跨目錄讀取上：共用材料目錄在 pane 工作目錄之外，而依 `references/limits-exposure.md` 的能力表，opencode 用內建讀取工具跨目錄會撞核准對話框、agy 一律要核准——兩者現在都退居備援（reviewer 那一路的旗標 `--auto` 與 `--dangerously-skip-permissions` 把那道詢問自動答掉了），複製這個做法照舊不變，因為若任一旗標日後失效，那一半會整條重新成立——複製進來就都落在自己的工作目錄底下了。

`.supervisor.log` 是 `launch` 不必等到整場審查結束就能返回的關鍵（它返回之前仍要花掉那道逐格確認的預算，見 `references/limits-operations.md` 兩類宿主平台那一條；這裡講的是它不會被卡到全部 reviewer 都跑完）。監督行程是被 `disown` 的背景子行程，若不重導向就會原樣繼承呼叫端當下的標準輸出與標準錯誤，而管線要等到寫入端全部關閉才會收到 EOF——監督行程卻要等到全部 reviewer 結束才會結束，於是以管線擷取 `launch` 輸出的呼叫會被卡到整場審查結束。落點選在執行目錄根層而不是 `logs/` 底下，是因為 `logs/` 在派送結束後就被設成唯讀，而監督行程在那之後還要持續寫。`.roster` 則是另一回事——它必須在 `prepare` 那一步就寫，因為 reviewer 一旦結束，它當時解析到的 model 名稱就沒有地方查得回來了。

**「跑完了沒有」只有一條判準：輸出檔本身。** 那三項條件與其計數粒度的唯一定義都在 `SKILL.md` 的「回報與張貼」節，這裡一律不複述、以該處為準；粒度之所以要釘死，是因為腳本判的就是那個粒度，兩端不對齊就會對同一個檔案算出相反的答案。這個判準不涉及標準輸出與標準錯誤的緩衝競態，因為根本沒有把這兩股輸出寫進任何檔案——reviewer 的標準輸出就是它 pane 上的畫面，沒有留存。

只要內容切得出來就會留下內容檔，不管 reviewer 貼成功、貼失敗，還是沒有發布。它不是 PR 上那則 comment 的逐位元組副本：開頭比 `review.md` 多一個回音室標記、而且沒有結束標記（形狀見 `references/backfill-posting.md`），只供本機稽核；要與 PR 比對、或拿去補貼的，一律是該 reviewer 的 `review.md`。三種情形共用同一條保留規則比分開處理更難出錯。`no-content` 的那一則不會有這個檔。

執行目錄刻意做成兩層而不是扁平：「補貼走完之前執行目錄原封保留」與「腳本回收陳舊執行目錄底下的 worktree」這兩條，都建立在每次執行各有自己的目錄這個前提上，扁平之後對同一個 PR 再跑一次就會蓋掉上一次保留下來的證據，而需要保留證據的情境——逾時與中斷——恰好正是最可能立刻重跑的情境。父層名稱不帶任何雜湊，代價是兩個同名但不同 remote 的 repo 會混在同一個父層底下，不會互相覆寫。

這裡刻意以家目錄下的絕對路徑定址，不套用暫存檔規則中「先在工作區根目錄建立 `.tmp` 符號連結」那一步。呼叫腳本時的工作目錄是使用者的 repo 工作副本，為跑一次 review 在那個 repo 根目錄留下一個符號連結，是不必要的持久寫入，與整體設計方向相反。

收尾時 prompt 檔、各 reviewer 的工作目錄與輸出檔、切出來的內容檔與摘要檔會隨執行目錄一起刪除：執行目錄是本 skill 自己建的，收尾就由它自己收，不留在磁碟上。**直接收的依據是腳本的張貼確認，不是每一格都 `ready`**：腳本沒有任何一處觀測 `gh pr comment` 的結束碼，每一格都 `ready` 推不出「已經貼上 PR」（見 `SKILL.md` `ready` 那一條）；推得出的是關 pane 前那道 PR 比對，而它**方向只有一邊**：`.pane-close-status` 上的 `pane_closed=yes` 代表那則 comment 當時確實在 PR 上，反過來沒有那一行只代表確認不到，`gh` 查詢自己失敗與根本沒貼共用同一個值（claude 那一格的逾時行另帶 `post=`，能縮小範圍但同樣不是確據，見 `references/closing.md`「pane 定案」）。所以每一格都是 `pane_closed=yes` 時直接收；不是的話先走補貼、再收——執行目錄一刪，補貼就沒有來源了。

**舊版在收之前還有一道停下閘門，要使用者自己去 PR 上確認那幾則在不在，拿掉它是刻意的**：那道閘門讓執行目錄大量殘留——使用者沒有回覆、或流程沒有走回收尾，目錄就永遠留著，而未全綠的那幾種本來就不收。拿掉之前實際觀測到家目錄暫存區累積了三十多個執行目錄，對應的監督行程全都已經結束，其中兩個連 worktree 都還在。代價要記清楚：`.pane-close-status` 落在 reviewer 寫得到的那一層（見 `references/limits-exposure.md`「執行目錄根層沒有上鎖」那一條），一行偽造的 `pane_closed=yes` 就能讓執行目錄在沒有人核對過 PR 的情況下被收掉，連同補貼的資料來源；這是為了不留殘留而接受的取捨。**刪除的條件不只全數確認或補貼走完這一項**：呼叫 `cleanup` 之前還要每一格的關閉結果都已定案，而且關 tab 那次讀檔要排在它之前；完整的條件與順序以 `references/closing.md` 為準，這裡不複述。補貼還沒走完的執行目錄原封保留，**不受「任務結束後主動清除暫存檔」的例行清除約束**，它只由 `cleanup` 收，任務收尾時不要另外刪。worktree 由監督行程自己移除，不需要代勞，但有兩種情形它不會被移除掉：有 reviewer 既沒寫完輸出檔、PR 上也查不到它那則 comment，監督行程還沒走到那一步（只缺輸出檔而 comment 查得到的那一種會被記成 `posted-no-output` 並移出待處理集合，不會卡在這裡）；或走到了而那次移除失敗——失敗被靜默吞掉，流程照常往下跑，所以這一種從摘要檔上看不出來，只能靠查那個目錄還在不在。

腳本把 jq 列為硬性前置需求，缺席會在 `prepare` 的檢查階段直接拒絕執行，早於任何對使用者 repo 的寫入動作——不會出現「jq 缺席才發現，但 repo 已經被動過」的情形。
