# 設計理由與已知限制

本檔是 `pr-review-by-multi-agents` 的理由層。`SKILL.md` 只寫規則，規則為什麼是這樣、外部 CLI 的實際行為量測結果、被否決過的替代方案都記在這裡。

執行流程時不需要載入本檔。什麼時候該打開它，以 `SKILL.md` 的 Reference 載入時機表那一列為準，這裡不複述那份症狀清單。

涉及外部 CLI 或 git 實際行為的每一項都標出憑據等級：「實測」指以真實二進位跑過同型探測，「推斷」指從其他已知行為推得、沒有直接量測，「未查證」指沒有測過也推不出來。三者不得互相代換。

## 這套流程的注入面

### reviewer 必須寫得出輸出檔，放行寫入的代價是明知才選的

互動式 reviewer 不再是腳本的子行程，沒有標準輸出可以被切走，交付途徑只剩檔案，所以三家原本關掉的寫入工具是刻意重新打開的。代價是：給 reviewer 寫入能力沒有辦法只給一個目錄——四家 CLI 的路徑範圍機制各不相同（見底下能力表），放行寫入實際上就是放行到這個使用者身分寫得到的範圍。因此「只寫那一個輸出檔」與「讀取一律限於座標資訊給出的那幾個路徑」都只是契約文字，沒有機制在後面擋——後者現在寫成正面白名單而不是列舉禁區，射程涵蓋所有未列出的路徑，但強度不變，仍然只有文字。

這一點值得說白，因為被審查的 diff 與 issue 內容是外部可控、會原樣進入模型 context 的提示注入管道，而這個倉庫審查的正是使用者的 AI 工具設定檔。兩項收斂手段——每個 reviewer 各給一個隔離家目錄、pane 的工作目錄限縮成它自己那一個可寫目錄——都只是提高門檻，不是機制保證。

實質變化是行為門檻消失而不是機制失守：舊狀態下寫檔對 reviewer 而言是契約禁止、工具也不給，一個沒有被注入的模型根本不會往那個方向走；新狀態下寫檔是它的正常動作，注入一句「順便把某段內容寫進某個檔案」與它當下正在做的事沒有任何違和，成功率高得多。對 codex、opencode、agy 三家，殘留風險受各自的路徑範圍機制所限，量級與 claude 不同，不要套用同一句話。

### 哪幾段路徑上沒有 AI，哪幾段有

切內容、判斷可不可信這一步留在監督行程，因為它是 shell 子行程而不是 AI agent，跑的是固定指令、沒有注入風險；它只認腳本當初指定的那個輸出檔路徑，絕不解析 reviewer 自己印出來的路徑。

合流那一步不同，它必須讀懂 review 的內容才做得了比對與去重，只能交給 AI agent。它不需要 worktree（輪到它跑時 worktree 已經被刪了），產出一樣只走標準輸出、由監督行程從一組起訖標記之間切出來，拿的是各 CLI 給得出的最窄授權——但「最窄」有多窄因 CLI 而異（見底下合流授權那一條）。注入文字有可能原樣穿過 review 落到合流行程手上，這一點無法消除。

真正決定要不要貼的雖然是 main agent 這個 AI agent，但它讀的只是摘要檔裡的結構化欄位，review 內容本身不會經由這條路徑進入它的 context。**射程只到這條路徑為止，不是整體保證**：review 全文另有兩條進得來的通道——pane 畫面，以及輸出檔與監督行程從它切出來的各份內容檔（含合流那一份）——關掉它們的是 `SKILL.md` 那條禁令，而那是一項要求，沒有機制在後面擋。這道區隔還以摘要檔沒有被動過手腳為前提，而那個前提不是機制保證（見底下執行目錄根層那一條）。

委派 `github-manager` 張貼時交出去的是內容檔的絕對路徑，並要求以檔案張貼、不讀進來重打。這項要求降低了、但沒有消滅注入面：`github-manager` 本身具備 Read 工具，沒有任何權限機制阻止它把這個檔案讀進自己的 context。

### 為什麼不由模型轉述兩份契約

兩份契約的全文都由腳本原文嵌入對應行程的 prompt。改成由模型轉述後，四個嚴重度等級的界線會在轉述中糊掉，數份 review 失去可比性，而合流那一端的信心重算整套建立在那些等級與檔位對得起來的前提上，前提一垮，重算出來的值就沒有意義。

## 各節規則的成因

### 為什麼把 herdr 環境確認前移到平台選擇之前

判定依據就在呼叫端自己的環境變數裡，不呼叫腳本也答得出來。照原本的順序走，使用者會先被問完一整輪平台勾選，才在呼叫腳本那一刻撞上結束碼 `4`——那是他當下無論怎麼選都改不掉的拒絕。前移省掉的是那一輪白問，不接手把關：呼叫端可能根本沒走這一步，環境也可能在這裡與呼叫腳本之間變掉。

### 平台選擇改成單選選單

harness 的提問元件沒有「預先勾選」這個狀態（選項只有標題與說明兩個欄位），所以改用單選達到同樣的一次按鍵通過。四個選項的順序依使用者當初指定並已釘死於 `SKILL.md`，每次執行照那個固定順序列出，不重新徵詢要什麼順序。

被這次改動取代的舊規則要記下來，免得日後被當成遺漏：舊版是逐平台自由勾選、三個標示為預設，並且**無論使用者是否已經在觸發語句裡指名平台都要列出清單取得確認**。取代它的是「已指名就不列選單，只在指名的平台中有缺席者時才停下詢問」，代價是使用者指名時若記錯平台名，會晚一步才發現。舊版另有一個沒被寫進去的缺口：規則沒有規定「使用者什麼都不選時該怎麼辦」，實際使用中出現過 main agent 回報「你什麼都沒選」並重新盤點可用平台的浪費，新規則第二條就是補這個。

frontmatter 原本明列「由單一 agent 執行的審查」不觸發本 skill，與選項 3 直接矛盾，因此併寫成「未指名跨平台交叉審查的一般 code review 請求」不觸發——觸發門檻管的是使用者的意圖，不是最後派出幾家。

### 為什麼旗標值不得含換行

`prepare` 的解析結果是以四行 `key=value` 交回主流程的，值裡的換行可以在其中偽造出一行 `clis=`，把實際派送的平台整組換掉。

### 為什麼腳本拆成 prepare 與 launch 兩階段

中間夾著一段只有 main agent 做得到的工作——依版面配置建立 herdr 的 tab 與 pane。拆開換來三件事：pane 的工作目錄從一開始就是對的，不必在 pane 裡送 `cd` 去搶 shell 提示符的時序；前置檢查失敗發生在任何 pane 存在之前，不會留下一排空 pane 要收拾；準備了卻沒有啟動的那一次留下的殘骸落在陳舊 worktree 回收的涵蓋範圍內。

### 建立 tab 為什麼要指定 workspace

`herdr tab create` 的落點預設由 UI 焦點決定，不是由呼叫端所在的位置決定，所以那一步一定要帶 `--workspace`。以下都是對真實 herdr 二進位（0.8.2）的量測。

`tab create --help` 的簽章確有 `--workspace` 這個選項，值是 workspace ID（實測）。省略它時，tab 落在當下 UI 焦點所在的 workspace（實測）：把 caller context 的三個環境變數 `HERDR_WORKSPACE_ID`、`HERDR_TAB_ID`、`HERDR_PANE_ID` 全部偽造成另一個 workspace 的值再呼叫，tab 仍然落在當時焦點所在的那個 workspace，可見這個子命令根本不讀 caller context——換句話說，落點錯掉時沒有任何呼叫端能設定的環境訊號救得回來。帶 `--workspace` 指向呼叫端自己的 workspace 時落點正確（實測）：探測當時焦點在別的 workspace，tab 仍落在呼叫端這一邊。

`HERDR_WORKSPACE_ID` 確實存在於真實 herdr pane 的環境裡（實測：在一個 herdr pane 中直接印出環境，得到 `HERDR_ENV=1`、`HERDR_PANE_ID=w2E:p1`、`HERDR_TAB_ID=w2E:t1`、`HERDR_WORKSPACE_ID=w2E`，另有 `HERDR_SOCKET_PATH` 與 `HERDR_BIN_PATH`；workspace 那一個的值與該 pane 實際所屬的 workspace 相符），與環境閘門讀的 `HERDR_ENV`、收尾守衛讀的 `HERDR_TAB_ID` 同屬 herdr 注入每個 pane 的 caller context。本 repo 內另外兩處記錄列的變數組都不含它，**不要拿它們當作這個變數不存在的證據**：倉庫根層的 `hooks/herdr-agent-state.sh` 只檢查它自己要用的那三個（`HERDR_ENV`、`HERDR_SOCKET_PATH`、`HERDR_PANE_ID`），本 skill 的 `scripts/run-review.sh` 那段註解記的是當初為 `HERDR_ENV` 那道閘門一併確認到的幾個，兩處都不是窮舉。

**因此不為它加空值守衛，也不把它併進 `HERDR_ENV` 那道閘門**：那個變數若真的是空字串，herdr 當場以 `workspace_not_found` 失敗、結束碼 `1`（實測），不會靜默改落到別處。**這個論證吃 `SKILL.md` 第二階段那條失敗出口**——`tab create` 失敗一律停下回報、不得拿掉 `--workspace` 重試。有那條出口在，守衛只是把同一個停下點提早到呼叫之前，買不到額外的保護；少了它，守衛也補不上缺口，因為守衛判的是空值，判不了那次重試——ID 解不到那一種，拿掉旗標的重試會成功（推斷；實測只到上面那兩點，整個 workspace 相關失敗類別沒有量測），而它成功之後只是安靜地落錯 workspace。

`pane split` 不在這個問題的射程內（實測）：它帶的是明確的 pane ID，而那個 ID 取自 `tab create` 的 JSON 回應——焦點位於另一個 workspace（`w2F`）時對指名的 `w2E:pC` 下切割，回傳的新 pane 是 `w2E:pD`，tab 與 workspace 都跟著被切的那個 pane 走。整段流程裡會被焦點牽著走的只有 `tab create` 這一處。

### 陳舊執行目錄的三層判準與 600 秒寬限期

「什麼算陳舊」因為這次拆分而改成三層，要照這個順序讀：該執行目錄下的 `.supervisor.pid` 指向存活行程時**絕不回收**；`.supervisor.pid` 在而那個行程已死，判為陳舊、可回收；連 `.supervisor.pid` 都還沒有時，改看 `.prepared-at` 這個時間戳，落在 600 秒寬限期內的不回收，超過寬限期、或根本沒有 `.prepared-at`（舊版留下的執行目錄），才落回原本「目錄名尾端行程編號是否存活」的檢查。

三層各守各的，不要混：進行中的審查不論跑多久都是第一層在擋。中間那層寬限期覆蓋的是另一段完全不同的時間——`prepare` 返回到 `.supervisor.pid` 被寫出之間那段空窗，也就是人在建 herdr tab 與 pane、加上 `launch` 逐 CLI 派送的那幾分鐘。那段空窗裡執行目錄兩種訊號都給不出來：`.supervisor.pid` 還沒有，而目錄名尾端那個 `prepare` 的行程編號已經死了，舊判準會把一次即將開跑的執行判成陳舊，把它的 worktree 從底下移除掉。所以 600 秒是照建 pane 那段空窗定的，不是照審查全長定的。

回收掃的是本次執行目錄的同層目錄，而執行目錄的父層是 repo 名加 PR 編號，所以只有下一次針對**同一個 PR** 的執行才清得到它。執行目錄本身不在回收範圍內：那個機制只刪陳舊執行目錄底下的 worktree 子目錄。

### 合流工作目錄落點：一個被否決的替代方案

`launch` 要在目標 repo 內呼叫，是因為合流在 claude 與 agy 兩家沒有任何工作目錄旗標，繼承的就是呼叫當下的工作目錄。被否決的替代方案是讓監督行程在啟動合流之前切到 `base_dir`。技術上做得到——腳本舊的無頭 reviewer 路徑對 claude 就是這樣處理的（啟動前 `cd`、啟動後還原），只是那個函式現在已經沒有生產呼叫者、僅留給測試與交叉引用。否決的理由不是做不到，而是那屬於腳本的行為變更，尚待決定。

腳本自己的 worktree 清理已經不再是那條契約的理由：`launch` 那兩條會移除 worktree 的路徑都先讀 `prepare` 寫在執行目錄根層的 `.repo-path`，讀得到才以 `git -C` 指定要動哪一個 repo。**但那是有退路的，退路仍然吃 cwd**：`.repo-path` 讀不到時退回不帶 `-C` 的裸指令，靠呼叫當下的工作目錄解析，而這一路的失敗被靜默吞掉，不會有任何訊息。退路不是理論上的——舊版 `prepare` 建出來、當時還沒有 `.repo-path` 的執行目錄就會走到它。

### prompt 尺寸門檻的兩道檢查

主要攔截點在 `prepare`：每寫出一個平台的 prompt 檔就當場檢查，超標即以結束碼 `1` 失敗退出，此時還沒有任何 herdr tab 或 pane 被建立。`launch` 那一道原樣保留當第二道防線，真正會走到它的是舊版 `prepare` 準備出來、當時還沒有那道檢查的執行目錄；落在那一道時，那一格的 agent 已經起來、但不會收到任何 prompt，整次執行中止。

### 為什麼 `blocked` 要當成一輪等待的結束條件

互動模式帶進來一個無頭模式沒有的失效模式——卡在核准對話框的 reviewer 會一直等下去，而能回答的只有人，main agent 不代答。沒有這一條，一個 `blocked` 的 reviewer 會安靜地把兩小時死線吃完。它結束的只有這一輪，不是整場等待。

「已回報過的那一格離開了 `blocked`」不在背景等待指令的四個返回條件裡，事件發生的當下沒有取樣，所以重新武裝釘在既有的取樣點（下一次心跳或嚴格檢查）上。「中間有沒有離開過」這一問答不出來，也不必答——取樣看到的現值不是 `blocked` 就夠。

### 5 秒與喚醒次數

喚醒次數大致等於實際派出的 reviewer 數量加上心跳次數，再加上合流那一次與收尾那一次，不是每 5 秒醒一次；5 秒只決定「某個訊號出現」到「main agent 看到它」之間最多差幾秒，review 與合流本身都以分鐘計，這個粒度夠用。摘要檔由背景監督行程建立，與腳本印出摘要之間有極短的競態，所以檔案還不存在時當成零行。

### 死線為什麼是總量、心跳為什麼錨定派出時刻

若每輪各給兩小時，四個 reviewer 加上合流依序完成的最壞情況會疊成十小時，兩小時的上界就形同虛設。心跳若改成「從上一次事件起算 15 分鐘」，某個 reviewer 提早在第 7 分鐘完成、那一輪提早結束，下一次心跳就落在第 22 分鐘，之後第三輪到底是第幾分鐘就說不準了；錨定在派出時刻，第三輪永遠等於第 45 分鐘。

### 為什麼完全不讀 pane 畫面

pane 裡沒有標準輸出與標準錯誤的分流，讀 pane 就是把外部可控的 review 全文引進 main agent 的 context，正是這整套設計要關掉的注入管道；`terminal_title` 與 `terminal_title_stripped` 是同一條管道的窄版。輸出檔那四項射程內的觀測不把外部可控文字帶進 context，所以與這條禁令不衝突，而完成判準那三項少了它就答不出來。

畫面那一側唯一的例外是腳本自己：`launch` 階段在送出 prompt 之前會對每個 pane 讀畫面，最多兩次——第一次讀到空的就等一秒再讀一次，兩次都空才判失敗，因為剛啟動時讀到空是已知的無害渲染時序。那是 shell 行程在讀，讀到的內容只用來判斷是不是空的，沒有任何 AI 看到它。**這道檢查買到什麼要照它的實際射程讀**：它攔得下的只有完全沒有渲染出任何內容的 pane；停在登入選單或未核准對話框上的那兩種攔不下來，因為那兩種畫面必然不是空的，照樣通過。它把 `agent start` 自己回報的成功與 `agent_status` 不可信（實測過三次：畫面停在登入選單或未核准的對話框上，狀態欄位照樣回報就緒或完成）留下的缺口縮小了，但沒有關閉。除此之外沒有第二個讀畫面的地方，畫面內容也沒有被留存成任何檔案。

無頭那個年代靠「標準輸出裝模型輸出、標準錯誤裝 CLI 自己的訊息」把風險切開，pane 裡兩股輸出是混的，切不開，所以那條切分連同它未經實測的但書一起消失，取而代之的是「完全不讀畫面」這條更硬的規則。

**這條禁令是要求不是保證，而兩側的查證程度不同，不要併成一句讀。** 檔案那一側是完整查證過的：本倉庫的權限設定 `deny` 清單是空的、`allow` 含全域讀取，唯一與檔案存取有關的 hook 只掛在 `Edit` 與 `Write`、攔不到讀取，所以沒有一條機制攔得住 main agent 直接把輸出檔讀進來。pane 指令那一側只能說到這裡：權限設定沒有任何一條規則點名拒絕這類指令；另有一條掛在所有 Bash 呼叫上的 hook，它實際拒絕什麼未查證，因此不當成保護計入。兩側合起來，這條禁令目前只靠 `SKILL.md` 的那段指示撐著。

### 為什麼 tab 只能整個關或整個留

沒產出完整輸出檔的 reviewer 其 pane 不能關，因為純標準輸出的 log 檔已經不存在，失敗的錯誤訊息只在那個畫面上；而關 tab 會把裡面的 pane 一起帶走。不做部分關閉，是因為在使用者正在閱讀的時候抽掉幾格會讓版面在眼前跳動，換來的整齊很有限。

四項守衛之外還要提醒使用者切過去看終局訊息，理由是保留條件蓋不到全部：契約有兩條路徑（核對做不到、重寫那一次被拒）會留下一個監督行程判得為完整、因而照樣被貼出去的輸出檔，同時把唯一的警告只印在畫面上。契約自己載明會讓錯誤內容流到 PR 上的只剩一種形態（標記之上有內容，而那不是這次那份 review），標記出現第二處那一種已經被完成判準的唯一性那一項攔下來了；這種一格既不算失敗、tab 照關，訊息就跟著沒了。

### 全綠與「worktree 沒被移除」為什麼可以同時成立

reviewer 那幾行的 worktree 狀態是在移除**之前**就算完的，而腳本兩條清理路徑的移除都被 `|| true` 吞掉、失敗後直接往下跑合流，中間沒有任何檢查。於是每個 reviewer 都 `ready`、該貼的那一則也貼成功，worktree 卻還在。這條路不必靠任何竄改就走得到：`.repo-path` 讀不到而退回裸指令、裸指令又失敗，結果一樣。

刪除前一律 `chmod -R u+w` 的代價是解鎖，解鎖是為了刪除才付的；刪除沒發生，代價就不該留著，所以要把鎖補回去。

### 為什麼本地分支用強制刪除

敢用強制刪除的底氣在於：這個分支的內容完全等於 GitHub 上那個 PR 的 head，本地沒有任何獨有 commit，刪掉隨時 fetch 得回來。至於為什麼不改用一般刪除，`SKILL.md` 已寫，此處不複述；只補它沒寫的那一半代價——拖到下一次執行才被清掉的期間，那些殘留會落進派出前那道要使用者一一同意的清單裡，變成他每次都要看過一遍的雜訊。

刪不成而留到下一次執行的情形至少有三種：main agent 被中斷、沒能走到收尾這一步；走到了收尾，但 worktree 還在而 git 擋下這次刪除（逾時退出通常是這一種）；以及走到了收尾，但組不出分支名或記不到 repo 路徑而依規定不刪。

### 回音室標記的第二個用途

`<!-- pr-review-by-multi-agents -->` 除了過濾回音室之外，讓事後補貼時有東西可以核對。刻意不做獨立的 slash command 參數或模式，`references/backfill-posting.md` 那份指引就夠；代價是這條路徑得使用者主動開口。

### 單則張貼的代價

舊版逐則貼，逾時或 session 被中斷時已經貼出去的那幾則還在；改成單則之後，只要「該貼的那一則」沒被貼出去，PR 上就是一則都沒有——派兩個以上平台時卡在合流沒跑到，只派一個平台時沒有合流這一步，卡的是那份原始 review 沒被貼，兩種路徑的損失同樣是全部。這是選擇「一則彙整過的 comment」這個格式的必然代價，不是設計缺陷——不可能同時要求跨平台比對過的單一結論、又要求每份跑完就立刻可見。

## 已知限制

互動模式與無頭模式是兩組不同的量測條件，多項結論方向相反，所以底下這些量測不能拿去套用在合流那一路（它仍是無頭執行），反之亦然——凡是兩路都提到的，各自標明是哪一路。要重新確認只能對真實二進位重跑同型探測，讀腳本或官方說明推不回來。

### 四個平台在互動 reviewer 那一路的能力現況

要查某個平台在某一面向上是什麼狀況，以本表為準；底下各條補的是後果與處置，不重寫表裡的事實。

| 面向 | claude | codex | opencode | agy |
| --- | --- | --- | --- | --- |
| 檔案寫入的路徑範圍 | 工作目錄內放行；**`auto` 模式下對工作目錄之外的寫入行為本身未經量測**（未查證），唯一測過的路徑範圍樣本不是這個模式 | `workspace-write` 沙箱限定在工作目錄加 `/tmp`、`$TMPDIR`，目錄外跳核准對話框（實測） | 工作目錄內放行；內建寫入工具寫到目錄外會跳「Access external directory」核准對話框（實測）；經 Bash 重導向寫到目錄外未測（未查證） | 目錄內外都要核准，差別只在目錄外那個對話框多一行 workspace 提示與一個永久放行選項（實測） |

### 逐條限制

- **CLI 自身的權限機制都保證不了唯讀，那幾個位置靠 chmod 守，而 chmod 守得比字面上弱**：腳本以 `chmod` 鎖住 worktree、共用材料目錄、每個 reviewer 自己那份材料副本與 log 目錄，各 CLI 自身的旗標與沙箱降級為第一層，只負責限制模型會去嘗試的動作範圍，不是唯讀承諾的依據。兩個缺口要認得。其一，reviewer 與腳本跑在同一個使用者身分底下，那些檔案的擁有者就是它自己，它把權限位元改回去就能寫——四家裡只有 opencode 那份設定檔明文拒絕了 `chmod`，agy 因為預設一律詢問而會讓這類指令撞上核准對話框，claude 與 codex 則沒有任何一條擋它。其二，這幾道鎖的強度並不相同：worktree 那道上不成即中止整次執行（連同 worktree 一起移除、非零結束碼），材料那兩道是靜默盡力（失敗不影響流程，也不會有任何訊息），log 目錄那道失敗只往標準錯誤印一行警告、照樣繼續跑。log 目錄那道鎖是在所有 reviewer 都啟動之後才上，只擋新開檔案；「不擋已經開啟的檔案控制代碼」這個但書在目前的佈局下沒有指涉對象——`logs/` 只剩 `<cli>.prompt`，腳本派送當下讀完即關。下游後果是：要判斷某次 review 有沒有可能動過 worktree，看的是摘要檔那一行的 worktree 狀態比對結果，不是某個 CLI 的權限設定。
- **執行目錄根層沒有上鎖，摘要檔與內容檔就放在 reviewer 寫得到的地方**：上鎖的只有 worktree、材料與 log 那幾處，而 `summary.txt`、各份 `.comment-body-*.md`、`.roster`、`.supervisor.pid`、`.prepared-at`、`.repo-path` 與合流的 prompt 全在執行目錄根層，那一層自始至終可寫；reviewer 的 prompt 裡就有 worktree 與自己工作目錄的絕對路徑，往上一層即是。後果要說白：main agent「只讀結構化欄位」這道區隔，以及「只交出路徑、由 `github-manager` 以檔案張貼」這條保證，實際上都架在一個 reviewer 寫得到的檔案上——寫得到那一層的 reviewer 可以改掉別人那一行的 `content_status`、改掉 `content_file` 指向的內容，或補一整行進去。**那一層還有兩個控制檔，後果與資料面竄改不同類**：`.repo-path` 被改成指向另一個 repo 時，`git worktree remove --force` 以結束碼 128 失敗、訊息是該路徑不是一個工作區，目標目錄完全不被刪除（實測：自建兩個 scratch repo，以不相干的那個去移除另一個 repo 的 worktree；測試套件裡沒有對應斷言，所以這一條會隨 git 行為改版而過時，沒有回歸保護接得住）；而兩條清理路徑都在移除之前無條件跑過 `chmod -R u+w`，所以竄改換來的是 worktree 留著、唯讀保護已被解掉，本地分支也連帶刪不掉。射程僅止於此，不構成對別的 repo 的破壞。`.prepared-at` 那一支更尖銳：把同層某個正處在 `prepare` 與 `launch` 之間的執行目錄的 `.prepared-at` 刪掉，會讓它退回已死的 `prepare` 行程編號檢查而被判為陳舊，於是那個即將開跑的執行的 worktree 被從它底下強制移除；射程限於同層的其他執行，本次自己的目錄在掃描中被排除。**佈局變更後這個風險對三家自然減輕**：pane 的工作目錄現在是每個 reviewer 自己那一個專屬目錄，依上表 codex、opencode、agy 三家寫到工作目錄外都會跳核准對話框，竄改交接帳本因此不再是無聲直寫；**claude 不在此列**，它在 `auto` 模式下對工作目錄之外的寫入沒有量測過，在拿到證據之前這條風險對它保守視為原樣成立。這仍然不是機制保證。不改的理由是結構性的：摘要檔就在那一層而監督行程整場都在寫它，上鎖會直接讓流程停擺。因此這裡的處置是揭露而非承諾——PR 上出現的內容與某份輸出檔對不上、或摘要欄位與輸出檔明顯矛盾時，從這裡查起。
- **純標準輸出的 log 檔消失，失敗 reviewer 的錯誤訊息只存在於畫面上**：reviewer 現在跑在 pane 裡，`logs/` 底下只剩 prompt 檔，沒有 `<CLI>.log` 也沒有標準錯誤檔。契約要求 reviewer 在中止、寫入被拒、核對做不到這幾條路徑上把說明印在自己的 pane 上，而目前沒有任何機制把畫面內容留存成檔案，關掉那格 pane 訊息就永遠消失。這是「任一個 reviewer 沒有完整輸出檔就整個 tab 留著」的全部理由。
- **opencode 每次啟動都會觸發真實網路下載，事後留下約 160MB 磁碟佔用**（實測）：每個新建的 opencode 隔離家目錄第一次啟動時都會向公開 npm registry 發出真實請求。因為本設計是每個 reviewer 各給一個新的隔離家目錄、每次 review 都重新建立，這筆成本與耗時是每次都要付的，不是一次性的；而且這個下載發生在 opencode 自己的任何權限層生效之前。
- **herdr 對 agy 核准對話框的 `blocked` 偵測，可靠性因對話框類型而異**：agy 的「Create file」這一類檔案寫入確認框，兩次實測都沒有被正確回報成 `blocked`（一次 `done`、一次 `idle`，兩次的假陰性值本身還不一致，樣本數 2）；「Requesting permission for: `<command>`」這一類指令核准框則四次全部正確回報 `blocked`。其他類型無法從這兩類的結果類推（未查證）。影響限於失去早期通知——使用者少了一次「有 reviewer 在等你」的即時提醒；但不會造成誤判完成，因為完成判準是輸出檔那三項，對話框沒被核准之前輸出檔根本不存在。而 agy 的互動模式沒有任何等效的逾時旗標（`--print-timeout` 只適用列印模式，實測），卡在對話框就是一直卡著，直到有人回答或死線到期。
- **agy 預設連契約要跑的 `git diff` 都要人工核准**（實測）：它是四家中唯一連契約指令都要問的平台，腳本因此在它的隔離家目錄裡寫入兩條允許規則。agy 的允許規則是逐字比對整條指令字串的字首，pane 的工作目錄改成 reviewer 專屬目錄之後，契約指令實際送出的是 `git -C <worktree 絕對路徑> diff`，`command(git diff)` 這個字首根本不匹配，真正放行它的是另外那條比對帶 `-C` 路徑的規則。把 worktree 路徑一併傳進 `--add-dir` 也取代不了這條規則——那只解決路徑歸不歸屬工作區，不解決指令執行前的字首核准閘門。症狀對照：agy 那一格如果從一開始就停在核准對話框上，先確認這條規則有沒有被寫進去。
- **`--check-clis` 只驗 PATH 存在性**：它對四個 CLI 各跑一次存在性檢查，不含任何認證或可用額度的檢查，所以使用者可能選中一個通過檢查的平台，卻在派送之後才因未認證或額度不足而失敗。herdr 不在這道檢查的範圍內，但另有 `HERDR_ENV` 那道閘門管它；那道閘門讀的是環境訊號，判得準的只有「呼叫端自己跑在 herdr pane 裡」，不是 `herdr` 這個指令本身可不可用——後者腳本從頭到尾不驗證，缺席會等到建 pane 或 `launch` 起 agent 那一刻才浮現。`--check-clis` 刻意不受那道閘門約束：閘門存在的目的是擋副作用，而這條診斷路徑本來就沒有副作用，擋它防不到任何東西，反而把一個設計成使用者選平台之前就能安全跑的診斷耦合到 herdr 上。腳本端已有測試鎖定這個例外。
- **prompt 以單一命令列引數傳遞，受作業系統單一引數長度上限約束**（實測 131,072 位元組，140,000 已失敗）：`herdr agent prompt` 只接受位置參數形式的文字，沒有檔案輸入或標準輸入旗標。材料移出 prompt 之後尺寸不再隨 PR 大小變動，審查契約本身仍是 prompt 的主要佔比，所以**契約有意義的變動之後要重新量一次**。2026-09-04 對定稿後的檔案實測（source `run-review.sh` 之後直接呼叫 `build_prompt`，傳入契約路徑與一組座標值）：契約 51,335 bytes，組出的 prompt 51,814 bytes（契約加上實際量到的座標段 479 bytes），佔腳本 100,000 檢查門檻的 51.8%，餘裕 48,186 bytes。對照本次改動開工時（同日）對 main 版契約的實測：prompt 97,939 bytes、97.9%、餘裕僅 2,061 bytes——當時「契約再成長就會讓每一次審查被擋下，不論 PR 大小」確實成立，精簡買到的就是這段餘裕。**重量的時機要釘在最後一次編輯之後**：光是這個檔案家族，就有三組數字在寫下之後被下一輪改動推翻，所以上面那條不是客套話。越線是硬失敗而非靜默截斷。門檻本身壓在四家都實測過能完整送達的約 101KB 之下，離作業系統硬上限更遠，所以越線不等於當場毀損。
- **兩項風險收斂手段都是提高門檻而非機制保證**：隔離家目錄擋的是 reviewer 被誘導去寫使用者真實的設定目錄，擋不掉的是——claude、codex、agy 這三家的憑證以符號連結掛進去、方向是雙向可寫，CLI 若在 token 更新時寫回，寫入會直接落到使用者真實的憑證檔上；**opencode 不在此列**，它的隔離家目錄裡一條憑證連結都沒有，代價落在別處，見下一條的 model 敘述；憑證類環境變數照樣穿透；而隔離改變的只是波浪號展開的家目錄解析，寫死絕對路徑的寫入完全穿透。把摘要檔與狀態檔放進 reviewer 的 prompt 不會提到的位置，擋的只是「就在隔壁而且路徑已經給你了」這個近便性，屬於模糊化。
- **隔離家目錄只覆寫 `HOME` 一個環境變數，而 `.roster` 記的 model 與 pane 裡實際跑的 model 不保證一致**：建立 pane 時只帶 `HOME`（opencode 另帶一個設定檔路徑），其餘環境原樣繼承，`GEMINI_API_KEY`、`CLAUDE_CONFIG_DIR` 這類變數會直接穿透到 pane 裡的行程，設了這類變數的機器上隔離的實際範圍是未知的（未查證）。連帶的一件事要認得：腳本寫進 `.roster`、最後呈現在 comment 開頭揭露段落那組 `platform/model` 裡的 model，讀的是使用者真實的設定檔；而 pane 裡的 CLI 讀的是隔離家目錄，那裡面沒有任何 model 設定。opencode 已實測會因此落到它內建的免費模型，claude 與 codex 在隔離家目錄下實際會落到哪一個 model 未經量測（未查證）。所以揭露段落裡的 model 應該當成「呼叫端這一端解析到的 model」讀，不是「那一格實際跑的 model」。
- **agy 的 model 是破例硬編碼，會隨 Gemini 改版過時**：另外三個 CLI 都能從各自的設定檔讀回預設 model，agy 沒有任何途徑讀得回來（它的 models 子命令不標預設、json 輸出沒有 model 欄位、狀態檔裡也沒有），而 comment 開頭的揭露段落要求每個派出的平台都附一個真實的 model 值，所以腳本破例把它寫死（model 只出現在那段揭露裡，每則 finding 的第三行只寫平台名，不要為了這一條把 model 補回每則 finding）；尾綴 `-high` 是 agy 自己編碼推理力度的方式，也是它不必再傳 `--effort` 的原因。代價是這個值會過時：症狀是 agy 那一格起不來或當場報錯，或揭露段落裡的 model 名稱與實際跑的那個對不上。
- **agy 的工具被自動拒絕時結束碼是零而標準輸出全空，這一條只適用於合流那一路**：無頭模式下 agy 對未列在允許清單裡的工具一律自動拒絕，被拒之後它仍以結束碼零結束、什麼都不印，所以在無頭的 agy 上「結束碼為零」不等於「正常完成」。互動式 reviewer 沒有適用對象——它不是這支腳本的子行程，沒有結束碼可言，而且互動模式下未列入清單的動作呈現為詢問而不是靜默拒絕。但合流那一路仍是無頭執行、仍可能選中 agy 跑：這種執行會呈現為 `exit=0` 配 `content_status=no-content`；要小心的是日後有人改拿結束碼本身當判準，那會把一次全空的執行讀成成功。憑據是實作階段對真實 agy 二進位的實測，腳本註解裡沒有這一條。
- **合流的授權因 CLI 而異，「不給任何工具」只對 claude 完全成立，agy 只關得住網路那一軸**：合流那一路維持無頭執行、旗標不變，所以這組結論整條沿用，不受互動模式那組量測影響。claude 整個停用 `Bash`、允許清單留空——**零工具，已用真實二進位實測**：探測條件與合流實際傳的旗標相同，在臨時目錄裡要求它建立一個檔案，寫入被擋下，而且不是模型自我克制，是工具根本不存在（逐字回覆為 `No such tool available: Write. Write is disabled for this session, in subagents as well as here.`），該訊息明載停用範圍涵蓋 subagent，所以「改派 subagent 代寫」這條旁路一併封住。agy 的允許清單寫成空的，而它在無頭模式下對指令、取網址與未沙箱三類本來就預設拒絕——**那三類為零，但檔案寫入不為零**，兩半要分開讀：前半是它網路面確實關著的依據，也是合流優先挑它跑的理由；後半是實測結論而非待查證的推斷，agy 的寫入工具根本不經過它的權限層。而合流這一路比 reviewer 那一路更沒有兜底，落點還比敘述過的更寬——它是等 worktree 被刪除之後才跑的，而 agy 這一支沒有帶任何工作目錄旗標（有的只有 codex 的 `-C` 與 opencode 的 `--dir`），繼承的是呼叫 `launch` 當下的工作目錄，依呼叫端契約那就是**使用者的 repo 工作副本**。釘住不等於安全：那裡沒有任何一層鎖，比執行目錄根層更敏感，agy 的隔離家目錄底下還把使用者的真實憑證檔以符號連結掛著；而契約背後沒有執行機制，沒被遵守時落點就變成呼叫端當下所在的任何目錄。claude 這一支同樣沒有目錄旗標、落點相同，差別在它是零工具、根本寫不出東西。codex 走的仍是 `-s read-only` 沙箱：那個模式只限制本地檔案系統寫入，shell 照常可用、網路照樣通，也沒有更緊的旗標可加——**仍有 shell 與網路，已用真實二進位實測**：一次真實的 `codex exec -s read-only` 執行，要它跑一道 curl 打本機的監聽埠，請求確實有到。opencode 用的是一份只拒絕 `edit` 與 `bash` 兩項工具的設定檔，比 reviewer 那份逐條動詞黑名單緊得多，但它終究是點名兩項的拒絕清單、不是空的允許清單——**比 reviewer 那一路窄，但不是零；這一句是推斷**，憑據是那份設定檔逐字只點名兩項，那兩項以外的工具面沒有被實測探過。合流的 CLI 選取規則正是為這個不對稱而設。
- **GitHub 側沒有任何機制層級的保證，只有契約文字**（推斷：沒有人實際從 reviewer 那一格試過對 GitHub 發寫入請求，這一條是從能力表那幾項實測結果推得的）：reviewer 不需要也不應該執行任何 GitHub 指令，契約也明文禁止它動 GitHub。但依上表，claude 在 `auto` 模式下 shell 直接放行，所以若被審查的 diff 或 issue 內容成功誘導模型主動去執行 GitHub 寫入操作，旗標層沒有任何機制擋得下它；唯一的屏障是那需要網路與使用者自己的 gh 憑證，而本腳本對這兩者沒有做任何隔離。worktree 狀態比對補不上這裡，它只涵蓋檔案系統。PR 狀態或既有留言出現非預期異動時，從這裡查起。
- **remote 名稱假設為 origin**：腳本只驗證當前工作目錄的 `origin` 是否對應到目標 PR 所屬的 repo，不符即拒絕執行，不會改試其他 remote 名稱。慣用 origin 以外名稱指向 GitHub 的使用者會直接被拒絕。
- **腳本會寫入使用者當前的 repo**：六項寫入裡有五項落在使用者當前的 repo 上——fetch 這個 PR 的 base 分支並強制更新對應的遠端追蹤 ref、fetch 這個 PR 的 pull ref、建立一個以 `pr-review-` 開頭並帶 PR 編號與唯一後綴的本地分支、強制刪除形狀為 `pr-review-` 接數字再接數字、兩段皆為純數字的陳舊分支、清理 worktree 殘留登記。第六項橫跨兩處：它移除的是前次執行留下的殘留 worktree 目錄，而那個目錄在家目錄暫存區的前次執行目錄底下、不在 repo 裡，落在 repo 內的只有它連帶清掉的那筆 worktree 登記。上面是清單而不是執行次序（強制刪除排在 pull ref 之前）。第一項的順序要留意：`origin` 身分比對排在解析 base ref 之前執行，就是為了避免「remote 不符而被拒絕執行」的那一次也已經留下副作用。刪除前會逐一驗證兩段確實是純數字，所以只帶同一個前綴、形狀不同的分支（例如 `pr-review-notes`）不會被碰；但使用者若剛好有同形狀的分支，仍會被一併強制刪除，這正是派出前那道同意閘門存在的理由。
- **共用工作區的並發比對可能誤標，誤標與否由 main agent 判讀**：所有 reviewer 共用同一個 worktree，腳本在每個 reviewer 啟動前取一次該 worktree 的 git 狀態快照，監督行程再於該 reviewer 寫完輸出檔後取一次；前後不同即記為 `withheld`。由於多個 reviewer 同時執行、而比對是依序輪詢的，前一個的事後快照可能被還在跑的後一個影響。方向仍然是保守的——寧可漏貼，也不把失去事實依據的內容貼上公開 PR。保證也僅限於此——前後快照的比對擋不住改完又還原：reviewer 若寫入檔案後在自己寫完 review 之前刪掉，或把已追蹤檔案改回位元組相同的內容，兩次快照會相等而判為正常。
- **狀態比對涵蓋被 gitignore 忽略的路徑**：這是刻意的選擇，為的是不讓「違反會被偵測到」這個承諾在被忽略的路徑上落空。代價是某個 CLI 若在工作區內產生自己的快取或暫存檔、而該路徑剛好被忽略，會造成誤報。
- **監督行程沒有自己的逾時，一個永遠不寫完輸出檔的 reviewer 會讓它一直等下去**：它輪詢的是檔案，不是行程；某個 reviewer 卡在對話框或死在 pane 裡而沒有寫完輸出檔時，那個 cli 永遠留在待處理集合裡，於是 worktree 不會被移除、合流不會啟動、摘要檔也不會再長。這正是 main agent 那個兩小時死線存在的理由——它是這條路上唯一的收束機制。「它會一直留著」只在永遠等不到輸出檔時才成立；合流正在跑的那一種不同，那一路自己會走到結束。
- **main agent 逾時或被中斷，之後才跑完的那些沒人張貼**：兩小時死線到期、或使用者中途中斷 session，都會讓之後才產出的東西永遠沒人張貼——監督行程不受影響，仍會照常等 reviewer 寫完、切內容、寫摘要、刪 worktree，該起合流時照樣起，但不再有人讀摘要檔去貼。改成單則張貼之後這件事的代價變大了：唯一要貼的那則排在最後，中斷幾乎必然是一則都沒貼上去。內容檔仍會產生、保留在執行目錄下，需要使用者事後主動要求補貼。
- **codex 與 opencode 上沒有心跳與中途進度，等完才貼**：這兩個平台沒有背景喚醒機制，做不到 Claude Code 上的輪詢、心跳與嚴格檢查。等待期間唯一會浮現的中途訊號是某一格進入 `blocked`；除此之外沒有進度可看，使用者只能等阻塞結束，或自己切到那幾格 pane 上看。agy 那類偵測不到的核准對話框連這個訊號都不會有。
- **合流行程本身可能誤判共識與矛盾**：它只讀各份 review 的文字，沒有 worktree、也沒有 diff——就算這一次落在仍留著 shell 的那一家上，被審查的程式碼也早就不在它手上了。措辭差很多的同一件事可能被拆成兩則，於是獨立平台數少算、信心被壓低；措辭相近的兩件事可能被併成一則，於是平台數多算、信心被抬高；而「一份說有問題、另一份明確說沒問題」也可能被讀成矛盾，或反過來漏成沉默。合流契約用取最高嚴重度、只上調不下修這類規則把誤判方向壓向保守，但壓不掉誤判本身。對某一則存疑時就去翻原始的各份 review——未全綠的執行目錄不會被刪，那幾份內容檔還在。

## 產出物位置

產物主要落在使用者家目錄下的暫存目錄中，父層是 repo 名稱加 PR 編號，子層才是本次執行目錄；唯一落在該處之外的，是留在使用者 repo 的那個本地分支。

```text
~/.tmp/<repo 名>-pr-<PR 編號>/<時間戳記>-<行程編號>/
├── worktree/                     # 各 reviewer 共用的程式碼工作區，唯讀，跑完後由監督行程刪除
├── materials/                    # pr.md、issue.md、design.md 的共用來源，寫完即設為唯讀
├── logs/                         # 只剩每個派出的 CLI 各一份 <cli>.prompt；全部派出後整個目錄設為唯讀
├── reviewers/
│   └── <cli>/
│       ├── workdir/              # pane 的 --cwd，唯一刻意為 reviewer 開放寫入的目錄
│       │   ├── materials/        # 從共用 materials 複製過來，複製後立刻整個設為唯讀
│       │   └── review.md         # 這個 reviewer 的輸出檔，檔尾一行結束標記
│       └── home/                 # pane 的 --env HOME=，隔離家目錄；opencode 的權限設定檔也在這裡
├── synthesis.log                 # 合流行程的標準輸出，另有 synthesis.log.stderr
├── .synthesis-prompt             # 合流行程吃的完整 prompt：合流契約全文、派出名單、各份 review
├── .roster                       # prepare 選中的每個 CLI 與其解析到的 model；合流的揭露段落與 launch 的平台核對都讀它
├── .prepared-at                  # prepare 建立本目錄當下寫的時間戳，下次執行判斷本次是否還在陳舊回收的寬限期內
├── .repo-path                    # 目標 repo 的絕對路徑，launch 那兩條 worktree 清理路徑據此以 git -C 指定 repo
├── .pr-body-raw                  # PR 的原始內文，issue 推導只讀這一份，不讀 materials/pr.md
├── .materials-status             # 本次材料蒐集結果，摘要的材料清單據此印出
├── .git-status-before-<cli>      # 該 reviewer 啟動前的 worktree 狀態快照
├── .comment-body-<cli>.md        # 監督行程從該 reviewer 的輸出檔切出來的 comment 內文
├── .comment-body-synthesis.md    # 合流那一則；派兩個以上平台時正常情況下唯一會貼上 PR 的那一份，只派一個平台那一次不會有這個檔
├── .supervisor.pid               # 監督行程自己的行程編號，供存活檢查
├── .supervisor.log               # 監督行程那個背景子行程自己的標準輸出與標準錯誤
└── summary.txt                   # 每個完成的 reviewer 一行，合流再一行，七個欄位
```

上面只列主要項目，目錄下另有合流行程的結束碼檔與狀態快照檔等內部檔案。兩份 opencode 權限設定檔的位置與檔名都不同，不要混為一談：reviewer 那份是 `reviewers/opencode/home/opencode-permission.json`，跟著它自己的隔離家目錄放，並且要在建立 pane 時就以 `--env OPENCODE_CONFIG=` 指過去；合流那份是執行目錄根層的 `opencode-synthesis-permission.json`。同一個理由，合流若跑在 agy 上，它的隔離家目錄是根層的 `agy-synthesis-home/`，不是 `reviewers/agy/home/` 那一個。目錄名尾端的唯一後綴是腳本自身的行程編號，用來讓同一秒對同一個 PR 啟動的兩次執行不撞目錄；本地分支尾端的後綴與它是同一個值。

`reviewers/<cli>/workdir` 是這套互動設計的核心目錄：它同時是 herdr pane 的 `--cwd`，也是唯一刻意為 reviewer 開放寫入的地方。材料為什麼要複製一份而不是讓 reviewer 讀共用的那個目錄，理由在跨目錄讀取上：共用材料目錄在 pane 工作目錄之外，而依上面的能力表，opencode 用內建讀取工具跨目錄會撞核准對話框、agy 一律要核准，複製進來就都落在自己的工作目錄底下了。

`.supervisor.log` 是 `launch` 能立刻返回的關鍵。監督行程是被 `disown` 的背景子行程，若不重導向就會原樣繼承呼叫端當下的標準輸出與標準錯誤，而管線要等到寫入端全部關閉才會收到 EOF——監督行程卻要等到全部 reviewer 結束、合流也跑完才會結束，於是以管線擷取 `launch` 輸出的呼叫會被卡到整場審查結束。落點選在執行目錄根層而不是 `logs/` 底下，是因為 `logs/` 在派送結束後就被設成唯讀，而監督行程在那之後還要持續寫。合流那幾個產物落在根層是同一個理由。`.roster` 則是另一回事——它必須在 `prepare` 那一步就寫，因為 reviewer 一旦結束，它當時解析到的 model 名稱就沒有地方查得回來了。

**兩條路徑判斷「跑完了沒有」的方式不同，不要互相套用。** reviewer 那一路靠的是輸出檔本身，那三項條件與其計數粒度的唯一定義都在 `SKILL.md` 的「回報與張貼」節，這裡一律不複述、以該處為準；粒度之所以要釘死，是因為腳本判的就是那個粒度，兩端不對齊就會對同一個檔案算出相反的答案。這個判準不涉及標準輸出與標準錯誤的緩衝競態，因為根本沒有把這兩股輸出寫進任何檔案——reviewer 的標準輸出就是它 pane 上的畫面，沒有留存。合流那一路仍是無頭執行，它把內容包在一組起訖標記之間印到標準輸出，監督行程靠那兩行標記切內容；`synthesis.log` 與它的標準錯誤檔因此要分成兩個檔——兩股輸出合流時緩衝行為不同，標記行可能被標準錯誤的內容插斷，切出來的東西就不可信了，所以 `synthesis.log` 保持純標準輸出。

只要內容切得出來就會留下內容檔，不管 main agent 事後貼成功、貼失敗，還是根本沒有委派張貼：`ready` 而張貼成功時它是 PR 上那則 comment 的副本；張貼失敗時它是使用者唯一能拿回來手動張貼的那一份；`withheld` 時它是判斷這則 review 到底該不該人工放行的依據。三種情形共用同一條保留規則比分開處理更難出錯。`no-content` 的那一則不會有這個檔。

執行目錄刻意做成兩層而不是扁平：「未全綠就把整個執行目錄原封保留」與「腳本回收陳舊執行目錄底下的 worktree」這兩條，都建立在每次執行各有自己的目錄這個前提上，扁平之後對同一個 PR 再跑一次就會蓋掉上一次保留下來的證據，而需要保留證據的情境——逾時與中斷——恰好正是最可能立刻重跑的情境。父層名稱不帶任何雜湊，代價是兩個同名但不同 remote 的 repo 會混在同一個父層底下，不會互相覆寫。

這裡刻意以家目錄下的絕對路徑定址，不套用暫存檔規則中「先在工作區根目錄建立 `.tmp` 符號連結」那一步。呼叫 `prepare` 時的工作目錄是使用者的 repo 工作副本，為跑一次 review 在那個 repo 根目錄留下一個符號連結，是不必要的持久寫入，與整體設計方向相反。

全綠時 prompt 檔、各 reviewer 的工作目錄與輸出檔、切出來的內容檔與摘要檔會隨執行目錄一起刪除，因為每一則 review 都已確認可信、該貼的那一則也已成功貼上 PR，不再有查證價值；未全綠時執行目錄原封保留，**不受「任務結束後主動清除暫存檔」的例行清除約束**，因為這些檔案正是事後查問題與補貼的唯一憑據，任務收尾時不要刪。worktree 由監督行程自己移除，不需要代勞，但有兩種情形它不會被移除掉：有 reviewer 沒寫完輸出檔，監督行程還沒走到那一步；或走到了而那次移除失敗——失敗被靜默吞掉，流程照常往下跑，所以這一種從摘要檔上看不出來，只能靠查那個目錄還在不在。

腳本把 jq 列為硬性前置需求，缺席會在 `prepare` 的檢查階段直接拒絕執行，早於任何對使用者 repo 的寫入動作——不會出現「jq 缺席才發現，但 repo 已經被動過」的情形。
