# 結束碼

`scripts/run-review.sh` 回傳非零結束碼時對照本檔，判斷這一次動到了什麼、要不要補救、怎麼補救。

`launch` 自己有三道檢查——環境閘門（`4`，五個子命令都掛同一道）、平台清單核對（`2`）、PATH 再驗（`3`）——另外在派出第一個 reviewer 之前寫派出時刻檔 `logs/.dispatched-at`，那個檔已存在時以 `2` 拒絕、寫不出來時以 `1` 結束；其餘前置檢查落在 `prepare`。`run` 是 `prepare`、建 pane、`launch` 三段依序跑在同一個行程裡，兩半的結束碼語意原樣適用，建 pane 那一段自己失敗時是 `1`。

| 結束碼 | 原因 | 有沒有留下副作用 | 怎麼補救 |
| --- | --- | --- | --- |
| `0` | 成功：`prepare` 是座標已備妥、還沒有 reviewer 起來，`launch` 是已派出 | 正常流程 | 往下走 |
| `1` | 兩種性質相反的失敗共用這一碼：前置條件不成立（gh、jq、PR 存在性、git repo、`origin`、審查契約檔、base ref、worktree 建立或唯讀化、材料、prompt 尺寸任一不過；`launch` 寫不出 `logs/.dispatched-at`（派出時刻檔）也屬這一類，那時尚未派出任何 reviewer），或 `launch` 派送途中失敗 | 「什麼都沒動到」只到找不到契約檔為止；再往後 repo 已被動過（遠端追蹤 ref 已更新、同形狀陳舊分支已強制刪除、pull ref 已 fetch 且本次分支已建立），強制刪除排在 pull ref 之前。`run` 在建 pane 那一段失敗是這一碼底下唯一**不呼叫任何清理**的路徑，另外留下一個半成品的 tab：那一條連一行座標都不會印，tab ID 也拿不到，tab 要請使用者自己關（切到一半的那一次，tab 自己的 root pane 也還在——關掉它是所有 pane 都切完之後才做的事），而執行目錄、worktree、使用者 repo 那一側的 worktree 登記與本次分支全部原封留著。`launch` 寫不出派出時刻檔那一種會呼叫失敗清理（標準錯誤先後印出含 `failed to write the dispatch time` 與 `reviewer dispatch failed before any reviewer was launched` 的兩行），盡力移除 worktree，執行目錄與本次分支留著；在 `run` 底下，座標（含 `base_dir` 與 `tab_id`）是在呼叫 `launch` 之前就印出的，而失敗清理不碰 herdr，所以 tab 與已建好的每一格 pane 都還在（裡面沒有起任何 agent），tab 要請使用者自己關。**派送途中因 `agent start` 回報失敗而落到這一碼的那一種現在多一道前提，據此講後果才不會與事實相反**（這道前提只適用這一種，不適用寫不出派出時刻檔那一種）：`agent start` 回報失敗之後腳本先查那一格有沒有 agent，查得到就當成已啟動、繼續派送與監督，只有明確查到零筆才因 `agent start` 失敗走這條失敗路徑（查詢自己失敗或結果解析不了一律保守當成已啟動），所以走到這一碼時，那一格在**查詢當下**查無登記中的 agent——證得了的只到這裡，不等於那一格從來沒起來過——失敗清理移除 worktree 因此不會抽在一個當下查得到的活 reviewer 腳下 | 靠標準錯誤有沒有指出已派出的 reviewer 分辨兩種性質，再照表下三條處置。例外是 PR 連結解析不出（`--pr` 打錯，或沒給連結而當前分支沒有對應的 PR），那是當場改旗標值或補上連結就能解的 |
| `2` | 用法錯誤：未知旗標、旗標缺值、`prepare` 一個平台旗標都沒給、旗標值含換行、`launch` 缺 `--base-dir` 或給了相對路徑、`--agent` 值不是 `<cli>=<pane_id>` 的形狀或重複、`--agent` 指名了這次 `prepare` 沒選中的平台、`--base-dir` 底下沒有 `.roster`；`wait` 與 `cleanup` 缺 `--base-dir`、`cleanup` 拿到的路徑不是絕對路徑或不存在、`wait` 的 `--extend-minutes` 不是 1 到 6 位純數字、`wait` 讀到的 `logs/.dispatched-at` 缺漏、為空或不是 1 到 12 位純數字，同樣落在這一碼；`launch` 發現 `logs/.dispatched-at` 已經存在（同一個執行目錄重跑 `launch`）也是這一碼 | 無（`launch` 拒絕重跑那一種同樣不做任何清理） | 前面幾種當場改旗標；沒選中的平台與缺 `.roster` 那兩種改旗標沒用（沒選中的平台沒有 prompt 檔、工作目錄與隔離家目錄），要回頭重跑。`wait` 讀不到合法 `logs/.dispatched-at` 那一種改旗標也沒用，但**先確認真的是這一種**：`wait` 以 `2` 結束還可能是未知旗標（例如帶了已移除的 `--deadline-at`）、`--extend-minutes` 格式不合（例如 `30m` 或 7 位數）、缺 `--base-dir`，或 `--base-dir` 抄錯——`cmd_wait` 對它只檢查非空、不檢查存在，抄錯時讀不到檔，印出的正是同一則 `.dispatched-at` 缺漏訊息。標準錯誤那一行點名 `logs/.dispatched-at`，而且這次帶的 `--base-dir` 逐字等於 `run` 座標印出的 `base_dir`，兩項都成立才算這一種，也就是**等待迴圈的終止出口**；其餘照前面幾種當場改旗標，改正後重新呼叫 `wait`。這一種的成因是舊版腳本建立的執行目錄（沒有這個檔），或這個檔被改寫（上鎖前的派送期間、上鎖失敗而整場可寫、或上鎖之後同一使用者身分把權限改回再寫，見 `rationale.md`）；一律對照 `run` 的標準錯誤有沒有出現 log 目錄上鎖失敗那則警告，有就據此告訴使用者。不要自己補寫那個檔，也不要改從執行目錄名稱或別處算出時間傳進去——那正是本 skill 把時間運算收回腳本要關掉的那一道。終止出口成立後，之後每一次 `wait` 都會立刻以 `2` 返回，所以停止呼叫 `wait`、不重試，依序處置：一，那個 `base_dir` 已經不存在時，據實回報執行目錄已不存在、監控因此中止，沒有旗標可改、不重新呼叫；二，否則先以 `summary.txt` 當下的內容核對，所有派出的 reviewer 都已有摘要行時，這就是 `SKILL.md`「等到哪一行才算等完」的終點，照常走回報與收尾；三，還有 reviewer 沒有摘要行時才中止監控、不走收尾：原文回報，並告訴使用者本次監控已中止，reviewer 與監督行程不受影響、照常進行，中止監控不會讓 reviewer 貼不出去，但個別 reviewer 仍可能沒有發布，請他自己到 PR 上確認；之後的狀態回報與收尾不會自動發生（後果照 `rationale.md`「main agent 逾時或被中斷」那一條講）；交出 `summary.txt` 與執行目錄的絕對路徑。這一支不呼叫 `cleanup`，執行目錄保留。**`wait` 以 `2` 結束時，中止監控而不走收尾的只有終止出口的第一、三支**；所有派出的 reviewer 都已有摘要行、監督行程已死、死線到期而使用者不延長或 `deadline` 那一條的兩項條件都不成立，這幾種是等待的正常結束（見 `SKILL.md`「等待與判斷」），不是省略。`launch` 拒絕重跑那一種不要再跑一次 `launch`，回報即可 |
| `3` | 選定的平台中有 CLI 不在 PATH 上，訊息會列出是哪幾個 | 分兩個發出點，副作用相反。`prepare` 那一道不留副作用，它排在所有 gh 往返與對 repo 的寫入之前；`launch` 那一道是同一次派送前的再驗，`run` 走到它時前半段已經整個做完——執行目錄、worktree、遠端追蹤 ref 的更新、本次那個本地分支，以及 herdr 的 tab 與底下每一格 pane 都已經產生 | `prepare` 那一道當場再問一次要跳過還是改挑。`launch` 那一道只做得到跳過（從 `--agent` 拿掉），而**那只在分階段除錯時構得到**：`run` 的 `--agent` 是腳本拿自己剛建的 pane 在內部組的，那幾個 pane 識別碼只出現在成功那一次的派出摘要裡，落在這一碼時摘要根本還沒印，編排端沒有東西可以拿掉，只能改平台旗標整個重跑 `run`，並把上一次留下的 tab（要請使用者自己關）與執行目錄照 `1` 底下分支與執行目錄那兩條處置交代給使用者。改挑沒選中的平台會以 `2` 被拒、要重跑 `prepare` |
| `4` | 呼叫環境不成立：五個子命令各自在解析旗標與任何前置檢查之前確認 `HERDR_ENV` 恰為 `1` | 零副作用（本次執行目錄從未被建立是實測；「使用者的 repo 也從未被觸碰」是從控制流推得的推斷，測試沒有對應斷言） | 改旗標沒用，要在 herdr 環境裡重新發起 |

回報時先靠標準錯誤有沒有指出已派出的 reviewer 分兩種性質，處置相反：

- **沒有指出**：把訊息原文回報，**不重試、不改用其他途徑**——這類失敗全是環境前提不成立，繞道會在前提不成立下派出審查、產出沒有依據的 review。`2` 與 `3` 不屬於這一類，補救方向照上表那一列。
- **指出了**：原文轉達那份清單，說明這些 agent 無人監督、這次不會有監督行程去讀它們的輸出檔，結果只會停在各自的 `reviewers/<cli>/workdir/review.md` 裡，並把 pane 留著讓使用者決定要不要終止。

`1` 底下三條處置不在表格裡，逐條照做（其餘展開說明見 `rationale.md`）：

- **找不到審查契約檔**代表安裝不完整，照「兩條安裝路徑都不存在」處理，不要在沒有審查標準的情況下自行湊一份派出去。
- **這條路徑上留下的本次分支不要自己去刪**：分支名尾端那段是腳本自己的行程編號，前半段就失敗的那一次連執行目錄都不會印出來、更推不回來，組偏了就是對使用者自己的同前綴分支下強制刪除。交給腳本的陳舊分支清除機制——那道掃描是 repo 範圍、不看 PR 編號，所以之後任何一次在這個 repo 裡跑到建 worktree 那一步的執行都掃得到它，不必是同一個 PR。但**掃得到不等於刪得掉，要看 worktree 還在不在**，先確認自己落在哪一種：走到失敗清理的那幾條路徑（`prepare` 的每一種失敗、`launch` 寫不出 `logs/.dispatched-at` 那一種，以及 `launch` 派送途中失敗）worktree 要嘛從未建立、要嘛已被盡力移除，掃描不會被擋，下一次執行就刪掉了；不呼叫任何清理的有兩條——`run` 建 pane 那一段失敗，以及 `launch` 的 PATH 再驗（`3` 引到這裡的那一種）——worktree 一定還留著，走了失敗清理而那次移除本身也失敗的一種同理。**worktree 還在的那幾種 git 會擋著這個分支**，要等針對**同一個 PR** 的下一次執行先把 worktree 移除，同一次執行接著才刪得掉它；此時**不要照前一種對使用者說「之後任何一次執行都會刪掉那個分支」**。
- **執行目錄已建好時據實告訴使用者位置**，這些目錄不會被任何機制自動清掉：已經印過 `base_dir` 就交出去，還沒印到就請他到 `~/.tmp/<repo 名>-pr-<PR 編號>/` 底下看。派送途中失敗那一種另要轉達哪幾個 reviewer 成了無人監督的孤兒。
