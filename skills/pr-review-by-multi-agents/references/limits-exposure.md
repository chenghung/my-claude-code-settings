# 已知限制：權限與暴露面

本檔記四個平台在互動 reviewer 那一路的能力量測，以及 reviewer 的讀寫、憑證、環境變數與 GitHub 寫入各軸實際擋得住多少，連同用來察覺越界的 worktree 狀態比對有哪些盲區、揭露段落裡的 model 準不準。派送、等待與收尾的已知限制在 `references/limits-operations.md`；規則的成因與產出物目錄結構在 `references/rationale.md`。

**量測前提**：互動模式與無頭模式是兩組不同的量測條件，多項結論方向相反：底下這些量測全部取自互動 reviewer 那一路，不要拿去套用在任何無頭執行上，反之亦然。要重新確認只能對真實二進位重跑同型探測，讀腳本或官方說明推不回來。

涉及外部 CLI 或 git 實際行為的每一項都標出憑據等級：「實測」指以真實二進位跑過同型探測，「推斷」指從其他已知行為推得、沒有直接量測，「未查證」指沒有測過也推不出來。三者不得互相代換。

## 四個平台在互動 reviewer 那一路的能力現況

要查某個平台在某一面向上是什麼狀況，以本表為準；底下各條補的是後果與處置，不重寫表裡的事實。

| 面向 | claude（每一格都帶表下那兩段的量測條件但書，不要當成無條件的實測讀） | codex | opencode（每一格都是不帶 `--auto` 時的量測，而 reviewer 那一路現在帶 `--auto` 啟動；見表下但書） | agy（每一格都是不帶 `--dangerously-skip-permissions` 時的量測，而 reviewer 那一路現在一律帶這個旗標；另有一次條件不同的實測與本欄不符。兩項但書都在表下 agy 那兩段，不要當成無條件的實測讀） |
| --- | --- | --- | --- | --- |
| 檔案寫入的路徑範圍 | 明傳 `--permission-mode auto` 時工作目錄內放行、無人介入（實測）；不帶這個旗標時同一個寫入會跳 claude 自己的 Create-file 核准對話框、herdr 把那一格回報成 `blocked`（實測），腳本因此改成明傳，見表下那兩段；**`auto` 模式下對工作目錄之外的寫入已量測，量到的是放行**：在 herdr 環境下以 `--permission-mode auto` 啟動的 Claude Code agent，被要求用 Bash 在工作目錄以外的路徑建檔，檔案確實被建立、過程中沒有出現任何核准框（實測；該次量測做在別的流程上，不是本腳本 reviewer 那一格的隔離家目錄佈局） | `workspace-write` 沙箱限定在工作目錄加 `/tmp`、`$TMPDIR`，目錄外跳核准對話框（實測） | 工作目錄內放行；內建寫入工具寫到目錄外會跳「Access external directory」核准對話框（實測，不帶 `--auto` 時）；經 Bash 重導向寫到目錄外未測（未查證）；**reviewer 那一路這道核准對話框不會出現**，`--auto` 旗標會把它自動答掉（推斷：由旗標說明的自動核准語意推得） | 目錄內外都要核准，差別只在目錄外那個對話框多一行 workspace 提示與一個永久放行選項（實測）；**reviewer 那一路這兩個對話框都不會出現**，旗標會把它們自動答掉（推斷：由旗標自身說明的自動核准語意推得，正式條件下沒有端到端量過） |
| 跨目錄讀 worktree | 讀檔、列目錄、`git -C <path> diff` 三項全數直接放行（實測） | 讀取完全不受限，該沙箱只限定寫入（實測） | 經 Bash 的讀取直接放行；改用它自己內建的讀取工具在不帶 `--auto` 時會撞上與寫入共用的同一道外部目錄核准對話框（實測）；reviewer 那一路該對話框同樣被 `--auto` 自動答掉，複製材料的做法因此退居備援 | 一律詢問，要在允許清單裡加一條比對實際指令字首的規則才放行（實測，見下面 agy 那一條）；reviewer 那一路這道詢問同樣被旗標自動答掉，那條允許規則因此退居備援 |
| shell | 放行，不詢問（實測） | 放行，不詢問（實測） | 工作目錄內放行；設定檔裡逐條指令樣式的拒絕清單照樣生效（實測） | 未列入允許清單的一律跳核准對話框，`agent_status` 正確回報 `blocked`（實測）；reviewer 那一路不會再跳這個框，所以這一格連同它那個 `blocked` 訊號在那一路上都沒有適用對象 |
| 網路 | **未關閉**，`curl` 直接放行（實測） | **預設關閉**，沙箱層攔下，是四家中唯一預設關上網路的（實測）；**reviewer 那一路有一個例外**：隔離家目錄裡的 `.codex/rules/default.rules` 放行以 `gh pr comment` 加本次 PR 網址開頭的單一指令，直接在沙箱外執行、不詢問（實測：codex-cli 0.156.1，契約那種本次 PR 網址加 `--body-file` 絕對路徑的寫法，對一個不存在的 PR 端對端跑過；同一組條件下，改指向別的 PR 網址、或以編號加 `-R` 的寫法，都跳核准框；射程、舊版三 token 規則的歷史與串接指令見下面 GitHub 側機制那一條）；沒有規則檔時，網路型指令被沙箱攔下之後 codex 跳出是否在沙箱外重試的核准對話框，按下核准就放行（實測，以 `gh api user` 測）；規則檔存在時，其餘網路指令照舊被攔下、再跳核准對話框（推斷，同下面那一條） | 部分關閉：設定檔裡的 `curl*`、`wget*`、`nc*` 被自動拒絕（實測）；其餘外連管道未列入清單、落到內建預設放行（實測為預設放行，清單本身不宣稱窮舉） | 攔在確認層，跳核准對話框、沒人核准就出不去（實測）；「連線本身會不會被允許」那一層本次探測未到達（未查證）；**reviewer 那一路連這道確認都沒有了**——旗標把它自動答掉，這一格描述的那道攔截在那一路上不成立 |
| 沒有明確規則時的預設行為 | 四個樣本全數放行、不詢問（實測，不帶權限模式旗標那一次的觀測；那四個樣本是哪四個沒有留下記錄，所以這一格說不出自己涵蓋到哪些動作）；**檔案寫入不在這一格的射程內**，同一組條件下寫檔會跳 Create-file 核准對話框，以第一列為準 | 工作目錄內的一般寫入直接放行、不詢問（實測） | 工作目錄內的讀寫與 shell 全部直接放行（實測）；reviewer 那一路帶 `--auto` 啟動，未被明確拒絕的請求一律自動放行 | 一律詢問，五個樣本沒有一項是自動放行（實測）；取網址類與未沙箱類工具未測（未查證）；reviewer 那一路一律自動放行，這一格只描述不帶旗標時的行為 |

claude 那一欄的「`auto` 模式」是腳本明傳的，不是它自己落到的預設，這個前提怎麼修正過來的要跟著讀：早先那次觀測是在隔離家目錄裡以 `agent start` 起 claude、不帶任何權限模式旗標，狀態列逐字顯示 `⏵⏵ auto mode on`（實測），當時據此認定 `auto` 已經是預設、不必明傳。狀態列那個讀數本身沒有錯，錯在它預測不了行為——同樣不帶旗標的條件下，reviewer 在自己工作目錄裡寫輸出檔照樣跳出 Create-file 核准對話框、herdr 把那一格回報成 `blocked`，也就是每一次 claude review 都要有人先按一下鍵才交得出東西；明傳 `--permission-mode auto`、其餘條件相同，同一個寫入無人介入、五秒內完成（皆實測，claude 2.1.259 配 herdr 0.8.2）。所以「`auto` 已是預設、因此不必明傳」那整條推論作廢，腳本改成一律明傳權限模式，不依賴任何預設。量測條件因此要分開讀：claude 那一欄只有檔案寫入那一格是在明傳 `auto` 的條件下量到的，其餘幾格都還是不帶旗標那一次的觀測，明傳之後沒有重新量過（未查證）；唯一有前後對照的就是寫入那一格，方向是明傳之後更寬鬆而不是更嚴，所以那幾格「放行」的觀測不預期會反轉（推斷）——但已知一項例外：經 shell 對外的 `gh pr comment` 在明傳 `auto` 之後被分類器擋下（實測，見 GitHub 側那一條），shell 與網路兩格對外寫入的動作因此不能照「放行」讀。

三條較窄的替代方案都實測無效，記在這裡免得日後有人重試：`--permission-mode acceptEdits` 之下對話框仍然出現，只是選項少一個——代表那個模式確實生效，只是不涵蓋 `Write` 這個工具；把 `Write` 放進 `--allowedTools` 無效；在隔離家目錄自己的 claude 設定檔裡寫 `permissions` 允許清單也無效（這一項量的是 `Write`、不帶權限模式旗標、claude 2.1.259；同一個設定檔裡的 `Bash(gh pr comment …)` 允許規則，在明傳 `auto` 的互動 pane 下確實生效，claude 2.1.325，實測，見 GitHub 側那一條——條件不同，兩者不互相推翻）。`dontAsk` 的方向相反，它是自動拒絕而不是自動放行，受測的 reviewer 在它底下回報 `Write` 與 Bash heredoc 兩條路都被拒，最後什麼都沒寫出來（皆實測）。探測期間還有一個一度造成誤判的細節：寫入路徑若落在使用者的 claude 設定目錄底下，claude 會另外以「這是敏感檔案」為由跳框，那是與上面不同的一條規則（實測）；正式流程每個 reviewer 的工作目錄不在那底下，不受這一條影響。

**opencode 那一欄要帶的但書是旗標：reviewer 那一路的 opencode 現在以 `--auto` 啟動，欄裡描述的外部目錄核准對話框在那一路上不會出現。** 起因與 claude 及 agy 同形：避免無人看顧的隔離 pane 因等待核准對話框而停滯卡死。旗標本身查證過：`opencode --help` 逐字列出 `--auto`，說明為「auto-approve permissions that are not explicitly denied (dangerous!)」（實測）。它的射程是自動核准所有未被設定檔明確拒絕的權限請求；因此腳本為 reviewer 寫入的 `opencode-permission.json`（設定檔中針對高風險 bash 指令的 deny 清單）成為它在危險動作上的核心屏障。

**agy 那一欄要帶的第一項但書是旗標：reviewer 那一路的 agy 現在以 `--dangerously-skip-permissions` 啟動，欄裡每一格描述的核准閘門在那一路上都不會出現。** 起因與 claude 那一欄明傳 `--permission-mode auto` 同形：agy 的模型呼叫寫入工具存 `review.md` 時會跳自己的工具權限請求，而那是一格無人看顧的隔離 pane，沒有人按得下去。旗標本身查證過：`agy --help` 逐字列出這個旗標，說明為「Auto-approve all tool permission requests without prompting」（實測）。**它的射程比那一個寫入請求寬得多**——這一路的模型觸發的每一個工具權限請求都被自動核准，不只是寫入那一個，也不只是腳本寫進隔離家目錄那兩條 `git diff` 允許規則涵蓋得到的範圍。這是實質的暴露面擴大，不是等價改寫：它沒有跟著做 claude 與 codex 兩家做過的那次 curl 外連探測（未查證），所以這裡記的地位是一項使用者指定的刻意取捨，不是一項被獨立驗證為安全的結論。旗標日後若被改名、收窄或移除，欄裡那五格就重新成為 reviewer 那一路的實況，底下每一條標著「退居備援」的敘述也會跟著重新生效。

**第二項但書是量測條件，引用 agy 那幾格時要一起帶上。** 對 agy 1.1.27 做過一次 A/B 探測，不帶旗標的控制組一樣無人介入就執行了 shell 指令、也一樣寫出了工作目錄之外的檔案，與這一欄的「目錄內外都要核准」「一律詢問，五個樣本沒有一項是自動放行」對不上。**但那次的量測條件與腳本的正式流程不同**：用的是使用者的真實家目錄與其既有的允許清單，不是腳本為每個 reviewer 建的隔離家目錄。所以這不是全稱推翻，只說明這一欄的成立條件比欄裡寫的窄；正式條件下尚未重測（未查證）。兩項但書的方向一致：這一欄描述的限制，在 reviewer 那一路上實際擋得住多少，比字面弱。

## 逐條限制

- **CLI 自身的權限機制都保證不了唯讀，那幾個位置靠 chmod 守，而 chmod 守得比字面上弱**：腳本以 `chmod` 鎖住 worktree、共用材料目錄、每個 reviewer 自己那份材料副本與 log 目錄，各 CLI 自身的旗標與沙箱降級為第一層，只負責限制模型會去嘗試的動作範圍，不是唯讀承諾的依據。兩個缺口要認得。其一，reviewer 與腳本跑在同一個使用者身分底下，那些檔案的擁有者就是它自己，它把權限位元改回去就能寫——四家裡只有 opencode 那份設定檔明文拒絕了 `chmod`；agy 過去因為預設一律詢問而會讓這類指令撞上核准對話框，**reviewer 那一路現在不會了**（旗標把那道詢問自動答掉，見上面能力表 agy 欄與表下第一項但書），所以在那一路上沒有任何一條擋它的是 claude、codex、agy 三家。其二，這幾道鎖的強度並不相同：worktree 那道上不成即中止整次執行（連同 worktree 一起移除、非零結束碼），材料那兩道是靜默盡力（失敗不影響流程，也不會有任何訊息），log 目錄那道失敗只往標準錯誤印一行警告、照樣繼續跑。log 目錄那道鎖是在所有 reviewer 都啟動之後才上，只擋新開檔案；「不擋已經開啟的檔案控制代碼」這個但書，對腳本自己的讀寫在目前的佈局下沒有指涉對象——`logs/` 只有 `<cli>.prompt`、`.dispatched-at` 與 `.changed-files`。腳本自己對 `.dispatched-at` 的寫入只有 `cmd_launch` 在派出第一個 reviewer 之前那一道單次重導向，讀取內容的只有 `cmd_wait` 的一次 `cat`（`cmd_launch` 另外只以 `[ -e ]` 檢查它在不在，讀腳本確認）；對 `.changed-files` 的寫入只有 `cmd_prepare` 在派出任何 reviewer 之前那一道單次重導向，讀取內容的只有監督行程每格核對覆蓋範圍段時 `_coverage_compare` 那一次唯讀的 awk `getline`（`_record_coverage_status` 另外只以 `[ -r ]` 檢查它可不可讀，讀腳本確認）；走命令列那三家的內容是腳本在派送當下讀完即關，claude 那一份改由 claude 自己在啟動時循檔案路徑讀（腳本只量它的尺寸、不讀內容），兩種讀法都不需要寫入控制代碼。reviewer 在上鎖之前開出的寫入控制代碼則不受這道鎖約束，但這個缺口已被本條「其一」那個缺口（同一使用者把權限位元改回去就能寫）涵蓋，與 `references/rationale.md`「放在 `logs/` 而不是執行目錄根層」那一段一致。下游後果是：要判斷某次 review 有沒有可能動過 worktree，看的是摘要檔那一行的 worktree 狀態比對結果，不是某個 CLI 的權限設定。
- **執行目錄根層沒有上鎖，摘要檔與內容檔就放在 reviewer 寫得到的地方**：上鎖的只有 worktree、材料與 log 那幾處，而 `summary.txt`、各份 `.comment-body-*.md`、`.roster`、`.supervisor.pid`、`.prepared-at`、`.repo-path`、`.pr-url`、`.last-working-<cli>`、`.reviewer-confirm-status`、`.pane-<cli>`、`.pane-close-status` 與 `.coverage-status` 全在執行目錄根層，那一層自始至終可寫；reviewer 的 prompt 裡就有 worktree 與自己工作目錄的絕對路徑，往上一層即是。後果要說白：main agent「只讀結構化欄位」這道區隔，以及補貼時「只交出路徑、由 `github-manager` 以檔案張貼」這項要求，實際上都架在 reviewer 寫得到的檔案上，後者本來就只是降低了、但沒有消滅注入面，架在這一層上又再打一次折扣——寫得到那一層的 reviewer 可以改掉別人那一行的 `content_status`、改寫別人的 `reviewers/<cli>/workdir/review.md`（補貼時比對、請使用者確認與張貼的對象都是這份檔；每個 reviewer 的工作目錄同樣座落在執行目錄底下、沒有上鎖），或偽造一整行摘要補進去。`references/backfill-posting.md` 對摘要行的 cli 值只接受四個平台名之一，擋得住拿一個帶路徑片段的 cli 值把組出來的 `review.md` 路徑指到別處，擋不住直接改寫某個合法平台名底下那份 `review.md`。**那一層還有五個控制檔，後果與資料面竄改不同類**：`.repo-path` 被改成指向另一個 repo 時，`git worktree remove --force` 以結束碼 128 失敗、訊息是該路徑不是一個工作區，目標目錄完全不被刪除（實測：自建兩個 scratch repo，以不相干的那個去移除另一個 repo 的 worktree；測試套件裡沒有對應斷言，所以這一條會隨 git 行為改版而過時，沒有回歸保護接得住）；而兩條清理路徑都在移除之前無條件跑過 `chmod -R u+w`，所以竄改換來的是 worktree 留著、唯讀保護已被解掉，本地分支也連帶刪不掉。**讀這個檔內容的地方現在有四處，射程最遠的是刪分支那個函式**（收尾子命令、失敗清理，以及下一次針對同一個 PR 的執行回收陳舊 worktree 時都呼叫它；收尾子命令開頭另以它可不可讀當執行目錄標記，那一道不讀內容）：它據此以 `git -C <該路徑> branch -D` 刪那個執行目錄自己的分支，所以射程不只停在本次 worktree——被指到的那個 repo 裡，形狀恰為 `pr-review-<該次 PR 編號>-<該次行程編號>` 的分支會被強制刪除。回收那一路讀的是同層別次執行的 `.repo-path`，所以改掉某個將被回收的執行目錄裡這個檔，下一次執行就會替竄改者對別的 repo 下這道刪除（連同在那個 repo 裡移除 worktree 與 prune）。實際危害很小，因為分支名是腳本從執行目錄自己的路徑推導的，竄改者選不到要刪哪一個名字（推斷：讀刪分支那個函式的推導方式得出，沒有對真實 repo 跑過這個情境）；但這是一條指向別的 repo 的破壞路徑，別再寫成全稱否定。這條指令為什麼從編排端收進腳本、舊禁令為什麼因此不再適用，記在 `references/rationale.md`「為什麼本地分支用強制刪除」那一節。`.prepared-at` 那一支更尖銳：把同層某個正處在 `prepare` 與 `launch` 之間的執行目錄的 `.prepared-at` 刪掉，會讓它退回已死的 `prepare` 行程編號檢查而被判為陳舊，於是那個即將開跑的執行的 worktree 被從它底下強制移除；射程限於同層的其他執行，本次自己的目錄在掃描中被排除。**動本次自己那一份的方向相反、落在安全側**：孤兒偵測拿它當時間界線，刪掉或改成解析不了的值只會讓每一次確認都判成無法確認，於是誰的 pane 都不關（把它改成一個更早的時間則會把界線放寬回去，讓前次執行留在同一個 PR 上的舊 comment 重新成為候選）。**後三個是這次新增的，三個都是本次那幾道機制自己的狀態檔，被動過的後果同樣無聲**：`.last-working-<cli>` 是 `stalled` 唯一的時間基準——派出當下先寫一個時間戳進去當起算點，`wait` 每一輪讀它比對已經多久沒讀到工作中、讀到工作中就覆寫成當下（對那一格查詢失效的每一輪同樣覆寫成當下，失效之前已經累積的停滯時間也一起歸零，不只是暫停累積；腳本測試涵蓋：17 種變形回應都把它改寫成當下時間）——把它改寫成一個未來的時間戳，等於讓那一格的 `stalled` 在它下次被讀到工作中之前一直失效；把它刪掉效果一樣，腳本那一行讀不到值就直接跳過這一格，於是它在那之前不再有資格觸發 `stalled`，兩種都不會有任何訊息。**失效期不是永久，射程要照兩種對象分開講**：`wait` 每一輪只要讀到那一格 `working` 就把這個檔覆寫成當下時間，兩種竄改都會就此被沖掉（查詢失效的那一輪同樣會覆寫它，推斷：由測試涵蓋的覆寫行為推得，未對竄改情境實測）——對真的卡死、從此不再被讀到工作中、其間也沒碰上查詢失效的那一格，效果確實等同關掉（那正是竄改者要的），但對停住又恢復的那一種不成立，恢復的那一輪就自己修好了。`.reviewer-confirm-status` 是逐格確認步驟寫、印派出摘要時讀的那一份，同儕 reviewer 只要把某一格那行改成工作中，摘要就會對一格從未開始的 reviewer 印出「已進入審查中」——那正是本次要修的那個缺陷的人為版本，差別在於摘要本身給的是一句要他放心的話，連「請切過去看」都不會出現。**接得住這一支的不是腳本而是編排端**：`SKILL.md` 要求轉達之前對任何標為「已進入審查中」的那一行，另外以 pane 識別碼向 herdr 自取一次即時狀態核對，而那個值不是同儕寫檔改得掉的；但它與這一層其餘每一條一樣是要求而非機制，沒有任何東西在後面強制它真的被執行。**`.pane-<cli>` 是同一本交接帳本的另一半，被動過的後果比上一條更直接**：它記的是派工當下那一格的 pane 識別碼，`wait` 每一輪讀它回去，才能在射程涵蓋整個 herdr 服務、不限本次執行的 `herdr agent list` 裡認出本次那幾格；被改成別的 pane 識別碼，本次每一次狀態取樣就整段落到別人那一格上——`stalled` 的時間基準會被那一格的 `working` 一路沖掉，於是本次這一格真的停住也永遠不觸發，而這正是腳本原本照 cli 名稱前綴比對再取第一筆時那個缺陷的人為版本（**缺陷的兩半查證程度不同，不要併成一句讀**：並行條件在這台機器上真實存在過是實測——本次流程進行期間，`herdr agent list` 上同時有另一個 session 對別的 PR 派出的 claude，兩邊的 agent 名稱都以同一個前綴開頭；至於那段程式碼真的讀到過別次執行那一格、真的沖掉過本次的計時，沒有人觀測到那次誤讀發生，是從選取邏輯推得的推斷——照前綴比對再取第一筆，而清單順序不受本次執行控制。改以 pane 識別碼精確比對之後這條自然發生的路已經封死，剩下的只有竄改這一條）。被刪掉則相反，**而後果的方向與舊敘述相反，舊的那句（說還活著的 reviewer 會被判成消失）依實際資料流不成立、不要再沿用**：讀不回識別碼的是腳本那一側，於是它對那一格一律讀成 `unknown`——不再產生 `blocked`，`stalled` 卻照常產生：`unknown` 不在 `stalled` 的排除項裡，`.last-working-<cli>` 又在派出時就已寫入，計時滿 300 秒就返回，被帶進 `--reported-stalled`、重新武裝之後還會再次返回，這才是它真正的症狀（讀腳本得出）；主線上，編排端那條投影指令的識別碼取自派出摘要、不經過這個檔，所以它仍然拿得到真實狀態，不會把還活著的 reviewer 判成消失。兩種都不會有任何指出竄改的訊息（推斷：由該檔的寫入點與 `wait` 的讀回路徑推得，沒有實際竄改它跑過一次）。補貼路徑則不同：跨 session、手上沒有該次派出摘要時，它會讀這個檔，被改成格式正確的別格識別碼時可能讓「排除還在跑的」那一關放行（見 `references/backfill-posting.md`）。**逐格關 pane 之後這一支多一個後果，比狀態誤讀直接得多**：監督行程確認完 comment 是照這個檔記的識別碼下 `herdr pane close`，而守衛只擋「等於編排端自己那一格或那個 tab」這兩個值，所以被改成第三方的 pane 識別碼時，被關掉的就是那一格。**這一條不是推斷**：腳本對材料目錄、log 目錄與 worktree 三者都下過遞迴唯讀，唯獨執行目錄根層從未設過唯讀，而每個 reviewer 的隔離家目錄與工作目錄都座落在執行目錄底下，所以 reviewer 確實寫得到這兩個檔。**射程是有界的，不要讀成「任何 pane 都關得掉」**：關之前會比對編排端自己那一格與那個 tab 的兩個環境變數值，所以關不掉編排端自己，構得到的是第三方的 pane。**收尾子命令的存活檢查也吃這個檔與 `.roster`**：`cleanup` 在刪執行目錄之前，逐一讀 `.roster` 列出的平台與各自的 `.pane-<cli>`，向 herdr 查那一格還有沒有 agent，有、或查不準就拒刪；把這兩個檔刪掉或清空，檢查就跳過那一格，把識別碼改成一格沒有 agent 的 pane 則會查到那一格上而放行（改成一格還有 agent 的反而會拒刪，落在安全側），於是那道檢查要擋的競態——還開著的 reviewer 在刪除途中往執行目錄寫回東西、讓刪除失敗——重新成立（推斷：由該檢查的讀取路徑推得，沒有實際竄改測過）。**`.pr-url` 是同一批新增的控制檔，被改的方向決定後果**：comment 確認整段會落到被指到的那個 PR 上——那邊查不到相符的 comment 時每一格都不關，落在安全的那一側；但那邊若有一則逐位元組相同、或帶著回音室標記又點名同一家 CLI 而且建立時間晚於本次 `.prepared-at` 的 comment，本次那一格就會被關掉、甚至被補上一行 `posted-no-output`，畫面上的訊息跟著消失。**它另有一個讀取者，而且刻意只讀一次**：`launch` 在逐格派送迴圈開始之前讀它一次，同一個值往下傳給每一家，codex 隔離家目錄裡那條放行規則的第四個 token、claude 隔離家目錄 `settings.json` 那條允許規則裡的網址，都是這個值（見下面 GitHub 側機制那一條）。在派送前就固定，是因為 claude 一段式啟動、一起來就開始讀 PR 內容，這一層又沒上鎖，而派送順序不保證 codex 排在前面——延到輪到 codex 才讀，先起來的 reviewer 就有機會先改掉它，把 codex 的放行規則指到別的 PR（腳本測試涵蓋：派送 claude 時改寫這個檔，codex 規則仍是改寫前的網址）。剩下的窗口是 `prepare` 寫出它到 `launch` 讀它之間：檔案仍在這一層，但那段時間本次的 reviewer 還沒有任何一個在跑，本次之內沒有已知的寫入者；同一台機器上其他執行的 reviewer 以同一使用者身分仍寫得到，只是這個路徑不在它們的 prompt 裡（皆推斷）。**固定下來的只有交給規則檔的那個值，不是規則檔所在的目錄**：規則檔在 codex 自己的隔離家目錄裡，同樣座落在執行目錄底下、reviewer 寫得到，而那個目錄有兩個窗口。派送之前：`reviewers/codex/home` 在 `prepare` 階段就已建好，`_write_codex_home_interactive` 只做 `mkdir -p .codex/rules` 再覆寫 `default.rules`，不清掉同一目錄裡的其他檔案，所以比 codex 早派出的 reviewer（例如排在它前面、一起來就開始工作的 claude）可以先在那裡多放一份 rules 檔（讀腳本得出，不是推斷）；codex 啟動時若會載入 rules 目錄下所有 `.rules` 檔（未查證），那一份根本不需要任何重讀就會生效。派送之後：改寫 `default.rules` 本身要生效，得 codex 起來之後會重讀它，這一點同樣未查證。任一條成立時會壞掉的是：放行範圍可能被放寬到不限於 `gh` 的指令都不經詢問就在沙箱外執行（推斷）。腳本不為此改動，這裡只做揭露。之後再改 `.pr-url`，影響的只剩監督行程那一路的 comment 確認（上一句）與補貼路徑。**佈局變更後這個風險對 codex 自然減輕**：pane 的工作目錄現在是每個 reviewer 自己那一個專屬目錄，依上表 codex 寫到工作目錄外會跳核准對話框，竄改交接帳本在它身上因此不再是無聲直寫；**claude、opencode 與 agy 都不在此列**，claude 在 `auto` 模式下經 Bash 往工作目錄之外建檔已經量到是放行（見上表第一列），所以這條風險對它不再是保守假設，而是量到的成立；opencode 與 agy 那道目錄外的核准對話框則分別被 `--auto` 與 `--dangerously-skip-permissions` 自動答掉（推斷：由旗標的自動核准語意推得，正式條件下沒有端到端量過；而表下第二項但書那次條件不同的探測裡，連不帶旗標的控制組都寫出了工作目錄之外的檔案），減輕的程度因此與 claude 同級而不是與 codex 同級。這仍然不是機制保證。不改的理由是結構性的：摘要檔就在那一層而監督行程整場都在寫它，上鎖會直接讓流程停擺。因此這裡的處置是揭露而非承諾——PR 上出現的內容與某份輸出檔對不上、或摘要欄位與輸出檔明顯矛盾時，從這裡查起。
- **opencode 那筆「每次啟動都下載、事後留下約 160MB」的代價已經不成立，不要再沿用**：那是隔離家目錄裡一個 opencode 目錄都沒連時量到的舊條件（當時實測：只有 7 個免費層模型，啟動後 90 秒內另外拉了 24MB、在 `.config/opencode` 底下重建 63MB）。現在建隔離家目錄那一步把使用者真實的四個 opencode 狀態目錄整組連進去（`.config`、`.cache`、`.local/share`、`.local/state` 底下各一個，來源不存在時才略過該條連結），同一組探測量到的是：解析得到 96 個模型、同一個 90 秒窗內拉取不到 1MB、沒有任何重建、使用者自己設定的預設模型解析得到（實測）。四個要一起連才有這個結果——只連其中三個而漏掉 `.config` 那一個時，模型數雖然回到 96，仍然拉 21MB、仍然重建那 63MB，而且使用者的預設模型解析不出來（實測）。腳本為 reviewer 寫的那份權限拒絕設定檔在 `.config/opencode` 連進來之後照樣生效，因為 opencode 是把它併進設定目錄原本的設定、而不是整個取代（實測）。
- **agy 預設連契約要跑的 `git diff` 都要人工核准（實測），腳本為此寫的那兩條允許規則現在退居備援**：它是四家中唯一連契約指令都要問的平台，腳本因此在它的隔離家目錄裡寫入兩條允許規則。agy 的允許規則是逐字比對整條指令字串的字首，pane 的工作目錄改成 reviewer 專屬目錄之後，契約指令實際送出的是 `git -C <worktree 絕對路徑> diff`，`command(git diff)` 這個字首根本不匹配，真正放行它的是另外那條比對帶 `-C` 路徑的規則。把 worktree 路徑一併傳進 `--add-dir` 也取代不了這條規則——那只解決路徑歸不歸屬工作區，不解決指令執行前的字首核准閘門。**以上是不帶旗標時的形狀；現在真正放行這道指令的不是這兩條規則，而是 `--dangerously-skip-permissions`。** 規則沒有從腳本裡刪掉是刻意的：旗標日後若被改名、收窄或移除，它們是這一格僅剩的退路，而那個時候沒有人會先注意到旗標不見了——留著要付的代價是零，刪掉要付的代價是那一格從此連 `git diff` 都跑不動。症狀對照也跟著換：agy 那一格如果從一開始就停在核准對話框上，代表旗標已經不生效，先確認旗標與這兩條規則是不是都還在。
- **這一條交代的兩項是隔離家目錄與摘要檔位置的模糊化，強度要分軸讀：寫入面是提高門檻，檔案類憑證面是零**：隔離家目錄擋的是 reviewer 被誘導去寫使用者真實的設定目錄，擋不掉的是——claude、codex、agy 這三家的憑證以符號連結掛進去、方向是雙向可寫（**claude 那一份的來源跟著 `CLAUDE_CONFIG_DIR` 走，沒設定才退回 `$HOME/.claude`**：以 clauth 這類 profile 機制管理憑證的機器上，`$HOME/.claude` 底下那份是沒有任何機制會更新的殘留檔，照舊連過去會讓那一格的 claude 以登出狀態啟動、永遠進不到工作中，而監督行程會一直輪詢一個不會被寫出來的 `review.md`——實際撞過一次，症狀是那一格畫面停在登入或帳號過期的畫面上），CLI 若在 token 更新時寫回，寫入會直接落到使用者真實的憑證檔上；**opencode 也在此列，只是形狀不同**：它沒有單一的具名憑證檔可連，連進去的是它自己那四個狀態目錄整組（見上面 opencode 那一條），認證所需的東西就在裡面（推斷：由四個全連之後使用者自己設定的預設模型解析得到、而且不再重新下載推得，沒有單獨驗證過憑證實際放在哪一個目錄裡），所以穿透的方向與另外三家相同；**憑證類環境變數那一支曾經是這裡最壞的一項，現在已經另有機制關掉，不再由這一條負責**：關掉它的不是隔離家目錄——隔離家目錄只覆寫 `HOME`，攔不到任何一個經背景服務行程繼承進來的變數，這一點沒有變——而是寫進每個隔離家目錄的那份 `.zshrc` 白名單清理，當初那組值層量測與現在的射程都記在下一條，這裡不重複。**取用環境變數這一類憑證不需要任何檔案讀取**——值就在自己行程的環境裡——所以底下符號連結那一半從來就只涵蓋檔案類憑證；而檔案類這一半沒有被那道清理碰到，以下每一句都仍然原樣成立。隔離改變的只是波浪號展開的家目錄解析，檔案類憑證的讀取與寫入都完全穿透，**讀取這一半不必寫死絕對路徑就成立**：三家的憑證本來就以符號連結掛進隔離家目錄（本條開頭那一句），在 pane 裡照家目錄相對路徑讀就已經解析到使用者的真實憑證檔，既不需要知道絕對路徑，也不經過任何跨目錄讀取判定，claude、codex、agy 三家都是如此——agy 那一次讀取依上表本來一律要核准，與底下寫入那一步同一個形狀，但 reviewer 那一路的旗標把那道詢問自動答掉了，所以無聲讀得到的現在是這三家全部（agy 那一半是推斷，由旗標的自動核准語意推得，沒有量過）。**值要送得出去同樣不必經過任何機制，兩條通道四家一律成立**：其一，reviewer 把值寫進自己的輸出檔——那是它被設計要做的事、落在自己工作目錄內，依上表 claude、codex、opencode 三家直接放行，agy 那一次寫入本來要使用者核准、不核准就交不出 review，而那正是 reviewer 那一路加上旗標之後被自動核准掉的那一個請求，所以這條通道現在四家一律無聲成立——而那份內容接著由 reviewer 自己在同一格裡呼叫 `gh pr comment` 貼上公開的 PR（主線已經是直連張貼，不再經監督行程切出、也不再由 main agent 委派，只剩事後補貼那條路徑還走委派），這整條通道從頭到尾沒有任何權限層；其二，各 CLI 自己對模型 API 的連線不在任何拒絕清單的射程內，注入只要讓模型讀到值，值就已經到了該廠商那一端。**上表跨目錄讀檔與網路那兩格只描述其中一條路**——以 shell 讀檔案類憑證再自己外連——不要拿它們當成整體的外流判準：claude 那兩格都放行，這一條路在它身上接得起來（推斷：由能力表跨目錄讀 worktree 與網路那兩格接成，沒有人真的從 reviewer 那一格跑過讀憑證再送出去的端到端量測，而依表下說明那兩格是不帶權限模式旗標那一次的觀測，在明傳的正式條件下屬於未查證）；**agy 現在也接得起來**——它那兩格本來都攔在核准層，而 reviewer 那一路的旗標把兩道都自動答掉了（推斷，與上一句同一種：沒有端到端量測，只是那兩格的閘門已經不在）。**codex 與 opencode 現在也接得起來**：依能力表兩家讀檔都不受擋（codex 完全不受限，opencode 經 Bash 直接放行），而單一一道 `gh pr comment` 可以不經詢問，把 `--body-file` 指到任何檔案送出——opencode 是拒絕清單不涵蓋它、又以 `--auto` 啟動，落點不限 repo 與 PR；codex 靠隔離家目錄的規則檔，而那條規則只放行以本次 PR 網址為目標的那一道，不經詢問的落點限於本次 PR（前提同執行目錄根層沒有上鎖那一條；推斷：由能力表讀取那一格與這兩項設定推得，沒有端到端量測，見下面 GitHub 側機制那一條）。隔離家目錄對上面任何一條都擋不到，而**契約文字也只接得住一半**：reviewer 契約的讀取白名單以路徑界定、點名的禁區也全是檔案，沒有一條把行程自己的環境列為來源（這一句講的是契約本身涵蓋到哪裡，不是還開著的缺口——環境那一類已由下一條那道清理關掉）；真正接得住的是「疑似憑證或個資只描述位置與性質，不抄值」那條輸出規則，連同讀回核對裡對應的那一項必過項（第二次核對時抄出了值就停下、不發布；兩者都是 reviewer 自己的判斷，沒有機制在後面），而它涵蓋的是通道一——值被寫進輸出檔再貼上 PR——通道二（模型自己那條對廠商 API 的連線）沒有任何一條條文涵蓋得到。把摘要檔與狀態檔放進 reviewer 的 prompt 不會提到的位置，擋的只是「就在隔壁而且路徑已經給你了」這個近便性，屬於模糊化。
- **pane 的環境會在 CLI 起來之前被清成一份白名單，而 `.roster` 記的 model 與 pane 裡實際跑的 model 不保證一致**：建立 pane 時只帶 `HOME`（opencode 另帶一個設定檔路徑），但 pane 繼承的環境不是呼叫行程的環境：直接在 pane 裡印出環境變數，`CLAUDE_CONFIG_DIR` 與 `CLAUDECODE` 都是空字串，而呼叫行程當下前者有一個真實路徑值、後者是 `1`；`HOME` 則確實等於建立 pane 時以 `--env` 指定的隔離家目錄（實測）。pane 繼承的是 herdr 背景服務行程的環境，這一條已經端到端量過（實測）：讀那個背景服務行程（herdr server）自己的環境，使用者 shell 啟動檔裡實際 `export` 的八個變數全部在裡面；另外新建一個 pane 再列一次變數名，同樣八個也全部在 pane 裡。**這組量測是做出下面那個決定的依據，留著當歷史說明，不要因為現在關掉了就刪掉**——它也是日後判斷有沒有退回原樣的基準。探測 pane 的建立條件是它站得住的關鍵：那個 pane 建立時就帶了指向隔離家目錄的 `HOME`，而那個目錄裡當時只有一個大小為零的 `.zshrc`（腳本本來就會放這個空檔，為的是壓住 zsh 對全新家目錄跳出的新使用者精靈；它同時反證了這台機器沒有把 zsh 的啟動檔目錄變數指到別處，否則這個排除論證會漏掉一條路），使用者的真實啟動檔不可能被 source，八個變數卻照樣全在——這正是排除掉「pane 裡的 shell 自己 source 了使用者啟動檔、於是自行 export 出同樣那八個」這條替代解釋的證據。值那一層也量過：在 pane 內與呼叫端各對三個變數的值取 sha256 前十二碼比對，三個全部相同，過程沒有輸出任何原文；那批變數裡有四個是憑證性質的，涵蓋 CI、第三方 SaaS 與內部服務三類，沒有一個是這次 review 用得到的東西，四個都確認出現在 pane 的環境裡（實測），值層那次比對的三個就是這四個裡的三個，剩下的那一個只有名稱層的證據。一跳的精度照本檔的憑據等級講：實測照字面涵蓋的是新建的那一個 pane，正式 reviewer 那幾格另外帶了指向隔離家目錄的 `HOME`（opencode 再帶一個設定檔路徑），真正跑 CLI 的又是在那個 pane 內被起起來的行程，這一跳幾乎確定成立但沒有直接量到（推斷）。**2026-09 這一輪整併把這條路關掉了，手段就是那個 `.zshrc` 本身**：空檔改寫成一段白名單清理，pane 自己的互動 shell 在 `herdr agent start` 把 CLI 起來之前執行它，清單以外每一個已經 export 的變數一律移除。所以「寫在使用者 shell 啟動檔裡的變數會進到 pane」仍是既成事實、不是可能式，改變的是它們在 CLI 看到之前就已經被移除。清理只能落在這裡、不能落在建立 pane 的當下：herdr 的 `--env` 只設得了變數，移除不了變數。四件事要跟著讀。其一，**靠的是白名單而不是列舉機密**：清單以外一律清除。列黑名單只擋得住今天量到的那四個，使用者明天多 export 一個就靜默漏掉；白名單漏掉的方向相反，漏的是功能、不是明天才出現的機密。**但不要把它讀成「pane 的環境裡沒有任何敏感值」**：清單上留著的不只是路徑與終端機那類單純的值，還有一整組通往使用者本人 session 的通道，清理之後照樣在 pane 的環境裡，而腳本沒有逐項記為什麼保留它們——`SSH_AUTH_SOCK`（使用者的 ssh agent，接得上它就用得到那把 agent 願意代簽的金鑰）、`DBUS_SESSION_BUS_ADDRESS` 與 `XDG_RUNTIME_DIR`（使用者 session 的訊息匯流排，以及它底下那組執行期 socket）、`DISPLAY` 與 `WAYLAND_DISPLAY`（有圖形 session 的機器上是顯示伺服器的連線位址）、以及 `HERDR_SOCKET_PATH` 配 `HERDR_BIN_PATH` 與那三個座標變數（等於把驅動 herdr 自己的能力留在 pane 裡，而編排端與其餘 reviewer 都跑在同一個 herdr 底下；推斷：由這支腳本自己就是在 pane 裡靠這幾個變數呼叫 herdr 推得，沒有人從 reviewer 那一格實際試過）。其二，**這份清單的地位是實測起點，不是已證明的充分必要集**：實測到的是「保留這幾個變數時四家 CLI 都起得來、其中 claude 能無人介入寫出輸出檔」（實測）。某一家可能有某項功能需要一個被清掉的變數，症狀會是那項功能靜默失效、而不是啟動失敗——驗收條件釘在真的寫出輸出檔、不是釘在起得來，正是為了這一點；至於清理之後 pane 裡確實不再有那幾個變數，是從 `.zshrc` 的內容推得的，沒有在清理後的 pane 內重跑一次值層比對（推斷）。其三，**這份清單會過期，兩個方向的症狀不一樣**：使用者日後在自己 shell 啟動檔新增的變數會被清掉、不會被放行（安全的那個方向，代價是他可能查不出某個設定為什麼在 pane 裡沒生效）；反過來，某天有一家 CLI 需要一個新變數時沒有任何機制會自己發現，得有人回來改這份清單，新增平台時也要逐項重新確認。其四，**這道機制成立吃三個前提，三個都是外部行為，任一個不成立時失效都是無聲的**。（一）pane 起的互動 shell 是 zsh——`.zshrc` 只有 zsh 讀。這台機器上是（實測：全新的隔離家目錄第一次啟動會跳 zsh 的新使用者精靈，當初放那個空檔正是為了壓住它）；預設 shell 不是 zsh 的機器上 herdr 會在 pane 裡起什麼、這道清理還在不在，未查證。（二）zsh 解析啟動檔的目錄就是那個隔離家目錄。這一條原本是一條靜默繞過的路：pane 繼承的是 herdr 背景服務行程的環境，其中若帶著指向別處的 `ZDOTDIR`，zsh 就改讀那邊的啟動檔，我們寫的這份 `.zshrc` 一次都不會被 source（實測：`ZDOTDIR` 指向別處時清理就不再發生，沒有任何錯誤訊息；把 `ZDOTDIR` 從白名單拿掉補不了這個洞，那份白名單就長在讀不到的那個檔裡）——現在建立 pane 時以 `--env` 把它與 `HOME` 一起釘向該 reviewer 的隔離家目錄，這條路封死了（`--env` 設得進去是實測，但量到的是 `HOME` 那一個；`ZDOTDIR` 釘死之後沒有在 pane 內重跑一次驗證，推斷）。（三）CLI 是在那個已經 source 過 `.zshrc` 的 shell 裡被起起來的，時序上排在清理之後（推斷：腳本以 `herdr agent start --pane` 指名那一格，這一跳沒有直接量測，與上面「清理後沒有重跑值層比對」是同一個缺口）。三者共通的失效症狀是同一個：沒有任何錯誤訊息，變數照樣進到 CLI，那一格看起來完全正常。因此底下兩處跨機器的宣稱，射程都只到這三個前提成立的機器為止。設定目錄那個變數的結論因此整個換掉，**現在關掉它的是這道機制，不是這台機器碰巧沒有設定**：`CLAUDE_CONFIG_DIR` 不在白名單裡，所以**只要其四那三個前提成立**，不論使用者有沒有把它 `export` 在自己 shell 啟動檔裡，它都會在 CLI 起來之前被清掉；前提不成立的那種機器上這一句整個不成立，而且不會有任何症狀提醒你。先前的記載留著對照：那時它不在 shell 啟動檔的 `export` 清單裡、不在背景服務行程的環境裡、也不在 pane 裡（實測），實例是關的、機制卻是開的，任何一台 export 了它的機器都會讓 claude 對設定目錄的隔離整個失效——白名單落地之後，「機制是開的」這半句不再成立。上一輪這裡引本倉庫部署註記當佐證是歸錯支了，記下來免得再被加回去：那份註記講的是 clauth 啟動 claude 時把這個變數設進被它啟動的那個行程，正是量測已經排除掉的呼叫端那一支；使用者的 shell 啟動檔裡搜這個變數只有一行註解、零個 `export`（實測）。連帶的一件事要認得：腳本寫進 `.roster`、最後呈現在 comment 開頭揭露段落那組 `platform/model` 裡的 model，讀的是使用者真實的設定檔（那一步跑在腳本自己的行程裡，不受上面那道清理影響）；而 pane 裡的 CLI 讀的是隔離家目錄：claude 與 codex 那裡面沒有任何 model 設定，`CLAUDE_CONFIG_DIR` 這條把 claude 指回真實設定目錄的路也已經被上面那道清理關掉，兩家實際會落到哪一個 model 未經量測（未查證）。**opencode 已經不在這個顧慮裡，舊版那句「已實測會落到內建的免費模型」不要再沿用**：那是一個 opencode 目錄都沒連時的觀測，四個狀態目錄整組連進來之後，使用者自己設定的預設模型解析得到（實測，見上面 opencode 那一條）。所以揭露段落裡的 model 對 claude 與 codex 仍應當成「呼叫端這一端解析到的 model」讀，不是「那一格實際跑的 model」。
- **agy 的 model 是破例硬編碼，會隨 Gemini 改版過時**：另外三個 CLI 都能從各自的設定檔讀回預設 model，agy 沒有任何途徑讀得回來（它的 models 子命令不標預設、json 輸出沒有 model 欄位、狀態檔裡也沒有），而 comment 開頭的揭露段落要求每個派出的平台都附一個真實的 model 值，所以腳本破例把它寫死（平台名與 model 只出現在那段揭露裡，finding 裡不帶，不要為了這一條把 model 補回每則 finding）；尾綴 `-high` 是 agy 自己編碼推理力度的方式，也是它不必再傳 `--effort` 的原因。代價是這個值會過時：症狀是 agy 那一格起不來或當場報錯，或揭露段落裡的 model 名稱與實際跑的那個對不上。
- **GitHub 側的機制只擋得住 reviewer 主動下 `gh` 指令這一軸，而且現在是 codex、opencode 與 claude 三家有——codex 那一層是要人按下核准才放行的對話框，只讓出以 `gh pr comment` 加本次 PR 網址開頭的單一指令，opencode 那一層不涵蓋 `gh pr comment` 的任何變體，claude 那一層是 auto 模式的分類器，允許規則確定放行的只有以 `gh pr comment` 加帶雙引號的本次 PR 網址起頭的單一指令，其餘交給分類器判定（是否一律擋未查證）；agy 這一軸全靠契約文字**（除了 codex 在與 reviewer 同構的 pane 裡跑過的那幾次——對不存在的 PR 執行 `gh pr comment` 的幾次，以及沒有規則檔時以 `gh api user` 測的那一次——和下面 claude 那一句列的那幾次之外，四家都沒有端到端量測；那幾次不是在正式 reviewer 那一格裡跑的，也沒有真的貼出內容；底下其餘引的是能力表各格自己的實測）：**reviewer 必須執行一道 GitHub 指令，這是契約自己要求的，舊版寫成「不需要也不應該、契約明文禁止它動 GitHub」是講反了**：契約的完成條件就是 PR 上存在一則它自己透過 `gh pr comment` 貼出的 review comment，而那條禁令的實際形狀是「以『發布』一節的 `gh pr comment` 發布，是唯一允許的外部狀態變更。其餘一律禁止」——擋的是授權範圍以外的寫入，不是全部。**先說那一軸以外的**：內容進 GitHub 的正式通道現在是 reviewer 自己在它那一格裡呼叫 `gh pr comment` 直連張貼，main agent 不代為執行、也不委派其他 agent 重複發布（舊版寫的「輸出檔經監督行程切出、再由 main agent 委派張貼」已經被直連張貼取代，只剩事後補貼那條路徑還走委派）。這條通道上本來有閘門的只有寫輸出檔那一步，而且只有 agy 有（依上表它目錄內外都要核准），另外三家直接放行——**而 reviewer 那一路的旗標已經把 agy 那一道也自動答掉，現在四家一律直接放行**；寫完之後的整條下游——reviewer 自己把它貼上公開 PR——四家一律沒有任何閘門，底下這三層對它一點作用都沒有。回到 `gh` 指令這一軸：claude 依上表 shell 直接放行，但那一格與 claude 欄其餘幾格一樣，是不帶權限模式旗標那一次的觀測（見表下那兩段）；明傳 `--permission-mode auto` 之後，對外的 `gh` 寫入要先過 auto 模式的分類器，而沒有允許規則時它擋下過契約授權的那道 `gh pr comment`：2026-11-16 一次以私人測試 PR 跑的完整流程裡，claude 那一格（herdr 互動 pane、腳本自己建的隔離家目錄與旗標）的對話紀錄記著被分類器以「Destructive or Unwanted Actions」拒絕，`gh` 根本沒執行，PR 上也就沒有它的 comment（實測）。所以被審查內容誘導出來的 GitHub 寫入多半也會被它擋下（推斷），但它是模型判斷、不是逐字比對的規則，不保證每一種寫法都擋（未查證）。**這一層也讓出了一道窄口**：腳本在它的隔離家目錄寫了 `.claude/settings.json`，只有一條允許規則 `Bash(gh pr comment "<本次 PR 網址>" *)`，網址的來源與格式驗證和 codex 那道相同（見下面）。量測都用 claude 2.1.325、與腳本相同的旗標與隔離家目錄、PATH 最前面放一支只記錄參數的假 `gh`、目標是不存在的 repo，全程沒有貼出任何內容。**互動那一路**：照 `_build_reviewer_panes` 的方式建兩格 herdr pane、以 `herdr agent start` 帶腳本的旗標起 claude、prompt 由腳本自己的 `build_prompt` 從現行契約組出，兩格都審完並以契約那道指令單獨執行、沒有被擋（實測）。**無頭那一路只當旁證讀**（`claude -p`，條件與本節前提不同）：沒有規則時被以「Unsanctioned Communication」拒絕，重現了上面的事件；有規則、單獨執行 3 次全數不經分類器直接執行；同規則但同一行後面以 `;` 串接 `echo "rc=$?"`，3 次全被擋（皆實測）——沒命中規則的那一段把整行送回分類器，這是推斷的機制；`&&`、管線、`$(…)`、反引號等其他串接寫法沒有測，會不會被放行未查證，其中 `--body "$(…)"` 的形狀符合規則的萬用尾段，關係到本機檔案外流，尤其不要當成已擋。契約的「發布」一節因此要求單獨執行。規則比對原始指令字串：不帶引號的規則不命中契約那道帶引號的指令（實測，在判定固定的 default 模式下比對），反方向推斷相同。`--edit-last`、`--delete-last` 配本次網址同樣命中，作用限於本次 PR（推斷，憑據同下面 codex 那一段）。**無頭那一路另有一次更直接的實測**，比表格那一格更貼近這個結論，但兩路量測條件不同、只當旁證讀：腳本註解記著 `dontAsk` 那個模式的唯讀 Bash 豁免實際放行過 `gh` 的留言指令，而且把那道指令寫進 `--disallowedTools` 也擋不住。互動式 claude 分支實際帶的旗標是 `--disallowedTools WebFetch`，關的是它內建的取網址工具，與 `gh` 無關（本檔別處沒有提過這個旗標，所以在這裡點名）。另外兩家各有一層，強度不一樣，不要讀成同一級：codex 是沙箱攔下之後再跳核准對話框，不是不需要人的自動阻斷——依網路格那個沙箱預設關閉網路，而 `gh` 寫入要走網路：沒有規則檔時，網路型 `gh` 指令在沙箱內連不上網路，codex 接著跳出是否在沙箱外重試的核准對話框、herdr 把那一格回報成 `blocked`，使用者按下核准就放行、執行成功（實測：codex-cli 0.156.1、herdr 互動 pane、與腳本相同的隔離家目錄結構，以 `gh api user` 測）；**而且這一層讓出了一道窄口：以 `gh pr comment` 加本次 PR 網址開頭的單一指令**：腳本在它的隔離家目錄寫了 `.codex/rules/default.rules`，內容只有一條 `prefix_rule`，比對四個 token——`gh`、`pr`、`comment`，加上本次 PR 網址，例如 `prefix_rule(pattern=["gh","pr","comment","https://github.com/o/r/pull/7"], decision="allow")`。第四個 token 形式固定為 `https://github.com/<owner>/<repo>/pull/<N>`，與 reviewer prompt 座標區塊「PR」那一行逐字相同，由 `prepare` 組成並寫進執行目錄的 `.pr-url`，`launch` 在派送任何 reviewer 之前讀一次固定下來再交給規則檔（為什麼要在派送前固定，以及規則檔所在的目錄仍在 reviewer 寫得到的地方，見執行目錄根層那一條）；網址為空或格式不符時，產生隔離家目錄的函式直接回傳失敗，不會退回不帶網址的寬規則（細節見腳本 `_write_codex_home_interactive` 的說明文字）。**實測分三組，條件各不相同，不要併成一句讀**（皆 2026-09-26）：其一，`codex execpolicy check`（codex-cli 0.156.1，規則第四個 token 為 `https://github.com/o/r/pull/7`）判為放行的是「該網址加 `--body-file`」「該網址加 `-R evil/repo` 加 `--body`」「該網址加 `--delete-last`」三道，不命中的是指向 pull/8 的網址、編號寫法 `gh pr comment 7 --body-file …`、編號加 `-R` 三道；同樣六道對不帶網址的三 token 規則全部命中。其二，herdr 互動 pane（codex-cli 0.156.1，隔離家目錄與腳本同構，規則第四個 token 指向一個不存在的 PR）：契約寫法——本次 PR 網址加 `--body-file` 絕對路徑——不跳框、直接連到 GitHub，回傳找不到該 PR；改指向另一個編號的網址，先在沙箱內連線失敗、再跳核准框、herdr 回報 `blocked`；編號加 `-R` 的寫法同樣跳框。兩次跳框都按了拒絕，全程沒有貼出任何 comment；那次也觀察到核准框的顯示形狀：`$ gh pr comment` 起頭、每個參數各佔一行，再截斷成 `[… 13 lines] ctrl+a view all`（實測，只觀察過這一次），`references/waiting.md`「codex 核准框的核對」那節六題是非的第一題因此實務上多半導向拒絕。其三，gh 2.100.0：完整 PR 網址與 `-R` 同時給時，不論順序都以網址解析 repo（`GH_DEBUG=api` 顯示查詢的是網址那個 repo，`-R` 給的是另一個），所以網址命中的那一道無法用 `-R` 轉到別的 repo；這一點沒有在 codex pane 裡重跑。**放行那一側剩下的是推斷**：`--edit-last`、`--delete-last` 配本次網址照樣命中（execpolicy 那一組實測到的只有 `--delete-last`），作用限於本次 PR 上使用者本人的最後一則——那一則可能是他親手寫的，也可能是同一批其他 reviewer 以同一個帳號剛貼的，連續呼叫還可以逐則往回刪（推斷：本機 gh 2.100.0 的 `gh pr comment --help` 寫明這兩個旗標作用在 current user 的最後一則 comment，由此推得，沒有量測）。**這道收窄的代價是明知才收的**：reviewer 若以編號或其他寫法張貼，會重新跳核准框（別的 PR 網址與編號加 `-R` 是上面 pane 內實測；只給編號不加 `-R` 只有 execpolicy 判定，執行期沒量過；把旗標放到網址前面等其他寫法，是由規則逐 token 比對開頭推得，推斷）。**不帶網址的三 token 規則是過去狀態，記在這裡當歷史，不要讀成現行**：PR #46 起、直到 issue #47 的 F1 把它收窄成四 token 之前，那條規則只有 `gh`、`pr`、`comment` 三個 token，比對完這三個之後接什麼都不看，所以不經詢問的射程不限 repo、也不限 PR 編號，`--edit-last`、`--delete-last` 可以作用在任何 PR 上使用者本人的最後一則；那時 codex 從要人按核准變成不詢問，這組寬射程因此四家一律成立。當時的實測是單一一道 `gh pr comment` 以 `--repo` 加 `--body`、以及契約那種 PR 網址加 `--body-file` 兩種寫法，對不存在的 PR 都不詢問、直接連到 GitHub。**收窄之後的外流面要照實講**：`gh pr comment` 在沙箱外執行，`--body-file` 或 `--body` 可以帶入使用者帳號讀得到的任何本機檔案內容，而依上表 codex 的讀取完全不受限，所以使用者讀得到的任何本機檔案內容，仍然可以不經詢問貼到本次 PR 上，貼到別的 PR 或別的 repo 則要人按核准（前提同執行目錄根層沒有上鎖那一條；推斷：由 `gh` 的語意、能力表跨目錄讀取那一格與上面三組實測推得，沒有端到端量測）；agy 與 opencode 沒有這道收窄（agy 在這一軸上沒有工具層閘門，opencode 的拒絕清單不涵蓋 `gh pr comment`，見下面），不經詢問就能貼到任何 repo 的任何 PR；claude 規則確定放行的只有本次 PR，其餘落點交給分類器判定（見上面 claude 那一句）——所以「四家合起來，可以把本機任何讀得到的檔案貼到任何 repo 的任何 PR」這組射程仍然成立（射程本身是推斷：本機 gh 2.100.0 的 `gh pr comment --help` 逐字列出 `-R, --repo` 與作用在 current user 的 `--edit-last`、`--delete-last`）。**codex 的落點雖然收窄到本次 PR，兩面不可逆在本次 PR 上照樣成立，不要讀成已解除**：規則只比對開頭四個 token，網址之後接什麼參數都放行，所以以 `--body-file` 貼出去的本機檔案內容一樣收不回（repo 若公開就是公開外洩），`--delete-last` 也一樣能逐則往回刪本次 PR 上使用者帳號的最後一則——而本次 PR 正是同一批其他 reviewer 以同一帳號貼 comment 的地方（推斷，憑據同上）。**串接寫法的查證程度分三級，不要讀成同一級**：以放行的開頭起頭、再用分號或 `&&` 接上另一個網路指令，或在 `--body` 裡以 `$(…)` 塞進另一個網路指令，三種寫法在三 token 規則下都是整行先在沙箱內失敗、再跳出核准對話框，理由寫的是在沙箱外重試整行（實測，同一組條件）；現行四 token 規則下這三種沒有重跑（推斷：同一種整行不命中的機制）；管線、反引號、換行等其他寫法在兩種規則下都沒有測，會不會被放行未查證——若其實會被放行，整行在沙箱外不經詢問執行，影響不限於 `gh`。`codex execpolicy check` 撐不起這一段的推論：它不拆解 `bash -lc` 的內容，連單純的 `bash -lc "gh pr comment …"` 都判成不命中（三 token 規則下實測），所以不能拿它的判定推論執行期對複合指令的行為；它對上面那六道單一指令的判定（四 token 規則下實測）、以及判 `gh api -X DELETE` 不命中（三 token 規則下實測），也只是對單一指令的比對。其餘 `gh` 寫入指令照舊被沙箱擋下、再跳核准對話框（推斷：由前綴比對的語意與上面沒有規則檔那次實測推得，沒有逐一量測）；opencode 是自動拒絕，腳本為 reviewer 寫的那份設定檔逐條拒絕了 `gh` 的狀態變更子命令，但那是逐條指令名的字首黑名單，與網路格描述的是同一種東西、要帶上同一個但書——清單不宣稱窮舉、其餘管道落回內建預設放行，所以它擋得住按名叫出來的 `gh` 寫入，擋不住等價的其他管道；**而且 `gh pr comment` 不在裡面**：腳本的互動版設定刻意拿掉了那一條拒絕，好讓契約那道張貼過得去，而 opencode 又以 `--auto` 啟動，所以 `gh pr comment` 的任何變體都不經詢問放行，射程與上面三 token 規則時期的 codex 相同，不限 repo、不限 PR 編號（推斷，憑據同那一段）。**agy 曾經是第三層，現在沒有了，這是實質的暴露面擴大，不要淡化成措辭調整**：它那一層是人工閘門——未列入允許清單的一律跳核准對話框，而它的允許清單只有兩條 `git diff` 規則——本來就只撐得起 shell 送出的指令那一路（依它的預設行為格，取網址類與未沙箱類工具未測、未查證，那正是不經 shell 直接打 API 的路），而且使用者按下去就開了；`--dangerously-skip-permissions` 把那道對話框整個自動答掉之後，這一軸上旗標層什麼都不擋，剩下的只有契約文字，以及底下那個對四家一律成立的憑證與網路前提。**那份 `gh` 拒絕清單因此不是裝飾**，下一次精簡設定不要順手拿掉——它是 opencode 在這一軸上唯一的屏障。claude 那個 `--disallowedTools WebFetch` 要照它自己的軸讀，別拿上面那句類推：它買到的是關掉工具層那一條取網址路徑，等價的 Bash 路徑照樣開著（能力表 claude 網路格是未關閉、`curl` 直接放行；腳本註解另記著一次更直接的實測，同樣是無頭那一路——移除 `WebFetch` 想關掉的那條外流路徑經 Bash 仍然開著，四種旗標組合都打得到本機監聽埠）。所以它值得留著，但不要當成擋得住。**agy 這一軸上剩下的只有契約文字（claude 另有分類器那一層），憑證不構成任何門檻——舊版把「需要使用者自己的 gh 憑證」寫成僅剩的屏障，那是講反了，不要再沿用**：腳本為四個 reviewer 建隔離家目錄時，每一個都把使用者真實的 gh 設定目錄以符號連結掛進去（來源跟著 `GH_CONFIG_DIR` 走，沒設定才退回 `$HOME/.config/gh`），所以 pane 裡的 `gh` 照家目錄相對路徑解析到的就是使用者真實的那一份設定與憑證，不需要任何跨目錄讀取，也不是一種待量測的可能性。**這是刻意授予、四家一律成立**：審查契約本來就要求 reviewer 自己執行 `gh pr comment` 張貼，整套直連張貼的設計依賴它成立，拿掉它交付路徑就斷了。所以這一軸的實況是：codex、opencode 與 claude 各有一層工具面的攔截（沙箱層、逐條指令名的拒絕清單、auto 模式的分類器，見上面幾句；codex 那一層要人按下核准才放行，只讓出以 `gh pr comment` 加本次 PR 網址開頭的單一指令；opencode 那一層不涵蓋 `gh pr comment` 的任何變體；claude 那一層由模型自動判定、不問人，允許規則確定放行的只有以 `gh pr comment` 加帶雙引號的本次 PR 網址起頭的單一指令，其餘寫法擋不擋未查證），agy 連那一層都沒有，四家共通的剩餘屏障只有契約裡那條「除授權的 `gh pr comment` 之外不得寫入 GitHub」的文字——**注意它擋的是授權範圍之外，而不是全部 GitHub 動作**（同項開頭已經更正過這一點）。**環境變數那一支照舊記著，但它現在是一條旁路、不是門檻**：讀真實 `gh` 二進位的完整環境變數清單，與憑證及定址相關的有 token 類四個（一般兩個、企業版兩個）、一個設定目錄變數、一個主機變數（實測），token 類優先於已儲存的憑證。這幾個在這台機器上全部既不在背景服務行程的環境裡、也不在使用者 shell 啟動檔的 `export` 清單裡（實測），而且六個沒有一個列在 pane 的環境白名單上，所以結論與上面設定目錄那個變數同形：這條路上關掉它們的是機制而不是這台機器的巧合——換一台把其中任何一個 `export` 在自己 shell 啟動檔裡的機器，那個變數一樣會在 CLI 起來之前被清掉，`gh` 不會因此帶著認證，也不會被指向使用者自己的設定與主機。**同形也包含前提**：這一句的射程止於環境清理那一條其四所列的三個前提成立時，前提不成立就靜默退回原樣，六個變數照樣進到 CLI。**清掉那六個變數並不會讓 `gh` 失去認證**：認證是由本條開頭那道設定目錄符號連結給進去的，環境變數只是另一條入口。家目錄那一條因此已經有明確答案、不再是未查證的分支——隔離家目錄改變了波浪號展開的家目錄解析，而腳本正是把使用者真實的 gh 設定目錄連在那個解析結果上，所以 pane 裡那一份看得到的就是使用者自己的設定與已儲存的憑證。網路那一邊本腳本確實沒有做任何隔離。worktree 狀態比對補不上這裡，它只涵蓋檔案系統。PR 狀態或既有留言出現非預期異動時，從這裡查起。
- **共用工作區的並發比對可能誤標，誤標與否由 main agent 判讀**：所有 reviewer 共用同一個 worktree，腳本在每個 reviewer 啟動前取一次該 worktree 的 git 狀態快照，監督行程再於該 reviewer 寫完輸出檔後取一次；前後不同即記為 `withheld`。由於多個 reviewer 同時執行、而比對是依序輪詢的，前一個的事後快照可能被還在跑的後一個影響。**這個標記擋不住張貼**：張貼由 reviewer 在自己那一格直連完成，它觀測不到 worktree 狀態，所以判成 `withheld` 的那一則很可能已經貼出去，而它依據的程式碼在審查期間被動過；標記影響的只有回報與收尾（腳本不對它做張貼確認、因此不會全數確認，收尾前要先走補貼那一條，而補貼流程不代貼它）。偵測本身也有盲區——前後快照的比對擋不住改完又還原：reviewer 若寫入檔案後在自己寫完 review 之前刪掉，或把已追蹤檔案改回位元組相同的內容，兩次快照會相等而判為正常。
- **狀態比對涵蓋被 gitignore 忽略的路徑**：這是刻意的選擇，為的是不讓「違反會被偵測到」這個承諾在被忽略的路徑上落空。代價是某個 CLI 若在工作區內產生自己的快取或暫存檔、而該路徑剛好被忽略，會造成誤報。
