# 收尾清理

載入時機見 `SKILL.md` 的 Reference 載入時機表那一列。`SKILL.md`「收尾清理」那節列的是步驟順序，本檔是每一步的條件、守衛與回報方式。狀態投影指令、查詢失效處置與 `unknown` 的三種成因在 `SKILL.md`「等待與判斷」那節；「疑似卡死」與 `stalled` 的處置在 `references/waiting.md`。

## 先做的兩件事

**收尾有兩件事要無條件先做，做完才輪到下面的判斷。** 第一件是查 `.supervisor.pid`（見下面「先查 `.supervisor.pid`」那段）。**第二件是對每一個派出的 CLI 各取一次即時 `agent_status`**（用 `SKILL.md`「等待與判斷」那節那條狀態投影指令，pane 識別碼取自派出摘要）——**這一步不掛在關 tab 那道守衛底下**：守衛是逐項成立才往下走，一旦卡在前面某一項就永遠跑不到這次查詢，而那正是最需要它的情況（有格子沒關成、或狀態檔與實際對不上）。所以它是收尾回報的固定步驟，不論 tab 關不關都要跑，結果用在兩個地方：判「狀態存疑」（見下面那段揭露的定義），以及供關 tab 守衛第五項直接引用、不另外再查一次。

**先查 `.supervisor.pid` 裡那個行程編號還活不活著，還活著就要告訴使用者。** 這一查要排在呼叫 `cleanup` 之前，執行目錄一刪那個檔就沒得查了。觸發這項揭露的是這個訊號，不是「有沒有 reviewer 沒寫完輸出檔」——全數確認那一支也可能查到它仍存活。還活著時據實說明這個背景行程仍在輪詢、編號從 `.supervisor.pid` 取得，要不要終止由他決定；**它還活著有一種良性成因，要一併講、不要只講「還在等 reviewer」**：worktree 的移除不等關閉佇列清空，所以每個 reviewer 都完成之後，它可能只是還在把剩下那幾格的關 pane 重試跑完（每格上限兩分鐘），那一段時間它活著是正常的；腳本沒有提供終止它的途徑，這裡也不代為終止，所以這是揭露而不是承諾。**終止有一個立即後果，要在他決定之前先講**：還在關閉佇列裡那幾格的缺行會當場成為最終結果——那一行只有活著的監督行程寫得出來——那幾格從此永遠開著、tab 因此關不掉，而 `pane_closed=yes` 是編排端唯一拿得到的正面張貼憑據，也一併失去。**它還活著的原因若是還有 reviewer 沒交出輸出檔，終止的後果更重**：那幾格從此不會有摘要行，worktree 也不會再被移除（移除是它把待處理集合跑空之後才做的事），本次因此不可能再全數確認。**下一次執行那一層的後果同樣要講清楚**：行程一死而 `.supervisor.pid` 仍在，下一次針對同一個 PR 的執行會把這個執行目錄判為陳舊、強制移除它底下的 worktree，而那幾個 reviewer 可能還在跑，程式碼會從它們底下被抽走。

**查詢失效的收尾變體**（查詢失效本身的處置見 `SKILL.md`「等待與判斷」那節，這一段只管收尾時點，否則那一支會把收尾無限期擋住）：走到收尾時每一格都已經定案、沒有對象可等，此時重取一次仍無輸出，就據實回報這一輪查不到狀態、**tab 不關**（守衛拿不到它要的狀態就是沒過），但**清理照常判**——全數確認那一支的清理條件全部讀檔案、不依賴這次查詢，條件齊了就呼叫（要走補貼的那一支照 `references/backfill-posting.md` 處理，它在狀態取不到時要先停下來問），並告訴使用者 tab 留著的原因是狀態查不到、不是還有 reviewer 在跑。這種時候 `cleanup` 多半會以「無法確認」拒刪（推斷：它的存活檢查問的是同一個 herdr 查詢，由腳本推得；只有比對到的那一筆 `agent_status` 變形而 `agents` 仍是陣列時，拒刪原因會是「還有 agent」，同樣由腳本推得），要照下面「執行目錄沒刪掉」那一類回報執行目錄保留，然後結束這一輪收尾，不要等狀態查詢恢復，也不要讓使用者以為執行目錄已經刪掉。

## pane 定案

**pane 由腳本逐格關，自己判的只有 tab。** 編排端不自己關任何一格 reviewer pane：監督行程在每個 reviewer 完成之後，先確認它那則 comment 真的貼在 PR 上——`ready` 那一路是把 PR 上每一則 comment 的本文與該 reviewer 的 `review.md` 全文逐位元組比對（只差尾端換行不計），`posted-no-output` 那一路用的是回音室標記、揭露段落點名、建立時間晚於本次派送這三項合起來的歸屬判定——四道守衛全部通過才關那一格：該 CLI 的 pane 識別碼檔案存在、那個識別碼不等於 `HERDR_PANE_ID` 也不等於 `HERDR_TAB_ID`、PR 位址讀得出來、comment 確認通過。**第二道守衛吃一個沒有被驗過的前提**：它比的是那兩個環境變數的值，而環境閘門只驗 `HERDR_ENV` 恰為 `1`，從未確認那兩個變數非空；任一為空時比對不會命中，那道「關不掉編排端自己」的保護等於不存在。實務上 herdr 會把這兩個值注入每一格 pane，所以這是前提而不是缺陷——但要當成前提記著，不是當成保證。**任何一道沒過就不關**，是哪一個 CLI、因為什麼原因沒關，逐行記在執行目錄根層的 `.pane-close-status`（一行一個 CLI）；那是編排端唯一讀得到的關閉結果，回報哪幾格還在時照它講、不要自己推測。

**確認不到不是一次定生死，但也不是無限等：`ready` 那一路會重試。** reviewer 的順序是先寫完輸出檔、讀回核對、最後才呼叫 `gh pr comment`，而摘要行在輸出檔一完整時就寫出，所以第一次確認幾乎必然早於那則 comment 落地。因此那一路改成每五秒再試一次，從它進入待關閉狀態起算滿兩分鐘仍確認不到才放棄、那一格留著，並在狀態檔寫下與其他失敗原因分開的 `reason=confirm-timed-out`（`posted-no-output` 那一路不重試，它是先在 PR 上找到 comment 才走過來的，沒有這個時間差要追）。**兩件事跟著這道重試走，回報時不要誤讀**：摘要行完全沒有因此延後；worktree 的移除條件仍只看待處理集合有沒有清空、不等關閉佇列，所以監督行程可能在 worktree 已經移除之後還活著一小段時間，單純把剩下的關閉重試跑完——那不是異常。

**`pane_closed=yes` 的強度分兩路，不得併成一句讀**：`ready` 那一路是內容相符的硬證據（PR 上真的有一則與那份輸出檔逐位元組相同的 comment）；`posted-no-output` 那一路只是歸屬啟發式——它認得出「有人在本次派送之後貼了一則長成這樣的 comment」，認不出「是不是這一格 reviewer 貼的」（能滿足那三項的身分包括每個 reviewer 自己，而契約本來就授權它執行 `gh`，被審查的 diff 與 issue 又是公認的注入管道，詳見 `references/rationale.md`）。反過來則兩路都不成立：`reason=confirm-timed-out` 與 `reason=comment-not-confirmed` 都只說確認不到，`gh` 查詢自己失敗也落在這兩個值上，不得讀成「確定沒貼上去」。`withheld` 與 `no-content` 那幾格根本不會被交給關閉流程，所以它們在這份檔案裡連一行都不會有——**缺行與 `pane_closed=no` 一樣算沒關成**，這正是一個失敗的 reviewer 保住自己畫面的方式。**但有一種缺行是暫時的**：剛落地為 `ready` 的那一格可能還在重試佇列裡、還沒寫出它那一行，所以摘要剛湊齊那一刻讀到的缺行未必是最終結果——等它定案再據以回報、再判 tab 關不關。**定案不等於只會落在那兩個值上**：第一次嘗試就可能卡在某一道守衛沒過、或關閉動作自己失敗，那幾種不經過重試視窗；兩分鐘是等待的上界，不是值的清單，照狀態檔那一行的原文轉達即可。**這個等待要有終止條件，否則會等成死結**：`.supervisor.pid` 裡那個行程編號已經不存在時，當下的缺行就是最終結果——那一行只有活著的監督行程寫得出來——那幾格從此永遠開著，不要再等；嚴格檢查判定監督行程已死、以及收尾時使用者決定終止它，都落在這一種。**另外兩種終止條件同樣要用上，否則一樣會停在等一個不會出現的結果**：其一，`withheld` 與 `no-content` 那幾格根本不會被交給關閉流程，它們的缺行從第一刻起就是終局，不必等；其二，監督行程還活著時等待有上界，**但上界要留餘裕，錨點也要釘在最後一則 reviewer 摘要行**（不要用摘要檔的整體定義去推）：逾時那一行要等該格重試冷卻到期的那一輪、而且那一輪的確認嘗試又失敗才寫得出來，中間還夾一次網路往返，所以實際落點比「最後一則 reviewer 摘要行落地加兩分鐘」還要再晚最多一個重試間隔。**過了這個時點要再重讀一次狀態檔，仍然缺行才照最終結果讀**——照字面在那一刻就定案，可能在監督行程其實還持有那一格時呼叫清理，正好撞進「順序寫反的兩個方向都會壞」那段講的結局。

## 全數確認與補貼

**執行目錄與本次那個本地分支是本 skill 自己建的，收尾時由本 skill 自己收，不留在磁碟上。** 收的時機只分兩支，判準是**全數確認**：每一個派出的 CLI 在 `.pane-close-status` 裡都有一行，而且都是 `pane_closed=yes`——腳本已經親自在 PR 上對到每一格的那則 comment（兩路的強度差別見「`pane_closed=yes` 的強度分兩路」那段）。
- **全數確認**：直接收，收完把結果回報給使用者。`.supervisor.pid` 那個行程仍存活時，先照「先查 `.supervisor.pid`」那段揭露，等它自己結束或使用者決定之後再收。
- **沒有全數確認**：先補貼、再收。那一行不是 `pane_closed=yes`（含缺行）的每一格，有本地 `review.md` 的（`ready` 或 `withheld`）載入 `references/backfill-posting.md` 照它處理，`no-content` 那幾格沒有東西可補。每一格都走到**終點**才收，終點只有三種：那一格的 review 已經在 PR 上（補貼成功，或去重判定已經貼過）；使用者決定不貼；`no-content`。`withheld` 交出自行張貼指令那一種，要等使用者回報已經執行（算第一種）或決定不貼才算終點。補貼流程的其他結局——張貼失敗、還在跑而先不補、狀態取不到、去重答不出、摘要行或 cli 值不合格式而無法補貼——都不是終點：照實告訴使用者，由他決定再試還是放棄，放棄就算「使用者決定不貼」。補貼路徑自己的停下閘門（目錄確認、PR URL 確認、公開確認）照它的規定逐一過完。

**還有格子始終沒有摘要行時收不了**：那幾格的 reviewer 沒跑完，worktree 不會被移除，那幾格也還沒定案（定案的終止條件見「pane 定案」那節），`cleanup` 什麼都刪不掉。照「執行目錄沒刪掉」那一類交出執行目錄的絕對路徑，等那幾格有了結果再回到這裡。這一條、以及建 pane 途中失敗、`references/exit-codes.md` 列出的失敗路徑、main agent 被中斷，是執行目錄會留在磁碟上的幾種情形。

## tab 的去留

**tab 的去留自己判**，守衛五項，**全部成立才關**：只關 `run` 印出的那一個 `tab_id`；它不得等於環境變數 `HERDR_TAB_ID`（main agent 自己就跑在某個 tab 裡，關錯就是把編排者殺掉）；時機兩端都要釘住——下端是每個 reviewer 都有摘要行、`.pane-close-status` 裡每一格都已定案，上端是**這道守衛連同它那次讀檔都必須排在呼叫 `cleanup` 之前**（同「先查 `.supervisor.pid` 再呼叫 `cleanup`」那條的道理：檔案就在執行目錄裡，`cleanup` 正常結果就是把整個執行目錄刪掉，一刪就沒得讀了）；**每一個派出的 CLI 在 `.pane-close-status` 裡都有一行而且都是 `pane_closed=yes`**——還開著的那一格正是失敗訊息只存在於畫面上的那一格，關 tab 會把它一起帶走，而腳本刻意不關它就是為了留住那段訊息；**第五項直接引用收尾那次固定的逐格狀態查詢**（見本檔「先做的兩件事」，不在這裡另外再查一次，也不因為前四項沒過就跳過那一步）：任何一格還在 `working` 或 `blocked` 就不關，改成回報並詢問。**這一查撞上 `unknown` 是預期中的事**：已經被關掉的那幾格在 herdr 的清單裡不存在、一律回 `unknown`，走到這個時點時往往每一格都是——依 `SKILL.md`「等待與判斷」那節 `unknown` 的第三種成因，那是收尾的正常終局，**不得判成狀態查詢整組失效、也不得回報成任何一格消失**；這道守衛要答的只有「還有沒有哪一格在 `working` 或 `blocked`」。`done` 不納入這項守衛，也不納入死線那組條件的第一項。**排除它的理由不吊在「它會自行轉回 `idle`」上**：`done` 既不是「有人在等你回答」也不是「還在跑」，這兩處要攔的就是那兩種，所以就算它不會自己轉回去，照樣不該算進來。至於它是剛完成一輪問答後的短暫狀態、不施加任何動作也會很快轉回 `idle`，**是推斷不是實測**——`SKILL.md`、本檔與 `references/rationale.md` 都沒有留下對應的量測記錄，憑據只有這個狀態名自身的語意與流程中它從不持久的觀察；要靠它下判斷就得先對真實二進位量一次。**「都貼上去了」現在是關 pane 的前提，但答它的是腳本不是編排端**：確認在腳本那一側完成，編排端只讀 `.pane-close-status`；不要把它改寫成一條要編排端自己去 PR 上核對才過得了的守衛，那正是上一版把它排除在外的理由——一個編排端答不出來的條件不會讓人停下，只會被唯一拿得到的代理指標頂替。**第四項就是全數確認**：tab 能關的那一次，執行目錄也會直接收，兩件事的順序照「順序寫反的兩個方向都會壞」那段——先判 tab、再呼叫 `cleanup`。

**還要知道這道守衛吃的是什麼層級的訊號**：`.pane-close-status` 與摘要檔同在執行目錄根層，而那一層自始至終 reviewer 寫得到（見 `references/rationale.md`），所以一行偽造的 `pane_closed=yes` 就能讓守衛通過、tab 被關掉，把那一格自己的錯誤畫面一起帶走（同一行也會讓那一格被算進全數確認，執行目錄因此不經補貼就被收掉，見 `references/rationale.md`）——恰好推翻「`pane_closed=yes` 的強度分兩路」那段那句「失敗的 reviewer 靠這個保住自己畫面」。關之前那次 agent 狀態查核只接得住一半：它攔的是 `working` 與 `blocked`，而停在錯誤畫面上的那一格通常是 `idle`。這裡只做揭露、不新增機制，但**「狀態存疑」要有可觀察的定義，不留自由心證**：就用收尾那次固定查詢本身的矛盾——狀態檔把某一格記成 `pane_closed=yes`，而那次查詢對同一格回來的值**不是 `unknown`**（例如 `idle` 或 `done`；整條指令沒有輸出不算回來一個值，那是查詢失效，照本檔「查詢失效的收尾變體」那段處理）。憑據是實測：在一格 pane 裡起一個 agent，關閉前後各查一次 herdr 的 agent 清單，關閉前那個 pane 命中一筆、關閉後命中零筆，直接查那個 agent 則得到找不到的錯誤。**但要連同一個映射細節一起記，否則會把判準定錯邊**：那條投影指令在 `agents` 陣列裡比對不到這一格時給的是 `unknown`，所以 pane 關掉之後它回的仍然是 `unknown`、不是空值——編排端因此分不出「已關」與「因別的緣故不在清單裡」，兩者都呈現為 `unknown`，可用的矛盾訊號只剩「記成關閉成功、值卻不是 `unknown`」這一側。這兩件事同時成立時，那一格要連同還開著的那幾格一起講給使用者聽，讓他有機會在關 tab 之前切過去看。

每一格都關成功時，tab 底下已經沒有本次留下的 pane（tab 自己的 root pane 在建 pane 那一段結束時就被關掉了），關它只是收掉一個空殼；最後一格被關掉之後那個 tab 還在不在沒有量過（未查證），所以這一步回報「找不到那個 tab」要當成正常結果，不是錯誤。

五項守衛之外還要對使用者說一句，**時點錨在收尾回報的當下，也就是關 tab 與 `cleanup` 兩個不可逆動作之前**，錨在它們之後就沒有意義了。**不要拿「到那時已經沒有格子開著」當理由**：守衛通過不等於每一格真的關掉，狀態檔就在 reviewer 寫得到的那一層，一行偽造的 `pane_closed=yes` 就能讓守衛放行而那一格其實還開著（見上面那段揭露）。所以收尾回報時就請他切過去看看**還開著或狀態存疑的那幾格** pane 上有沒有終局訊息（保留條件蓋不到全部，見 `references/rationale.md`）。這是告知，不改變收尾條件。**這是同一條繞經人的注入管道在本 skill 的第三個入口，照 `SKILL.md`「腳本返回時」那節的「只問類別」辦，不另立寬鬆版本**：這裡問的類別是「有沒有終局訊息、屬於哪一類」。這一處風險最高——終局訊息本來就是錯誤訊息的形狀，最容易被整段貼回來。

## 呼叫 `cleanup` 與回報

**兩項條件同時成立才把執行目錄與本次那個本地分支交給腳本收**（每一次呼叫都適用，唯一的例外見下面「補貼還沒走完……都不要呼叫」那段）：全數確認，或沒有全數確認但補貼已經走完（見「全數確認與補貼」那節）；`.pane-close-status` 裡每一個派出的 CLI 都已定案（還在重試佇列裡的缺行不算定案，判準與終止條件見「pane 定案」那節）。**呼叫之前還有一件事要先做完**：關 tab 那道守衛要讀的狀態檔就在執行目錄裡，而 `cleanup` 正常結果就是把整個執行目錄刪掉，所以那次讀檔與 tab 的去留判斷都要排在這一步之前（見上面「tab 的去留」那節）。

**沒有全數確認而補貼還沒走完、或 `.pane-close-status` 裡還有任何一格沒定案，都不要呼叫 `cleanup`**（這道閘門，連同上面「由本 skill 自己收」「兩項條件」那兩段與下面「任一格尚未定案」那一條，照常適用於每一次呼叫；唯一的例外是「刪除失敗」之後、使用者明確要求再收的那一次——閘門要讀的檔案可能已經不在，這時依使用者的明確要求與下面「執行目錄沒刪掉」那一段的確認處理）：worktree 已被移除、而且存活檢查沒有擋下時（放行條件見下面「執行目錄沒刪掉」那一段），它會直接刪掉整個執行目錄，而那是 `references/backfill-posting.md` 唯一的資料來源，刪掉不可回復。**那道存活檢查取代不了這道閘門**：它只看 agent 在不在，不看那份 review 貼上了沒；某一格的 pane 已經被關掉時，它就不會擋（那一格的 CLI 自己結束之後 herdr 是否也不再列它、因而同樣不擋，沒有量測）。改成據實回報執行目錄的絕對路徑，等補貼走完、那幾格定案之後再呼叫 `cleanup` 收。**還沒收的執行目錄只由 `cleanup` 收**（那條路徑才會連同本次分支一起處理、並做存活檢查），不受暫存檔規則的例行清除約束。

**順序寫反的兩個方向都會壞，而且壞成不同的樣子。** 先 `cleanup` 再判 tab：狀態檔已經隨執行目錄消失，而依「`pane_closed=yes` 的強度分兩路」那段，缺行等同沒關成，整份檔案不見最可能被讀成每一格都沒關成，於是一個其實已經空掉的 tab 永遠留著。還有格子沒定案就 `cleanup`：關閉流程每一次嘗試都要從執行目錄根層讀 `.pane-<cli>` 與 `.pr-url`，目錄一沒，下一次嘗試就停在第一道守衛（拿不到 pane 識別碼），而那一行失敗原因要追加的路徑同樣不存在、寫入被吞掉，那一次呼叫卻仍然回報成功，於是呼叫端把它當成終局、不再放回佇列——**那幾格是在下一次嘗試就無聲掉出佇列，不是一路重試到上限**，結果是永遠開著、而且連一行原因都留不下（逐位元組那道確認在這條路上根本輪不到被呼叫，流程停在更前面那道守衛）。還在關閉重試佇列裡的那一格，pane 通常還開著、agent 也還在，所以 `cleanup` 的存活檢查多半會拒刪，這個失敗形態大多會被腳本擋下（推斷：由腳本讀出，沒有量測）。**因此任一格尚未定案時不要呼叫 `cleanup`**（每一次呼叫都適用，唯一的例外見上面「補貼還沒走完……都不要呼叫」那段），這條不因為那道檢查而放寬：agent 已經離開、狀態檔卻還沒定案的那幾種情形，存活檢查擋不住。這一項與收尾那一項條件（全數確認，或補貼已經走完）各自獨立，兩項都成立才收。

```bash
<run-review.sh 路徑> cleanup --base-dir "<base_dir>"
```

它自己從執行目錄推導分支名與目標 repo，印三行：worktree 是否被移除、執行目錄刪掉了沒（沒刪成附原因）、分支刪掉了沒（沒刪成附原因）。照這三行回報即可，**不自己組分支名，也不自己下刪除指令**——那個名字要從執行目錄路徑逐段拆出來才組得成（PR 編號在父層名稱裡，尾端那段行程編號在目錄名裡），拆偏一段、或路徑本身被搬過改過，強制刪除就落在使用者自己那條同前綴的分支上，而那種分支可能帶著只存在於本地的 commit，刪掉沒有任何地方救得回來（本次這個分支之所以敢強制刪，靠的是它的內容等於 PR head、隨時 fetch 得回來，別的分支沒有這個底氣）。腳本自己從執行目錄與 `.repo-path` 推導同一組值，少掉的正是這一手轉抄。

「執行目錄沒刪掉」那一行有四種來源，性質不同，**要照它附的原因分開回報，不要收在同一句**。**任何一種都不在同一次收尾裡自動重試 `cleanup`**：照原因回報、交出執行目錄的絕對路徑，然後結束這一輪收尾；之後使用者明確要求再收一次時才再呼叫。附「worktree 還在」的是正常結果，什麼都沒被刪，每一格都 `ready` 與「worktree 沒被移除」可以同時成立；附「reviewer 那一格還有 agent」或「那一格是否還有 agent 無法確認」的（原因裡會點名是哪個 cli），是 worktree 已移除之後、刪任何東西之前，腳本依 `.roster` 與各格的 `.pane-<cli>` 向 herdr 查到那一格仍有 agent，或是 herdr 查詢失敗、輸出解析不了、沒有 agent 清單——「無法確認」就是這三種，回報時要一併說明——執行目錄完全沒被刪，分支那一步照舊嘗試（沒有 `.roster`、或某一格沒有 `.pane-<cli>` 或內容為空時，那一格不列入這道檢查、不擋刪除）。**原因只點名第一個被擋下的 cli**，後面還有沒有別格它不說，所以回報時要從 `.pane-close-status` 裡不是 `pane_closed=yes` 的那幾格，加上收尾那次固定查詢的結果，一次列出所有可能還開著的格子。要告訴使用者：這些格子由他自己看完畫面後關掉，編排端不關 pane、也不終止任何行程（不關 pane 的理由見「pane 由腳本逐格關」那段；不終止 reviewer 的出處是 `references/waiting.md` `stalled` 與「疑似卡死」那兩條，不終止監督行程的出處是本檔「先查 `.supervisor.pid`」那段）；使用者自己關 pane 不會更新 `.pane-close-status`，所以 tab 也要由他自己關。之後他明確要求再收時才再呼叫 `cleanup`，腳本會自己重新做存活檢查；這時執行目錄是完整的、閘門要讀的檔案都在，收尾閘門照常適用。呼叫 `cleanup` 之前若已經有任何一格是 `pane_closed=no`，那一格的 agent 通常還在，可以預期會被這一道拒刪、先告訴使用者（推斷：互動式 CLI 完成後不會自行退出，由腳本只在確認張貼之後才關 pane 推得，沒有量測）；附「刪除失敗」的是刪到一半——腳本的刪除分兩階段，第一階段刪掉執行目錄裡 `.repo-path` 以外的一切，第二階段確認只剩 `.repo-path` 之後才連同目錄一起刪掉它，任一階段沒刪完都會印這個原因。執行目錄還在，這一種要把絕對路徑交出去講；腳本這時會把材料與 log 目錄重新鎖回唯讀，但那只在這兩個目錄還在時才成立，它們可能已在第一階段被刪掉。第一階段中途失敗時 `.repo-path` 仍在；第二階段的遞迴刪除途中有東西寫入，或最後移除目錄本身失敗（例如父層目錄不可寫），`.repo-path` 可能已經被刪，下一次呼叫會得到「不是本 skill 的執行目錄」。要告訴使用者：排除阻礙（例如還開著的 reviewer 那一格）由他自己處理，之後他明確要求再收時才再呼叫；這時腳本的存活檢查多半已經因為缺檔而跳過，閘門要讀的檔案也可能已經不在，所以再收之前要由使用者確認 reviewer 那幾格都已經關掉，編排端不為這一步另外自創 herdr 查詢（這一次的閘門怎麼處理，見「補貼還沒走完……都不要呼叫」那段的例外）；附「不是本 skill 的執行目錄」的代表 `base_dir` 給錯、那是舊版留下的目錄，或前一次 `cleanup` 在第二階段中斷（`.repo-path` 已刪而目錄還在），三行全部什麼都沒做——前一次呼叫印過「刪除失敗」、這一次才得到這個原因時屬最後那一種，要把絕對路徑交給使用者人工處理，不要判成 `base_dir` 給錯。

**分支刪除在三條路徑上都會被嘗試**：worktree 還在、reviewer 那一格還有 agent 或無法確認而拒刪執行目錄、以及往下刪執行目錄的那一條。worktree 還在時擋下它的是 git 自己拒絕刪除仍被檢出的分支，不是腳本跳過了那一步，所以那一行照樣印得出理由；reviewer 還在那一條則照舊嘗試刪除，因為 worktree 已經移除，那道存活檢查只管執行目錄。不要因為「worktree 還在時」或「reviewer 還在時」它不刪執行目錄，就推論分支那一步也一併跳過。
