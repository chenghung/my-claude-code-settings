# 狀態欄位缺漏的兩種成因

載入時機見 `SKILL.md` 的 Reference 載入時機表那一列。本檔接在 `SKILL.md`「腳本返回時」那節之後：缺欄位那一行一律比照「尚未進入審查中」處理，不得讀成任何肯定訊號，也不得略過不提。這個讀法與成因無關；成因只決定還要多講什麼、還要一併回報什麼。兩條成因各有自己的辨識訊號：

- **確認結果檔一開始就建不出來**：確認步驟往標準錯誤印一行專屬警告後就整個返回，沒有任何一格拿得到狀態值，於是每一行都落到不帶欄位的那個分支。判準是標準錯誤上有沒有那則專屬警告，有才是這一條。屬這一條時，除了逐行的安全側讀法之外，還要加上「本次的確認整個沒跑成、任何一格是否已開始都無從判斷」，並把那則警告一併回報（`SKILL.md`「腳本返回時」那節必轉達的兩則警告之一）。這一條是全有全無的，**但那是這一條的性質，不是整個形態的保證**——只有某幾行缺時看下一條。
- **逐格結果的追加寫入中途失敗**：確認步驟先清空結果檔，再逐格追加每一格的結果；那些追加帶著防護，失敗只丟棄結束碼、流程照常往下走，於是結果檔裡只剩失敗之前那幾格，**摘要會同時出現帶狀態欄位與不帶狀態欄位的行**。**沒有腳本自己印的專屬警告可以辨識它**，編排端最直接的訊號就是摘要裡出現了混合的行——看到混合即是落在這一條。**但它不是完全靜默**：bash 對失敗的重導向本來就會往標準錯誤印一行，所以標準錯誤上會有訊息，只是不是本腳本格式化過的那一則，**不要拿它去頂替上一條那則專屬警告**。屬這一條時，帶欄位的那幾行仍然有效、照其字面處理（第一種形態該做的那次核對不因此免掉，見 `SKILL.md`「腳本返回時」那節），缺欄位的那幾行走安全側，另外把「出現了混合」這件事本身據實回報。

**所以缺欄位的行不保證都由那則專屬警告解釋得了**：追加寫入中途失敗那一條不印任何專屬警告。標準錯誤上沒有那則警告時，缺欄位的行照安全側讀法處理，不要因為沒有警告就把缺欄位讀成別的意思；也不要把 bash 自己那一行重導向失敗訊息當成那則警告——那一則不是本腳本印的，據它加上「本次的確認整個沒跑成」就是誤報。
