# 已知限制：派送、等待與收尾

本檔記派送、等待、收尾與寫入使用者 repo 各環節的已知限制。四個平台的能力量測與權限、暴露面相關的限制在 `references/limits-exposure.md`；規則的成因與產出物目錄結構在 `references/rationale.md`。

**量測前提**：互動模式與無頭模式是兩組不同的量測條件，多項結論方向相反：底下這些量測全部取自互動 reviewer 那一路，不要拿去套用在任何無頭執行上，反之亦然。要重新確認只能對真實二進位重跑同型探測，讀腳本或官方說明推不回來。

涉及外部 CLI 或 git 實際行為的每一項都標出憑據等級：「實測」指以真實二進位跑過同型探測，「推斷」指從其他已知行為推得、沒有直接量測，「未查證」指沒有測過也推不出來。三者不得互相代換。

## 逐條限制

- **純標準輸出的 log 檔消失，失敗 reviewer 的錯誤訊息只存在於畫面上**：reviewer 現在跑在 pane 裡，`logs/` 底下只剩 prompt 檔、派出時刻檔 `.dispatched-at` 與變更檔清單 `.changed-files`，沒有 `<CLI>.log` 也沒有標準錯誤檔。契約要求 reviewer 在中止、讀回核對停下、讀不回來、發布失敗這幾條路徑上把說明印在自己的 pane 上，而目前沒有任何機制把畫面內容留存成檔案，關掉那格 pane 訊息就永遠消失。**這個事實原樣成立，它現在支撐的是兩層結論**：失敗的那一格 pane 不關（關閉的前提是那則 comment 被確認貼上 PR，失敗的 reviewer 本來就過不了那一道），以及只要還有一格沒被關掉，tab 就整個留著。
- **herdr 對 agy 核准對話框的 `blocked` 偵測，可靠性因對話框類型而異——這是歷史量測記錄，reviewer 那一路現在沒有適用對象**：量測本身仍是事實，agy 的「Create file」這一類檔案寫入確認框，兩次實測都沒有被正確回報成 `blocked`（一次 `done`、一次 `idle`，兩次的假陰性值本身還不一致，樣本數 2）；「Requesting permission for: `<command>`」這一類指令核准框則四次全部正確回報 `blocked`；其他類型無法從這兩類的結果類推（未查證）。**但 reviewer 那一路的 agy 現在帶 `--dangerously-skip-permissions`，這幾類對話框根本不會出現，這一條的適用對象因此消失**：留著是當基準——旗標日後若被改名、收窄或移除，對話框回來，這一條連同它的後果（失去早期通知，使用者少了一次「有 reviewer 在等你」的即時提醒）就整條重新適用。兩件事與旗標無關、照樣成立：它不會造成誤判完成，因為完成判準是輸出檔那三項，對話框沒被核准之前輸出檔根本不存在；而 agy 的互動模式沒有任何等效的逾時旗標（`--print-timeout` 只適用列印模式，實測），真的卡住就是一直卡著，直到有人回答或死線到期。**這條量測同時是「herdr 的狀態欄位不保證涵蓋每一種停住的形態」這個一般性結論的出處**，而那個結論不隨旗標消失——`references/waiting.md` 死線那組條件的第二項、以及 `wait` 的 `stalled` 事件之所以存在，都是因為它。
- **`--check-clis` 只驗 PATH 存在性**：它對四個 CLI 各跑一次存在性檢查，不含任何認證或可用額度的檢查，所以使用者可能選中一個通過檢查的平台，卻在派送之後才因未認證或額度不足而失敗。herdr 不在這道檢查的範圍內，但另有 `HERDR_ENV` 那道閘門管它；那道閘門讀的是環境訊號，判得準的只有「呼叫端自己跑在 herdr pane 裡」，不是 `herdr` 這個指令本身可不可用——後者腳本從頭到尾不驗證，缺席會等到建 pane 或 `launch` 起 agent 那一刻才浮現。`--check-clis` 刻意不受那道閘門約束：閘門存在的目的是擋副作用，而這條診斷路徑本來就沒有副作用，擋它防不到任何東西，反而把一個設計成使用者選平台之前就能安全跑的診斷耦合到 herdr 上。腳本端已有測試鎖定這個例外。
- **兩件事合起來決定了派送的形狀，讀這一條要兩半一起讀：第一則 `agent prompt` 會被靜默丟棄，而多行契約又不可能改走 `agent start` 躲開它**（皆實測）。前一半：`herdr agent start` 之後送出的第一則 `herdr agent prompt` 會被靜默丟棄——不是被拒絕、不是被排隊，就是沒有送達——而 `agent prompt` 不論如何都回報成功，那一格的畫面停在啟動橫幅與一條空的輸入行上、不是任何對話框，所以三個地方都看不出異常。憑據是 agy 1.1.27 經 herdr 的兩次獨立重現，兩次的差別在於 `herdr agent start` 與**第一則** `herdr agent prompt` 之間分別隔了 6 秒與 15 秒，結果相同——這兩個數字量的是啟動到第一則 prompt 之間的間隔，也是那兩次探測唯一控制住的變因。**重送與原送之間的延遲不是受控變因**，所以那兩次撐不起任何特定的重送間隔，它們真正建立起來的只有「一次重送就足以恢復」；腳本那個重送上限就是照這個觀測再加一次餘裕定的，是推理值而不是量測值，理由記在腳本那個常數自己的說明文字裡。卡住之後會持續多久也量到了：prompt 被丟棄之後，那一格的 `agent_status` 在 60 秒以上的觀測期間內反覆取樣、全程維持 `idle`，任務完全沒有開始（實測；這 60 秒是那次探測的觀測時長，與逐格確認那份共用的 60 秒預算沒有關係，那個預算是推理定的、不是從這裡量出來的）。這個持續時間是「這不是慢、是根本沒開始」的判別依據——少了它，`idle` 這個值本身分不出「還在啟動中」與「這一則 prompt 沒送到」，而那正是舊設計誤判的地方。而且它是間歇而非必然——另有一次真實執行裡，codex、opencode、agy 三家的第一則 prompt 全部乾淨送達。**舊版那道「`herdr pane read` 讀得到東西就算就緒」的守衛擋不住它，把它復原也補不起來**：那道檢查只確認 pane 渲染出了東西，而啟動橫幅大約一秒內就渲染出來了；這個 bug 活在「橫幅已渲染」到「這個 CLI 自己的 TUI 輸入處理真的接得住文字」之間那個更窄、更晚的窗口，非空檢查對它沒有任何視野。守衛因此被移除且刻意不復原，**不要以為把它加回來就關掉了這條路**。修法取重送而不是復原守衛，因為三項觀測合起來只指向重送：drop 可重現、同一句 prompt 隔一會兒重送每次都立刻成功、而且它是間歇的（皆實測）——重送落在派出後那道逐格確認裡（見下面兩類宿主平台那一條），只對走兩段式的那三家有對象可重送，claude 是一段式的，第一次確認不到就直接記為未確認。後一半是為什麼躲不掉：**`herdr agent start` 拒絕任何含換行的 agent 引數**——結束碼非零、錯誤碼 `invalid_agent_argument`、訊息逐字為 `agent arguments cannot be encoded safely for the target shell`，而且**與長度無關**，兩行、十幾個位元組的引數照樣被同樣的錯誤拒絕，四家各自那些照 `--help` 都能接起跑 prompt 的一段式機制全部重現同一個結果。審查契約永遠是多行 markdown，所以這是結構性上限而不是值得再試一次的機率問題：**不要再嘗試把多行契約塞進 `agent start`**。這個方向已經被推翻過一次——曾經有一版把四家全部改成一段式，撞上這條才退回；連帶被推翻的還有「agy 的一段式交付已經實測確認」那個讀法，那次探測用的是單行 prompt，結果推廣不到腳本真正要送的多行契約。claude 逃掉這一條，只因為它送進 `agent start` 的兩個引數都是單行：契約走檔案路徑、起跑訊號是一句固定短語，契約內容本身從來不是引數（見 `references/rationale.md`「四家的契約傳遞方式為什麼不對稱」那一節）。
- **codex、opencode、agy 三家的 prompt 以單一命令列引數傳遞，受作業系統單一引數長度上限約束；claude 那一家已經不受它約束**（實測 131,072 位元組，140,000 已失敗）：`herdr agent prompt` 只接受位置參數形式的文字，沒有檔案輸入或標準輸入旗標，那三家的契約全文因此非過這條命令列不可。claude 改走 `agent start` 的檔案路徑旗標之後（見 `references/rationale.md`「四家的契約傳遞方式為什麼不對稱」那一節），它的契約內容整段不再經過任何命令列，同一道 100,000 門檻對它只剩治理意義——擋的是契約無限成長，不是搶在作業系統之前攔下一次硬失敗；門檻仍然四家共用一個值，因為契約檔不論最後被誰讀都該有上界，維護兩個值不比一個值好。材料移出 prompt 之後尺寸不再隨 PR 大小變動，審查契約本身仍是 prompt 的主要佔比，所以**契約有意義的變動之後要重新量一次**。2026-11-25 加入 deep module 判準的契約定稿後實測（source `run-review.sh` 之後直接呼叫 `build_prompt`，傳入新契約路徑與一組座標值，照腳本實際寫檔的方式以 `printf '%s'` 寫出、不加換行後量）：契約 17,111 bytes，座標區塊 584 bytes，組出的 prompt 合計 17,695 bytes，佔 `PROMPT_BYTE_LIMIT`（100,000）的 17.7%，餘裕 82,305 bytes。前一次是 2026-11-16 加入覆蓋範圍段後的 16,976 bytes（17.0%），量的是 16,380 bytes 的契約；同日契約又長到 16,488 bytes，那時沒有重量。座標區塊的大小會隨路徑長度浮動，所以 prompt 合計與餘裕是這一組座標下的值，不是定值。更早一次（2026-09-04）對當時 main 版契約的實測是 prompt 97,939 bytes、97.9%、餘裕僅 2,061 bytes——那時「契約再成長就會讓每一次審查被擋下，不論 PR 大小」確實成立，之後的精簡買到的就是這段餘裕。**重量的時機要釘在最後一次編輯之後**：光是這個檔案家族，就有三組數字在寫下之後被下一輪改動推翻，所以上面那條不是客套話。走命令列那三家越線是硬失敗而非靜默截斷。門檻本身壓在四家都實測過能完整送達的約 101KB 之下，離作業系統硬上限更遠，所以越線不等於當場毀損。
- **agy 的工具被自動拒絕時結束碼是零而標準輸出全空，這一條現在沒有適用對象，留著是當基準**：無頭模式下 agy 對未列在允許清單裡的工具一律自動拒絕，被拒之後它仍以結束碼零結束、什麼都不印，所以在無頭的 agy 上「結束碼為零」不等於「正常完成」（憑據是實作階段對真實 agy 二進位的實測，腳本註解裡沒有這一條）。互動式 reviewer 沒有適用對象——它不是這支腳本的子行程，沒有結束碼可言，而且互動模式下未列入清單的動作呈現為詢問而不是靜默拒絕。日後若有人要為這個 skill 新增任何無頭執行的階段，這一條就重新適用：不要拿結束碼當完成判準。
- **remote 名稱假設為 origin**：腳本只驗證當前工作目錄的 `origin` 是否對應到目標 PR 所屬的 repo，不符即拒絕執行，不會改試其他 remote 名稱。慣用 origin 以外名稱指向 GitHub 的使用者會直接被拒絕。
- **腳本會寫入使用者當前的 repo**：五項寫入裡有四項落在使用者當前的 repo 上——fetch 這個 PR 的 base 分支並強制更新對應的遠端追蹤 ref、fetch 這個 PR 的 pull ref、建立一個以 `pr-review-` 開頭並帶 PR 編號與唯一後綴的本地分支、清理 worktree 殘留登記。第五項橫跨兩處：它回收的是同一個 PR 前次執行留下的陳舊 worktree 目錄，而那個目錄在家目錄暫存區的前次執行目錄底下、不在 repo 裡，落在 repo 內的是它連帶清掉的那筆 worktree 登記，以及**該次執行自己的那個本地分支**（分支名從那個執行目錄自己的路徑推導，與 `cleanup` 同一套推導）。上面是清單而不是執行次序。第一項的順序要留意：`origin` 身分比對排在解析 base ref 之前執行，就是為了避免「remote 不符而被拒絕執行」的那一次也已經留下副作用。**刪分支只刪推導得出的那一個名字，從不列舉 repo 裡同前綴的分支挑著刪**，所以使用者自己的分支，不論形狀像不像，都不會被碰（為什麼拿掉了舊版那道 repo 範圍的掃描，見 `references/rationale.md`「為什麼本地分支用強制刪除」那一節）。
- **監督行程沒有自己的逾時，一個既不寫完輸出檔、也沒把 comment 貼上 PR 的 reviewer 會讓它一直等下去**：它輪詢的是檔案，不是行程；某個 reviewer 卡在對話框或死在 pane 裡而沒有寫完輸出檔時，那個 cli 永遠留在待處理集合裡，於是 worktree 不會被移除、摘要檔也不會再長。**兩種缺輸出檔的情形要分開，只有一種還會這樣卡著**：貼過 comment 而沒寫出輸出檔的那一種現在收斂得了——每六十秒對 PR 查一次，歸屬得了就補一行 `posted-no-output` 並移出待處理集合（見 `references/rationale.md`「貼了 PR 卻沒有輸出檔的 reviewer 為什麼要另外收斂」那一節）；連貼都沒貼過的那一種仍然沒有任何機制收得了它，這一段描述的就是它。這正是 main agent 那個兩小時死線存在的理由——它是這條路上唯一的收束機制。「它會一直留著」只在永遠等不到輸出檔、PR 上也查不到它那則 comment 時才成立。**監督行程自己也有一條會停住的路，症狀與上面相同**：claude 那一格確認逾時時，監督行程會同步讀那一格的 transcript 來判 `post=`（見 `references/closing.md`「pane 定案」），而檢查完到讀取之間，reviewer 若把那份檔換成 FIFO，讀取就一直阻塞，其他每一格的摘要行、關 pane 與 worktree 移除都跟著停住（推斷：由腳本讀出，沒有實測）。刻意不加逾時：寫得到那個目錄的 reviewer 本來就寫得到執行目錄根層，這條路沒有擴大它的能力；收束同樣靠兩小時死線。
- **main agent 逾時或被中斷，不影響已經貼上去的那幾則，但之後就沒有人回報了**：兩小時死線到期、或使用者中途中斷 session，監督行程都不受影響，仍會照常等 reviewer 寫完、切內容、寫摘要、關 pane、刪 worktree；而每一則 review 是 reviewer 自己貼的，不靠 main agent，所以中斷不會讓它們貼不出去。失去的是回報與收尾：沒有人再讀摘要檔、沒有人向使用者轉達狀態、執行目錄也不會被清掉。各 reviewer 的 `review.md` 仍保留在執行目錄下；真有哪一則沒貼成功，要靠使用者事後主動要求補貼。
- **兩類宿主平台的差別只剩「要不要背景執行」**：輪詢、心跳排程與死線倒數整段都在 `wait` 裡，五個返回事件與返回之後要下的判斷兩邊一模一樣，所以 codex 與 opencode 上一樣拿得到心跳與嚴格檢查。差別在 Claude Code 有背景喚醒機制、可以把 `wait` 丟到背景，codex 與 opencode 沒有（實測，截至 2026-08；第三方 CLI 的能力會隨改版變動），只能前景呼叫——代價是那一次呼叫在事件返回之前一直佔著 main agent。規則層原本為兩類平台各寫一份輪詢迴圈，兩份在「`blocked` 要不要重新武裝」上的語意只靠散文互相對照維持一致；迴圈收進 `wait` 之後那個分歧點消失了，只剩重新武裝那一半仍在編排端，因為只有它知道自己有沒有再取樣過那一格。另外那個缺口——一格卡著而 herdr 沒有把它回報成 `blocked`，於是連事件都不會產生——現在有兩道補上，而且缺口本身已經不再是 agy 專屬的形狀（它那幾類對話框在 reviewer 那一路上已經不會出現，見上面 herdr 偵測那一條），改由 codex 承接：它沒有 claude 的 `--permission-mode auto`、opencode 的 `--auto`，也沒有 agy 那個旗標那樣的自動核准途徑（唯一的例外是張貼那一道：隔離家目錄的規則檔讓以 `gh pr comment` 加本次 PR 網址開頭的單一指令直接在沙箱外執行、不詢問（契約那道寫法實測過），所以照契約張貼時它不再卡在那則 comment 的核准上，見 `references/limits-exposure.md`「GitHub 側的機制只擋得住 reviewer 主動下 `gh` 指令這一軸」那一條；指向別的 PR 網址或以編號加 `-R` 張貼時照舊會跳框（實測），其他不以 `gh pr comment` 緊接本次網址開頭的寫法推斷同樣會跳；反過來，以本次網址開頭、後面接其他參數的寫法不會跳框（規則只比對開頭四個 token；execpolicy 判定實測到網址後接 `-R`、`--delete-last` 仍命中），其他核准對話框也照舊會出現）。**兩道接的是兩個時點，不是兩種互斥的失效形態**：派出後那道逐格確認落在 `run` 返回之前——逐格等它進入工作中，全部 reviewer 共用一份 60 秒預算，走兩段式的那三家確認不到就重送 prompt（最多兩次），結果印在派出摘要每一行的狀態欄位上——那個欄位靠的是 `.reviewer-confirm-status` 這個中繼檔，而**它缺席有兩條成因，缺的範圍與辨識訊號都不一樣，不要只記第一條**：檔案一開始就建不出來的那一次是全有全無的——確認步驟往標準錯誤印一行專屬警告後整個返回，沒有任何一格拿得到狀態值，於是每一行都不帶欄位，那時派出摘要對「誰開始了」一個字都說不出來，而那則專屬警告就是辨識它的訊號；逐格結果的追加寫入中途失敗則是部分遺失——結果檔裡只剩失敗之前那幾格，摘要於是帶欄位與不帶欄位的行混在一起，而這一條沒有腳本自己印的專屬警告可以認（bash 對失敗的重導向仍會往標準錯誤印一行，但那不是本腳本格式化過的那一則），編排端最直接的訊號就是混合本身（見 `references/rationale.md`「逐格確認那六處追加為什麼各帶一道防護」那一節與 `references/limits-exposure.md`「執行目錄根層沒有上鎖」那一條，以及 `references/missing-status.md` 的兩條成因）；`wait` 的第五個事件 `stalled` 落在其後的整場等待裡——同一格連續 300 秒沒有被讀到工作中、而且還沒有摘要行時返回（對那一格查詢失效的那一輪不返回，並把計時基準改寫成當下，失效之前已經累積的停滯時間一起歸零，所以 herdr 間歇性失效時它可能一直不返回，要靠嚴格檢查接手），`blocked` 優先於它。**一格從頭到尾沒開始的 reviewer 會被兩道各報一次，這是刻意的，不是重複**：`stalled` 的起算基準是派出當下就寫進 `.last-working-<cli>` 的那個時間戳，不是等到第一次觀測到工作中才建立，所以它不需要那一格先動過就算得出停了多久；前一道給的是派出當下那一瞬的答案，後一道給的是五分鐘後仍然如此。不要為了讓兩道看起來各司其職而把「必須先觀測到工作中」加進 `stalled` 的條件——那正好拆掉這裡最要接住的一種：從頭到尾沒動過、而確認步驟只來得及說一句「尚未確認」的那一格。**重送的代價要一起記**：重送的判準是「這一格在預算內沒有被讀到工作中」，不是「這份 prompt 確定被丟棄」，而兩者腳本分不出來，能觀測到的只有前者。所以一格健康、只是比那份預算慢的 reviewer 照樣會被再送一份完整的審查契約進同一個 session（上限兩次），使用者切過去看時可能看到同一份契約出現第二份甚至第三份；重複送達的那一份會被那家 CLI 怎麼處理沒有量過（未查證），已知的形態只到畫面上出現重複的 prompt。取這個判準是明知的：一份真的被丟棄的 prompt 會讓那一格從頭到尾不動、只能靠人發現，而多送一份的代價止於畫面上多一段重複。**兩道都只據狀態判斷，所以是縮小而不是關閉**（「只據狀態判斷」不等於畫面文字沒進過腳本行程——確認那一道用的 `herdr agent wait` 成功時回的 body 確實帶著那一格畫面上的模型輸出，擋住它的是腳本刻意丟棄而不是根本沒碰到，見 `references/rationale.md`「為什麼完全不讀 pane 畫面」那一節）：herdr 的狀態欄位涵蓋得到哪幾種停住的形態沒有保證（同上），而確認步驟不論確認到與否都絕不讓派出失敗、絕不中止、絕不清理已派出的 reviewer——一格尚未確認很可能只是慢，或正停在一個只有人回答得了的對話框上，那不是拋棄它的理由。「那一格卡著就只能靠心跳那幾行事實或使用者自己切過去看」因此不再是唯一的路，但切過去看仍然是唯一能分辨它到底停在哪裡的方法。
- **跨平台的比對留給讀 PR 的人做，這個 skill 不代勞**：幾則 review 各自獨立貼在 PR 上，哪幾項彼此印證、哪幾項只有一家提，由讀的人自己看；對某一則存疑時就去翻 PR 上那幾則原文——執行目錄在收尾時就收掉了，本地不留副本。
- **狀態投影分不出 herdr 原生的 `unknown`，本次不修**：herdr 自己也有原生的 `unknown` 狀態（herdr 0.9.1 `herdr --skill` 原文：「`unknown` means an agent is present but Herdr cannot classify it confidently; it does not prove completion.」），`SKILL.md` 那條投影會把比對到的那一筆的原生 `unknown` 原樣輸出，與「沒被比對到」分不出來，所以「兩次都 `unknown` 才宣告 agent 已經不在」可能誤判一個還在、只是 herdr 分類不出狀態的 agent。
