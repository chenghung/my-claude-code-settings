# 事後補貼指引

載入時機見 `SKILL.md` 的 Reference 載入時機表那一列。

## 先釘住是哪一次執行

**執行目錄的絕對路徑由使用者指定，或由他對列出的候選點頭**；本 session 剛跑完、收尾時已經回報過路徑的那一次，把該路徑複述一次取得他確認即可。**列出候選是允許的，替他選定不行**：這些目錄落在 `~/.tmp/<repo 名>-pr-<PR 編號>/<時間戳記>-<行程編號>/`，把該父層底下的目錄列給他挑沒有問題，但不得以「時間戳最新的那一個」代替他回答。補貼情境本來就是使用者多半不記得路徑的那一種，列候選正是讓他點得下頭的前提。

需要這道確認的理由：同一個 PR 的多次執行共用同一個父層，未全綠的執行目錄不會被任何機制自動刪掉，也不會被後一次執行覆蓋，所以同一個父層底下累積多個保留目錄是常態。挑錯一個的後果不可回復——貼上公開 PR 的會是上一次逾時留下的那份過期 review，而下面那道去重查詢只在部分情形攔得住它：那份過期內容在該 PR 上找不到逐字相同的既有 comment，所以該 PR 上另有帶標記的 comment 時它會把你攔到第三出口，一則帶標記的都沒有的那次則直接放行。

**在發出任何指名 PR 的委派之前——去重查詢也算一次——把從該目錄父層推得的 PR 編號複述給使用者，並停下等他回覆，確認之前不委派。** 前面那道確認的是目錄，這一道確認的是它對應到哪一個 PR。閘門擋在這裡而不是只擋在張貼前，是因為去重查詢本身就得指名 PR 才問得出來：擋晚了，那次比對會在編號還沒確認的狀態下發出，比對結果來自另一個 PR 時，跳過或補貼的判斷整個建立在錯的 PR 上；而張貼一旦發生，comment 貼上公開 PR 沒有收回路徑。使用者給的路徑不是 `~/.tmp/<repo 名>-pr-<PR 編號>/` 這個形狀（例如目錄被搬過）、PR 編號推不出來時，停下問他，不猜。

## 貼哪一則

讀該執行目錄的 `summary.txt`，把 `content_status` 為 `ready` 而還沒貼的貼掉。**補貼同樣照單則規則走**，不是把所有 `ready` 一次倒上去：先看合流那一行，是 `ready` 就只補它一則；那一次派出兩個以上平台而沒有那一行、或它是 `withheld`、`no-content`，才改補各平台 `ready` 的原始 review，並同樣說明彙整失敗。那一次本來就只派一個平台時，補的是它自己那則未經交叉比對的原始 review，不說成彙整失敗。

## 貼之前先去重

需要補貼的情境恰好是判斷不了「哪幾則已經貼過」的情境，所以貼之前先委派 `github-manager` 查一次。委派時把本次要貼的那幾份 `content_file` 絕對路徑一起交出去（逐則補多份時就是那幾份），問句形式如下，都能用是或否回答：

- **逐份各問一次**：PR 上帶回音室標記（`<!-- pr-review-by-multi-agents -->`）的既有 comment 裡，有沒有任何一則的原始 body 與**這一份** `content_file` 逐字相同？比對取 API 拿到的 body 原文，容許行尾字元、結尾換行與尾端空白的差異，渲染後的外觀不納入比對。（**「API 取回的 body 與當初送出的位元組一致」這個前提未查證**；換行正規化若真的發生，容差放寬到行尾字元這一層才不會讓每一份都判成不相同。）
- **整體問一次**：PR 上有沒有帶那個標記、卻對應不到本次任何一份 `content_file` 的 comment？這一問掃該 PR 上帶標記的每一則；「對應得到」取上一問那條逐字比對，容差相同。

出口三條，逐份各走一條：

- **這一份有逐字相同的那則**：已經貼過，跳過它。
- **這一份沒有，而整體那一問也答否**：沒貼過，照上面的規則貼。
- **整體那一問答是**：停下問使用者，**不得逕自視為未貼過**。那則對應不上的可能是貼上去之後被編輯過，也可能來自同一個 PR 的另一次執行；照字面當成沒貼過就會補出第二則帶同一標記的 comment，而 comment 沒有收回路徑。

**整體那一問答是時一律走第三條**，不因為某一份已經對上而略過它。**自己這一輪剛貼上去的那則不算「對應不到」**：它對得上本次某一份 `content_file`，逐則補多份而中途再查一次時，不因為它而落進第三出口。回答不是明確的是或否時（比對做不到、回應含糊）同樣停下問使用者，不自行推定。

**這次委派同樣把 `content_file` 的絕對路徑交出去，所以同樣要明講這些檔案一份都不得刪除或移動、需要暫存副本請自行複製。** `github-manager` 自己的規範是 body 以暫存檔傳遞、貼完刪除，而這些路徑正好長在 `~/.tmp` 底下，看起來就是該刪的那一種；去重又跑在張貼之前，任何一份被刪掉，後面那次張貼就沒有東西可貼。**這一次是要它讀檔來比對，與張貼那次「不要讀進來重打」不衝突**——同一輪裡它會收到這兩條看起來相反的指示，交代時要分清楚：比對是它在自己那一端讀，張貼要的是不要把內容重新打一遍。

這一步的注入曝險比主線那次委派大（核對必然把兩側的全文一起讀進 `github-manager` 的 context），是明知並接受；能收窄的只有範圍——只比對帶那個標記的幾則，不要把整串討論串掃過去。

## 這條路徑同樣關著讀檔那道門

**補貼路徑不得把 `content_file`、`.comment-body-*.md` 或任何 `review.md` 讀進 main agent 的 context**，包含為了上面那次去重比對而讀。這條禁令與 `SKILL.md` 輪詢那節寫的是同一條，不因為補貼發生在輪詢之外、或發生在另一個 session 而放寬：比對與張貼一律委派出去，main agent 這一端只經手路徑與結構化欄位。委派張貼本身照 `SKILL.md`「張貼」節那段的要求走，補貼這一次不例外。
