# PR Review by Multi-Agents

同時派出多個獨立的 AI agent CLI 行程——claude、codex、opencode、agy 四者中選一個以上——對同一個 PR 各做一次完整 code review，每個行程把 review 全文包在一組起訖標記之間印到標準輸出。腳本的監督行程負責把內容從標準輸出切出來、判斷是否可信，寫進一份摘要檔；全部 reviewer 結束後，監督行程再起一個合流行程，把判定為可信的那幾份合成唯一一則要張貼的 comment。真正把內容張貼成一則繁體中文 comment 到該 PR 上的是 main agent：讀摘要檔，把合流那一則委派 `github-manager` 貼出去，只有合流沒產出時才退回逐則張貼（見「回報」節）。目的是取得多模型的觀點差異與盲點互補，並讓那些差異在同一則 comment 裡並排呈現，不是把 review 卸載到背景。

reviewer 自己不張貼、也不寫任何檔案，是刻意的：被審查的 diff 與 issue 內容是外部可控、會原樣進入模型 context 的提示注入管道，而這個倉庫審查的正是使用者的 AI 工具設定檔；給 reviewer 寫入能力沒有辦法只給一個目錄，等於把整個帳號權限範圍交出去。切內容、判斷可不可信這一步留在監督行程，因為它是 shell 子行程而不是 AI agent，跑的是固定指令、沒有注入風險。合流那一步不同，它必須讀懂 review 的內容才做得了比對與去重，只能交給 AI agent——它不需要 worktree（輪到它跑時 worktree 已經被刪了），產出一樣只走標準輸出、一樣由監督行程切出來，拿的是各 CLI 給得出的最窄授權；但「最窄」有多窄因 CLI 而異，只有 claude 與 agy 鎖得到零工具，codex 與 opencode 鎖不到，詳見「已知限制」那條逐 CLI 的說明。agy 那個「零」不能照字面讀：它的無頭模式預設拒絕只涵蓋指令、取網址與未沙箱三類，檔案寫入根本不經過它的權限層，而合流跑的時候 worktree 已經刪了、工作目錄就是那個自始至終沒上鎖的執行目錄根層，連 reviewer 那一路的 chmod 兜底都沒有。正因為這個不對稱，合流優先挑 claude 或 agy 來跑——挑它們關掉的是外洩軸（網路），不是檔案寫入面。注入文字有可能原樣穿過 review 落到合流行程手上，這一點無法消除。真正決定要不要貼、要不要委派張貼的雖然是 main agent 這個 AI agent，但它讀的只是摘要檔裡的結構化欄位（結束碼、worktree 狀態、`content_status` 這類事實），review 內容本身連同其中可能夾帶的注入文字，不會經由這條路徑進入 main agent 的 context。這道區隔以摘要檔沒有被動過手腳為前提，而那個前提不是機制保證：摘要檔、各份內容檔與名單檔都放在執行目錄根層，那一層沒有上鎖，而 reviewer 從自己的 prompt 就拿得到 worktree 的絕對路徑、往上一層就是那裡（見「已知限制」）。委派 `github-manager` 張貼時交出去的是內容檔的絕對路徑，並要求以檔案張貼、不讀進來重打。這項要求降低了、但沒有消滅注入面：`github-manager` 本身具備 Read 工具，沒有任何權限機制阻止它把這個檔案讀進自己的 context，這道防線目前只靠委派時的這句自然語言指示撐著。

實際工作大半在 `scripts/run-review.sh` 裡：材料抓取、worktree 建立、prompt 組裝、CLI 行程啟動、監督、合流行程的啟動與記錄、收尾清理都由它負責。張貼與進度回報則是 main agent 自己的工作——選定平台組合、呼叫腳本、輪詢摘要檔、委派張貼、判斷收尾條件。不另行以 subagent 或自己組 prompt 的方式重做審查或合流本身：兩份契約的全文都由腳本原文嵌入對應行程的 prompt，改成由模型轉述後，四個嚴重度等級的界線會在轉述中糊掉，數份 review 失去可比性，而合流那一端的信心重算整套建立在那些等級與檔位對得起來的前提上，前提一垮，重算出來的值就沒有意義。

## 蒐集三項輸入

三項輸入依下表取得，各自對應一個具名旗標：PR 連結是 `--pr`、issue 連結是 `--issue`、design document 路徑是 `--design`。任一項取不到就省略該旗標或給空字串（兩者等價，腳本一視同仁），不阻斷流程，也不用猜測值填補：契約把空字串明確渲染成「不存在」，reviewer 會據此略過對應審查軸並在自己的 review 中載明，合流那一則會照實承接這些範圍交代；而猜錯的 issue 或 design document 會讓所有 reviewer 拿錯的需求當判準，且不會有任何明顯徵兆——四個平台一起錯、合流那一則也跟著錯，看起來反而像是有共識。

| 輸入 | 取得方式 |
| --- | --- |
| PR 連結 | 使用者指名了就原樣傳。沒指名時先確認目標（見下）；確認過程中若拿到了連結或編號就原樣傳，只憑「就是當前分支那個」確認下來的則傳空字串，腳本自己會從當前分支推導，不必先在這裡查一次 |
| issue 連結 | 明示覆寫，可省略。只在使用者於對話脈絡中明確給出 issue 連結或編號時才傳；沒有明確給出就傳空字串，腳本會自己從 PR 內文的 closing keyword（`Closes`、`Fixes`、`Resolves` 後接 issue 編號）推導，不必也不應在這裡代為讀取 PR 內文去找 |
| design document 路徑 | 從對話脈絡取得，也就是本次工作採用的設計文件或 spec 檔路徑，一律傳絕對路徑；脈絡中沒有就傳空字串，不去掃描 repo 湊一份 |

design document 傳絕對路徑不是風格偏好：這個路徑只在 `main()` 自己的 shell 裡被用來 `cp` 進材料目錄，`main()` 從頭到尾沒有切換過工作目錄，reviewer 完全看不到這個路徑、只看得到已經複製進 `materials/design.md` 的內容——不是因為 reviewer 的工作目錄是 worktree。真正的理由是呼叫腳本當下的 cwd 未必等於使用者心裡預期的那個基準：相對路徑會依腳本被呼叫時的實際 cwd 解析，猜錯就是另一個檔案或根本不存在，結果一樣是整條設計符合度軸靜默失效。

**目標 PR 要與使用者當下談的工作一致，才可以派出。** 這是上面「取不到就傳空字串、不阻斷流程」的唯一例外，而且性質不同：那條講的是材料缺了照樣審，這條講的是打到哪個 PR。comment 一旦貼上會發出通知、對協作者可見，而契約禁止 reviewer 刪改任何留言，沒有收回路徑；腳本的 `origin` 比對只保證打到當前 repo 的某個 PR，不保證是使用者要的那一個。因此分三種情形：使用者指名了 PR，直接派出；使用者沒指名，但當前分支對應的 PR 就是本次對話正在進行的工作，直接派出；兩者都不成立時，先停下與使用者確認目標 PR，確認前不呼叫腳本。

## 選擇平台組合

派送哪幾個平台完全由旗標決定。舊版會偵測 PATH 上裝了哪些 CLI、自行決定派誰、缺席的靜默跳過，那個行為已經整個移除：現在腳本只跑指名的那幾個，指名了卻不在 PATH 上就以結束碼 3 拒絕整次執行，不會自行降級成剩下的那幾個。少了那層自動判斷，選誰就成了 main agent 必須當面問清楚的事，不能靠腳本代為決定。

呼叫腳本前先跑一次前置查詢：`<run-review.sh 路徑> --check-clis`（路徑的定位方式見下一節，兩處是同一條路徑）。它對 claude、codex、opencode、agy 四個平台各印一行可用或缺席，不做任何其他前置檢查、不建立任何目錄、不碰使用者的 repo——所以在使用者還沒決定派誰之前跑它是安全的，而它也是派送前唯一能拿到可用性事實的途徑。

拿到那四行之後，把下面四個固定組合列給使用者挑。使用者挑的是整組，不是勾選個別平台，所以**可用性要標註在組合上**：每一組旁邊寫它整組可用，還是缺了哪一個 CLI。逐平台列可用性、讓使用者自己把四行事實換算成四組能不能跑，那個換算沒有理由留給他做。

| 組合 | 平台 | 適用 |
| --- | --- | --- |
| a | agy、opencode | 小型變更 |
| b | claude、agy | 重大變更 |
| c | claude、agy、opencode | 重大變更 |
| d | claude、agy、opencode、codex | 重大變更 |

這張表的形狀本身帶著資訊，值得一併說給使用者聽：agy 出現在四組的每一組裡，是事實上的必選核心；codex 只出現在 d，只有最重大的變更才動用。所以由 a 往 d 挑不是等比例地多審一點，而是在「要不要加上 opencode」與「要不要動用 codex」這兩道門檻上做取捨。

**無論使用者是否已經在觸發語句裡指名了組合，都要列出這份選單並取得確認**，不得因為他已經指名就跳過。每個平台各自消耗大量 token，而派出去的結果會在公開 PR 上留下通知、沒有收回路徑；使用者指名時通常不知道哪一個當下缺席，照他說的直接派，最好的情況是換來一次結束碼 3 的失敗，最壞的情況是他以為那一組都審過了。

挑中的組合含缺席的 CLI 時，當場問要跳過缺席的那個、用其餘的跑，還是改挑另一組，不自行決定。腳本在正式派出時會再驗一次，選定組合中有 CLI 不在 PATH 上就以結束碼 3 拒絕整次執行、不靜默降級，所以這個決定沒有別的地方可做；替使用者決定等於替他挑了審查陣容，而陣容正是這個 skill 唯一需要他決定的事。

跳過缺席的之後一個平台都不剩時（例如組合 a 的兩個都缺席，或四個 CLI 全部缺席），直接停下回報，不呼叫腳本。照字面走會組出一次沒有任何平台旗標的呼叫，腳本以結束碼 2 拒絕，而那個結束碼的定義是呼叫端用法錯誤——使用者拿到的訊息會指向一個他無從修正的方向，而真正的事實是這台機器上沒有任何一個 reviewer CLI 可用，該裝哪一個才是他要知道的。

使用者主動指定這四組以外的自訂組合時，照他指定的派，不把他導回選單。這四組是設計過的預設搭配，不是允許清單，腳本本身也接受任意子集；使用者已經明確講出陣容時，選單剩下的用途只有確認可用性，那一步照做——跑 `--check-clis`、標註哪些缺席、缺席時照樣問要跳過還是改挑——但不拿選單去覆寫他已經表達過的選擇，那與替他決定要跳過還是換一組是同一件事。這條不適用於只有一個平台的自訂請求：frontmatter 那道門檻明列「由單一 agent 執行的審查」不觸發本 skill，所以那不是一個更小的組合，而是要回到門檻本身判斷該不該用這個 skill；若與使用者確認後仍決定這樣派，比照上面「跳過缺席之後只剩一個平台」那段的告知義務——交叉驗證不成立、不會有合流、PR 上那一則就是那個平台未經合流的原始 review。

組合 b 只有兩個平台，一樣會有合流：合流的門檻是判定為可信的 review 達兩份以上，不是派出了幾個平台。派出當下就確定不會有合流的只有一種情形——使用者選擇跳過缺席的 CLI 之後只剩一個平台，這時要一併告知後果：交叉驗證不成立，PR 上那一則就是那個平台未經合流的原始 review。另有一種情形要到跑完才知道：某份 review 事後被判為不可信，可信份數掉到一份，合流一樣不會啟動（見「回報」節）。

## 呼叫腳本

腳本是本 skill 目錄下的 `scripts/run-review.sh`。執行環境有告知本 skill 的 base directory 時直接據此組出路徑；取不到時依序測試下列兩條安裝路徑，取第一個存在的：

1. Claude Code：`$CLAUDE_CONFIG_DIR/skills/pr-review-by-multi-agents/scripts/run-review.sh`，該環境變數未設時以 `~/.claude` 代入。倉庫的安裝腳本用同一個變數決定部署根目錄，personal 訂閱那套部署會把它指向另一個設定目錄，路徑寫死成 `~/.claude` 會在那套部署下找不到檔案。
1. codex 與 opencode：`$AGENTS_HOME/skills/pr-review-by-multi-agents/scripts/run-review.sh`，該環境變數未設時以 `~/.agents` 代入。兩者共用這一條，而安裝腳本同樣允許以這個變數覆寫該目錄。

兩條都不存在時停下回報，不自行改用其他途徑——不改跑倉庫工作副本裡的那一份，也不改以 subagent 重做審查。找不到腳本代表本 skill 沒有被正確安裝，繞道會讓這件事被一次看似成功的執行蓋過去。

呼叫形式是具名旗標：三項輸入各自帶值，四個平台各是一個開關，至少要給一個平台旗標。旗標之間的順序不影響結果，值與名稱綁在一起，不存在把 issue 連結錯當成 PR 連結那類錯位：

```bash
<run-review.sh 路徑> --pr "<PR 連結>" --issue "<issue 連結>" --design "<design document 路徑>" \
  --claude --codex --opencode --agy
```

三項輸入的旗標可以整個省略，也可以帶空字串。旗標值不得含換行，腳本會直接拒絕：解析結果是以四行 `key=value` 交回主流程的，值裡的換行可以在其中偽造出一行 `clis=`，把實際派送的平台整組換掉。

結束碼有四種，分開的理由是讓「重挑一次就好」與「重跑幾次都一樣」不必靠讀訊息分辨：

- `0`：成功派出，此時 reviewer 還在背景跑。
- `1`：兩種性質相反的失敗共用這一碼，分辨只能靠讀標準錯誤訊息有沒有指出已啟動的行程編號（見「回報」節）——這是四種結束碼沒能拆乾淨的一處，看到 `1` 不要直接當成「還沒動到任何東西」。
  - **前置條件不成立**，重跑面對的條件與上一次完全相同：gh 缺席或未登入、jq 缺席、PR 不存在、不在 git repo 內、當前工作目錄的 `origin` 不是這個 PR 的 repo、找不到審查契約檔、base ref 解析不出、worktree 建不起來或唯讀化失敗、材料抓不到。其中兩條的處置與其餘不同：**找不到審查契約檔**代表安裝不完整，與上面「兩條安裝路徑都不存在」是同一件事、照同一條處理，不要在沒有審查標準的情況下自行湊一份派出去；**PR 連結解析不出**（`--pr` 的值打錯，或沒給連結而當前分支沒有對應的 PR）是呼叫端當場改得掉的，改掉旗標值或補上連結再跑一次即可，不屬於「重跑也一樣」那一類。副作用方面，「什麼都沒動到」只到找不到契約檔為止：從解析 base ref 那條起 repo 已經被動過，動到哪一步視失敗落在哪裡而定——遠端追蹤 ref 已更新、pull ref 已 fetch、同形狀的陳舊分支已被強制刪除、本次分支已建立。worktree 會被移除，但本次那個分支通常留著——**這條路徑上不要自己去刪它**。分支名尾端是腳本自己的行程編號，而這個結束碼下的訊息不會印出執行目錄、派送失敗的訊息裡也只有各 reviewer 的行程編號，沒有任何途徑取得那個後綴；「收尾清理」那條的強制刪除以「範圍嚴格限於這一個分支名」為前提，這裡滿足不了，剩下的做法只有列舉同形狀分支再猜是哪一個，而那恰好是分支閘門那道同意機制要防的動作。交給腳本下一次執行的陳舊分支清除機制處理即可：它會強制刪掉同形狀的陳舊分支，而下一次派出前那道閘門會把它列出來讓使用者過目——真正刪掉的那一刻仍然有人看過。家目錄那一側也留了東西：worktree 唯讀化失敗與材料抓不到這兩條路徑（以及下一則的派送途中失敗）上，暫存區裡本次的執行目錄已經建好並留著，而腳本回收陳舊執行目錄的機制只清「worktree 子目錄還在」的殘骸——這幾條路徑的 worktree 都已被移除，那些目錄因此永遠不會被自動清掉，也不在「收尾清理」的涵蓋範圍內。據實告訴使用者這件事；確切路徑在這條路徑上同樣拿不到——後綴一樣是腳本自己的行程編號，而失敗訊息不會印出執行目錄——要找就是到 `~/.tmp/<專案專用資料夾>/pr-review/` 底下看這次前後留下的那幾個，留或刪由他決定。
  - **派送途中失敗**：已經有 reviewer 起來、成為無人監督的孤兒行程，worktree 也已被強制移除，重跑不會回到原狀。處置見「回報」節那兩個分支。
- `2`：用法錯誤——未知旗標、旗標缺值、一個平台旗標都沒給、旗標值含換行。
- `3`：選定組合中有 CLI 不在 PATH 上，訊息會列出是哪幾個。這道檢查排在所有 gh 往返與任何對 repo 的寫入之前，所以被它擋下的執行不會留下任何副作用；它與 `1` 分開，就是為了讓上一節那個「跳過缺席的還是改挑一組」的問題可以當場再問一次。

執行時的工作目錄要落在目標 PR 所屬 repo 的工作副本內：腳本以當前工作目錄的 `origin` remote 驗證是否為同一個 repo，不符即拒絕執行。

**派出前先確認不會刪掉使用者自己的分支。** 腳本會強制刪除當前 repo 中形狀為 `pr-review-<PR 編號>-<唯一後綴>`、兩段皆為純數字的陳舊分支，不看有沒有合併過，只有正被某個 worktree 檢出的會被 git 自己擋下來。這件事發生在建立 worktree 的階段，排在結束碼 `2`、`3` 與全部前置檢查之後——被那些擋下的執行一個分支都不會刪，這與上面說 `3` 不留副作用是同一件事的兩面，不衝突。真正走到那一步時，比對範圍已經收斂成這個精確形狀，撞名需要刻意模仿，但撞上了照樣會被刪，所以這道閘門仍然要走：呼叫腳本前先列出當前 repo 所有 `pr-review-` 開頭的分支——這是本地唯讀 git 操作，不涉及 gh，不必走委派——凡符合上述精確形狀的一律視為會被刪掉的對象，先告知並取得同意再派。不能只挑「不是本次那一個」來問：本次要建立的分支尾端是腳本自己的行程編號，呼叫之前那個值還不存在，沒有辦法預先把它排除，所以同形狀的每一個都算在內。沒有這類分支就直接派，不打斷流程。這道閘門與上面確認目標 PR 那道同一個理由：刪掉未合併的分支同樣沒有收回路徑，而「已知限制」那節是給遇到症狀時事後對照用的，救不了這一件。

## gh 呼叫的歸屬

本 skill 涉及兩種 gh 呼叫，歸屬不同，分開處理。

- **腳本執行的 gh**：不算 main agent 自行處理，呼叫腳本不需要改走委派。倉庫規則把透過 gh 對 issue、PR、comment 的實際操作劃給 `github-manager`，規範的對象是 main agent 自己要不要動手；經由腳本內部（材料抓取、base ref 查詢）發出的呼叫沒有被那條規則界定，兩種讀法都成立，因此在此明說取這一種。
- **main agent 自己要下的 gh**：屬於 main agent 行為，一律委派 `github-manager`，不自行呼叫 gh。現在只剩一種——把摘要檔中判定為可信（`content_status` 為 `ready`）的內容張貼成 PR comment：正常情況下是合流那一則，且只有那一則；合流沒產出時才改貼各平台的原始 review，見下面「回報」節。

## 回報

### 腳本返回時

腳本印出的摘要分五部分：本次執行目錄與其中 `summary.txt` 的絕對路徑；實際派出了哪幾個 reviewer，附各自的行程編號與 log 檔路徑；跳過了哪幾個，附原因；本次收集到的審查材料；派出兩個以上平台時，另有一行預告全部 reviewer 結束後會嘗試合流一次，附合流 log 的路徑。照這份摘要向使用者回報，並指名本次實際的目標 PR——使用者沒指名 PR 時，這是他確認打對地方的唯一機會，PR 編號可從摘要裡的 log 路徑或執行目錄名取得。摘要點出「本次只有一個 reviewer、交叉驗證不成立」時一併轉達。

兩處措辭要照原樣保留分寸，不要在轉達時補強或壓縮。「已跳過的 reviewer」那一節現在恆為空——組合是明確選定的，缺席的 CLI 在腳本啟動之初就被結束碼 3 擋掉，不會有跑到一半才跳過的事，那一節留著只是格式相容。合流那一行寫的是「會嘗試合流一次」而不是承諾：能不能真的產出，取決於屆時有幾份 review 被判定為可信，而摘要印出來的當下一份都還沒跑完。

**標準錯誤出現 log 目錄上鎖失敗的警告時，必須一併回報。** 腳本遇到這種情形只往標準錯誤印一行警告、仍以結束碼 `0` 結束，摘要那五部分裡沒有任何欄位反映它，不特地看標準錯誤就完全無聲。而那道鎖是唯一擋得住「某個 reviewer 覆寫另一個 reviewer 的 log、把冒充的內容包進契約標記裡」的防線（見「已知限制」），失效時這次執行的每一份 log 都少了那層保護，使用者有權在任何東西被貼上 PR 之前知道這件事。

材料那部分要照實轉達給使用者，這是補上的一個訊號：缺料原本完全不出聲——issue 抓不到、design document 路徑打錯、PR 沒有 closing keyword，三種情形都一樣，使用者第一個看到的訊號只會是最後那則 comment 的審查範圍交代裡寫著「因材料不存在而未審此軸」——而那已經是幾十分鐘之後的事了。issue 那一條有四種值：已取得（由 PR 本文的 closing keyword 推導）、已取得（呼叫端明確指定）、未提供（PR 本文未宣告 closing 的 issue）、嘗試取得但失敗（issue 參照無法解析，或已取得編號但抓不到，例如 issue 不存在或無權限）。design document 那一條有三種值：已提供、未提供、呼叫端提供了路徑但檔案不可讀。轉達時不要把這些壓成一句「材料不齊」：「未提供」是使用者自己的選擇（沒打算給這份材料），「不可讀」通常是路徑打錯，當場就能請使用者確認修正——兩者對使用者的意義不同，混在一起講就失去了這個區分原本要補上的價值。

腳本印完摘要就返回，此時 review 行程還在背景跑，合流行程連起都還沒起；張貼是 main agent 之後的事，見下面「在 Claude Code 上的輪詢與張貼」。

腳本以非零結束碼結束時分兩種情形，靠標準錯誤訊息有沒有指出已啟動的行程編號分辨：

- **訊息沒有指出任何已啟動的行程編號**：可能是前置檢查不通過（gh 缺席或未登入、jq 缺席、PR 不存在、base ref 或 worktree 建不起來，也就是結束碼 `1` 那一類），也可能是派送到第一個 CLI 就失敗、一個 reviewer 都還沒起來；兩者處置相同，把訊息原文回報，不重試、不改用其他途徑——這類失敗全是環境前提不成立，重跑一次面對的條件與上一次完全相同，只會再失敗一次，而繞道則會在前提不成立的情況下把審查派出去，產出沒有依據的 review。結束碼 `2` 與 `3` 不屬於這一類：那是呼叫端自己的用法錯誤或選了缺席的平台，當場改掉旗標或重挑一次組合即可，兩者都還沒走到派送。
- **訊息指出了已啟動的行程編號**：派送途中失敗，較早啟動的 reviewer 變成無人監督的孤兒行程，worktree 也已被強制移除。這一次不會有監督行程去讀它們的輸出，所以它們的 review 不會被張貼、也不會有摘要檔可讀——內容留在各自的 log 裡。腳本把那些編號印出來就是為了讓人有東西可以終止——原文轉達該清單，並說明這些行程無人監督、結果只會停在 log 中。

### 在 Claude Code 上的輪詢與張貼

腳本返回之後 reviewer 還在背景跑，它們全部跑完之後還有合流那一步，要等到合流那一行寫進摘要檔，才拿得到真正要張貼的那份內容；而張貼本身現在是 main agent 的責任，不再是監督行程的事。以下輪詢、心跳、張貼、收尾構成同一個迴圈，缺一不可地銜接在一起；心跳與嚴格檢查的細節見下一小節「兩層檢查」。

**輪詢迴圈**：每一輪，main agent 以背景模式起一個等待指令，該指令每 5 秒檢查一次 `summary.txt` 的行數，滿足下列任一條件即結束：行數比這一輪開始時多、到達下一個心跳時點、到達總死線。背景指令結束時 Claude Code 會通知，main agent 據此被喚醒——喚醒次數等於實際派出的 reviewer 數量加上心跳次數，再加上合流那一次與收尾那一次，不是每 5 秒醒一次；5 秒只決定「某一行寫進摘要」到「main agent 看到它」之間最多差幾秒，review 與合流本身都以分鐘計，這個粒度夠用。摘要檔由背景監督行程建立，與腳本印出摘要之間有極短的競態，檔案還不存在時當成零行繼續等，不當成錯誤退出。

**等到哪一行才算等完**：正常情況是等到合流那一行——它是最後才寫進摘要檔的一行，`cli` 欄形如 `synthesis:<CLI>`。但合流不是每次都會啟動：判定為可信的 review 不足兩份時它整個不跑，那一行永遠不會出現，此時「所有 reviewer 都已有摘要行」就是終點，再等下去只是空等到死線。兩種終點都遲遲到不了時，執行目錄下的 `.supervisor.pid` 是判準，但要看對東西：那個檔案從建立起就不會被刪除，所以判的不是它在不在，而是裡面那個行程編號現在還活不活著（與「兩層檢查」第六項同一個判法）。監督行程已經死了，就代表合流那一行不會再出現，不必把兩小時等滿。

**心跳排程錨定在派出時刻**：心跳固定落在派出後第 15、30、45、60 分鐘，依此類推；中途因為有新摘要行而醒來的那些不佔輪次。錨定的理由是防止漂移：若心跳改成「從上一次事件起算 15 分鐘」，某個 reviewer 提早在第 7 分鐘完成、那一輪提早結束，下一次心跳就落在第 22 分鐘，之後第三輪到底是第幾分鐘就說不準了；錨定在派出時刻，第三輪永遠等於第 45 分鐘。

**總死線兩小時，是總量而非每輪各算**：若每輪各給兩小時，四個 reviewer 加上合流依序完成的最壞情況會疊成十小時，兩小時的上界就形同虛設。死線一到就結束等待，把已經寫進 `summary.txt` 的那幾行照下面的方式處理完，其餘據實回報為仍在進行中，並註明這是逾時當下的觀察而非確定失敗；只有使用者明確要求時才放寬死線，不自行延長。

**逐行處理，但只張貼一則**：每讀到一行新摘要就立刻回報那個 reviewer 的結束狀態——這是使用者在這段等待中唯一看得到的進度，而 reviewer 那幾行本身不會被貼到 PR 上，回報是它們唯一的去處。張貼只發生一次，對象是合流那一行：它的 `content_status` 為 `ready` 時，委派 `github-manager` 張貼它，且只張貼它一則，再回報張貼結果。

**合流沒產出時退回逐則張貼**：合流那一行是 `withheld` 或 `no-content`，或根本沒有那一行（可信份數不足兩份而未啟動，或監督行程沒走到那一步），就改把各平台 `content_status` 為 `ready` 的原始 review 各貼一則，並在回報中明說彙整失敗、這幾則是未經合流的原文。這句說明不可省略：讀者少掉的是跨平台的去重、嚴重度取最高與信心重算，不知情的話，他會把幾份各說各話的 review 當成已經整理過的結論讀。

**單則張貼的代價要認得**：改成一則之後，中斷的損失從部分擴大為全部。舊版逐則貼，逾時或 session 被中斷時，已經貼出去的那幾則還在；現在只要合流那一步沒跑到，PR 上就是一則都沒有，那幾份 review 全數滯留在執行目錄的內容檔裡等待事後補貼。這是選擇「一則彙整過的 comment」這個格式的必然代價，不是設計缺陷——不可能同時要求跨平台比對過的單一結論、又要求每份跑完就立刻可見；補救途徑是下面的補貼指引，不是回頭改成逐則貼。

`summary.txt` 每行對應一個行程，七個欄位，順序固定：`cli`、`pid`、`exit`、`ended_at`、`worktree_status`、`content_status`、`content_file`。前面幾行各是一個 reviewer，最後多出來的那一行是合流：`cli` 欄的形式是 `synthesis:<實際執行合流的 CLI 名稱>`，其餘五欄與 reviewer 行同格式，所以同一套逐行解析不必為它開特例，只要認得 `cli` 欄那個前綴。`worktree_status` 只有三個字面值：reviewer 行是 `ok` 或 `invalidated`，合流行固定是 `n/a`——合流跑的時候 worktree 已經被刪了，它也不需要，沒有東西可比對。

合流跑在哪一個 CLI 上不是固定的，選法也不是「誰先跑完就是誰」：優先挑產出了可信 review 的 claude 或 agy，只有這兩家都沒有可信 review 時，才退回摘要順序、取第一則可信的那一個。理由是授權不對稱——claude 與 agy 鎖得到零工具，codex 與 opencode 鎖不到（見「已知限制」；agy 那個「零」只涵蓋指令、取網址與未沙箱三類，檔案寫入不在其中）——而合流是整條流程裡唯一把每一份可信 review 全文從頭讀到尾的行程，也就是注入價值最高的那一個；同一次執行裡明明有鎖得死的可用，卻把它交給仍握著 shell 與網路的那一家，是不必要的曝險。退回取法而落到 codex 那一次，合流確實仍有 shell 與網路可用。**合流那一行的 `cli` 欄不是 `synthesis:claude` 也不是 `synthesis:agy` 時，必須主動轉達給使用者**，理由與 log 目錄上鎖失敗那條警告完全相同：使用者不會自己去翻那一欄，不講他就不知道這次的合流多帶了一段暴露面——落在 codex 是仍有 shell 與網路，落在 opencode 是 `edit` 與 `bash` 以外的工具面照樣開著——而那正是他判斷要不要照貼的依據之一。`content_status` 只有三個值：

- `ready`：標記完整、內容切得出來、結束碼為零、worktree 狀態正常，可張貼。合流那一行沒有 worktree 這一項，只看前三項。
- `withheld`：內容切得出來，但結束碼非零或 worktree 狀態失效，這則 review 失去事實依據，不可張貼；內容檔仍保留供人工判斷。回報時要把同一行的結束碼與 worktree 狀態一併給出——那是判斷它是不是被並發輪詢誤標的唯一依據（見「已知限制」）。合流那一行落到這裡只可能是結束碼非零。
- `no-content`：標記不成對，或標記之間是空的，沒有東西可貼，也不會有內容檔，`content_file` 欄位留空。

**委派張貼**：交給 `github-manager` 的是 PR 編號與 `content_file` 那個絕對路徑（合流那一則是 `.comment-body-synthesis.md`，退路的逐則各是自己的 `.comment-body-<行程編號>.md`），並要求以檔案張貼、不要把內容讀進來重打。這是一項要求，不是保證：那段文字的源頭是外部可控的 diff 與 comments，讀進任何一個模型的 context 都是多一次不必要的注入曝險，而 `github-manager` 本身具備 Read 工具，目前沒有任何權限機制擋住它把這個檔案讀進 context，全靠委派時的這句指示。以檔案張貼仍有實益：不會被超長內容截斷、不會被模型順手改寫。張貼失敗重試一次，仍失敗就記為未貼——以 `github-manager` 明確回報操作失敗為準，不確定的回應不算失敗；重試後仍失敗，把 `content_file` 的絕對路徑交給使用者手動處理。

### 兩層檢查

檢查分兩層，兩層都只對還沒完成的 reviewer 做。等待合流那一行的那一段沒有未完成的 reviewer，這兩層檢查也就沒有對象，該段的判準只剩監督行程是否存活（見上面「等到哪一行才算等完」）。

**例行心跳**（第 15、30 分鐘）：對每個還沒完成的 reviewer 報一行事實——elapsed 時間、累計 CPU 時間、該 CLI 的標準輸出 log 檔與標準錯誤檔的大小與 mtime。只報事實，不下判斷。

**嚴格檢查**（第 45 分鐘起，之後每輪都做）：對每個還沒完成的 reviewer 逐項查六件事：

1. 行程還在不在，以及 `ps` 的狀態碼是什麼。
1. 累計 CPU 時間自上一輪起有沒有增加。
1. 兩個 log 檔的大小與 mtime 自上一輪起有沒有變化。
1. 標準錯誤檔尾端最後數行。
1. 結束碼檔是否已經存在——存在代表它其實跑完了，只是監督行程還沒輪到它。
1. 監督行程本身是否存活，依據是執行目錄下的 `.supervisor.pid`。

只讀標準錯誤、不讀標準輸出：標準輸出裝的是模型輸出，源頭是外部可控的 diff 與 comments，讀進 main agent 的 context 等於自己開一條注入管道；標準錯誤預期只裝 CLI 自己的訊息，風險較低。這個切分是推理出來的判斷，不是像本節其他做法一樣經過實測驗證——四個 CLI 在詳盡或除錯模式下，是否可能把推理片段、或夾帶了外部可控輸入的錯誤訊息印到標準錯誤，並未查證過（見「已知限制」）。

嚴格檢查的結論收斂成三種：

- **已死**：行程不存在且沒有結束碼檔。回報即可，監督行程會在一秒內偵測到並補上一行 `exit` 值為 `unknown` 的摘要，流程不會卡住。
- **疑似卡死**：已跑超過 45 分鐘的門檻（與嚴格檢查啟動的時間點相同），且累計 CPU 時間與兩個 log 檔大小自上一輪起完全沒動。把全部觀測值原文交給使用者，並詢問要不要終止它讓其餘流程繼續；main agent 不自行終止——終止等於丟掉那一份 review，而且卡死是靠間接證據推斷的、可能誤判，某些 CLI 在等模型回應時確實會長時間零 CPU、零輸出。
- **仍在正常運作**：附上觀測到的證據，繼續等。

疑似卡死的判定需要跨心跳比對「自上一輪起有沒有變化」，所以 main agent 要記住上一次的觀測值；這在對話脈絡裡自然帶著，不必額外存檔。

### 收尾清理

執行目錄與本地分支的去留分開判斷，適用不同規則：

- **執行目錄**：全綠——每個派出的 reviewer 都有摘要行、都是 `ready`，而且本次該貼的那一則也成功產出並貼成功——才刪除整個執行目錄。「該貼的那一則」在派出兩個以上平台時就是合流那一行：它得存在、是 `ready`、且貼成功；只派一個平台時本來就不會有合流，那一則就是該 reviewer 自己的原始 review。合流那一行缺席或不是 `ready` 時，即使每個 reviewer 都 `ready` 也不算全綠——那恰好是最需要保留現場的一種結果：幾份可信的 review 都在，只差沒被合起來，那些內容檔是事後補救的唯一依據。刪除前必須先對整個執行目錄套用 `chmod -R u+w`，再執行刪除：`materials/` 與 `logs/` 都已經被腳本設成唯讀（`chmod -R a-w`），目錄本身沒有寫入權時，裡面的檔案連刪都刪不掉——直接對整個執行目錄 `rm -rf` 會逐檔 `Permission denied`、以非零結束碼收場，兩個目錄原封留在原地，而且每跑一次全綠的執行都會多留一組刪不掉的唯讀目錄。任一項不成立就整個目錄原封保留，回報絕對路徑。這裡的「貼成功」與「委派張貼」定義的「失敗」不是互補關係：只有拿到 `github-manager` 明確回報張貼完成才算成功，回應不確定、拿不到明確結果的一律不算全綠——即使那個回應也還沒到「明確回報失敗」的門檻。寧可多留一次執行目錄，也不要在張貼結果沒有確認的情況下刪掉唯一還留著內容檔的地方。
- **本地分支**：不論這次執行是否全綠，一律以強制刪除（`git branch -D`）清掉腳本建的那個本地分支——分支名尾端的行程編號等於執行目錄名尾端那一段，範圍嚴格限於這一個分支名，不對其他任何分支下強制刪除。強制而非一般刪除是明訂的界線，不是隨手選的：這個分支的內容完全等於 GitHub 上那個 PR 的 head，本地沒有任何獨有 commit，刪掉隨時 fetch 得回來；而一般刪除對未合併的分支幾乎必然失敗，結果是每跑一次就留一個，最後仍舊被腳本自己的陳舊分支清除機制強制刪掉——同樣是強制刪除，只是拖到下一次執行，中間那些殘留還會落進「呼叫腳本」那道閘門要使用者一一同意的清單裡。worktree 已被監督行程移除，分支沒有診斷價值；若 worktree 還在（例如逾時退出時監督行程還沒清完），git 自己會擋下這次刪除，是安全的。

**補貼指引**：使用者事後要求把某次沒貼完的貼上去時，讀該執行目錄的 `summary.txt`，把 `content_status` 為 `ready` 而還沒貼的貼掉。補貼同樣照單則規則走，不是把所有 `ready` 一次倒上去：先看合流那一行，它是 `ready` 就只補它一則；沒有那一行、或它是 `withheld` 或 `no-content`，才改補各平台 `ready` 的原始 review，並同樣說明彙整失敗。需要補貼的情境——逾時、session 被中斷——恰好就是對話脈絡已經斷掉、沒有依據判斷「哪幾則其實已經貼過」的情境，直接照 `summary.txt` 貼一輪可能造成重複張貼；補貼前先請 `github-manager` 查一下 PR 上是否已經有帶回音室標記（`<!-- pr-review-by-multi-agents -->`）、內容與該則 `content_file` 相符的 comment，有就跳過那一則。這一步的注入曝險比主線那次委派大，要認得：主線委派只交出路徑、明說不要讀進來，這裡的核對卻必然把 PR 上外部可控的 comment 全文與內容檔的 review 全文一起讀進 `github-manager` 的 context。沒有更省的做法——兩邊都沒讀過就判斷不了重複——所以這裡是明知並接受，不是這條路徑比較乾淨；能收窄的只有範圍：只比對帶那個標記的幾則，不要把整串討論串掃過去。這也是那個標記除了過濾回音室之外的第二個用途：讓事後補貼時有東西可以核對。刻意不做獨立的 slash command 參數或模式，一段指引就夠；代價是這條路徑得使用者主動開口。

### codex 與 opencode 上的等待與張貼

本節講的是 main agent 自己跑在哪個平台上，與本次派出了哪幾個 reviewer 是兩件事。張貼職責三個宿主平台一致，都是 main agent 的事；有落差的只剩等待粒度。codex 與 opencode 截至 2026-08 沒有背景喚醒機制（第三方 CLI 的能力會隨改版變動，這是可過期的實測結論，日後值得重新確認），做不到心跳、中途進度回報與嚴格檢查——那些都建立在「背景指令結束時會被喚醒」這個機制上。這兩個平台改成單一阻塞：在一次 shell 呼叫裡等到摘要檔出現合流那一行、或等到所有 reviewer 都已寫進摘要而其中可信的不足兩份（合流不會啟動，不會再有新行）、或到達兩小時總死線為止。等待結束後依 `summary.txt` 張貼，判準與 Claude Code 上完全相同：合流那一行是 `ready` 就只貼它一則，否則退回逐則貼各平台 `ready` 的原始 review 並說明彙整失敗。逾時處理也一致，已寫進 `summary.txt` 的照樣處理，其餘據實回報為仍在進行中。少了心跳與中途進度不代表功能打折：張貼是 main agent 的事之後，這兩個平台若像啟動腳本那樣起完就返回、不再等，就不會有任何一方去讀 `summary.txt` 完成張貼——功能會整個消失，因此等待本身在這兩個平台上同樣不可省略，只是退化成一次阻塞、結束後一次貼完。

## 已知限制

二十項多數是實作與審查過程中查證出來的事實，其中三項不是，各自在該項裡標明：標準錯誤那條風險切分是推理、沒有實測；agy 的 browser 類是未經查證的推斷；憑證環境變數那條是完全沒查證過的環境假設。另有一組項目的憑據只存在於對真實二進位的實測——agy 的三項（工具被自動拒絕時結束碼為零且輸出全空、json 的 `status` 欄位不可信、browser 類未逐一測試）、網路那一項裡的 agy 實測，以及合流授權那一項裡 claude 零工具那次探測——腳本註解、探測紀錄與其他任何檔案都沒有記載，本節是它們唯一的記錄處；要重新確認只能對真實二進位重跑同型探測，讀腳本或官方說明推不回來。遇到對應症狀時直接對照本節，不要當成待修的 bug 追。

- **不指定 model，opencode 預設 model 可用與否由使用者自負**：claude、codex、opencode 都不帶 model 參數，一律使用它們自己設定的預設值——硬編碼一個 model 既違背「永遠跟得上使用者設定變更」的原意，那個值本身也會過時；agy 是唯一的例外，理由與代價見下面硬編碼那一項。代價是使用者必須自行確保 opencode 的預設 model 可用；實測時它曾因帳戶餘額不足而失敗，該路會以非零結束碼結束並呈現在摘要檔中。
- **remote 名稱假設為 origin**：腳本只驗證當前工作目錄的 `origin` 是否對應到目標 PR 所屬的 repo，不符即拒絕執行，不會改試其他 remote 名稱。慣用 origin 以外名稱指向 GitHub 的使用者會直接被拒絕。
- **腳本會寫入使用者當前的 repo**：reviewer 對 worktree 是唯讀的，但腳本本身不是。六項寫入裡有五項落在使用者當前的 repo 上——fetch 這個 PR 的 base 分支並強制更新對應的遠端追蹤 ref、fetch 這個 PR 的 pull ref、建立一個以 `pr-review-` 開頭並帶 PR 編號與唯一後綴的本地分支、強制刪除形狀為 `pr-review-` 接數字再接數字、兩段皆為純數字的陳舊分支、清理 worktree 殘留登記。第六項橫跨兩處：它移除的是前次執行留下的殘留 worktree 目錄，而那個目錄在家目錄暫存區的前次執行目錄底下、不在 repo 裡，落在 repo 內的只有它連帶清掉的那筆 worktree 登記。第一項的順序要留意：`origin` 身分比對現在排在解析 base ref 之前執行，就是為了避免一個先前存在過的問題——比對若排在解析 base ref 之後，解析 base ref 的 fetch 會先動到使用者的 repo，於是連「remote 不符而被拒絕執行」的那一次也已經留下副作用；現在的順序下，remote 不符的拒絕不會再造成這個副作用。刪除前會逐一驗證兩段確實是純數字，所以只帶同一個前綴、形狀不同的分支（例如 `pr-review-notes`）不會被碰；但使用者若剛好有同形狀的分支，仍會被一併強制刪除，派出前的檢查見「呼叫腳本」。最後一項清理的是另一種東西，不要跟上面那個分支誤刪風險混為一談：`_reap_stale_run_dirs` 見到某個先前執行目錄的行程編號已經不對應任何存活行程、且該次的 worktree 子目錄還在時，會強制移除它並清掉對應的 worktree 登記——清的是這個 skill 自己上次執行留下的殘骸（行程已死、目錄仍在），不是使用者自己的東西，也不是 `git worktree prune` 那種只清「登記還在但目錄已經不存在」的被動清理，是主動找、主動刪。本次建立的那個分支，main agent 會在本次任務收尾時嘗試刪除（見「回報」節的收尾清理），不論這次執行是否全綠；只有 main agent 逾時或被中斷、沒能走到收尾這一步時，這個分支才會留到下一次執行時被腳本自己的陳舊分支清除機制盡力清掉。它尾端的唯一後綴與執行目錄名尾端是同一個值（見「產出物位置」），不是摘要裡任何一個 reviewer 的行程編號，拿 reviewer 的編號去找會找不到。
- **共用工作區的並發比對可能誤標，誤標與否由 main agent 判讀**：所有 reviewer 共用同一個 worktree，腳本在每個 reviewer 行程啟動前，於自己的派出迴圈裡取一次該 worktree 的 git 狀態快照，監督行程再於行程結束後取一次；前後不同即在摘要檔中把該次 review 記為 `withheld`（連同結束碼與 worktree 狀態一起寫進同一行）。由於多個行程同時執行、而比對是依序輪詢的，前一個行程的事後快照可能被還在跑的後一個行程影響。方向仍然是保守的——寧可漏貼，也不把失去事實依據的內容貼上公開 PR——但這一判斷現在落在 main agent 身上：main agent 讀到 `withheld` 那一行時，把同一行的結束碼與 worktree 狀態一併回報給使用者，讓使用者判斷這是不是被並發輪詢誤標的；內容檔還在執行目錄下，使用者確認後可要求委派 `github-manager` 手動貼上去。監督行程與腳本本身不再介入這個判斷，只負責如實記錄那兩個值。保證也僅限於此——前後快照的比對擋不住改完又還原：reviewer 若寫入檔案後在自己結束前刪掉，或把已追蹤檔案改回位元組相同的內容，兩次快照會相等而判為正常。

| 網路 | 分兩路，結論相反：reviewer 那一路未關閉，`curl` 經 Bash 打得通，四種權限組合實測皆放行（實測）；合流那一路已關閉，允許清單留空加明確停用 `Bash`，連 Bash 工具本身在該 session 裡都不存在，網路管道隨之一併關閉（實測） | 未關閉：沙箱不限制網路 I/O，`curl` 打得通（實測） | 部分關閉：`curl`、`wget`、`nc` 三條被拒（實測）；其餘外連管道未列入拒絕清單、落到 `--auto` 預設放行（未查證） | 已關閉：`curl`、內建取網址工具、複合指令旁路皆被拒（實測）；browser 類未逐一測（未查證） |
| 無頭模式預設拒絕的涵蓋範圍 | 沒有這一層，拒絕範圍完全由腳本傳入的旗標決定（實測） | 沒有這一層，只有 `-s read-only` 一個開關，且它在非互動下會升級（實測） | 沒有這一層，未列進拒絕清單的一律落到 `--auto` 預設放行（實測） | 指令、取網址、未沙箱三類，檔案寫入明確不在其中（實測）；browser 類算不算落在那三類內沒有查證過（未查證） |

chmod、網路、合流授權三條各展開表中的一面：chmod 那條展開「檔案寫入」，補的是作業系統層的兜底鎖在哪三個位置、三道鎖的強度差在哪；網路那條展開「網路」，補的是各平台為什麼只能做到這個程度；合流授權那條展開的是同一組能力在合流那一次執行下的樣貌——工作目錄與可用工具都與 reviewer 那一路不同。每格括號裡標的是該格的依據：「實測」指以真實 CLI 二進位跑過同型探測，「未查證」指沒有測過、只能從其他行為推斷，兩者不得互相代換。要查某個平台在某一面向上是什麼狀況，以本表為準；三條限制補的是後果與處置，不重寫表裡的事實。claude 的「檔案寫入」、「shell」與「網路」三格分 reviewer 與合流兩路寫，不是贅述：兩路傳的旗標組合不同，同一個 CLI 因此得出相反的結論，把其中一路的結果套到另一路就會出錯。

- **CLI 自身的權限機制都保證不了唯讀，那幾個位置靠 chmod 守，而 chmod 守得比字面上弱**：截至 2026-08 實測，四者在 reviewer 那一路各有各的繞過方式，逐平台的形式見上表「檔案寫入」那一列（claude 那格另記了合流那一路的相反結論，本項不涵蓋那一路）；其中 agy 那一格與另外三格性質不同——不是權限層擋不住，是寫入工具根本不經過權限層。因此腳本以 `chmod` 拿掉權限位元的方式鎖住 worktree、材料檔目錄與 log 目錄三個位置，各 CLI 自身的旗標降級為第一層，只負責限制模型會去嘗試的動作範圍，不是唯讀承諾的依據；log 目錄那道鎖是在所有 reviewer 都啟動之後才上，只擋新開檔案，不擋已經開啟的檔案控制代碼。這道鎖是提高門檻，不是機制保證，兩個缺口要認得。其一，reviewer 與腳本跑在同一個使用者身分底下，那些檔案的擁有者就是它自己，它把權限位元改回去就能寫——而四個 CLI 的拒絕清單裡，只有 opencode 那一份列了 `chmod`，claude、codex、agy 都沒有任何一條擋它。其二，三道鎖的強度並不相同，不要因為並列就當成同一種：worktree 那道上不成即中止整次執行（連同 worktree 一起移除、非零結束碼），材料檔那道是靜默盡力（失敗不影響流程，也不會有任何訊息），log 目錄那道失敗只往標準錯誤印一行警告、照樣繼續跑（所以「回報」節要求看到那行警告必須轉達）。reviewer 本來就不需要寫任何檔案，只把 review 印到標準輸出，所以 claude、codex、opencode 三者的寫入工具在旗標層已經完全不放行，那道 chmod 對它們是第二層防線、留著擋旗標層擋不住的路徑；agy 沒有旗標層那一道可用，chmod 對它就是唯一的一道——而依上面兩個缺口，那一道本身也不是保證。下游後果是：要判斷某次 review 有沒有可能動過 worktree，看的是摘要檔那一行的 worktree 狀態比對結果，不是某個 CLI 的權限設定。opencode 的 bash 黑名單另外新增了 `git fetch*`：`git fetch` 語意上是讀，卻會更新本地的遠端追蹤 ref，寫的是共用的 `.git` 物件與 ref、不在 worktree 這棵樹底下，chmod 鎖不住，原本會落到 `--auto` 的預設放行，現已補上。
- **執行目錄根層沒有上鎖，摘要檔與內容檔就放在 reviewer 寫得到的地方**：上鎖的只有 worktree、材料檔目錄與 log 目錄三處，而 `summary.txt`、各份 `.comment-body-*.md`、`.roster` 與合流的 prompt 全在執行目錄根層，那一層自始至終可寫；reviewer 的 prompt 裡就有 worktree 的絕對路徑，往上一層即是。後果要說白：main agent「只讀結構化欄位、review 內容不進 context」這道區隔，以及委派張貼時「只交出路徑、由 `github-manager` 以檔案張貼」這條保證，實際上都架在一個 reviewer 寫得到的檔案上——寫得到那一層的 reviewer 可以改掉別人那一行的 `content_status`、改掉 `content_file` 指向的內容，或補一整行進去。這不是機制保證，是目前的實際強度。不改的理由是結構性的：摘要檔就在那一層而監督行程整場都在寫它，上鎖會直接讓流程停擺；而同身分可回復權限位元（見上一項）本來就是這個隔離手段的固有上限，多鎖一層也擋不住存心繞過的。因此這裡的處置是揭露而非承諾——PR 上出現的內容與某份 log 對不上、或摘要欄位與 log 明顯矛盾時，從這裡查起。
- **網路是一條 worktree 唯讀保護涵蓋不到的外洩管道，四個平台現況不同，只有 agy 在工具層真正關上**：被審查的材料——PR、issue、design document 全文——是外部可控、不可信的內容；reviewer 只要有能力對外發出請求，注入文字就能誘導它把讀到的東西編碼進網址、送到攻擊者控制的主機。這與檔案寫入、與 GitHub 操作是三件不同的事：它不寫任何檔案，也不改 git 狀態，worktree 的 chmod 唯讀權限與啟動前後的 git 狀態比對完全涵蓋不到它。四個平台現況要分開看，不是整齊劃一的樣貌：claude 拿掉了 `WebFetch` 授權，但那只關掉一條路徑，沒有關上這個面——`curl` 透過 Bash 工具仍然打得通，已用四種權限組合實測過（本腳本現行旗標、`--permission-mode auto` 或 `manual` 各加一條 `Bash(git diff:*)` 白名單、`--disallowedTools` 明確加一條 `Bash(curl:*)`），全部仍放行；唯一擋得住的做法是整個停用 `Bash` 工具，但那會連契約要求的 `git -C <worktree> diff <base-ref>...HEAD` 都跑不了，這條指令沒有其他管道可執行，所以沒有採用——**未關閉**。codex 的 `-s read-only` 沙箱只限制本地檔案系統寫入、不限制網路 I/O，也沒有其他旗標能獨立於檔案系統沙箱之外限制網路，實測 `curl` 一樣打得通——**未關閉**。opencode 的 deny list 新增了 `curl*`、`wget*`、`nc*` 三條，已用真實二進位逐一確認這三個指令被拒，但這不是窮舉——Python 的 `urllib` one-liner、`/dev/tcp` 重導向、`ssh`、`openssl s_client`、透過 `dig`/`nslookup` 的 DNS 外洩等仍未列在黑名單裡，一樣落到 `--auto` 的預設放行，這一層也沒有等同 worktree chmod 的作業系統層兜底——**部分關閉，仍有殘留空間**。agy 是四者中唯一在工具層真正被關上的：它在無頭模式下預設拒絕指令、取網址與未沙箱那幾類工具，而腳本給它的允許清單只有 `git diff` 一條，所以沒被列出的就跑不了；實測 `curl` 被拒、內建的取網址工具被拒、把命令藏進複合指令的旁路被拒，對照組的 `git diff` 照常放行——**已關閉，但不宣稱窮舉**，未逐一測試的部分見下面 browser 那一項。agy 這四項探測與本節 agy 那幾項一樣，只記在本節、腳本註解裡沒有；claude、codex、opencode 那三段的實測結論則都寫在腳本註解裡，兩者不要混為一談。契約要求 reviewer 不得連線是一條行為規則，在 claude、codex、opencode 上不是機制保證，不要把它當成已經被工具層擋下的事實；agy 上有工具層擋著，但那是四者中唯一的一個，不要把它的結果套到另外三個身上。
- **合流的授權因 CLI 而異，「不給任何工具」只對 claude 完全成立，agy 只關得住網路那一軸**：四路現況分開看。claude 整個停用 `Bash`、允許清單留空——那是本節網路那一項記載過唯一能關掉 claude 網路的做法，reviewer 那一路因為契約要跑 `git diff` 而不能用，合流不需要任何指令，正好用得上——**零工具，已用真實二進位實測**。探測條件與合流那一路實際傳的旗標相同（權限模式 `dontAsk`、允許清單留空、拒絕清單含 `Edit`、`Write`、`NotebookEdit`、`WebFetch`、`Bash`，提示詞走標準輸入），在臨時目錄裡要求它建立一個檔案：寫入被擋下，而且不是模型自我克制，是工具根本不存在——逐字回覆為 `No such tool available: Write. Write is disabled for this session, in subagents as well as here.`，另外追問 `Edit`、`NotebookEdit`、`Bash` 是否以延後載入的形式存在也都查無，目錄實況確認沒有任何檔案被建立。那句訊息明載停用範圍涵蓋 subagent，所以「改派 subagent 代寫」這條旁路一併封住。這與本項上面 chmod 那一條記載的「claude 擋不住檔案寫入」不衝突，兩者量的是不同的旗標組合：那一條講的是 reviewer 那一路——允許清單裡有讀取類工具、`Bash` 又因為契約要跑 `git diff` 的唯讀例外而必須留著，路徑形式的拒絕規則就擋不住；合流這一路是允許清單整個留空加上明確停用 `Bash`，那才是真正關得掉的組合。同一個 CLI 在兩條路徑上結論相反，來自旗標不同，不是兩次實測互相打架。agy 的允許清單寫成空的，而它在無頭模式下對指令、取網址與未沙箱三類本來就預設拒絕——**那三類為零，但檔案寫入不為零**，兩半要分開讀。前半是它網路面確實關著的依據，也是合流優先挑它跑的理由，這個方向仍然成立。後半不是尚待查證的推斷，是上表「檔案寫入」那一列與本節 chmod 那一項記載的實測結論：agy 的寫入工具根本不經過它的權限層，寫檔不在那三類預設拒絕之內。而合流這一路比 reviewer 那一路更沒有兜底——reviewer 寫 worktree 至少還撞得到 chmod 那道唯一防線，合流卻是等 worktree 被刪除之後才跑的，工作目錄就是執行目錄根層，而那一層自始至終沒有上鎖（見上面根層那一項），它的隔離家目錄底下還把使用者的真實憑證檔以符號連結掛著。所以結論分兩軸下：外洩軸（網路）確實關著，優先挑它跑的方向成立；檔案寫入面是開的，而且沒有第二層。網路那一軸的「已關閉」則仍帶著本節 browser 那一項的但書——預設拒絕只涵蓋那三類，browser 類算不算落在其中沒有查證過，所以是「那三類為零」，不是已經證實的全面為零，而合流又優先挑它跑。codex 走的仍是 `-s read-only` 沙箱：那個模式只限制本地檔案系統寫入，shell 照常可用、網路照樣通（與網路那一項同一組實測），codex 也沒有更緊的旗標可加，而且合流那一次是以執行目錄為工作目錄跑的，所以連「不給檔案系統」都不準確——**仍有 shell 與網路**。opencode 用的是一份只拒絕 `edit` 與 `bash` 兩項工具的設定檔，比 reviewer 那份逐條動詞黑名單緊得多，但它終究是點名兩項的拒絕清單、不是空的允許清單，這兩項以外的工具面照樣開著，同樣以執行目錄為工作目錄——**比 reviewer 那一路窄，但不是零**。合流的 CLI 選取規則正是為這個不對稱而設（見「回報」節）：優先挑 claude 或 agy，兩家都沒有可信 review 時才落到另外兩家——落到 codex 或 opencode 的那一次，這段暴露面是真實存在的，不是理論上的；而挑中 agy 的那一次，關掉的只有網路那一軸，檔案寫入面照樣是開的，且沒有 chmod 那道兜底。
- **GitHub 側沒有任何旗標層級的保證，只有契約文字**：reviewer 現在不需要也不應該執行任何 GitHub 指令——張貼由 main agent 委派 `github-manager` 完成，不是 reviewer 自己、也不是監督行程的事，契約也明文禁止 reviewer 動 GitHub。但截至 2026-08 實測有一個還沒關掉的殘留風險：真實的 claude 在本腳本使用的權限模式下，即使工具白名單完全不含任何 Bash 指令模式、甚至明確把張貼 comment 那條指令加進黑名單，gh 指令仍然會透過 Bash 實際執行——旗標層級沒有任何機制保證擋得下它。因此若被審查的 diff 或 issue 內容成功誘導模型主動去執行 GitHub 寫入操作，唯一的屏障是那需要網路與使用者自己的 gh 憑證，而本腳本對這兩者沒有做任何隔離。worktree 狀態比對補不上這裡，它只涵蓋檔案系統，抓不到任何 GitHub 上的動作。PR 狀態或既有留言出現非預期異動時，從這裡查起。
- **狀態比對涵蓋被 gitignore 忽略的路徑**：這是刻意的選擇，為的是不讓「違反會被偵測到」這個承諾在被忽略的路徑上落空。代價是某個 CLI 若在工作區內產生自己的快取或暫存檔、而該路徑剛好被忽略，會造成誤報。
- **main agent 逾時或被中斷，之後才跑完的那些沒人張貼**：張貼職責搬到 main agent 之後，兩小時總死線到期、或使用者中途中斷 session，都會讓之後才產出的東西永遠沒人張貼——監督行程不受影響，仍會照常跑完 reviewer、切內容、寫摘要、刪 worktree，該起合流時照樣起、照樣把合流那一行寫進摘要，但不再有人讀摘要檔去貼。改成單則張貼之後這件事的代價變大了：以前中斷只損失還沒貼的那幾則，現在因為唯一要貼的那則排在最後，中斷幾乎必然是一則都沒貼上去。內容檔仍會產生、保留在執行目錄下，只是不會自動出現在 PR 上，需要使用者事後主動要求補貼（見「回報」節的補貼指引）。
- **codex 與 opencode 上沒有心跳與中途進度，只有一次阻塞等完再貼**：這兩個平台沒有背景喚醒機制，做不到 Claude Code 上的輪詢、心跳與嚴格檢查；main agent 改為一次阻塞等到合流那一行出現、確定不會有合流，或到達死線，再依同一套判準貼那一則或退路的逐則（見「回報」節）。等待期間沒有任何中途進度可看，連哪個 reviewer 已經跑完都看不到，使用者只能等這次阻塞的呼叫結束，或事後打開執行目錄的 `summary.txt` 與 log 檔自行查看。
- **嚴格檢查「只讀標準錯誤」的風險切分是推理，未經實測驗證**：理由是標準輸出裝模型輸出、標準錯誤預期只裝 CLI 自己的訊息（見「回報」節「兩層檢查」）。這個切分沒有像本 skill 其他安全假設一樣經過實測——四個 CLI 在詳盡或除錯模式下，是否可能把推理片段、或夾帶了外部可控輸入的錯誤訊息印到標準錯誤，並未查證過。做法與推理維持不變，僅在此據實標注其未經驗證的性質。
- **agy 的工具被自動拒絕時，結束碼是零而標準輸出全空**：無頭模式下 agy 對未列在允許清單裡的工具一律自動拒絕，被拒之後它仍以結束碼零結束、什麼都不印。所以在 agy 上「結束碼為零」不等於「正常完成」。本 skill 的流程剛好不會被這一點騙到，因為可不可貼是靠起訖標記切不切得出內容判定的，這種執行在摘要裡會呈現為 `exit=0` 配 `content_status=no-content`；要小心的是日後有人改拿結束碼本身當判準，那會把一次全空的執行讀成成功。憑據是實作階段對真實 agy 二進位的實測，腳本註解裡沒有這一條，本節是唯一的記錄處（見本節開頭）。
- **agy 的 json 輸出中 `status` 欄位不可信**：工具被拒時它照樣回報成功，而內容是空的。腳本從頭到尾不解析 agy 的 json、只認起訖標記，所以現況不受影響；這一條是留給日後想改用那個欄位判定成敗的人——它量到的不是這件事。憑據與上一項同源：實作階段的實測，腳本註解未記載，本節是唯一的記錄處。
- **agy 的 `--print-timeout` 預設只有五分鐘，是它獨有的失效模式**：四個 CLI 中只有 agy 自帶逾時，而五分鐘跑不完任何一次真實 review，所以腳本明確把它覆寫成兩小時。這一條的用處在症狀對照：agy 那一路的輸出若在某個時間點整齊斷掉、log 停在半句話，先確認這個旗標有沒有被傳進去，而不是先懷疑模型。
- **agy 的 model 是破例硬編碼，會隨 Gemini 改版過時**：另外三個 CLI 都能從各自的設定檔讀回預設 model，agy 沒有任何途徑讀得回來（它的 models 子命令不標預設、json 輸出沒有 model 欄位、狀態檔裡也沒有），而 comment 的 `platform/model` 欄要求每一列都有真實的 model 值，所以腳本破例把它寫死成 `gemini-3.7-flash-high`；尾綴 `-high` 是 agy 自己編碼推理力度的方式，也是它不必再傳 `--effort` 的原因。代價是這個值會過時：Gemini 改版後它可能指向一個不存在或已淘汰的 model，症狀是 agy 那一路以非零結束碼失敗，或揭露段落裡的 model 名稱與實際跑的那個對不上。
- **agy 的 browser 類工具未逐一測試，網路那一條的「已關閉」不宣稱窮舉**：上面網路那一項列出的實測涵蓋的是指令與取網址兩類；agy 另有 browser 類工具沒有逐一測過，而且不能靠「無頭模式預設拒絕」把它推過去——腳本記載的預設拒絕範圍是指令、取網址與未沙箱這三類，browser 類算不算落在其中任何一類，本身就沒有查證過。所以這一項是**未經查證的推斷**，兩種可能都還沒被排除：它可能與另外兩類一樣被拒，也可能整類都在那三類之外、根本不受那份允許清單約束。要確認只能對真實 agy 二進位重跑一次同型探測。
- **隔離只覆寫了 `HOME` 一個環境變數，憑證類環境變數會原樣穿透**：agy 沒有指定設定檔位置的旗標，所以腳本改用一個隔離家目錄當它的設定來源，憑證以符號連結保留、不複製。但啟動時只覆寫 `HOME` 這一個變數，其餘環境原樣繼承，`GEMINI_API_KEY` 這類憑證變數會直接穿透到 agy 行程。本機這幾個變數皆未設定，所以目前不影響；而 agy 會不會優先採用它們、因而繞過那個隔離家目錄，完全沒有查證過——這是本節開頭說的「完全沒查證過的環境假設」。設了這類變數的機器上，隔離的實際範圍是未知的。
- **合流行程本身可能誤判共識與矛盾**：它只讀各份 review 的文字，沒有 worktree、沒有 diff、也沒有任何工具，哪幾則在講同一件事、哪兩則彼此互斥，全靠讀那些文字判斷。措辭差很多的同一件事可能被拆成兩列，於是獨立平台數少算、信心被壓低；措辭相近的兩件事可能被併成一列，於是平台數多算、信心被抬高；而「一份說有問題、另一份明確說沒問題」也可能被讀成矛盾，或反過來漏成沉默。合流契約用取最高嚴重度、只上調不下修這類規則把誤判方向壓向保守，但壓不掉誤判本身。對某一列存疑時就去翻原始的各份 review——未全綠的執行目錄不會被刪，那幾份內容檔還在。

## 產出物位置

產物主要落在使用者家目錄下的暫存目錄中、依本 repo 暫存檔規則命名的專案專用資料夾內，往下是 `pr-review`，再往下是本次執行目錄；唯一落在該處之外的，是上節那個留在使用者 repo 的本地分支。

```text
~/.tmp/<專案專用資料夾>/pr-review/<PR 編號>-<時間戳記>-<唯一後綴>/
├── worktree/                     # 各 reviewer 共用的程式碼工作區，跑完後由監督行程刪除
├── materials/                    # pr.md、issue.md、design.md，寫完即設為唯讀
├── logs/                         # 每個派出的 CLI 各有 prompt、行程編號、標準輸出 <CLI>.log
│   │                             # 與標準錯誤 <CLI>.log.stderr，跑完後保留；agy 也在其中
│   └── agy-home/                 # agy reviewer 的隔離家目錄，憑證是指回真正家目錄的符號連結
├── synthesis.log                 # 合流行程的標準輸出，另有 synthesis.log.stderr
├── .synthesis-prompt             # 合流行程吃的完整 prompt：合流契約全文、派出名單、各份 review
├── .roster                       # 派出當下每個 CLI 解析到的 model，合流的揭露段落靠它
├── .pr-body-raw                  # PR 的原始內文，issue 推導只讀這一份，不讀 materials/pr.md
├── .materials-status             # 本次材料蒐集結果，print_summary 據此印出材料清單
├── .comment-body-<行程編號>.md   # 監督行程從各 reviewer 標準輸出切出來的 comment 內文
├── .comment-body-synthesis.md    # 合流那一則，正常情況下唯一會被貼上 PR 的那一份
├── .supervisor.pid               # 監督行程自己的行程編號，供心跳檢查存活
└── summary.txt                   # 每個 reviewer 一行，合流再一行，七個欄位
```

合流那幾個產物落在執行目錄下、而不是 `logs/` 裡面，是被迫的而非分類偏好：`logs/` 在所有 reviewer 都啟動之後就被 `chmod` 設成唯讀（見「已知限制」那條 chmod 鎖），而合流是等 reviewer 全部結束才起的，那時候已經沒辦法在 `logs/` 底下新建任何檔案。`.roster` 則是另一回事——它必須在派出當下就寫，因為 reviewer 一旦結束，它當時解析到的 model 名稱就沒有地方查得回來了，而合流的揭露段落要列出全部原定派出目標與各自的 model。

標準輸出與標準錯誤分成兩個檔不是整理癖：review 全文包在一組起訖標記之間印到標準輸出，監督行程就靠那兩行標記切內容，而兩股輸出合流時緩衝行為不同，標記行可能被標準錯誤的內容插斷，切出來的東西就不可信了。`<CLI>.log` 因此保持純標準輸出，一個位元組的其他東西都不寫進去；`synthesis.log` 與它的標準錯誤檔分成兩個檔是同一個理由，合流那一則也是靠同一組標記切出來的。

只要內容切得出來就會留下這個檔，不管 main agent 事後貼成功、貼失敗，還是根本沒有委派張貼：`content_status` 為 `ready` 而張貼成功時，它是 PR 上那則 comment 的副本；張貼失敗時，它是使用者唯一能拿回來手動張貼的那一份；`content_status` 為 `withheld` 時，它是判斷這則 review 到底該不該人工放行的依據。三種情形共用同一條保留規則比分開處理更難出錯。`content_status` 為 `no-content` 的那一則不會有這個檔，因為根本沒有內容被切出來。合流那一份 `.comment-body-synthesis.md` 適用同一條規則，只是它的 `withheld` 只可能來自結束碼非零。

上面只列主要項目，目錄下另有各行程的結束碼檔與狀態快照檔等內部檔案。兩份 opencode 權限設定檔的位置與檔名都不同，不要混為一談：reviewer 那份是 `logs/opencode-permission.json`，跟著它自己的 log 放在 log 目錄下；合流那份是執行目錄根層的 `opencode-synthesis-permission.json`，因為合流啟動時 `logs/` 早就唯讀了。同一個理由，合流若跑在 agy 上，它的隔離家目錄是根層的 `agy-synthesis-home/`，不是 `logs/agy-home/` 那一個。目錄名尾端的唯一後綴是腳本自身的行程編號，用來讓同一秒對同一個 PR 啟動的兩次執行不撞目錄；它與摘要中各 reviewer 的行程編號是不同的東西，不能拿某個 reviewer 的編號去拼執行目錄路徑。

log 刻意放在 worktree 之外：worktree 跑完會被刪除，而 log 是事後查問題的唯一憑據，混在一起會一起消失。

這裡刻意以家目錄下的絕對路徑定址，不套用暫存檔規則中「先在工作區根目錄建立 `.tmp` 符號連結」那一步。本 skill 執行時的工作目錄是使用者的 repo 工作副本，為跑一次 review 在那個 repo 根目錄留下一個符號連結，是不必要的持久寫入，與 reviewer 唯讀、逐行程比對 worktree 狀態的整體設計方向相反。

回收責任的條件見「回報」節的「收尾清理」：執行目錄依全綠與否決定去留，本地分支則不論全綠與否一律嘗試刪除。全綠時 log、標準錯誤檔、prompt、切出來的內容檔與摘要檔會隨執行目錄一起刪除，因為每一則 review 都已確認可信、該貼的那一則也已成功貼上 PR，不再有查證價值；未全綠時執行目錄原封保留，不受「任務結束後主動清除暫存檔」的例行清除約束，因為這些檔案正是事後查問題與補貼的唯一憑據，任務收尾時不要刪。worktree 都由監督行程自己移除，不需要代勞。

腳本現在把 jq 列為硬性前置需求，缺席會在檢查階段直接拒絕執行，早於任何對使用者 repo 的寫入動作——不會出現「jq 缺席才發現，但 repo 已經被動過」的情形。
