# PR Review by Multi-Agents

同時派出多個獨立的 AI agent CLI 行程，對同一個 PR 各做一次完整 code review，每個行程把 review 全文包在一組起訖標記之間印到標準輸出，再由腳本的監督行程切出內容、張貼成一則繁體中文 comment 到該 PR 上。目的是取得多模型的觀點差異與盲點互補，不是把 review 卸載到背景。

reviewer 自己不張貼、也不寫任何檔案，是刻意的：被審查的 diff 與 issue 內容是外部可控、會原樣進入模型 context 的提示注入管道，而這個倉庫審查的正是使用者的 AI 工具設定檔；給 reviewer 寫入能力沒有辦法只給一個目錄，等於把整個帳號權限範圍交出去。代貼職責放在監督行程，因為它是 shell 子行程而不是 AI agent，跑的是固定指令、沒有注入風險，而且三個平台行為一致。

實際工作全部在 `scripts/run.sh` 裡：worktree 建立、prompt 組裝、CLI 行程啟動、代貼、監督與清理都由它負責。本 skill 只做三件事——蒐集輸入、呼叫腳本、讀摘要檔回報結果。不另行以 subagent 或自己組 prompt 的方式重做這件事：審查契約全文由腳本原文嵌入每個 reviewer 的 prompt，改成由模型轉述後，四個嚴重度等級的界線會在轉述中糊掉，數份 review 也就失去可比性。

## Reference 載入時機

| Reference | 載入時機 |
| --- | --- |
| `references/reviewer-contract.md` | 本 skill 自己不載入。它是各 reviewer CLI 共吃的審查契約全文，由 `scripts/run.sh` 依自身路徑定位後原文嵌入每個 reviewer 的 prompt；只有要修改審查標準本身時才需要打開它 |

## 蒐集三項輸入

三項輸入依下表取得。任一項取不到就傳空字串，不阻斷流程，也不用猜測值填補：契約把空字串明確渲染成「不存在」，reviewer 會據此略過對應審查軸並在 comment 中載明；而猜錯的 issue 或 design document 會讓所有 reviewer 拿錯的需求當判準，且不會有任何明顯徵兆。

| 輸入 | 取得方式 |
| --- | --- |
| PR 連結 | 使用者指名了就原樣傳。沒指名時先確認目標（見下）；確認過程中若拿到了連結或編號就原樣傳，只憑「就是當前分支那個」確認下來的則傳空字串，腳本自己會從當前分支推導，不必先在這裡查一次 |
| issue 連結 | PR 連結傳了非空值時，從該 PR 內文的 closing keyword（`Closes`、`Fixes`、`Resolves` 後接 issue 編號）取得；PR 內文沒有寫就傳空字串 |
| design document 路徑 | 從對話脈絡取得，也就是本次工作採用的設計文件或 spec 檔路徑，一律傳絕對路徑；脈絡中沒有就傳空字串，不去掃描 repo 湊一份 |

design document 傳絕對路徑不是風格偏好：reviewer 的工作目錄是腳本開出來的 worktree，repo 相對路徑會解析到那份工作副本裡的另一個位置，多半根本不存在，結果是整條設計符合度軸靜默失效。

PR 連結傳空字串時，也就是只憑「就是當前分支那個」確認下來的那種情形，issue 連結跟著傳空字串——手上沒有 PR 就讀不到它的內文，而契約禁止 reviewer 從 PR 標題或分支名反推需求。代價是本輪的需求符合度軸會被略過（reviewer 會在 comment 中載明未審此軸）；要讓那一軸生效，請使用者直接給出 PR 連結。

**目標 PR 要與使用者當下談的工作一致，才可以派出。** 這是上面「取不到就傳空字串、不阻斷流程」的唯一例外，而且性質不同：那條講的是材料缺了照樣審，這條講的是打到哪個 PR。comment 一旦貼上會發出通知、對協作者可見，而契約禁止 reviewer 刪改任何留言，沒有收回路徑；腳本的 `origin` 比對只保證打到當前 repo 的某個 PR，不保證是使用者要的那一個。因此分三種情形：使用者指名了 PR，直接派出；使用者沒指名，但當前分支對應的 PR 就是本次對話正在進行的工作，直接派出；兩者都不成立時，先停下與使用者確認目標 PR，確認前不呼叫腳本。

## 呼叫腳本

腳本是本 skill 目錄下的 `scripts/run.sh`。執行環境有告知本 skill 的 base directory 時直接據此組出路徑；取不到時依序測試下列兩條安裝路徑，取第一個存在的：

1. Claude Code：`$CLAUDE_CONFIG_DIR/skills/pr-review-by-multi-agents/scripts/run.sh`，該環境變數未設時以 `~/.claude` 代入。倉庫的安裝腳本用同一個變數決定部署根目錄，personal 訂閱那套部署會把它指向另一個設定目錄，路徑寫死成 `~/.claude` 會在那套部署下找不到檔案。
1. codex 與 opencode：`$AGENTS_HOME/skills/pr-review-by-multi-agents/scripts/run.sh`，該環境變數未設時以 `~/.agents` 代入。兩者共用這一條，而安裝腳本同樣允許以這個變數覆寫該目錄。

兩條都不存在時停下回報，不自行改用其他途徑——不改跑倉庫工作副本裡的那一份，也不改以 subagent 重做審查。找不到腳本代表本 skill 沒有被正確安裝，繞道會讓這件事被一次看似成功的執行蓋過去。

呼叫形式是三個位置參數，順序固定不可調換，三者皆可為空字串——腳本只認位置不認名稱，順序錯了會把 issue 連結當成 PR 連結，而多數情況下這只會表現為一次難以追查的解析失敗：

```bash
<run.sh 路徑> "<PR 連結>" "<issue 連結>" "<design document 路徑>"
```

執行時的工作目錄要落在目標 PR 所屬 repo 的工作副本內：腳本以當前工作目錄的 `origin` remote 驗證是否為同一個 repo，不符即拒絕執行。

**派出前先確認不會刪掉使用者自己的分支。** 腳本每次啟動都會把當前 repo 中所有 `pr-review-` 開頭的分支逐一強制刪除，不看有沒有合併過，只有正被某個 worktree 檢出的會被 git 自己擋下來。本次執行建立的分支形狀固定是 `pr-review-<PR 編號>-<唯一後綴>`，兩段都是純數字，因此呼叫腳本前先列出當前 repo 所有 `pr-review-` 開頭的分支——這是本地唯讀 git 操作，不涉及 gh，不必走委派——凡不符合這個形狀的一律視為使用者自己的分支，先告知這些會被強制刪除並取得同意再派；沒有這類分支就直接派，不打斷流程。這道閘門與上面確認目標 PR 那道同一個理由：刪掉未合併的分支同樣沒有收回路徑，而「已知限制」那節是給遇到症狀時事後對照用的，救不了這一件。

## gh 呼叫的歸屬

本 skill 涉及兩種 gh 呼叫，歸屬不同，分開處理。

- **腳本與監督行程執行的 gh，包含代貼那一步**：不算 main agent 自行處理，呼叫腳本不需要改走委派。倉庫規則把透過 gh 對 issue、PR、comment 的實際操作劃給 `github-manager`，規範的對象是 main agent 自己要不要動手；經由腳本與它派出的子行程發出的呼叫沒有被那條規則界定，兩種讀法都成立，因此在此明說取這一種。
- **本 skill 自己要下的 gh 查詢**：屬於 main agent 行為，一律委派 `github-manager`，不自行呼叫 gh。張貼與結果查核都由腳本包辦之後，這裡只剩一種——為了取得 issue 連結而讀 PR 內文。委派出去的是查詢本身，判斷邏輯不隨之外包：issue 連結怎麼從內文的 closing keyword 抓出來，留在本 skill 判斷。

## 回報

### 腳本返回時

腳本印出的摘要分兩部分：實際派出了哪幾個 reviewer，附各自的行程編號與 log 檔路徑；跳過了哪幾個，附原因。照這份摘要向使用者回報，並指名本次實際的目標 PR——使用者沒指名 PR 時，這是他確認打對地方的唯一機會，PR 編號可從摘要裡的 log 路徑或執行目錄名取得。摘要點出「本次只有一個 reviewer、交叉驗證不成立」時一併轉達。

腳本印完摘要就返回，此時 review 行程還在背景跑。

腳本以非零結束碼結束時分兩種情形，靠標準錯誤訊息有沒有指出已啟動的行程編號分辨：

- **訊息沒有指出任何已啟動的行程編號**：可能是前置檢查不通過（gh 缺席或未登入、PR 不存在、CLI 全數缺席、base ref 或 worktree 建不起來），也可能是派送到第一個 CLI 就失敗、一個 reviewer 都還沒起來；兩者處置相同，把訊息原文回報，不重試、不改用其他途徑——這類失敗全是環境前提不成立，重跑一次面對的條件與上一次完全相同，只會再失敗一次，而繞道則會在前提不成立的情況下把審查派出去，產出沒有依據的 review。
- **訊息指出了已啟動的行程編號**：派送途中失敗，較早啟動的 reviewer 變成無人監督的孤兒行程，worktree 也已被強制移除。這一次不會有監督行程去讀它們的輸出，所以它們的 review 不會被張貼、也不會有摘要檔可讀——內容留在各自的 log 裡。腳本把那些編號印出來就是為了讓人有東西可以終止——原文轉達該清單，並說明這些行程無人監督、結果只會停在 log 中。

### 在 Claude Code 上等待並回報結果

張貼由監督行程完成、結果直接記在摘要檔裡，本 skill 不必自己去查 PR 上有沒有那則 comment。但要讀到完整的摘要檔就得等所有 reviewer 跑完，等待本身仍然必要。

以背景模式執行一個等待指令，等到摘要檔累積到與實際派出的 reviewer 數量相同的行數（監督行程每完成一個 reviewer 追加一行）為止；該背景指令結束時 Claude Code 會通知，本 skill 據此被喚醒。等待條件要一併容納兩件事：

- 摘要檔由背景監督行程建立，與腳本印出摘要之間有極短的競態，檔案還不存在時要當成零行繼續等，不能當成錯誤退出。
- 等待要有上界，取兩小時；只有使用者明確要求時才放寬，不自行延長——放寬條件一旦留給模型自由心證，上界就形同虛設，而逾時本來就有退路，延長換來的好處有限。監督行程被終止、機器休眠、某個 CLI 掛住數小時，都會讓沒有上界的等待停在原地永不返回，那比拿不到結果更糟——使用者不會收到任何訊號，這段回報等於靜默消失。逾時就結束等待，改讀當下的摘要檔，把已經寫進去的那幾行照下面的方式回報完，其餘的據實說明仍在進行中，並註明這是逾時當下的觀察而非確定失敗。

摘要檔是本次執行目錄下的 `summary.txt`，該目錄是摘要中任一 log 路徑的上兩層——腳本印出的摘要只給 log 路徑，不給摘要檔路徑。

摘要檔每一行對應一個 reviewer，帶五個欄位：行程編號、結束碼、結束時間、worktree 狀態比對結果、張貼結果。行內沒有 CLI 名稱，兩者的對應鍵就是行程編號——要指名到 CLI，拿行內的編號回頭對腳本印出的摘要，那裡每個派出的 reviewer 都附了自己的行程編號。

張貼結果三種值，回報時要分開講清楚，不能籠統說成「都跑完了」——三者對使用者的意義完全不同：

- `posted`：標記完整、內容切出成功、已張貼，這一則直接去 PR 上看。
- `no-content`：該 reviewer 的標準輸出裡找不到成對且順序正確的起訖標記，腳本判定它沒有產出可信內容，因此沒有嘗試張貼。PR 上不會有這一則，要知道發生了什麼事只能去讀它的 log 與標準錯誤檔。
- `post-failed`：標記完整、內容切出成功，但 gh 兩次嘗試都失敗。腳本把切出來的內容檔留在執行目錄下（檔名見「產出物位置」），使用者可以自己拿去貼——回報時把那個檔案的絕對路徑給出來。

worktree 狀態比對結果一併轉達，被標為失效的要指名到 CLI：那代表該 reviewer 執行期間 worktree 被動過，它的 review 失去依據。這是保守偵測、可能誤標（見「已知限制」），因此據實轉達即可，不要替使用者判定那則 review 到底有效與否。沒有人讀這個欄位的話，被竄改過的 review 會被當成正常結果報出去。

收尾時每個派出的 reviewer 都要指名到 CLI，說明它的張貼結果、非零結束碼（若有）與 worktree 狀態；沒有 `posted` 的，一併給出它的 log 檔路徑。

### codex 與 opencode 上沒有這段回報

截至 2026-08 實測，這兩個平台沒有等價的背景喚醒機制（第三方 CLI 的能力會隨改版變動，這是可過期的實測結論，日後值得重新確認），skill 啟動腳本後就返回，不會再回來讀摘要檔。

落差只在回報這一段，功能本身不受影響：三個平台的 reviewer 都會照常跑完，comment 也都由監督行程張貼，PR 上該出現的一樣會出現。差別是 Claude Code 上這個 skill 會等到全部跑完、把結果整理給使用者，另外兩個平台上啟動後即返回，張貼結果、結束碼與 worktree 狀態都要使用者自己看 PR、或事後打開執行目錄下的 `summary.txt` 與 log 檔。回報時把執行目錄與其中 `summary.txt` 的絕對路徑一併給出，讓他有地方可以開。

## 已知限制

七項都是實作與審查過程中查證出來的事實。遇到對應症狀時直接對照本節，不要當成待修的 bug 追。

- **不指定 model，opencode 預設 model 可用與否由使用者自負**：各 CLI 都不帶 model 參數，一律使用它們自己設定的預設值——硬編碼一個 model 既違背「永遠跟得上使用者設定變更」的原意，那個值本身也會過時。代價是使用者必須自行確保 opencode 的預設 model 可用；實測時它曾因帳戶餘額不足而失敗，該路會以非零結束碼結束並呈現在摘要檔中。
- **remote 名稱假設為 origin**：腳本只驗證當前工作目錄的 `origin` 是否對應到目標 PR 所屬的 repo，不符即拒絕執行，不會改試其他 remote 名稱。慣用 origin 以外名稱指向 GitHub 的使用者會直接被拒絕。
- **腳本會寫入使用者當前的 repo**：reviewer 對 worktree 是唯讀的，但腳本本身不是，五項寫入都落在使用者當前的 repo 上——fetch 這個 PR 的 base 分支並強制更新對應的遠端追蹤 ref、fetch 這個 PR 的 pull ref、建立一個以 `pr-review-` 開頭並帶 PR 編號與唯一後綴的本地分支、強制刪除所有 `pr-review-` 開頭的陳舊分支、清理 worktree 殘留登記。第一項的順序要留意：解析 base ref 排在建立 worktree 之前，而 `origin` 身分比對是在建立 worktree 那一步才做的，所以連「remote 不符而被拒絕執行」的那一次，也已經動過使用者的 repo，那不是一次零副作用的拒絕。使用者自己若有同前綴的分支會被一併強制刪除，派出前的檢查見「呼叫腳本」。本次建立的那個分支要等下一次執行才會被盡力清掉，因此每跑一次就在使用者 repo 留下一個分支，直到下一次執行為止；它尾端的唯一後綴與執行目錄名尾端是同一個值（見「產出物位置」），不是摘要裡任何一個 reviewer 的行程編號，拿 reviewer 的編號去找會找不到。
- **共用工作區的並發比對可能誤標**：所有 reviewer 共用同一個 worktree，腳本在每個 reviewer 行程啟動前後各取一次該 worktree 的 git 狀態快照，前後不同即在摘要檔中把該次 review 記為失效。由於多個行程同時執行、而比對是依序輪詢的，前一個行程的事後快照可能被還在跑的後一個行程影響。方向是保守的：在該行程結束時仍然存在的變更一定會被標記、不會漏抓，但最壞情況下無辜的 reviewer 也可能被誤標為失效。保證僅限於此——前後快照的比對擋不住改完又還原：reviewer 若寫入檔案後在自己結束前刪掉，或把已追蹤檔案改回位元組相同的內容，兩次快照會相等而判為正常。
- **CLI 自身的權限機制都保證不了 worktree 唯讀，檔案系統這一層靠作業系統權限守**：截至 2026-08 實測，三者各有各的繞過方式——claude 的寫入工具在它的權限模型裡無法限定路徑範圍，路徑形式的拒絕規則兩種寫法都測過、都無效；codex 的唯讀沙箱在非互動執行模式下會升級，實測寫得進去；opencode 的權限設定檔擋的是逐條指令動詞，一般的 shell 重導向寫檔直接繞過。因此腳本以作業系統層級的唯讀權限鎖住整個 worktree，各 CLI 自身的旗標降級為第一層，只負責限制模型會去嘗試的動作範圍，不是唯讀承諾的依據。現在 reviewer 的寫入工具已經完全不放行——它不寫任何檔案，只把 review 印到標準輸出——所以作業系統那一層是第二層防線而非唯一防線，留著是為了擋住旗標層擋不住的路徑。下游後果是：要判斷某次 review 有沒有可能動過 worktree，看的是摘要檔那一行的 worktree 狀態比對結果，不是某個 CLI 的權限設定。
- **GitHub 側沒有任何旗標層級的保證，只有契約文字**：reviewer 現在不需要也不應該執行任何 GitHub 指令，張貼是監督行程的事，契約也明文禁止 reviewer 動 GitHub。但截至 2026-08 實測有一個還沒關掉的殘留風險：真實的 claude 在本腳本使用的權限模式下，即使工具白名單完全不含任何 Bash 指令模式、甚至明確把張貼 comment 那條指令加進黑名單，gh 指令仍然會透過 Bash 實際執行——旗標層級沒有任何機制保證擋得下它。因此若被審查的 diff 或 issue 內容成功誘導模型主動去執行 GitHub 寫入操作，唯一的屏障是那需要網路與使用者自己的 gh 憑證，而本腳本對這兩者沒有做任何隔離。worktree 狀態比對補不上這裡，它只涵蓋檔案系統，抓不到任何 GitHub 上的動作。PR 狀態或既有留言出現非預期異動時，從這裡查起。
- **狀態比對涵蓋被 gitignore 忽略的路徑**：這是刻意的選擇，為的是不讓「違反會被偵測到」這個承諾在被忽略的路徑上落空。代價是某個 CLI 若在工作區內產生自己的快取或暫存檔、而該路徑剛好被忽略，會造成誤報。

## 產出物位置

產物主要落在使用者家目錄下的暫存目錄中、依本 repo 暫存檔規則命名的專案專用資料夾內，往下是 `pr-review`，再往下是本次執行目錄；唯一落在該處之外的，是上節那個留在使用者 repo 的本地分支。

```text
~/.tmp/<專案專用資料夾>/pr-review/<PR 編號>-<時間戳記>-<唯一後綴>/
├── worktree/                     # 各 reviewer 共用的程式碼工作區，跑完後由監督行程刪除
├── logs/                         # 每個 CLI 各有 prompt、行程編號、標準輸出 <CLI>.log
│                                 # 與標準錯誤 <CLI>.log.stderr，跑完後保留
├── .comment-body-<行程編號>.md   # 監督行程從標準輸出切出來的 comment 內文
└── summary.txt                   # 每個 reviewer 一行，五個欄位
```

標準輸出與標準錯誤分成兩個檔不是整理癖：review 全文包在一組起訖標記之間印到標準輸出，監督行程就靠那兩行標記切內容，而兩股輸出合流時緩衝行為不同，標記行可能被標準錯誤的內容插斷，切出來的東西就不可信了。`<CLI>.log` 因此保持純標準輸出，一個位元組的其他東西都不寫進去。

切出來的內容檔張貼成功與失敗都會留著：`posted` 時它只是 PR 上那則 comment 的副本，`post-failed` 時它是使用者唯一能拿回來手動張貼的那一份，兩種情形共用同一條保留規則比分開處理更難出錯。`no-content` 的那一則不會有這個檔，因為根本沒有內容被切出來。

上面只列主要項目，目錄下另有各行程的結束碼檔、狀態快照檔與 opencode 的權限設定檔等內部檔案。目錄名尾端的唯一後綴是腳本自身的行程編號，用來讓同一秒對同一個 PR 啟動的兩次執行不撞目錄；它與摘要中各 reviewer 的行程編號是不同的東西，不能拿某個 reviewer 的編號去拼執行目錄路徑。

log 刻意放在 worktree 之外：worktree 跑完會被刪除，而 log 是事後查問題的唯一憑據，混在一起會一起消失。

這裡刻意以家目錄下的絕對路徑定址，不套用暫存檔規則中「先在工作區根目錄建立 `.tmp` 符號連結」那一步。本 skill 執行時的工作目錄是使用者的 repo 工作副本，為跑一次 review 在那個 repo 根目錄留下一個符號連結，是不必要的持久寫入，與 reviewer 唯讀、逐行程比對 worktree 狀態的整體設計方向相反。

回收責任在使用者：log、標準錯誤檔、prompt、切出來的內容檔與摘要檔刻意在跑完後保留，是事後查問題唯一的憑據，因此不受「任務結束後主動清除暫存檔」的例行清除約束，任務收尾時不要刪。worktree 由監督行程自己移除，不需要代勞。
