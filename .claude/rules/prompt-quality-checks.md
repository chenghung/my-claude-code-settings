# Prompt Integrity Check

此規則為強制性規則，每次觸發後必須完整執行，不得跳過任何步驟。

## 設計原則

此節列出 LLM 產出 agents、rules、skills、commands、prompt 相關檔案時必須遵守的設計原則，共九條，依優先序由高到低排列。編號越小優先順序越高。當原則之間產生取捨時，優先滿足編號較小者。其中第 1 條「具體明確、無規則衝突」與第 2 條「動態載入、避免污染 main agent context」並列為最高準則，任何時候都不得為了其他原則的便利而違反這兩條。

### 具體明確、無規則衝突

prompt 指令必須具體明確，使 LLM 能百分之百依據指令完成任務，並禁止與其他 rule、agent、skill 之間出現互相矛盾的行為要求。

### 動態載入、避免污染 main agent context

此條與第 1 條並列為最高準則。動態載入額外資訊到 context window 時，必須避免污染 main agent 的主要目的。與主要目的非高度相關的內容，應盡量透過 skill 或 subagent 的方式動態載入，而不是常駐在 main agent 的 context 中。能委派給 subagent 處理的工作就盡可能委派。

`rules/` 目錄下的檔案會被 main agent 永久載入，因此只應放置「不論當前任務為何都需要的核心約束」，例如 routing 邏輯與全域行為準則；任何只在特定情境才需要的格式細節、語法說明、CLI 參數規格，不得放入 `rules/`，應改放至對應的 skill 或 subagent 定義中。

允許不同 subagent 之間有適度重複的內容。當「抽出共用內容到 rule」與「保留 subagent 之間的重複」兩者發生衝突時，優先保留重複而避免污染 main agent context——subagent 內容只在該 subagent 被委派時才載入，而 rule 是永久載入，代價截然不同。

### 精簡、避免重複

在滿足前兩條的前提下，盡可能減少重複或不必要的 prompt 內容。重複的指令會浪費 token，且可能在不同上下文中產生不一致的行為。本條的「避免重複」適用於同一個檔案內，或同一層級中會被同時載入的內容之間（例如多個 rule 之間、多個同時生效的 subagent 之間）；不同層級（rule vs subagent vs skill reference）之間的重複不在本條規範範圍，應以第 2 條（避免污染 main agent context）為優先判斷依據。

### 只寫模型推不出的內容

prompt 定義檔（涵蓋 agent、skill、rule 與 CLAUDE.md）只應寫入模型無法從自身訓練資料或工具自身介面推斷出來的內容。重述模型已內建的知識會浪費 token、稀釋真正重要的專屬指令，並在模型知識演進後與檔案內容產生過時矛盾。此原則對所有 model 等級一律適用，不因使用較小模型而放寬。

應寫入的內容限定為以下五類：

- 此 repo 或此 domain 特有、無法從通用知識推斷的慣例，例如 commit message 格式、特定知識庫的 typed frontmatter 欄位規則
- 具副作用且順序敏感、非直覺的流程檢查點，例如建立 PR 前必須先完成 push
- 外部工具的已知 quirk 或 bug
- 安全與權限邊界，例如禁止讀取某個 credential 設定檔
- 與 main agent 的成功與失敗輸出契約，包含應回傳哪些欄位、遇到哪些情況應停下並詢問使用者

禁止寫入的內容包含但不限於：

- 標準語法或語言特性教學，例如 Markdown / CommonMark / GFM 語法、程式語言語法、通用框架的標準用法
- 透過 help 指令或工具自身 schema 即可取得的 CLI flag 或參數逐項清單
- 模型已能自行推理的常識操作順序，例如先讀檔再編輯、先搜尋再判斷
- 已有工具會強制執行的規則之逐條複述，例如定義檔內已會呼叫 linter 時就不需再逐條教 lint 規則

**與其他原則的取捨：** 本原則優先序低於第 1 條「具體明確、無規則衝突」與第 2 條「動態載入、避免污染 main agent context」。當精簡到只剩推不出的內容與具體明確不產生歧義兩者發生衝突時，以第 1 條為準，應保留足以消除歧義的 repo 專屬指令，而不是為了精簡犧牲明確性。

**與第 3 條的分工界線：** 第 3 條「精簡、避免重複」處理的是同檔或同層之間的重複內容；本條處理的是模型已內建、推得出的知識，不論是否重複一律不寫。repo 專屬且推不出的內容若跨 subagent 重複，依第 2 條判斷允許適度重複，不受本條限制。

**CLI 範例的界線：** 禁止寫入清單中關於「透過 help 指令或工具自身 schema 即可取得的 CLI flag 或參數逐項清單」那一項，指的是型錄式窮舉某工具所有子指令與所有選項，這仍然一律禁止。但有一種情形構成界線內的例外，允許放入最小的 canonical 呼叫範例並要求 LLM 照此執行：當完成某項操作的 CLI 指令存在多種合理但不等價、不可互換的推導結果，且選錯會造成以下任一後果時——破壞與 main agent 的輸出契約、造成不可逆或順序敏感的副作用、或導致跨次執行結果不可重現。此例外的寫法限制：只放真正需要釘住的那一兩條具體呼叫，不放整個指令表面；並簡述為何必須是這個形式，不逐項解釋每個 flag 的語意。反向判準：若所有合理推導都等價，或選錯只會明顯失敗且能無害自我修正，則不適用本例外，仍歸禁止寫入清單。此例外本質上是應寫入五類中「repo 慣例」與「副作用順序檢查點」的具體化——模型推不出的是哪個形式才是被指定的 canonical 形式，而不是這個 CLI 怎麼用。

**模型能力與具體度的兩軸：** 本條開頭的「對所有 model 等級一律適用」必須分兩條正交的軸來理解。軸一是內容類型：禁止寫入的內容對所有模型一視同仁，不因模型較小而放寬，因為較小的模型同樣內建標準語法等通用知識，而且更容易被冗長 prompt 帶偏。軸二是執行具體度：對於已經落在應寫入五類內的合法內容，特別是副作用順序檢查點與 CLI canonical 範例，允許依模型能力反向調節說明的詳盡程度——能力較強的模型給意圖與約束、信任其自行推導；追求快速的小模型則把步驟與指令寫得更逐步、更釘死。關鍵閘門：軸二只能在已合法的內容範圍內提高具體度，永遠不得以模型較小為理由跨入軸一的禁區。換句話說，天花板（禁止寫入的內容）對全模型固定，只有地板（手把手的程度）才隨模型能力浮動。

### 單一職責、觸發條件明確

每個 agent、rule、skill 只承擔單一明確職責，其 description 或觸發條件必須讓 LLM 能無歧義地判斷何時該呼叫、何時不該呼叫。職責重疊是規則衝突的主要來源，屬於第一條能否成立的前置條件。

### Subagent 互相獨立、不交叉引用

每個 subagent 的 prompt 必須假設自己是獨立存在的，不得在內文中引用、提及或建議使用其他 subagent 的名稱。Subagent 被呼叫時是無狀態且獨立的，不知道其他 subagent 是否存在於當前環境，引用其他 subagent 等於做了一個它無法驗證的假設。職責邊界的說明應以「不處理什麼類型的問題」描述，而非「建議改用某某 subagent」。路由與分流是 main agent 或 skill 層級的責任，不是 subagent 的責任。

### 可驗證的成功條件

prompt 必須定義任務完成的判斷標準與輸出格式，例如應產出哪些檔案、應回傳哪些欄位、遇到哪些狀況應停下並詢問使用者。缺乏成功條件會讓 LLM 憑感覺收尾，main agent 也無法驗證 subagent 是否確實完成任務。

### 邊界與失敗行為明確

prompt 必須涵蓋越界輸入、資訊不足、工具呼叫失敗等情境下的應對方式，例如詢問使用者、回報失敗、或採用預設值。未定義的邊界行為會導致 LLM 自行腦補，產生跨 session 不一致的結果。

### 委派時只給意圖，不指揮內部實作

main agent 委派給 subagent 時，只描述目標與預期產出，不指定 subagent 內部應使用哪些工具或執行哪些步驟。抽象層級一致才能讓 subagent 發揮專長，也避免 main agent 的假設污染 subagent 的決策空間。

## 觸發條件

每當修改了以下任何一項設定後，必須立即執行本規則所定義的完整檢視流程：

- `skills/` 目錄下的任何檔案
- `agents/` 目錄下的任何檔案
- `rules/` 目錄下的任何檔案
- `.claude/rules/` 目錄下的任何檔案
- `CLAUDE.md`

## 檢視項目

### 上下文規則衝突檢查

確認新修改的內容與現有的其他 rules、agent 定義、skill 定義之間，沒有互相矛盾的指令或行為要求。任何衝突都必須在完成本次修改前解決。

### Subagent 交叉引用檢查

確認 `agents/` 目錄下任何 subagent 定義檔案的內文中，沒有出現其他 subagent 的名稱或對其他 subagent 的引用。職責邊界的描述必須以問題類型表達，而非以其他 subagent 名稱表達。發現此類引用必須立即移除或改寫。對 `agents/` 目錄下的 subagent 定義檔執行合規檢查時，必須先觸發 `subagent-architect` skill 載入最新的 frontmatter 規格、mandatory/optional sections、命名規範、forbidden patterns 等判準，依該 skill 內容進行驗證；本 rule 不重複格式細節。

### 幻覺風險檢查

確認所有 prompt 中沒有引用不存在的工具、不存在的檔案路徑、不存在的功能，或描述與實際行為不符的內容。發現任何此類問題，必須立即更正。

### 重複 prompt 檢查

找出跨檔案之間是否存在重複或高度相似的 prompt 片段。重複的指令會浪費 token，且可能在不同上下文中產生不一致的行為，必須合併或刪除冗餘內容。

### 模型內建知識重述檢查

確認 agents、skills、rules、CLAUDE.md 等 prompt 定義檔中，沒有重述模型已能從訓練資料或工具自身介面推得的內容，包含標準語法教學、語言或框架的通用用法、help 指令可得的 CLI flag 清單、常識性操作順序。發現此類內容時，先評估其是否落在第 4 條「只寫模型推不出的內容」所列應寫入的五類例外之內；若不屬於，必須刪除或改寫為僅保留 repo 或 domain 專屬、推不出的部分。

### Table of Contents 檢查

確認 `agents/`、`skills/`、`rules/`、`.claude/rules/` 目錄下的定義檔，以及根目錄與 `.claude/` 目錄下的 `CLAUDE.md`，這些 prompt 定義檔內沒有人工維護的目錄（Table of Contents）。這類檔案會整份載入 LLM context，ToC 對 LLM 不具導航價值，純屬 token 浪費，且在章節重新命名時會增加同步維護成本。發現此類 ToC 必須移除。此禁止僅適用於 prompt 定義檔；以人類讀者為對象的一般文件（例如專案 README 或對外文件）不受此限，可依其場景需要保留 ToC。

### 安全憑證檢查

嚴格禁止將任何敏感的安全憑證直接置於 `skills/`、`agents/`、`rules/` 或 `.claude/rules/` 目錄下的任何檔案中。

禁止放入的內容包含但不限於：API 金鑰、密碼、存取權杖（access token）、含有 token 的 webhook URL、私密金鑰（private key）、任何形式的 secret。

此類資訊必須透過環境變數或外部的 secrets 管理機制來處理，不得以明文形式寫入版本控制的檔案中。

若在檢視過程中發現既有檔案包含上述內容，必須立即向使用者提出警告，並建議以安全的替代方案取代。

## 檢視範圍

執行檢視時，必須涵蓋以下所有相關檔案：

- `rules/` 目錄中的全部 `.md` 檔案
- `.claude/rules/` 目錄中的全部 `.md` 檔案
- `agents/` 目錄中的全部 agent 定義檔案
- `skills/` 目錄中的全部 skill 定義檔案
- 根目錄與 `.claude/` 目錄下的 `CLAUDE.md`

## 執行要求

若在上述任何檢視項目中發現問題，必須在完成本次修改前主動提出並修正，不得將問題遺留至後續作業。
